# 測試方法

> 第一節只回答一件事：之後 gateway 做好了，我們用什麼方法量它。


## 第 2 頁　RFC 9411

RFC 9411 是 IETF 在 2023 年 3 月發布的，性質是 Informational，它**取代**了 RFC 3511。

它的測試對象是 Inline network security device，也就是 inline 模式的網路安全設備，例子是 NGFW 和 NGIPS。架構很單純：左邊一個 Client Emulator、右邊一個 Server Emulator，中間夾著被測設備 DUT，也就是我們的 Security Gateway。左右兩端各是一台 Test Equipment。

要先講一個區別：RFC 9411 的 throughput 指的是 Inspected Throughput，latency 指的是 TTFB／TTLB，這些都要用**有狀態**的連線量。我們第 5 頁量的是封包層級的轉送速率和轉送延遲，不是同一個東西，後面會再說明。


**備用 —— 為什麼不做 RFC 9411 的安全有效性測試？**

> 計畫範圍是依 dataset 的 feature 做本地／雲端偵測，RFC 9411 只參考效能測試流程。

---

## 第 3 頁　RFC 9411：測試流程

目前**我們只參考它的效能測試流程**
流程分兩步。**第一步是 Reference test，不放 DUT**，或是 DUT 只做 fast forwarding。目的是確認 testbed 本身不是瓶頸，並且記錄環境本身的 loss 和 latency。
第二步才是 DUT 做 benchmark。沒有第一步，就沒辦法分辨量到的上限是 DUT 的還是測試設備的。

下面是一輪負載的時間軸，分五段：Init,Ramp up,Sustain,Ramp down,Collection。Init 至少 5 秒，這段不能發起連線，也不量測。Ramp up 是把負載慢慢拉上去，不能把 DUT 壓垮，一樣不量測。**Sustain 是持續穩定的負載，建議至少 300 秒，只有在這一段量測，取樣間隔要小於 2 秒。** 之後是 Ramp down 與 Collection，收尾和收集結果。


**備用 —— 為什麼要先做 Reference test，不能直接跑 benchmark？**

> 因為 benchmark 量到的數字，是「整條測試路徑」裡最慢那一段的上限，不一定是 DUT 的上限。RFC 9411 §5 列了 Reference test 的幾個步驟（共 6 步），這裡講背後的目的，主要有四個：
> 1. **確認 testbed 不是瓶頸**：測試設備、switch、虛擬交換器本身可能就會掉包或增加延遲。如果流量產生器只送得出 300 Mbps，量到「gateway 跑 300 Mbps」其實是產生器的上限，不是 gateway 的。
> 2. **確認產生器送得夠快**：產生的流量要超過 DUT 預期的最大效能，否則壓不到 DUT 的極限。
> 3. **記錄環境本身的 loss 與 latency**：之後放上 DUT 量到的延遲，扣掉這個基準，剩下的才是 DUT 造成的。
> 4. **確認環境穩定**：特別是虛擬化環境，其他工作負載、VM 搬移，甚至機器過熱降頻，都會讓結果飄動。
>
> RFC 的做法是「不放 DUT」或「DUT 只做最單純的轉送」先跑一次，而且這一步是 MUST，要在所有 §7 測試之前做。
>
> 對應到我們的環境，這一步特別重要：
> - **Docker lab**：cli、gw、srv 都跑在同一台筆電上、共用 CPU，流量產生器和 gateway 會互搶資源。先讓 gw 只做純轉送（不載規則、不進 NFQUEUE）跑一次，才知道「環境本身」能到多少。
> - **Pi**：Raspberry Pi 3B+ 官方規格寫的是「Gigabit Ethernet over USB 2.0（maximum throughput 300 Mbps）」，網卡本身就有上限。先量純轉送的 Pi，加上規則後量到的下降，才是我們的檢查造成的成本。

**備用 —— MUST 與 RECOMMENDED**

> 要分清楚：Sustain 至少 300 秒是 RECOMMENDED，**不是 MUST**。Init 至少 5 秒也是建議值。這頁裡屬於 MUST 的有：Reference test，還有取樣間隔小於 2 秒。

## 第 4 頁　為什麼選 RFC 9411

比較三種做法。

RFC 2544 是 1999 年的，對象是 router、switch 這類網路互連設備，以 frame 為單位。它沒有有狀態流量，也沒有 L7 安全功能。

RFC 3511 是 2003 年的，專門針對防火牆。**它是有狀態的**，已經有併發 TCP、HTTP transaction 這些測試。它被取代的原因，是缺少 L7 安全功能。

最後一欄是適用對象，取自三份 RFC 的標題：2544 的標題是網路互連設備，也就是 router、switch 這類；3511 是防火牆；9411 是網路安全設備。三份裡只有 RFC 9411 是針對安全設備、又涵蓋 L7 安全功能的，這就是選它的原因。不過我們只參考它的效能測試流程。


**備用 —— 為什麼不能只靠 2544**

> 2544 量的是 frame 層級的轉送能力。一台防火牆把檢查功能全關，跑得再快，也不代表開了之後還有那個速度。

## 第 5 頁　後續測試規劃

後續只做一個測試：把**同一份可復現的 dataset**，分別重播過四種設定：Suricata、Snort 3、Gateway 只有本地、Gateway 本地加雲端。同一次執行，同時收效能和偵測兩組數據。
效能看 Throughput、Latency、Packet loss；偵測看 Detection rate、False positive rate，還有送到雲端的比例。
比較有兩組：Suricata、Snort 3 對上只有本地的 Gateway，這是開源方案當基準；只有本地對上本地加雲端，看雲端多帶來什麼、又要付出什麼代價。
效能的測試流程參考 RFC 9411，也就是 Reference test，再到 Sustain 量測。

> 口頭補充一點定位：本地的規則比對我們直接用 Suricata 或 Snort，不自己重寫；我們的重點是**本地／雲端分流**。所以拿它們當比較基準，是確認我們的本地端沒有比它們差，不是要打敗它們。

**備用 —— 偵測怎麼算？**

> - **單位是 flow**：因為 label 是以 flow 為單位標的。封包和 label 的對齊，沿用第 6、7 頁的方法，五元組加時間。
> - **每條 flow 的判決**：看 gateway 出口的抓包或 flow log。這條 flow 的封包沒有到出口，就算被擋下。
> - 四種結果：**TP** 是擋對（惡意的被擋）、**FP** 是擋錯（正常的被擋）、**FN** 是漏掉（惡意的放行）、**TN** 是放對（正常的放行）。
> - **Detection rate = TP ÷ (TP + FN)**；**False positive rate = FP ÷ (FP + TN)**；**送雲端比例 = 送到雲端的 flow ÷ 全部 flow**。
> - 定義要先講清楚：一條 flow 只要有任何一個封包被擋，就算這條 flow 被擋。沒有 label 的封包（例如 ARP）不列入計算。
> - 這些還是規劃，沒有量過，不報數字。如果之後雲端判定會快取，快取命中與否的差別，是下一階段的設計問題。

**備用 —— 效能和偵測一起測要注意什麼？**

> Packet loss 會混到兩種原因：一是**規則丟掉的封包**，這是偵測的結果；二是**設備處理不及而丟掉的封包**，這才是效能問題。
> 所以規則丟棄要另外用 counter 或 log 記錄，packet loss 只算第二種。不然 gateway 擋得越準，packet loss 看起來就越高。

**備用 —— 正式效能測試要處理的事（實作時）**

> 這一段是**之後實作要處理的事**，目前還沒做。Suricata、Snort 都是以 flow／stream 為基礎的引擎，重播要保證它們看到的流量和 dataset 一致：
> 1. 用**單一個 tcpreplay process 搭配 tcpprep 的 cache**，同步地從兩張網卡送出兩個方向，這樣 Suricata、Snort 才能做 stream reassembly。
> 2. **不要讓 srv 端回應**，避免出現 dataset 裡沒有的 RST。
> 3. 改完位址之後要**重算 checksum**（tcprewrite 的 `--fixcsum`）。
> 4. **沒有 handshake 的 flow**，Suricata 預設不解析（midstream 預設關閉），檢查工作量變少，throughput 會看起來偏高。
> 5. 第 8 頁的 Docker 測試是把兩個方向**分開重播**，拿來驗證流程可以，但正式效能測試必須改掉。
>
> 另外，Sustain 要怎麼套到 replay：要撐到 300 秒，tcpreplay 必須 loop（`--loop`）；loop 會重複送一模一樣的 flow，可能讓 cache 命中率偏高，可以考慮 `--unique-ip`，這是**實作時再評估的選項**。

**備用 —— 為什麼效能指標只有這三個？量的是什麼？**

> tcpreplay 本身只負責送封包，不量 throughput、latency 或 packet loss。這三個是在 gateway 兩側用抓包和 counter 量出來的。
> 我們量的是**封包轉送速率**和**封包轉送延遲**，不是 RFC 9411 的 Inspected Throughput（那要用有狀態流量量），也不是 TTFB／TTLB。CPS、Concurrent Connections 和 TTFB 需要真的建立連線，tcpreplay 不建立連線，所以這次不列。

**備用 —— 為什麼說「參考」RFC 9411，不說「照著做」？**

> RFC 9411 說它的效能測試方法不適用於依賴 ML 或行為分析的系統，這類功能**應該關掉**（should be disabled）。如果雲端用 ML，開著雲端量，就不符合它的前提，所以我們只參考測試流程，不宣稱符合 RFC 9411。

**備用 —— 雲端一定是 ML 嗎？gateway 加雲端能不能當 SUT？**

> 雲端不一定是 ML。我們的設計目前只寫「本地判斷不出來的才送到雲端做重量級分析」，沒有限定方法。
> - 如果雲端用 ML 或行為分析：RFC 9411 說這類功能應該關掉，所以整個 gateway 不完全在 RFC 範圍內，只參考流程。
> - 如果雲端不用 ML：這個限制不成立，但我們還是只參考效能測試流程，因為 RFC 沒有針對雲端路徑的指標。
>
> 至於 gateway 加雲端能不能當 SUT：RFC 9411 用的是 DUT/SUT 的說法，SUT 的定義在 RFC 2285 §3.1.2：「當成單一整體來測的一組網路設備」，所以 gateway 加雲端可以算一個 SUT。

**備用 —— 把 Suricata／Snort 放進 gateway 就夠了嗎？可以優化什麼？**

> 先講結論：本地規則比對放 Suricata／Snort 是合理的，但只放它們，有三個缺口：
> 1. 它們**只能偵測已知特徵**（signature），沒見過的攻擊看不出來。
> 2. 它們的判決只有 alert 或 drop，**沒有「不確定 → 送雲端」這條路**。這正是我們要補的。
> 3. 完整的 ET Open 規則集，在小型 ARM 設備上**很吃記憶體**。這是社群的使用經驗，不是官方規格；Pi 3B+ 只有 1 GB。我不會說「在 Pi 上一定跑不動」，實際能不能跑要量過才知道。
>
> 另外要講清楚：**Suricata 本身就有 flow bypass**，官方文件有寫，分本地（local）、capture 層、XDP 層三種。所以「快路徑／bypass」**不是我們的新貢獻**。我們的貢獻是**本地／雲端分流**。

**備用 —— 比較對象是我們自己設定的嗎？**

> 是，四種設定全部都是我們自己架設的，沒有拿別人的測試結果來比。同一個硬體、同一份 dataset，這樣差異才來自我們的設計，不是來自硬體或樣本。
> - Suricata、Snort 3 對上只有本地的 Gateway：開源基準。
> - 只有本地對上本地加雲端：雲端的增益與代價。
> - Zeek 是被動分析、不能 inline，所以不放進比較。

**備用 —— 為什麼 Zeek 不放進比較**

> 上次報告的開源引擎還有 Zeek。Zeek 是被動分析，只能看、不能 inline 擋流量，所以不放進比較。

# Datasets 可復現性

> 這一節的由來：上次報告提到這幾個資料集可以拿來做 ML training。ML 的訓練與評估，要能被別人重現，前提是資料本身可復現；這也對應到第 5 頁用的 dataset：它同時用在效能和偵測，四種設定都要重播同一份，所以資料本身要可復現。所以這節先問：上次那四個資料集，可不可以復現。

## 第 6 頁　要復現需要什麼、做不做得到

先說下面那張表怎麼讀。上表的「2.」是需求：label 能和原始流量對齊；下表的「2. 時間維度」是用來判斷這個需求的指標，也就是 label 的時間精確到哪裡。時間維度決定 label 能不能和封包對齊，因為 label 和封包對齊靠的是五元組加時間。

再講「復現」的定義。我依 ACM 的定義：**獨立的團隊，用原作者提供的資料與程式（artifact），得到相同的結果**。要說明一點：ACM 原本是用來評論文自己的 artifact，我是借它的標準來看第三方資料集。我們的用途是「別人拿同一份資料，重現我們的測試」，所以只需要兩件事，上面那張表：

① **拿得到同一份原始資料**，出處是 ACM 的 Artifacts Available（要有封存庫加 DOI 這類識別碼），以及 Ring 等人 2019 年的 NIDS 資料集綜述（公開可取得）。
② **label 能與原始流量對齊**，出處是 Engelen 2021。label 跟封包對不齊，就沒辦法逐筆驗證擋得對不對。

這兩條是有出處的需求，不綁任何工具。

看下面那張表，每個資料集評兩欄。① 用 ACM 的標準：放在封存庫、有 DOI 才打勾；② 看的是 label 能不能和封包對齊（可追溯），不是 label 對不對：
表上有兩個縮寫先說明：
- 「**需登記**」是指 CIC 的三個資料集要先在 cicresearch.ca 填下載表單（姓名、email 等）才拿得到檔案；IoT-23 在 Zenodo，不用填就能下載。要填表、又沒有 DOI，網站改版或關掉，別人就不一定拿得到同一份，所以打三角形。
- 「**修正版**」是指 CIC-IDS2017 由第三方重新整理過的版本，不是 CIC 官方的：Engelen 等人 2021 年發現原版切 flow 的方式有錯、有些只是攻擊嘗試也被標成攻擊，超過兩成的 trace 要重建或重新標註，所以從原始 PCAP 重新產生、重新標註，並公開程式和資料；Liu 等人 2022 年是同團隊的後續版本。
- **IoT-23**：放在 Zenodo、有 DOI，① 成立；② label 的時間是 Unix epoch、精確到微秒（例如 1533042911.474174），PCAP 也是微秒精度，兩邊一致，而且我們實測對齊 100%，所以我說它**已驗證可復現**。要補三個但書：對齊只抽了 23 個 scenario 裡的 2 個（Hakai-8-1 與 Somfy-01），實測細節下一頁講；IoT-23 v1 的 label 有作者承認的錯誤（v2 說 fewer errors，但沒列明細），和封包對齊之後才能去檢查；我們的測試樣本是從 Stratosphere 的個別檔案目錄下載的，不是 Zenodo 那包，也沒有跟 Zenodo 核對過。
- **CIC-IDS2017**：要先登記、沒有 DOI，① 是三角形。② 也是三角形，理由是時間只到「分」，追溯精度不夠。label 有已知錯誤是另一件事，所以要用修正版。但修正版放在大學網站，一樣沒有 DOI，所以 ① 還是三角形；修正版的時間精度我沒有查證。結論欄寫「修正版、未實測」。
- **CIC-DDoS2019**：要登記、沒有 DOI，① 是三角形。② 打勾：CSV 有五元組和微秒時間，條件上可以和 PCAP 對齊。它和 IoT-23 的差別是：條件符合，但我們沒有實測，所以結論欄是三角形、未實測。官網時程的疑問，被問到再講。
- **CICIoT2023**：要登記、沒有 DOI，① 是三角形。② 打叉：CSV 沒有時間欄位，label 是整次攻擊擷取為單位，只對得到檔案，**對不到 flow**（PCAP 實際怎麼分檔我沒有確認）。

要注意：CIC 三份我是依官方說明和公開欄位檢查的，**沒有下載**，只有 IoT-23 是實測。沒下載的原因是要填登記表單，而且檔案很大，例如 IDS2017 的 Wednesday 就約 13 GB，這次先以官方說明加上公開欄位判斷。另外，這頁講的是「可復現」，不是說這些資料集可以當 benchmark。

**備用 —— Label 是什麼、怎麼和原始流量對齊（舉例）**

> Dataset 通常分兩部分：**原始流量**是作者在實驗網路錄下來的封包（PCAP）；**label** 是另外一個檔案，把封包整理成一筆一筆的 flow（一條連線），再標註這筆是正常還是哪種攻擊。
>
> 以 IoT-23 Hakai 的一筆為例。Label 檔（Zeek `conn.log.labeled`）裡寫的是：開始時間 1533047044.299948、五元組 192.168.100.113:43324 → 178.128.185.250:50 TCP、持續 3.15 秒、來源送 3 個封包、對方沒回、label 是 Malicious C&C。
>
> 回到 PCAP，用同樣的五元組、時間落在開始到結束之間去找，剛好找到 3 個 SYN，第一個封包的時間就是 1533047044.299948，和 label 的時間到微秒都一樣。五元組相同、時間落在範圍內、封包數相同，這筆就對齊了。
>
> 所以 label 檔一定要有五元組和時間，而且時間要夠精確。CIC-IDS2017 的時間長得像「7/7/2017 3:30」，只到分鐘、沒有 AM/PM，同一分鐘內同一組五元組如果有好幾條連線，就分不出誰是誰，所以是三角形。CICIoT2023 的 CSV 連五元組和時間都沒有，所以打叉。

**備用 —— 為什麼 CIC 三份的 ① 是三角形**

> CIC 三份要先填表登記，放在機構網站，沒有 DOI。依 Ring 的標準算公開；依 ACM 的標準，沒有封存庫和識別碼，不保證之後拿到的還是同一份，所以標三角形。IoT-23 有 Zenodo DOI，兩種標準都符合。

**備用 —— IoT-23 與 CIC-IDS2017 的 ② 為什麼不是同一種理由**

> ② 這欄看的是 label 能不能和封包對齊。IoT-23 能逐筆對齊，我抽了兩個 scenario（Hakai-8-1、Somfy-01）都 100%，不是全部 23 個；它的 v2 說 v1 有 label 錯誤，但沒列明細，要先對齊才能檢查對錯。CIC-IDS2017 的 △ 是時間只到分，追溯精度不夠；它的 label 錯誤則是 Engelen 已經公開列出並重標，所以直接用修正版。Ring 2019 的 Labeled 只分類資料集有沒有 label，我沒有拿它當 ② 的出處。

**備用 —— 為什麼只需要 ①②，③④ 是什麼**

> 學界談資料集可復現時，常見還有兩條：③ 資料集的產生過程有完整紀錄（拓撲、擷取點、時程），④ 從原始封包到 label 的處理流程可以重做（標註程式、工具版本）。出處是 FAIR 原則的 R1.2（要有來源紀錄）、ACM 的 Functional 等級，以及 Gebru 等人 Datasheets 的 §3.4。
>
> 但這兩條是「**重做資料集本身**」才需要：例如我們想自己重新擷取、重新標註一份新的 IoT-23。我們不是要重做資料集，而是要拿現成的資料集來測，所以不需要 ③④。把它們也當成必要條件，會得到「四個都不行」這種對我們沒意義的結論。
>
> 完整的查證我另外整理了，需要的話可以提供。其中 ③④ 除了 CIC-DDoS2019 的④不成立（工具版本說法不一致、找不到標註程式），其餘都是部分成立。

**備用 —— IoT-23**

> 發布在 Zenodo，DOI 是 10.5281/zenodo.4743746，授權 CC BY 4.0，不用登記。要注意授權有矛盾：各 scenario 的 README 寫「需要 Stratosphere Lab 授權」，所以引用時以 Zenodo 為準。我們的測試樣本是從 mcfp（Stratosphere）的個別 scenario 目錄下載的，不是 Zenodo 那包 21 GB 的封存檔；驗證腳本只比對我們下載時自己記下的 SHA-256，沒有跟 Zenodo 核對過（mcfp 上的 tar 在 2022-03 被改過，是否與 Zenodo 相同不確定）。light 版沒有 PCAP，而且只在 Stratosphere 網站、不在 Zenodo，要 PCAP 得下載 full 版。
>
> **新發現一：IoT-23 有 v2。** 作者在 v2 的 changelog 說有「fewer errors」，等於承認 v1 的部分 label 有錯，但沒列出明細；v1 README 裡的感染時間軸（infection timeline）被作者評為「often incomplete and not accurate」，v2 把它刪了，這講的是 README 的文字，不是資料的時間戳記。v2 也用 pcapfix 修了部分 PCAP 的壞標頭，這和需求 ① 有關。v2 附上每個 scenario 的標註規則檔。但 v2 自稱還是 work in progress，也沒有 DOI。**我們用的是 v1**，也就是 Zenodo 那份。
>
> **新發現二：label 是怎麼產生的。** 官網說明：Zeek 先從 PCAP 產生 conn.log 的 flow，再由分析師人工判斷，用規則表加上 Flaber 這個程式貼 label。也就是「Zeek 產生 flow，label 是人工規則加 Flaber」，不是 Zeek 直接產生 label。Flaber 的 GitHub repo 是 2022 年才建立，比資料集晚兩年；公開的規則表只有 5 條通用規則，不是各 scenario 實際用的規則。
>
> 我們反推 Hakai 的 C&C label，結果剛好等於「目的 IP 加目的 port 50」；這是其中一條能完全重現 label 的規則，因為 port 50 只出現在 C&C，光看 port 50 也能完全重現。這呼應第 8 頁：這筆 Hakai C&C 樣本目前只驗證到 IP、port 層級的處置。

**備用 —— CIC-IDS2017**

> 它有兩種 CSV。`MachineLearningCSV` 那版只保留 Destination Port，其他鍵都拿掉了，所以完全對不回封包。`GeneratedLabelledFlows` 才有五元組和時間。時間只到「分」（所以第 6 頁 ② 標三角形），而且是 12 小時制、沒有 AM/PM，只有週一例外，精確到秒。
>
> 已知錯誤：Engelen 等人在 2021 年 IEEE SPW 指出，超過 20% 的 trace 被重建或重新標註，並釋出修正版（網址在 References 頁）；Liu 等人 2022 又做了更新的版本。我們說的「用修正版」就是指這些。
>
> **新發現三：CIC 官方的標註程式沒有公開。** Liu 等人 2022 自己說，他們的標註邏輯是 reverse-engineered，「for the first time」公開。官方只公開了 CICFlowMeter，而且沒有版本 tag、論文與官網都沒寫用了哪一版。這是依 Liu 的說法推論，原文沒有逐字說官方沒公開。另外要登記才能下載，也沒有 DOI。

**備用 —— CIC-DDoS2019**

> CSV 有五元組和微秒級時間，所以第 6 頁 ② 打勾，CSV 可以和 PCAP 對齊。2020 年版的官網說訓練日是 2019 年 1 月 12 日，但資料裡的日期是 2018 年 12 月 1 日。我的依據有兩個：一是鏡像 CSV 的第一筆 flow 時間是 2018-12-01 09:17:11.183810；二是 CICFlowMeter GitHub issue #69 有人用 Wireshark 打開官方 PCAP，第一個封包的時間到微秒都一樣。所以 CSV 和 PCAP 是一致的。PCAP 這部分我是引用別人的截圖，沒有自己下載。
>
> **新發現四：官網時程對不上。** 這是 issue #69 的第三方回報，**官方沒有確認**：2024 年有人說 PCAP 的起訖時間與官網時程對不上（擷取 8 小時 18 分，官網攻擊時段 7 小時 52 分）。但擷取本來就可能比攻擊時段更早開始、更晚結束，所以 8:18 對 7:52 不是強證據；比較有力的是 2020 年快照寫擷取 09:40–17:35（7 小時 55 分），仍與 8:18 不合，但回報者的時區設定不明。現行官網已經把日期那句刪掉，只在 2020 年的 Wayback 快照看得到。所以我的做法是不用官網時程切攻擊時段，**日期與時刻一律以資料內的時間為準**。
>
> 工具版本說法也不一致：官網寫 CICFlowMeter-V3，CICFlowMeter 的 repo 說明把 V4.0 和 CICDDoS2019 寫在同一句，實際用哪一版無法確認，repo 又沒有任何 tag。標註程式也找不到，同樣沒有公開。

**備用 —— CICIoT2023**

> CSV 沒有 IP、port、timestamp，而且順序已經打亂。依論文的標註方式，整次攻擊的擷取都標成該攻擊，所以它不是完全對不回，最細只能對到每次攻擊的整段擷取。PCAP 實際怎麼分檔、檔名有沒有帶攻擊名稱，官網沒寫，我沒有下載確認，所以「只到檔案」是依論文推的。攻擊期間的檔案也包含同時存在的正常流量，卻整檔標成攻擊，所以 label 本身就有雜訊。

## 第 7 頁　IoT-23 實測：label 對齊

> 這是 Hakai 這個 scenario 的對齊結果，對應需求 ②。只抽了兩個 scenario、v1 的 label 有錯誤這兩個但書，上一頁講過了，所以不能說整個資料集 100%。
>
> **怎麼做的**：寫了一支只讀檔的腳本。它讀 label 檔裡的每一筆 flow，拿這筆的五元組和時間範圍（開始時間到開始時間加持續時間）回 PCAP 裡找封包，再比較「找到的封包數」和 label 檔自己記錄的封包數（送出加收到）是不是一樣。
>
> **為什麼這樣能證明需求 ②**：label 檔本身記了每筆 flow 有幾個封包，這是一個獨立的答案。如果每一筆都能用五元組加時間找到、而且數量完全相同，就代表每筆 label 都能明確對應到它的封包，不會多也不會少。腳本不送封包、只讀檔，任何人拿同一份資料跑一次，會得到一樣的結果，這就是可復現。
>
> 三個數字：
> - 10,403 條 flow，**100%** 都對齊到封包。
> - 其中 C&C label 有 8,222 條，**全部是 S0**。S0 在 Zeek 的意思是只看到連線嘗試，沒有回應。
> - C&C 的封包裡，有 payload 的數量是 **0**。總共 12,334 個封包，payload 都是零。
>
> 這三個數字的意思：對齊本身沒問題，但 Hakai 這個 scenario 的 C&C label 只有 SYN，沒有任何應用層內容。這是這一個樣本的特性，下一頁會當作限制來講。

**備用**

> 我另外試了 Somfy-01 也是 130／130 對齊（共兩個 scenario）。另外觀察到 ARP 約佔 29.4%，這些封包沒有 label，因為 Zeek 的 conn.log 只記 IP 連線。「對齊」的定義是：PCAP 中依五元組加時間找到的封包數，等於 conn.log 的 orig_pkts 加 resp_pkts。label 值的大小寫也不一致，Hakai 是 Benign，Somfy 是 benign，用的時候要注意。


**備用 —— 怎麼驗證 IoT-23（三個步驟）**

> **Verify**：檢查雜湊與 PCAP 能不能讀，對應需求 1。雜湊是我下載時自己記下來的；這兩個樣本是從 Stratosphere 的個別檔案目錄（mcfp）下載的，**沒有跟 Zenodo 那包 21 GB 的封存檔比對過**，所以 Verify 證明的是「我給的樣本可以被核對」，不是「跟 DOI 那份相同」。
> **Align**：把 label 和封包對齊，對應需求 2，就是這頁的截圖。
> **Re-crop**：依記錄的五元組與時間重新裁切出小案例，確認輸出與原本的小案例位元組完全相同（byte-identical）。
> 整個過程只讀檔、不送封包，任何人拿同一份資料、跑同樣的腳本，會得到相同結果。腳本放在專案的 tests/dataset 目錄，分別是驗證雜湊與重新裁切、label 對齊、以及記錄裁切條件。

## 第 8 頁　IoT-23：能不能拿來測 gateway

> 這頁是**另一個問題**，不是可復現性：資料集可以復現，不代表能拿來測 gateway。
>
> 上面小圖是 Docker 實驗環境：三個節點，cli 在 LAN、srv 在 WAN，gw 兩邊都有掛，上面用 nft counter 數封包，兩張網卡各跑一個 tcpdump。cli 用 tcpreplay 把 PCAP 重播出去。
>
> **怎麼做的**，四步：
> 1. 用上一頁的對齊結果，從 PCAP 裡挑出一筆 C&C flow 的 3 個封包。
> 2. 把封包裡原本實驗室的 IP 和 MAC，改成我們環境的 cli 和 srv；內容和時間間隔不動。
> 3. 從 cli 重播出去，同時在 gw 的入口、出口兩側抓包，並記錄規則的 counter。
> 4. 先把規則停用跑三次當對照，再啟用跑三次。
>
> **為什麼這樣能證明可以拿來測 gateway**：
> - 只改位址、不改內容，所以 gateway 看到的就是資料集裡的流量本身。
> - 停用規則時封包會穿過去（出口 3），這證明路是通的；啟用後出口變 0，所以擋下來是規則造成的，不是封包在別的地方掉了。
> - 入口收到、counter 增加、出口沒有，三樣證據彼此獨立，同時成立才算擋下。
> - 重複三次結果一樣，表示這個測試本身可以重現。
>
> 重播的結果：規則啟用時，入口進來 3 個封包，出口是 **0**，nft 的 counter 是 3。規則停用、啟用各重播三次，結果一致。
>
> 所以**結論**是：目前的測試顯示，dataset 的 packet 改位址後，可以重播穿過 gateway，而且處置結果可以觀察、可以重複。
>
> **限制**要講清楚，但只針對這一個樣本：這筆 Hakai 的 C&C 只有 SYN，沒有 payload，所以目前只驗證到 IP 和 port 這個層級的處置。這不代表 dataset 不能用來測 detection；IoT-23 其他 21 個 scenario 有沒有 payload，我沒有查過。第 5 頁的測試要用哪一份 dataset，還在挑選。

**備用 —— 第 5 頁的測試要用哪一份 dataset？**

> 還沒定。條件有三個：可復現（第 6 頁）、要有 payload，才能驗證 IP／port 以外的處置（這頁的 Hakai C&C 只有 SYN，是這個樣本的限制）、label 可以和封包對齊（第 7 頁）。目前的候選有兩個：一是 CIC-IDS2017 修正版，但要先確認時間精度，而且要登記、沒有 DOI；二是 IoT-23 的其他 scenario，還沒查它們是不是也只有 SYN。兩個都還沒實測，所以現階段不指定。

**備用 —— srv 回 RST**

> 規則停用時，srv 會對收到的 SYN 回 RST。原因是 tcpreplay 不建立連線，重播出去的 SYN 到了 srv，那邊沒有人在聽，作業系統就會回 RST。這不代表資料集有問題，而是這個工具本來的行為。tcpreplay 只是這次用的工具，不是唯一方式。

**備用 —— 細節**

> Docker 裡的 cli 是一個容器，換到實機時對應筆電的 lan netns。重播之前要用 tcprewrite 改位址和 MAC，把 PCAP 裡的位址換成我們環境的；再用 tcpdump 依來源位址把封包拆成兩個方向，cli 端和 srv 端各自重播。（tcpprep 也能分方向，但它是給單機雙網卡用的，這次沒有用；正式效能測試要改用單一 process 加 tcpprep cache，見第 5 頁備用「正式效能測試要處理的事」。）

**備用 —— 對應到 Pi**

> 在 Pi 上，cli 和 srv 是同一台筆電的兩個介面，gw 換成 Raspberry Pi。拓撲等價，但 Docker 的虛擬網卡沒有 USB 網卡的 offload 和 MTU 行為，這一部分要上實機才驗得到。

# 測試工具

> 第三節：剛剛用的 tcpreplay 只是其中一種。實作 gateway 時，還有這些工具可以快速測規則，它們在 Docker lab 和 Pi 上都能用。

## 第 9 頁　六種候選工具

> 表格看三欄：工具、產生什麼流量、可以測哪一類規則。
>
> - **Nping**：TCP、UDP、ICMP 封包，可以測標頭欄位、TCP flags、速率門檻這類規則。
> - **hping3**：自訂 TCP/IP 封包，能測的類型同上，當 Nping 的備選。
> - **Scapy**：用 Python 自己組封包，最適合測規則邊界，也就是只差一個欄位的「命中」與「不命中」。
> - **Nmap**：連接埠掃描，測掃描偵測。目標要有開放的服務才有意義。
> - **SlowHTTPTest**：慢速 HTTP，測慢速連線與逾時，WAN 端要有 HTTP server 接。
> - **Tcpreplay**：重播 PCAP，測已知攻擊樣本，也就是 dataset 的 PCAP 重播；要先用 tcprewrite 改位址。能不能驗證到 detection，要看樣本有沒有 payload，像第 8 頁這筆 Hakai C&C 只有 SYN，目前只驗證到 IP／port 層級的處置。
>
> 六種工具在 Debian trixie 都有官方套件，所以 Docker lab 和 Pi 都能直接安裝。nping 是包在 nmap 套件裡的。

**備用 —— hping3**

> hping3 最後一次 commit 是 2014 年，實質上沒人維護。所以我把它放備選，優先用 Nping。

**備用 —— 怎麼用這些工具測規則**

> 一個循環四步：寫規則 → 用工具產生「應該命中」和「不應該命中」兩組封包 → 看 nft counter 和 log，確認該擋的有擋、不該擋的沒擋 → 不對就修規則再跑。只測命中不夠，還要確認沒有誤擋。第 8 頁「規則停用、啟用各重播三次對照」就是這個循環的一次實例。

**備用 —— 兩端在 Docker 與 Pi 上各對應什麼**

> 在 Docker lab，LAN 端是 cli 容器，WAN 端是 srv 容器，中間 gw 是容器，掛 nft counter 和 tcpdump。在 Pi 上，LAN 端是筆電的 lan netns，WAN 端是筆電的 eno2，中間換成 Raspberry Pi。實體環境的兩端是同一台筆電，用 network namespace 隔開，不然封包會直接走 loopback，不會經過 Pi。等價的是拓撲和測試流程；不等價的是 Docker 的 veth 沒有 USB 網卡的 offload 與 MTU 行為。

**備用 —— Tcpreplay 能做／不能做**

> 能做：依原速或指定速率重播、用 tcprewrite 改 MAC 和 IP、用 tcpprep 分方向。不能做：建立新的 TCP 連線、依伺服器回應調整、量測服務是否受影響，因為它不是網路協定堆疊，只是把封包原樣送出去。所以它適合驗證「處置」；需要真的建立連線的測試，要靠流量產生器。同一套工具裡的 tcpliveplay 可以對真實 server 重播，但只限單一 TCP session。
