### CICIoT2023

**4-1 原始資料與授權**

**4-2 標籤可追溯**
- 論文 Neto et al., Sensors 23(13):5941（https://www.mdpi.com/1424-8220/23/13/5941）§4：
  - 「for each attack executed, the entire traffic captured is labeled as belonging to that particular attack」
  - 「we only remove the timestamp from the list since it does not illustrate the network behavior—instead, it is used for sorting」
  - 「we split it into smaller chunks of 10 MB」
- 判定理由：
  - 準則 2 要求「每筆標籤」能對回封包。CSV 每列是 10 或 100 封包窗口的平均值，又沒有 IP、port、timestamp → 單列無法對回
  - 只有「PCAP 檔 → 攻擊類別」的檔案層級對應，相當於 Ring et al. 的「indirect」標註
  - 攻擊期間的檔案也包含同時存在的正常 IoT 流量，卻整檔標為攻擊 → 封包層級本身就有標籤雜訊
  - 所以判 ✗
  - 如果測試只需要「重播某個攻擊檔，看 gateway 的反應」，檔案層級可以用，但不能做逐 flow 對答案
- PCAP 實際檔名是否帶攻擊名稱：沒有下載過 → **UNCLEAR**

**4-3 產生過程紀錄**
- 論文 §3.2：「the Cisco switch is connected to the second part through a Gigamon Network Tap … sends it to two network monitors … using wireshark」。§3.3 寫「mergecap [48] is used to unify pcap files」
- Table 1 列出裝置與 MAC（例如「1C:FE:2B:98:16:DD」），**沒有 IP**。攻擊端是 7 台 Raspberry Pi
- 官網有 Topology chart／diagram 圖

## 3. 與舊表（`查證_資料集.md`）的差異

舊表是事實清單，沒有逐準則判定。以下列出本次查證後**需要修正或補充**的地方：

1. **CIC-DDoS2019 的「官網日期」已經不在官網上。** 舊表寫「官網 First Day 列的是 3/11」。現行官網沒有任何日期，只剩 First Day／Second Day；1/12、3/11 那句只存在 2020 年的 Wayback 快照。建議改寫為「官網曾寫 1/12、3/11（2020 快照），現已刪除」。這也說明官方說明頁會在不留紀錄的情況下改動。
2. **CIC-DDoS2019 的「CSV 與 PCAP 一致，不影響標籤對回封包」要打折。** issue #69 在 2024 年的回覆指出，PCAP 的起訖時間與官網時程差了不只一個整點時差，持續時間也不同（8:18 vs 7:52）。CSV 對 PCAP 可能還是一致，但**用官網時程對回封包是不可靠的**。
3. **CIC-DDoS2019 的工具版本互相矛盾。** 官網寫 CICFlowMeter-V3，CICFlowMeter repo 說明寫 V4.0 用於 CICDDoS2019，repo 又沒有任何 tag。舊表沒有記錄這點。
4. **CIC-IDS2017 的時區推論現在有第三方佐證。** issue #173 回報「12 hour format」「offset by 3 hours … local time」。它仍然不是官方說明，舊表「官方未說明」維持不變。
5. **官方沒有公開 CIC-IDS2017 的標註程式，這點現在有出處。** 依據是 Liu et al. 2022 的「labeling logic that has been reverse-engineered … made publicly available for the first time」。
6. **IoT-23 的授權不是單純的 CC BY 4.0。** Zenodo 寫 CC BY 4.0；mcfp 根目錄寫 CC-BY，沒標版本（本地紀錄連到 2.0）；各 scenario README 又寫「You need authorization from the Stratosphere Lab」。三處互相矛盾，引用時應以 Zenodo 為準並註明這個矛盾。另外，Zenodo record 是 2021-05 才建立，mcfp 上的 tar 在 2022-03 又被改過，兩份是否相同尚未驗證。
7. **IoT-23 有 v2，而且作者承認 v1 的問題。** v2 changelog 寫 v1 的 timeline「often incomplete and not accurate」，標籤改成「fewer errors and more reproducibility」，並附上每個 scenario 的 labels.config。舊表完全沒提到 v2。v2 仍是 work in progress，也沒有 DOI，所以本表仍以 v1 為評估對象。
8. **IoT-23 的標註工具要補充。** Flaber 是 2022-01 才公開，比資料集晚兩年，沒有版本 tag。公開的規則表只有 5 條通用規則，不是各 scenario 實際用的規則。另外，官網明說標註是由分析師在 dashboard 上人工判斷。所以「標籤是 Zeek 產生」只說對一半：**Zeek 產生 flow，標籤是人工規則加上 Flaber**。
