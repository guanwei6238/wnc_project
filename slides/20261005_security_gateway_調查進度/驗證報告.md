## 5. 問題清單與修改建議（依嚴重度）

### 🔴 A. RFC 9411 圖的 Test Equipment 範圍錯誤（P4）
- 現況：`groupnode(enclose: ((0,0),(1,0),(2,0)))` 把三個節點都框起來，標籤放在 `(1,1)`，離框很遠
- RFC 9411 Figure 1：Clients 與 Servers 各自在一個 Test Equipment 方框內，DUT/SUT 在兩框之間
- 建議：改成**兩個框**，分別 enclose `(0,0)` 與 `(2,0)`，各自在框下標「Test Equipment」；或取消框，只在兩個 Emulator 下方各放一行小字。同步更新 `slide_implement.md` P4 的 ASCII 圖

### 🔴 B. 截圖佔位（P10、P11）
- 把 `02_align.py`（Hakai）與 `03_replay.sh` 的輸出截圖放到 `assets/align.png`、`assets/replay.png`，再把 `main.typ` 的 `has-shots` 改成 `true` 重編
- 截圖內容需與本報告 #33–#38 的數字一致（已驗證輸出就是這些數字）

### 🟡 C. 「安全功能全開」→「建議安全功能全開」（P4、逐字稿第 2 頁）
- 表格「前提」改為「建議功能全開、≥ 500 CVE 驗證」或「RECOMMENDED 功能全開」

### 2.1 專案對應：`queue flags bypass` 等於 Fail-Open

| 檢查 | 結果 |
|---|---|
| `docker/gw.nft` 的內容 | `ct state new counter queue flags bypass to 0`，chain policy 是 accept |
| nftables wiki〈Queueing to userspace〉 | "the bypass option which will skip the enqueue of the packet to userspace if no application is listening to the queue. The rule will behave as an accept rule if there is no application waiting for packet." |
| `man nft` 的 QUEUE STATEMENT | bypass 的說明是 "Let packets go through if userspace application cannot back off" |
| 結論 | ✅ **對應成立**。講稿說「NFQUEUE 背後的程式沒在跑的時候，封包直接放行」，和官方語意一致：沒有程式綁定 queue 0 時，這條規則等於 accept，也就是 fail-open。拿掉 bypass 之後，沒有程式綁定時封包會被丟掉（fail-closed） |
| 補充（不影響結論） | ① bypass 只處理「沒有程式綁定」的情況。程式有綁定但 queue 滿了，kernel 預設是丟包；除非程式自己設定 `NFQA_CFG_F_FAIL_OPEN`。`security_gateway/src/main.rs` 沒有設定這個 flag，所以目前這種情況已經是 fail-closed。② `ct state established,related accept` 代表只有每條連線的第一個封包會送到 userspace。這和 Fail-Open 是兩件事，但如果有人追問「拿掉 bypass 就算完全照 RFC 了嗎」，要知道 inline 檢查的範圍目前也只有新連線（見問題 6） |

## 3. 問題清單（依嚴重度）

### 🟡 1. 「物件 1–256 KB」不精確，而且上下限都超出（A12）
- 位置：P4b 右欄第 2 列；逐字稿第 3 頁「物件大小從 1 KB 到 256 KB」；`slide_implement.md` 的 P4b 表格
- 問題：
  - 原文是 **1、16、64、256 KB 四種固定大小**，再加 Table 5 的混合組。不是連續區間
  - 混合組的範圍是 **0.2–347 KB**，上下限都在「1–256」之外
  - 物件大小是 §7.3／§7.7 吞吐量測試的 RECOMMENDED 參數，不是 §4.3 測試設備的通用 MUST。現在和「HTTP/1.1 以上（MUST）」放在同一格，會讓人以為等級相同
- 建議（擇一）：
  - 投影片改成「HTTP/1.1 以上；物件 1／16／64／256 KB＋混合」。字數多一點，可以縮小該格字級
  - 或投影片只留「HTTP/1.1 以上」，物件大小改放講稿
- 講稿改成：「HTTP 至少 1.1。吞吐量測試建議用 1、16、64、256 KB 四種固定大小，再加一組混合大小，混合裡從 0.2 KB 到 347 KB 共 10 種。」
- `slide_implement.md` 的 P4b 表格也要同步修改

### 🟢 2. 第 4 頁備用「MUST 的是……」容易被聽成只有三項 MUST

- 建議改成：「這兩頁的 MUST 有 Fail-Open 關閉、Inline、Reference test，還有 TLS ≥ 1.2、完整 handshake、取樣間隔小於 2 秒這些；Sustain 至少 300 秒和 Init 至少 5 秒只是建議值。」

### 1.3 「超出 RFC 的部分」逐項回 RFC 9411 原文

| 項目 | RFC 9411 原文 | 判斷 |
|---|---|---|
| 惡意程式 | Table 1 把 Anti-Malware 定義成安全功能，Table 2／3 列為 NGFW／NGIPS 的 RECOMMENDED 功能。但 Appendix A 的攻擊流量**只有 CVE**（A.1：「Section 4.2.1 defines the selection of the malicious traffic from the ... CVEs」） | 「有效性測試不含惡意程式樣本」正確。但 RFC 並非沒提到 malware，它是要開啟的功能，只是沒有測試 |
| 規避手法 | Anti-Evasion 同樣是 Table 2／3 的 RECOMMENDED 功能。Appendix A 沒有 evasion 測試 | 同上 |
| 私有清單 | 全文沒有公開／私有清單的概念（`grep -i private` 只出現在 IP 位址段） | 正確 |
| 背景 45% + 45% | A.3.2 原文如上 | 正確 |
| 94% 負載算「超出」 | RFC 的基準是 **HTTP 與 HTTPS 64 KB 吞吐量**各 45%。NetSecOPEN 用的是 **application traffic mix**，基準是 traffic mix 的最大吞吐量。兩者的流量種類與基準都不同，不能直接比大小 | 不成立，應改成「背景流量的做法不同」 |
| （逐字稿沒提）CVE 是否在背景流量下測 | A.6.2：「While generating background traffic (in the sustain phase), send the CVE traffic」，CVE 必須在背景流量下送出 | NetSecOPEN 的 5,388 個是**在沒有合法流量的情況下**測的，負載下只送 **50 個**。RFC 是要求整組 CVE（§4.2.1 建議 ≥ 500 個）在背景流量下送。這方面認證反而比 RFC 少，或者說是不同的拆法 |
| （逐字稿沒提）加密 CVE | A.1：CVE 以「encrypted and cleartext payload formats」送出；A.3.2 規定加密 CVE 的 cipher | 報告沒有說明 CVE 是否有加密版本，無法判斷 |

**結論**：「多了惡意程式、規避手法、私有清單」這部分有依據。但「94% 負載超出 45%+45%」和「認證做得比 RFC 的最低要求多」不成立，因為 CVE 主測是在無背景流量下做的，負載下只送 50 個，背景流量的種類也不同。比較中性也正確的說法是：「認證的做法和 RFC 不完全相同，有多的部分，也有拆開做的部分。」

## 2. 問題清單（依嚴重度）

### [中] 1. 「超出 RFC 要求」與「認證做得比 RFC 的最低要求多」說得太單方面（N12、1.3）
- 位置：逐字稿第 6 頁備用「超出 RFC 要求的部分」；`查證_RFC與工具.md`「超出 RFC 的部分」也是同樣的寫法
- 問題：
  - 5,388 個攻擊是在**沒有合法流量**的情況下測的（原文："performed without sending legitimate user traffic"）。RFC Appendix A 是要求 CVE 在背景流量下送
  - 負載下只送了 50 個 CVE。RFC 是整組（≥ 500）都在背景流量下送
  - 背景流量是 application traffic mix 的 94%，RFC 則是 HTTP／HTTPS 64 KB 吞吐量各 45%。基準不同，「94% > 90%」不能比大小
  - 惡意程式、規避手法在 RFC 裡是要開啟的安全功能（Table 2／3），只是 Appendix A 沒有測。說「超出」可以，但要說「超出 Appendix A 的測試範圍」
- 被問「所以認證比 RFC 嚴格嗎？」的時候，現在的講法會答錯
- 建議改成：
  > **和 RFC 的差異**：認證多測了惡意程式、規避手法和一份廠商不知道的私有清單，這些 RFC 的 Appendix A 都沒有要求。但做法也和 RFC 不完全一樣：5,388 個攻擊是在沒有合法流量時測的，負載下只送 50 個；背景流量用的是 traffic mix 跑到約 94%，RFC 則是 HTTP 與 HTTPS 各 45%。所以應該說「做法不同、範圍更廣」，不是單純「比 RFC 多」。
- `查證_RFC與工具.md` 的同一條也要同步改。`slide_implement.md` 事實 18 只引用該節，不必改

## 2. 問題清單（依嚴重度）

### [中] 1. 理由 (b)「送雲端路徑幾乎不會被觸發」說得太滿
- 位置：逐字稿第 6 頁 (b)；`slide_implement.md` 事實 15 (b)
- 問題：會不會送雲端，取決於**我們 gateway 本地規則的涵蓋範圍**，不是取決於 CVE 是「已知」。我們的設計是「本地判斷不出來才送雲端」，如果 gateway 本地沒有某個 CVE 的規則，那個 CVE 對 gateway 來說就是「判斷不出來」，反而會走雲端路徑。被問「CVE 也可能本地擋不到啊？」時會答不上來
- 原文能支持的只有：測試流量只分「合法背景流量」和「挑選過的 CVE」兩類，沒有設計「本地無法判斷」的流量，也沒辦法**控制**送雲端的比例
- 建議改成：「(b) 測試流量只有兩類：合法的背景流量和挑選過的 CVE，答案都是事先知道的。RFC 沒有設計『本地判斷不出來』的流量，所以沒辦法控制送雲端的比例，也就量不到『送雲端比例對效能的影響』。」

### [中] 2. (b)(c) 是推論，講稿沒有標示
- 位置：逐字稿第 6 頁「為什麼不能只靠 RFC 9411？有四個理由」
- 問題：(a)(d) 有原文依據，(b)(c) 是推論；(c) 前面掛了「§4.3.3」，聽眾會以為「反覆連同一批 server IP」「命中率偏高」都是原文。講稿在 tcpreplay 那段有明講「這是我的推論」，這裡沒有，處理方式不一致
- 建議：在四點之後加一句：「(a) 和 (d) 是原文看得到的；(b) 和 (c) 是我根據原文推的。」並把 (c) 改成：「(c) §4.3.3 規定每個 client 掃過同一個固定的 server IP 池；Sustain 段持續 300 秒以上，就會反覆連到同一批 IP。另外 Appendix A 也建議同一個 CVE 重送多次。如果雲端判定有快取，命中率會偏高。」（A.3.2 原文：「It is RECOMMENDED to generate each CVE multiple times (sequentially)」）
- `slide_implement.md` 事實 15 也可以在 (b)(c) 後加「（推論）」，和事實 4 的寫法一致

### [低] 3. 「RFC 9411 允許多元件系統」的出處
- 位置：逐字稿第 6 頁 SUT 段；`slide_implement.md` 事實 15 末句
- 問題：RFC 9411 只寫「DUT/SUT」，沒有定義 SUT。「多個設備當成一個整體」出自 RFC 2285 §3.1.2。結論沒錯，但被追問「9411 哪裡寫的」會找不到
- 建議改成：「RFC 9411 全文都寫 DUT/SUT，SUT 是 System Under Test。依 RFC 2285 的定義，SUT 可以是多個設備，當成一個整體來測，所以 gateway 加雲端可以算一個 SUT。」

### [低] 4. 第二層怎麼量吞吐量／延遲，沒有備答

## 2. 問題清單（依嚴重度）

### [高] 1. 第 4 頁「為什麼選 RFC 9411」的兩個理由都是這次不採用的部分
- 位置：第 4 頁表格「有狀態流量」「L7 安全功能」兩欄；講稿 L86「只有 RFC 9411 是針對安全設備、又涵蓋 L7 安全功能的，這就是選它的原因。不過我們只參考它的效能測試流程。」
- 問題：範圍收斂後，安全功能不做，效能測試又是用 tcpreplay 重播 dataset（無狀態、不建立連線，見 L106）。投影片打勾的兩個優點我們都沒用到，L86 的「選它的原因」和緊接的「不過只參考流程」互相抵消。聽眾很容易問：「那你們用的部分，跟 RFC 2544 有什麼差別？」講稿沒有準備答案
- 建議：
  - 第 4 頁的理由要改成和「效能測試流程」有關的。可行的方向是：RFC 9411 是目前針對 network security device、取代 3511 的方法，而且它規定了 Reference test（MUST）和 Sustain 段量測、取樣 < 2 s（MUST）。**但動手前要先查證** RFC 2544／3511 有沒有對應規定（例如 2544 的 trial duration 和 binary search），不能直接寫「只有 9411 有」
  - 最少要做的：L86 改成「選它的原因是它針對網路安全設備，而且是現行的方法；它的 L7 安全功能測試不在我們的範圍，我們用的是它的 Reference test 和 Sustain 量測規則」，並在第 4 頁加一段備用「我們用的部分跟 RFC 2544 有什麼差別」
  - 表格欄位要不要改，由使用者決定（例如把「L7 安全功能」改成「Reference test」，前提是查證後成立）

### [高] 2. 效能測試的「受測範圍」和「比較對象」對不上
- 位置：第 5 頁表格「受測範圍：整個 gateway（本地 + 雲端）」「比較對象：Suricata、Snort 3」；講稿 L98、L102、L134
- 問題：
  - 受測的是本地加雲端，比較對象卻是沒有雲端的單獨 Suricata／Snort 3。量到的差距會混入雲端路徑（送雲端、等判決）的成本，沒辦法說明差距來自哪裡
  - L102 自己說比較的目的是「確認我們的**本地端**沒有比它們差」，這和表格的「整個 gateway（本地 + 雲端）」矛盾
  - 第 10-04 版講稿寫的是「同硬體同規則」，這版 L98、L134 只剩「同一台硬體、同一份 dataset」。少了「同一套規則」，效能差距可能只是規則數量不同造成的
  - RFC 9411 §3 說，有 ML 或行為分析功能時「should be disabled」。如果雲端用 ML，把雲端打開量效能，正好是 RFC 說要關掉的情況。講稿 L110、L115 用「只參考、不宣稱符合」處理，這可以接受，但第 5 頁的設計和這一點有張力
- 建議：效能測試拆成兩個量測，或至少在講稿講清楚：(a) **只開本地** 的 gateway 和 Suricata／Snort 3 比（同硬體、同規則、同 dataset、同 inline 方式，例如都用 NFQUEUE）；(b) 同一個 gateway 雲端關／開，量雲端路徑多出的 latency 和 throughput 下降。表格可以不改，但 L98 至少補「和 Suricata／Snort 比的時候雲端關掉，雲端的成本另外量」。這會動到老師同意過的表格，要先和使用者確認

### [高] 3. 用「同一份 replay」比較 Suricata／Snort 3 inline，目前的重播方式不公平
- 位置：講稿 L98、L134（同一份 dataset 比較）；L293（srv 回 RST）、L297（用 tcpdump 拆成兩個方向，cli 和 srv 各自重播，沒有用 tcpprep）
- 問題（Suricata、Snort 3 都是以 flow／stream 追蹤為基礎的引擎）：
  1. **兩個方向沒有同步**：cli 端和 srv 端是兩個獨立的 tcpreplay process，兩邊的先後順序不保證。stream reassembly 要看到正確順序的雙向封包，順序亂掉時引擎可能不做 reassembly、產生 stream event，甚至在 inline 模式把封包丟掉
  2. **srv 的作業系統會插入不在 dataset 裡的 RST**（L293 已確認）。RST 會讓 Suricata／Snort 和 conntrack 提早結束 session，後面重播的封包會變成沒有 session 的封包
  3. **沒有 handshake 的 flow**（例如 Hakai C&C 只有 SYN，或 PCAP 從中途開始）：Suricata 預設 `stream.midstream: false`，這類 flow 不做 app-layer 解析，檢查的工作量比較少，throughput 會**偏高**；對我們自己的 nftables 規則則沒有這個差別。結果是三方做的工作量不同
  4. **改位址後的 checksum**：tcprewrite 改 IP 之後如果沒有重算 checksum（`--fixcsum`），Suricata 預設會檢查 checksum，壞 checksum 的封包不進 stream 處理
  5. **packet loss 的意義不同**：IPS 會因為規則 drop 惡意封包，所以「掉包」裡混著「規則擋的」和「處理不及的」。三方的規則不同，量到的 loss 就不能直接比
- 結論：同一份 replay 本身不矛盾，前提是 replay 保留雙向順序、不被真實 stack 干擾，並且把 policy drop 和 capacity drop 分開算。目前文件寫的做法（L297）兩個條件都沒有滿足
- 建議：在第 5 頁加一段備用「怎麼讓三方比得公平」：用 tcpprep 產生 cache，由**單一** tcpreplay process 透過兩個介面送雙向（`-i`／`-I`）；srv 端不要讓真的 stack 回應（例如 srv 介面不設 IP，或用 nft drop 掉）；tcprewrite 加 `--fixcsum`；效能測試用 benign 流量，或用 Suricata／Snort 的 drop 統計扣掉規則 drop。同時把附錄 L384 那類禁止事項補一條：「不要說同一份 replay 就公平，要先保證雙向順序與 checksum」。L297 的「tcpprep 這次沒有用」也要補一句「效能比較時會用」

### [中] 4. 講稿說「tcpreplay 量得到 throughput、latency、packet loss」，說過頭了
- 位置：講稿 L106；附錄 L359「（tcpreplay 重播量得到的）」
- 依據：Tcpreplay「The replay model」原文：「tcpreplay's statistics count packets handed to the interface successfully, not packets received by anything … whether a device downstream saw them … is measured on the other end (with a capture, a counter, or the device's own stats)」
- 問題：tcpreplay 自己只報「送出去多少」（offered load），latency 和 packet loss 都要在另一端（tcpdump、nft counter、DUT 統計）量。而且量到的東西和 RFC 9411 同名指標不同：
  - throughput：我們量的是在指定送出速率下 DUT **轉送出去** 的速率；RFC 9411 的 Inspected Throughput 是在有狀態 HTTP(S) 流量下、「examined and allowed」的速率（§6.3），而且要註明量的是哪一層
  - latency：我們量的是封包的轉送延遲（ingress 到 egress）；RFC 9411 的 latency KPI 是 TTFB／TTLB（從 SYN 到收到第一或最後一個 application data，§6.3）
- 建議：L106 改成「我們用 tcpreplay 重播 dataset 當輸入，在 gateway 兩側用 tcpdump 和 counter 量 throughput、latency 和 packet loss。這裡的 throughput 是轉送速率，latency 是封包轉送延遲，和 RFC 9411 的 Inspected Throughput、TTFB 不是同一個東西。CPS、Concurrent Connections、TTFB 需要真的建立連線，tcpreplay 不建立連線，所以不列。」附錄 L359 的括號改成「（用 dataset 重播、在 gateway 兩側量得到的）」

### [中] 5. 第 2 頁和第 5 頁用同樣的字講不同的指標
- 位置：第 2 頁「量測：效能（Throughput、Latency 等）」（這是在講 RFC 9411）；第 5 頁「Throughput、latency、packet loss」（這是在講我們的測試）；講稿 L36
- 問題：聽眾會以為第 5 頁量的就是 RFC 9411 的 Throughput／Latency。實際上 RFC 9411 的 latency 就是 TTFB／TTLB，正好是 L106 說量不到的那一項。這樣講稿前後會自相矛盾：第 2 頁說 RFC 量 latency，第 5 頁說我們量 latency，備用又說 TTFB 量不到
- 建議：投影片照老師同意的字樣不動；講稿 L36 補一句「它的 throughput 指的是 Inspected Throughput，latency 指的是 TTFB／TTLB，都要用有狀態的連線量」。L106 加上第 4 點建議的區分。另外可以補充：RFC 9411 裡跟我們最接近的量測，是 §5 Reference test 要記錄的「packet loss and latency introduced by the test environment」，這兩項是封包層級的

### [中] 6. 沒有說明 Reference test → Sustain 怎麼套到 replay 上
- 位置：第 3 頁講稿 L52–L55；第 5 頁要點與 L100
- 問題：RFC 9411 的流程是為有狀態流量寫的，直接套用到 replay 會有落差，講稿沒有提：
  - §5 step 2：Reference test 要用「HTTP or HTTPS throughput performance test」的 traffic profile、最小 object size。我們用的是 dataset replay
  - §4.3.4：Ramp up 要「從 0 拉到目標」、使用一組 unique client IP；Sustain 是「固定數量的 active clients」。tcpreplay 的速率是整次固定的（`--mbps`、`--pps`、`--multiplier`），沒有 ramp up，要分多次跑或自己寫腳本逐步加速
  - Sustain ≥ 300 s：IoT-23 的小案例遠短於 300 s，要用 `--loop` 重複送。同樣的 5-tuple 和 sequence number 重複出現，對有狀態的 DUT（conntrack、Suricata）來說是同一條 flow 的重送，不是新流量。可以用 tcpreplay 的 `--unique-ip` 讓每一輪換 IP
- 建議：第 3 或第 5 頁加一段備用「用 replay 怎麼做 Reference test 與 Sustain」，講上面三點，並說明這些偏離都要寫進測試報告（附錄可加一條「不要說完全照 RFC 9411 的 load profile；replay 沒有 ramp up，Sustain 要 loop」）

### [低] 7. §3 ML 排除的轉述不夠精確
- 位置：講稿 L110「RFC 9411 把依賴 ML 或行為分析的**功能**排除在範圍外」；L115
- 原文：「The performance testing methodology … is not intended for security devices or systems that rely on machine learning or behavioral analysis. If such features are present in a DUT/SUT, they should be disabled.」
- 問題：被排除的是「依賴 ML 的設備或系統」，對功能的要求是「should be disabled」。只說「排除」，少了「要關掉」這一半，而這一半正好跟第 2 點的「雲端開著量效能」有關
- 建議：L110 改成「RFC 9411 說它的效能測試方法不適用於依賴 ML 或行為分析的系統，這類功能應該關掉。如果雲端用 ML，開著雲端量就不符合它的前提，所以我們只參考流程、不宣稱符合」

### [低] 8. 第 3 頁備用段的「§5 列的理由有四個」和原文不符
