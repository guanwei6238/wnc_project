## 3. 技術查證 ★

每一條都**獨立查一手來源**，不採信規格書的自我宣稱。

### 3-A 🔴 `bpf_xdp_ct_lookup()` 的 kernel 版本寫錯了

| 項目 | 內容 |
|---|---|
| **宣稱** | 規格書 0.4 #4 與逐字稿第 7 頁備用：「kernel **5.19** 起有 `bpf_xdp_ct_lookup()` 這類 kfunc」 |
| **查證結果** | 🔴 **有出入 —— 正確答案是 Linux 5.18** |
| **證據** | 引入該 kfunc 的 commit 是 `b4c2b9593a1c`「net/netfilter: Add unstable CT lookup helpers for XDP and TC-BPF」（2022-01-14 撰寫，2022-01-18 併入）。我用 GitHub compare API 逐個 tag 比對祖先關係：對 `v5.17` 是 `diverged`（**不含**），對 `v5.18` 是 `behind / ahead_by 0`（**已包含**），對 `v5.19` 同樣已包含。並直接抓該 commit 的 patch 確認第 217 行新增 `bpf_xdp_ct_lookup(struct xdp_md *xdp_ctx, ...)`、第 306 行 `BTF_ID(func, bpf_xdp_ct_lookup)`。 |
| **來源** | https://github.com/torvalds/linux/commit/b4c2b9593a1c4c3a718370e34af28e817fd5e5c6 ／ https://kernelnewbies.org/Linux_5.18 ／ https://github.com/torvalds/linux/blob/master/net/netfilter/nf_conntrack_bpf.c |

> **為什麼這條最嚴重**：規格書自己把它列為「被指出時要拿出來反駁的那一題」。如果現場有人說「XDP 其實查得到 conntrack」，講者拿 5.19 去回，對方只要懂一點就會反打「是 5.18」，整段反駁的可信度就沒了。**把逐字稿與規格書 0.4 #4 的「5.19」全部改成「5.18」。**
>
> 投影片上沒有寫版本號，所以**投影片不用改**。

### 3-B 🔴 「能交給 user space：XDP ✗」是這份投影片最大的 Q&A 破口

| 項目 | 內容 |
|---|---|
| **宣稱** | 投影片 P8 表格：`能交給 user space` → XDP `✗`、netfilter `✓ 透過 NFQUEUE` |
| **查證結果** | 🔴 **字面上不成立 —— AF_XDP 就是 XDP 把封包交給 user space 的官方機制** |
| **證據** | Linux kernel 官方文件 AF_XDP 章節原文：「Using the XDP_REDIRECT action from an XDP program, the program can redirect ingress frames to other XDP enabled netdevs, using the `bpf_redirect_map()` function. **AF_XDP sockets enable the possibility for XDP programs to redirect frames to a memory buffer in a user-space application.**」並定義 `BPF_MAP_TYPE_XSKMAP`：「The XDP program can then redirect a packet to a specific index in this map.」 |
| **來源** | https://docs.kernel.org/networking/af_xdp.html |

> **為什麼危險**：規格書 0.4 #4 很細心地把 conntrack 那一格加了「**內建**」兩個字來防守，卻沒有對這一格做同樣的處理。而且逐字稿裡**完全沒有 AF_XDP 的備用段落**——這題被問到會完全沒準備。
>
> **兩個修法（擇一，都不需要改版面）**：
> 1. **改欄位名**（最乾淨）：`能交給 user space` → **`能交回 verdict 繼續走 kernel 路徑`**。這樣 XDP `✗` 就精確了：AF_XDP 是把封包**搬走**，不是交出去等判決再放回原本的轉發路徑。
> 2. **保留原欄位，補講稿備用段落**：
>    > 「這格講的是『交出去等 verdict、再回到原本的轉發路徑』這件事。XDP 當然有 **AF_XDP**，可以用 `XDP_REDIRECT` 配 `XSKMAP` 把封包丟進 user space 的記憶體 —— 但那是把封包**整個搬離 kernel 路徑**，user space 收完之後要自己決定怎麼送出去，沒有 NFQUEUE 那種『回一個 ACCEPT/DROP 然後 kernel 繼續處理』的語意。我們要的是後者。」
>
> 建議**兩個都做**。

### 3-C ET Open 授權 —— 親自下載 tarball 驗證

| 項目 | 內容 |
|---|---|
| **宣稱** | 投影片 P12：ET Open 授權 = **BSD + GPLv2**；規格書 0.4 #2 另稱「網路上有二手來源標成 MIT，與規則集自帶授權檔不符，不可採信」 |
| **查證方式** | 實際 `curl` 下載 `https://rules.emergingthreats.net/open/suricata-7.0.3/emerging.rules.tar.gz`（5.6 MB）並解開，讀 `rules/LICENSE` 與 `rules/BSD-License.txt`，再把全部 `*.rules` 的 sid 抽出來統計 |
| **查證結果** | ✅ **「BSD + GPLv2」屬實（且確定不是 MIT）**，但有**兩個必須知道的但書** |

**（1）`rules/LICENSE` 原文（一手，直接引用）**：

```
# This distribution may contain rules under three different licenses.
#
#  Rules with sids 1 through 3464, and 100000000 through 100000908 are under the GPLv2.
#  Rules with sids 2000000 through 2799999 are from Emerging Threats and are covered under
#  the BSD License
#  Rules with sids 2800000 through 2900000 are provided by Emerging Threats Pro ...
#  Copyright (c) 2003-2026, Emerging Threats
```

tarball 內確實同時附了 `LICENSE` 與 `BSD-License.txt`，**沒有任何 MIT 字樣**。

**（2）但書一：這份 tarball 實際上一條 GPLv2 規則都沒有。**

我把 71802 條規則的 sid 全抽出來統計：

| sid 區間 | 授權 | 實際條數 |
|---|---|---|
| 1–3464 / 100000000–100000908 | GPLv2 | **0** |
| 2000000–2799999 | BSD | **71802** |
| 2800000–2900000 | ETPro | **0** |

實際 sid 範圍是 **2000005 – 2527021**，全部落在 BSD 區間。

> 所以嚴格講：「BSD + GPLv2」是 **LICENSE 檔宣告的授權制度**，不是這份 tarball 的**實際成分**。
> **被問「哪些規則是 GPLv2？」時要答得出來**：「LICENSE 保留了沿襲 Snort 舊 sid 的 GPLv2 區段，但我實際抽過 suricata-7.0.3 這包的 71802 條 sid，全部落在 2000005–2527021 的 BSD 區間，現行版本沒有 GPLv2 規則。所以實務上整包就是 BSD。」
> 投影片寫「BSD + GPLv2」**不算錯、不必改**（那是授權檔的宣告），但講稿要補這一句。

**（3）但書二：🔴「MIT 是二手來源訛傳」的說法，規格書寫錯了。**

`license: MIT` 就寫在 **OISF（Suricata 官方）維護的 `suricata-intel-index`** 裡。我直接抓原始檔確認：

```yaml
  et/open:
    summary: Emerging Threats Open Ruleset
    vendor: Proofpoint
    license: MIT          # ← 就在這裡
    url: https://rules.emergingthreats.net/open/suricata-%(__version__)s/emerging.rules.tar.gz
```

來源：https://raw.githubusercontent.com/oisf/suricata-intel-index/master/index.yaml

而 emergingthreats.net 官方 FAQ 說的又是第三種：「Yup. **Free, as in BSD licensed**, which allows you to do what you like with them.」（https://community.emergingthreats.net/t/frequently-asked-questions/56）

> **這代表什麼**：任何人只要跑 `suricata-update list-sources`，螢幕上就會印出 `License: MIT`。所以現場如果有人說「我看到的是 MIT」，他不是看錯二手部落格，**他看的是 Suricata 官方索引**。
>
> **請把規格書 0.4 #2 與逐字稿第 11 頁備用段落改成**：
> 「ET Open 的授權在三個來源之間標示不一致：**OISF 官方的 `suricata-intel-index` 標 MIT**、**emergingthreats.net 的 FAQ 說 BSD**、**規則集 tarball 自帶的 `LICENSE` 寫 BSD + GPLv2 混合**。我們以**隨規則一起發布的 LICENSE 檔為準**，所以寫 BSD + GPLv2。」
>
> 這樣講比「MIT 是訛傳」強很多，也不會被拿 OISF 的檔案打臉。

### 5-3 ⚠️ 建議修：查無來源的效能數字

逐字稿第 9 頁備用：

> 有實測是 **MediaTek MT7620 開 hardware flow offload 之後，轉發只吃約 1% CPU**。

**查不到可靠一手來源。** 我們查了 OpenWrt 官方 wiki、`openwrt/openwrt` 的 issue/PR、以及論壇「Working hardware flow offload for MT7620」整串（forum.openwrt.org/t/.../89766），**找不到任何標示「約 1%」的官方或可歸屬量測**。相關但**不能**當出處的線索：有論壇使用者描述「全 gigabit 速度下 htop 幾乎看不到 CPU 使用」，但那是 MT7621 + MT7615DN 的個人觀察，既不是 MT7620、也不是量化數字。

> **改成定性**：「開了 hardware flow offload 之後，命中的連線整條由 PPE 轉發、CPU 幾乎不參與，這類 SoC 能跑滿千兆靠的就是這個；關掉的話一顆弱 ARM 核心做純軟體轉發是撐不住的。」
> 這樣立論一樣強，而且不用替一個查不到的數字背書。
