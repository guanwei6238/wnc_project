# 1. 實體與模擬環境建立

> 這一節只講一件事：**我們在什麼東西上面做實驗。**

## 第 2 頁　設備的目標形態

> 這是設備最終要長的樣子。
>
> 重點是**兩個網路 port**：內網一個、外網一個，實體分開。
> 這樣設備就站在流量的**必經路徑**上 —— 所有封包都得穿過它。
>
> 這件事決定了它**擋得住**。如果只是旁路接一條線鏡射流量，那只能看、不能擋。
>
> 然後上面這條虛線：**本地判斷不出來的，就送雲端分析。**

**備用 —— 如果問「送雲端的時候，那個封包在等嗎？」**

> 這是很好的問題，而且是這個架構的核心取捨，我們**還沒決定**。
>
> 三種做法：
> 1. **扣住等雲端回覆** —— 最安全，但延遲會多一個雲端往返，而且佇列會爆
> 2. **先放行、事後補救** —— 雲端說是惡意就砍掉那條連線。延遲最好，但第一批封包已經過去了
> 3. **先擋住、等放行** —— 最安全，但誤殺的體感很差
>
> 這三條的取捨就是我們要做的實驗之一。

**備用 —— 為什麼圖上不寫「非同步」**

> 因為「非同步」等於已經選了第二種做法。我們還沒選，所以不寫死。

---

## 第 3 頁　實體環境

> 閘道器是 **Raspberry Pi 3 Model B+**，跑 Raspberry Pi OS Lite 64-bit。
> 最終目標是 **ARM based 的設備跑 OpenWrt**。
>
> 內外網兩端怎麼來？**用同一台 laptop 的兩個網路介面，接成一個迴路。**
> 一個介面當內網端、一個當外網端，兩條線都接到樹莓派，流量就在這個迴路裡繞。
>
> 樹莓派只有一個內建網口，所以要**外接一張 USB 網卡**才湊得出兩個 port。

**備用 —— netns 的坑（這條一定要記得，不然會卡很久）**

> 這樣接有一個陷阱：**兩端必須用 network namespace 隔開。**
>
> 因為 Linux 會替每個本機 IP 自動加一條優先權最高的 `local` 路由。
> 當內網端去打外網端的 IP 時，kernel 發現**目的地就是自己**，直接走 loopback 送掉 ——
> 線接得好好的，但封包根本不會出去，樹莓派什麼都收不到。
>
> 把其中一端放進獨立的 netns，變成兩個獨立的網路堆疊，流量才會真的走實體線繞過樹莓派。
>
> 補一句：**Docker 用的也是 netns。** 所以模擬環境跟實體環境其實是同一個隔離機制，
> 差別只在一個走 veth、一個走實體網線。

---

## 第 4 頁　模擬環境

> 模擬環境用 **Docker** 搭三個容器節點：內網的 cli、中間的閘道器 gw、外網的 srv。
>
> **閘道器容器掛在兩個網段上**，對應實機的雙 port —— 形狀跟上一頁是一樣的。
>
> 用途是：在動實機之前，先把網路拓撲和 nftables 規則驗過。
>
> **補充一句（投影片上沒寫）：gw 這個閘道器容器規劃用 OpenWrt 當基底。**
> 這樣的話 musl、`.apk` 打包、procd 啟動腳本、UCI 設定這些 userspace 的東西，
> **在模擬環境就驗得到**，不用等實機。

---

## 第 5 頁　為什麼兩個環境都要

> 這頁回答一個大家大概會想問的問題：**為什麼不選一個就好？**
>
> 兩個方向：
>
> 一，**每改一次規則就搬上樹莓派重測，迭代太慢。** 所以邏輯的部分先在 Docker 驗完。
>
> 二，但 **Docker 容器共用 host 的 kernel**，有些東西它驗不到。
>
> 具體來說：
> - **Docker 驗得了**：nftables 規則語意、conntrack、NFQUEUE 的決策流程 —— 這些在兩邊是一樣的
> - **樹莓派才驗得了**：aarch64 指令集、資源受限環境下的行為、實體雙 port 接線與部署流程

**備用 —— ⚠️ 如果被問「網卡 driver 跟 XDP 模式呢？Docker 不是也測不到？」（很好的問題）**

> **這題要小心回答，因為直覺上的答案是錯的。**
>
> **Docker 其實測得到真實網卡** —— 只要用 `--network host`，
> 或是把實體網卡整張搬進容器的 netns（`ip link set eth0 netns <pid>`），
> 容器裡摸到的就是真的 driver，不是 veth。
> 我們現在的 compose 用 bridge/veth 所以碰不到，但那是設定問題，不是 Docker 的限制。
>
> **XDP 的 native / generic 也一樣** —— 只要 laptop 的網卡 driver 有實作 XDP hook
> （Intel `igc`/`e1000e`、Realtek `r8169` 這類大多有），在 laptop 上就測得出 native。
>
> **而且樹莓派反而更差**：Pi 3B+ 的網卡是 USB 介面的（LAN7515，走 `lan78xx`），
> USB 網路 driver 沒有實作 `ndo_bpf`，所以 **XDP 在樹莓派上永遠只有 generic**。
> 它是三個環境裡唯一保證測不到 native 的那個。

**備用 —— 那真正的界線在哪？**

> 不是「Docker vs 樹莓派」，而是**手上有哪張實體網卡**：
>
> | 環境 | 能驗到什麼 |
> |---|---|
> | veth（現在的 compose） | 只有軟體邏輯 |
> | laptop 的實體網卡 | 那張卡的 driver 行為、native XDP 跑不跑得起來 |
> | 樹莓派的 USB 網卡 | USB 網卡的行為（native XDP 一定沒有） |
> | **目標 SoC 的網卡** | **只有這個才回答得了我們真正在問的問題** |
>
> laptop 跟樹莓派**各自只代表自己那張卡**，
> 兩者都不能預測 MediaTek / Qualcomm 那顆 SoC 的 driver 支不支援 native XDP。
> **那件事只有拿到目標設備才知道。**

**備用 —— 那樹莓派到底不可取代在哪？**

> 三件事：
> 1. **aarch64 指令集** —— laptop 是 x86，這個換不掉
> 2. **資源受限的環境** —— CPU/RAM 等級接近 router，laptop 差太多
> 3. **真正獨立的一台設備** —— 實體雙 port 接線、部署流程、headless 運作

**備用 —— 誠實補一句（被追問時講，會加分）**

> 其實**兩個環境加起來也還不夠**。
>
> OpenWrt 自己的 kernel、還有 procd、UCI、apk 這些韌體環境，
> Docker 驗不到，樹莓派也驗不到 —— 因為樹莓派跑的是 Raspberry Pi OS，不是 OpenWrt。
> 那些要等目標設備。

# 2. Packet Processor 介紹

> 這一節講：封包處理有哪些方法，我們打算選哪個。

## 第 6 頁　封包分析的兩種方法

> 封包處理大致分兩條路。
>
> **方法 1 是留在 kernel 內** —— 封包照常走 kernel 的網路路徑，
> 我們在路徑上掛東西，代表技術是 XDP 加 netfilter。
>
> **方法 2 是 kernel bypass** —— 用 DPDK，封包**繞過整個 kernel**，直接進 user space。
>
> 兩者最根本的差別是**網卡還屬不屬於作業系統**。
> 方法 1 網卡還是 OS 的；方法 2 是整張網卡交給 user space 程式接管。
>
> 後面的取捨全部從這一點衍生出來。

---

## 第 7 頁　方法 1：留在 kernel 內

> 這是方法 1 的內部。封包從網卡進來，依序經過：
> **① XDP → 網路協定堆疊 → ② netfilter/nftables → 路由轉發**，
> 中間 netfilter 可以把封包透過 **③ NFQUEUE** 丟給 user space 決策。
>
> 下面這張表是 XDP 跟 netfilter 的能力差異。
>
> 最關鍵的是「適合做」這一列：
> **XDP 做無狀態就能判定的事；netfilter 做需要連線狀態才能判的事。**
> 這是 stateless 跟 stateful 的分工。
>
> XDP 位置在 stack 前面，所以快；但也因為在前面，
> 它沒有內建 conntrack、不能處理 IP 分片、也不能把封包交給 user space。
>
> 現成的東西：**`xdp-filter`** 可以參考。
>
> 函式庫方面，XDP/eBPF 有 **libbpf** 跟 **aya**、nftables 有 **libnftnl** 跟 **rustables**、
> NFQUEUE 有 **libnetfilter_queue** 跟 **nfq** —— 每一層都有現成的可以接。

**備用 —— 無狀態判定有哪些例子**

> 例如：**黑名單 IP、畸形封包、洪水攻擊**。
> 這些看單一個封包就能決定要不要丟，不需要知道這條連線之前發生過什麼。

**備用 —— `xdp-filter` 為什麼值得看**

> 它是 xdp-tools 專案裡的工具，支援比對 IP、TCP/UDP port、MAC。
> 重點是它**刻意不做複雜比對**，用功能換極高的丟包速率 ——
> 這個取捨正好示範了 ① 這一層該做什麼：**便宜、粗、快。**

**備用 —— 如果問「那為什麼不全部用 XDP 就好？」**

> 因為 XDP 看不到重組後的封包。
>
> **把惡意內容切在兩個 IP 分片裡**是規避 IDS 的經典手法 ——
> 單看任何一個分片都是正常的，要重組起來才看得出問題。
> 而 XDP 跑在重組之前，所以安全判斷不能只靠它。

**備用 —— ⚠️ 如果被問「AF_XDP 不就是 XDP 交給 user space 嗎？」**

> 對，**AF_XDP 確實是 XDP 把封包送進 user space 的官方機制** ——
> XDP 程式做 `XDP_REDIRECT` 進 `XSKMAP`，封包就直接落到 user space 的記憶體。
>
> 但那條路**跟 DPDK 是同一類**：封包一旦這樣送出去就**離開 kernel 的網路路徑**了，
> conntrack、nftables、路由通通不參與，後面全部要自己處理。
>
> 而**方法 1 的目標就是留在 kernel 內**。所以表格那一格問的是
> 「能不能送 user space 判斷完、**再把 verdict 交回來繼續走 kernel 路徑**」——
> **NFQUEUE 做得到，XDP 做不到。**
>
> 換句話說：要嘛留在 kernel（NFQUEUE），要嘛整個出去（AF_XDP／DPDK），**沒有中間態**。

**備用 —— 如果被指出「XDP 其實可以查 conntrack」**

> 對，這位同學說得沒錯。**kernel 5.18 起有 `bpf_xdp_ct_lookup()` 這類 kfunc，
> XDP 程式是可以查 conntrack 的。**
>
> 所以我表格寫的是「**內建** conntrack」—— XDP 沒有內建的整合，
> 要自己寫 BPF，而且執行時機仍然在分片重組之前。

## 第 8 頁　方法 2：kernel bypass（DPDK）

> 方法 2 的結構很單純：網卡綁給 **PMD driver**，
> 封包**繞過 kernel 堆疊**，直接進 user space 的應用程式，那個程式自己跑 polling 迴圈。
>
> 得到的是**極高的封包處理效能**。
> 失去的是 **conntrack、nftables、路由表 —— 全部不能用。**
>
> DPDK 側要做同樣的過濾，會用 **`rte_acl`** 這個分類函式庫，官方也有 `l3fwd-acl` 範例。

**備用 —— 「全部不能用」是什麼意思**

> 因為網卡被綁到 vfio-pci 之後，**kernel 就看不到那張網卡了**。
> netfilter、conntrack、路由表全都不會參與 —— 等於要自己重寫一套網路堆疊。

---

## 第 9 頁　目前選擇：方法 1

> 兩個理由。
>
> **第一，OpenWrt 上的主流做法就是這套。**
> 官方 feed 裡的 snort3、kmod-nft-queue、libnetfilter-queue 都是走這條路線。
>
> **第二，用 DPDK 會讓 OpenWrt 的 offload 全部失效。**
> OpenWrt 的 software flow offload、還有 MediaTek PPE 那類 hardware flow offload，
> **都是由 kernel 的 netfilter flowtable 驅動的**。
> 網卡一旦交給 DPDK，這些加速路徑就不存在了，等於退回純軟體轉發。

**備用 —— ⭐ 理由 1 最硬的證據（被質疑「主流」時直接拿出來）**

> 如果有人問「你怎麼知道那是主流做法」，最直接的證據是
> **OpenWrt 官方 feed 裡 `snort3` 這個套件的相依清單**：
>
> ```
> Package: snort3
> Version: 3.9.5.0-r5
> Depends: ..., kmod-nft-queue, ...
> ```
>
> **官方的 IDS 套件，相依項目直接列著 `kmod-nft-queue`** ——
> 也就是 OpenWrt 官方生態的 IDS 整合**就是走 NFQUEUE**，正是我們選的方法 1。
> aarch64 跟 x86_64 兩個架構都一樣。
>
> 這比「官方 feed 裡有這些套件」強得多 —— 不只是「有」，是**官方套件自己依賴它**。

**備用 —— 第二點的力道（這點值得展開講）**

> 這點反直覺。大家聽到 DPDK 都想到「快」，但在 router SoC 上**不一定**。
>
> 因為這類 SoC 的轉發效能**根本不是 CPU 給的，是 PPE 給的**。
> `nft_flow_offload` 會把 PPE 的 L3 flow table 直接寫進去，
> 命中的封包整條由硬體轉發、**CPU 幾乎不碰**。
>
> DPDK 把網卡拿走之後這條路就斷了，
> 變成用一顆弱 ARM 核心做純軟體轉發 —— **可能反而比原本慢。**

**備用 —— 如果被問「你們要做 DPI，本來就不能 offload 吧？」**

> 對，這兩件事是互斥的：**封包一旦被 offload，就繞過 netfilter，我們也看不到了。**
>
> 但這正好是設計的一部分：**已經有結論的連線才 offload**，
> 需要檢測的留在 CPU 上走完整路徑。
> 用 DPDK 的話是**連這個選項都沒有**，所有流量都只能走軟體。

**備用 —— ⚠️ 最可能被問的一題：「不用 DPDK 是因為 ARM 不支援吧？」**

> **不是，這是常見的誤解。DPDK 官方是支援 aarch64 的。**
>
> 官方有 Marvell OCTEON、NXP DPAA 這些 ARM SoC 的 PMD，
> 連我們剛提到的 `rte_acl`，實作裡都有 NEON —— ARM 的 SIMD —— 最佳化路徑。
>
> 我們不用它的理由就是投影片上那兩點，**跟指令集無關**。

**備用 —— 遷移成本（⚠️ 這點刻意沒放投影片，被問到再講，而且要講得小心）**

> 如果被問「換 DPDK 的話現有的東西要改多少」：
> `ct state`、set、NFQUEUE 在 DPDK 裡都沒有對應物，nftables 規則要整批改寫。
> 連線追蹤本身有 VPP、OVS-DPDK 這類現成框架可以接手，但那等於換一整套生態。
>
> ⚠️ **但這個理由不要當成主論點。**
> 因為它是**路徑依賴**：只有在「我們已經選了 nftables」的前提下才成立。
> 如果一開始就走 DPDK，模擬和開發都在 DPDK 生態裡，根本沒有換生態的問題。
> 主論點還是上面那兩點 —— 那兩點跟我們已經做了什麼無關。

**備用 —— 業界也是這樣做（外部佐證）**

> 邊緣防護設備的通行做法就是「XDP 在最前面丟棄 → 其餘交給 netfilter」。
> **Cloudflare 的邊緣 DDoS 防護就是這個架構。**
>
> 嚴格說他們的順序是 L4Drop（XDP）→ Unimog（也是 XDP，做 L4 負載平衡）→ iptables → L7。
> 他們選 XDP 而不是 user space bypass 的理由也值得引用：
> **XDP 不需要 busy polling，所以可以一直開著。**

**備用 —— 把封包交給 user space 很貴**

> NFQUEUE 要把封包複製到 user space、扣住、等 verdict，成本不低。
> 所以「**只把判不出來的送上去**」不是可有可無的最佳化，而是這個架構能不能成立的前提。

# 3. Benchmark

## 第 10 頁　可以量的指標

> 這頁列出我們打算量的指標。**投影片上只放名稱，實際講的時候一個一個帶過。**
>
> 左邊這幾個是**現在就量得出來的**：
> - **Throughput** —— 兩端對打的速率
> - **Latency** —— 封包往返時間
> - **Packet loss rate** —— 丟包率
> - **CPU utilization** —— 閘道器自己的 CPU 使用率，可以看出每一層處理花掉多少
> - **Concurrent connections** —— 同時連線數
> - **CPS / TPS** —— 每秒新建連線數
>
> 右邊這幾個**需要專門的流量產生器**，是後期才做的：
> - **NDR / PDR** —— 零丟包 / 部分丟包下的最大速率
> - **Frame size sweep** —— 從 64 到 1518 bytes 掃一遍
> - **pps / bps limits** —— 兩種上限。**小封包的時候瓶頸是 pps，不是頻寬**
> - **Latency percentile** —— p50 跟 p99，不能只看平均
> - **TTFB / TTLB** —— 第一個 byte / 最後一個 byte 的時間
> - **TLS handshake rate**

**備用 —— 為什麼 CPU utilization 值得量**

> 因為我們的架構分成三個階段，每一階段的處理成本不一樣。
> 量 CPU 使用率可以看出「封包停在哪一層」對負載的影響 ——
> 這比單看吞吐量更能說明分層設計有沒有效。

**備用 —— ⚠️ 如果被問「這些怎麼量才算數？」（這題很可能被問）**

> 這些指標**不用自己發明量法，有現成的 RFC 標準方法論可以依循**：
>
> - **RFC 2544**（1999-03）—— 最被引用的基礎方法論：frame size sweep、
>   每個 trial 至少 60 秒、丟包就降速重測逼近零丟包速率
> - **RFC 9411**（2023-03）—— **現行的安全設備方法論**，正式取代了 RFC 3511，來自 NetSecOPEN
> - **RFC 1242**（1991-07）—— RFC 2544 的術語定義來源
>
> 最關鍵的一點：**RFC 1242 定義的 Throughput 是「零丟包下的最大速率」，
> 跟 iperf3 直接跑出來的 bandwidth 不是同一個東西。**
>
> 所以如果之後只給 iperf3 的數字，第一個會被問的就是「**那你的丟包率是多少**」。

**備用 —— 如果再問「這三份 RFC 是怎麼找到的？」**

> 從先前整理的閱讀清單來的，三份內容都對過 rfc-editor.org 的原文確認過：
> 年份、標題、RFC 9411 obsolete 掉 RFC 3511 這件事，還有 RFC 2544 §9.1 的 frame size 清單。

# 4. 可用的規則

## 第 11 頁　規則來源與開源引擎

> 問題是：有沒有現成的 IDS 規則可以直接拿來用？**有，而且有兩套完全免費、授權清楚。**
>
> **左邊是規則來源。**
>
> - **ET Open** —— Proofpoint 的 Emerging Threats 開放規則集。
>   授權是 **BSD 加 GPLv2 混合**：ET 自己的規則是 BSD，沿襲 Snort 舊 sid 的那部分是 GPLv2。
>   它是 `suricata-update` 的預設來源，從 `rules.emergingthreats.net/open/` 取得。
>   維護上是**社群貢獻**，ETPro 才是 Proofpoint 研究團隊在做。
> - **Snort 3 Community Rules** —— Cisco Talos 發布，**GPLv2**，每日更新，是付費版的子集。
> - **Snort Registered** 免費但要註冊，內容比付費版**延遲 30 天**；**Subscriber** 付費、即時取得。
> - **威脅情報 blocklist** 是另一類來源，成本低很多 —— 公開的惡意 IP / domain feed，
>   可以直接灌進 **nftables set**（或更前面的 XDP 過濾），**在管線前段就命中，不需要做 DPI**。
>   授權各家 feed 不同，要個別確認。
>
> **右邊是可以用的開源引擎。**（視情況挑著講）
>
> - **Suricata** —— 支援 NFQUEUE 的 inline IPS，也支援 AF_PACKET IPS 模式。
>   **後者需要兩張專用網卡 —— 正好對應我們的雙 port 設計。**
> - **Snort 3** —— 多執行緒重寫版
> - **Zeek** —— 偏流量分析而不是阻擋，**適合用來萃取要送雲端的特徵**

**備用 —— 如果問「授權你怎麼確認的？」**

> **規則集的 tarball 裡面自帶 `LICENSE` 和 `BSD-License.txt`。**
> 網路上有些二手資料寫 ET Open 是 MIT，那跟規則集自帶的授權檔不符，不能採信。

**備用 —— ⚠️ 很可能被問：「Suricata 裝得上 OpenWrt 嗎？」**

> **這點要先說清楚：OpenWrt 官方 feed 裡沒有 Suricata。**
> master、25.12、24.10、23.05、22.03 各分支都沒有，只有社群 feed 要自己加、自己編。
>
> **官方 feed 裡有的是 Snort 3。**
>
> 不過 NFQUEUE 那側是好消息：`libnetfilter-queue`、`kmod-nfnetlink-queue`、
> `kmod-nft-queue` 官方 feed 都有，只是屬於 kmod 套件，預設映像不含，要自己勾。

**備用 —— 如果問「這些 IDS 規則是跑在 netfilter 裡嗎？」（很關鍵的一題）**

> **不是。這跟 nftables 規則是兩種完全不同的東西。**
>
> - **nftables 規則**跑在 kernel 的 netfilter 裡，比對的是 header 欄位、五元組、連線狀態
> - **ET Open / Snort 規則**是 Suricata、Snort 這類 **user space 引擎**的語法，
>   要做 payload 比對、TCP 串流重組、協定解析、PCRE —— **netfilter 根本做不到**
>
> 它們怎麼接起來？**就是靠 NFQUEUE。**
> netfilter 判不出來 → NFQUEUE → user space 引擎跑 IDS 規則 → 回 verdict。
>
> **這就是為什麼架構裡一定要有第三階段** —— 如果 IDS 規則能在 netfilter 裡跑，
> 我們根本不需要 NFQUEUE。

# 附錄：OpenWrt 整合（投影片上沒有，Q&A 被問到再講）

> 草稿原本有「怎麼遷移到實體 OpenWrt」這一點，但**投影片上刻意沒放** ——
> 因為那是之後的事，現階段講會失焦。被問到再拿出來。

## 一句話版本

> **大部分可以直接照搬，剩下的是 kernel 層那幾件，都有退路。**
>
> OpenWrt 22.03 起預設防火牆 firewall4 的底層就是 nftables，規則語意兩邊同一套。
> 而且閘道器容器本來就用 OpenWrt 當基底，所以 musl、`.apk` 打包、procd 啟動腳本、
> UCI 設定這些 **userspace 的東西在模擬環境就驗過了**。

## 真正要等實機的三件事

| 項目 | 要確認什麼 | 不行的話 |
|---|---|---|
| `kmod-*` 套件 | 裝置的版本跟 feed 對不對得上 | `apk add` 裝上去；對不上就自己建映像 |
| `CONFIG_DEBUG_INFO_BTF` | 正式設備的 kernel 有沒有開 | 要能重刷韌體；否則改用非 CO-RE 寫法 |
| XDP 模式 | NIC driver 支不支援 native | 退 generic；或把過濾移到 netfilter |

## 細節（真的被追問才講）

**為什麼這三件模擬驗不到**

> 因為**容器沒有自己的 kernel**，整台機器只有一個 kernel，就是 host 的。
> 這三件全部是 kernel 層或硬體層的；userspace 的差異跟 kernel 無關，所以 OpenWrt 容器驗得到。

**kmod 為什麼不能在容器裡裝**

> kernel module 編譯時會綁一個 **`vermagic`**，記錄 kernel 版本跟編譯選項。
> 載入時對不上正在跑的 kernel，kernel 直接拒絕、報 `Invalid module format`。
> OpenWrt 的 `kmod-nft-queue` 是對著 OpenWrt 的 kernel 編的，容器裡碰到的卻是 host 的 kernel。
> 連 `/lib/modules/$(uname -r)/` 的路徑都對不起來。**這是結構上不可能，不是比較難。**
>
> ⚠️ 但要分清楚：**NFQUEUE 的功能在模擬環境還是驗得到**，因為 host kernel 自己就有 `nfnetlink_queue`。
> 驗不到的是「OpenWrt 映像裡有沒有把這些 kmod 勾進去」。

**`apk add` 是什麼**

> `apk` 是 OpenWrt 25.12 起的套件管理器（取代 `opkg`），用法像 `apt install`。
> `apk add kmod-nft-queue` 會從官方 feed 下載編好的 `.ko` 裝到**正在跑的裝置上**，
> **不用重編、不用重刷**。
>
> 但 kmod 套件會宣告綁死 kernel 版本的相依（`kernel (= 6.6.x-1-<hash>)`），
> 所以裝置得跑標準 OpenWrt 釋出版、版本跟 feed 對得上才行。

**三件事的層次其實不一樣**

```
kmod-*     → apk add 就好，不用碰 kernel
BTF        → 非重編 kernel 不可（要能重刷韌體）
XDP native → 重編也沒用，看 driver 有沒有寫
```

**BTF 的細節**

> CO-RE 的 eBPF 需要 kernel 提供 BTF 型別資訊（`/sys/kernel/btf/vmlinux`）。
> Raspberry Pi 基金會的 kernel 跟 OpenWrt 的 kernel **預設都沒開** `CONFIG_DEBUG_INFO_BTF`。
> 退路是不用 CO-RE：傳統寫法綁目標 kernel 版本重編**我們的 eBPF 程式**（不是重編 kernel）。
> 另外開 BTF 會讓 kernel image 大好幾 MB，flash 有限的 router 要先算空間。

**XDP 模式的細節**

> native 掛在 driver 層，才是 XDP 快的原因；generic 跑在網路堆疊裡面，省 CPU 的優勢就沒了。
> 消費級 router 的網卡大多沒實作 native XDP hook，而且 **loader 會靜默 fallback、不報錯** ——
> 要 `ip link show` 看它印 `xdp` 還是 `xdpgeneric`。

**要跟計畫方問清楚的兩件事**

> 1. **設備會不會預裝 OpenWrt？我們能不能自己刷韌體？** —— 這決定 BTF 那條有沒有退路
> 2. **如果不能刷，裝置上跑的是哪個 OpenWrt 版本？** —— 這決定 `apk add` 通不通

**如果問「NFQUEUE 真的完全不用改嗎？」**

> 應用層程式碼跟 nftables 規則不用改，但**映像組建的設定要改** ——
> `libnetfilter-queue`、`kmod-nfnetlink-queue`、`kmod-nft-queue` 官方 feed 都有，
> 但屬於 kmod，預設映像不含。

# 附錄：不要犯的錯
