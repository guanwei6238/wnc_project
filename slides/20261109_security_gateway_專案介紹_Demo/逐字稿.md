# 一、當場講

## 封面

各位好，今天報告的是 security gateway 目前的實作，程式叫 wnc-gw，最後會現場 demo。

---

## 第 1 頁　大綱

分四個部分：架構、trust、設定與 doctor，最後是 demo。

---

## 第 2 頁　整體架構

中間的框是 gateway 這台機器，實線是已經實作的部分，虛線是規劃中、還沒做的。
eBPF 程式還沒寫，之後用來做 fast path：trusted connection 的 packet 在 TC 直接轉送，不進 netfilter。
netfilter 決定每個 packet 怎麼走：trusted connection 直接放行，其他的送給 Suricata（`ids` 送 copy、`ips` 送 packet 本身）；開多個 Suricata worker 時，也在這裡分配每條 connection 給哪個 worker。
Suricata 用載入的 rules 做 inspection，alert 寫進 EVE 檔。
wnc-gw 是控制程式，packet 不經過它：它裝我們自己的 nft table、啟動 Suricata、讀 Suricata 的 alert，再決定哪些 connection 要 trust，用 ct mark 讓 netfilter 直接放行。虛線的 edge AI 和 cloud 之後也是跟 wnc-gw 溝通，cloud 只回 trust、block、observe 三種動作。

---

## 第 3 頁　wnc-gw 的 subcommand

wnc-gw 主要有三個 subcommand。
- `doctor` 只檢查、不改東西；
- `trust` 可以手動 trust 一條 connection；
- gateway 本體是 `run`，
下面是 `run` 目前的生命週期：先跑一次 doctor，有 error 就不啟動；接著裝我們自己的 nft table、啟動 Suricata，等 Suricata 送出 `READY=1` 才開始 inspection，也就是把 packet 交給它；之後讀 Suricata 的 alert、做 auto trust。停止時把 table 移除，流量就直接通過。

---

## 第 4 頁　packet 怎麼走

轉送的 packet 都會經過 netfilter 的 forward hook，進到我們自己的 table。
SYN、FIN、RST：這三種一定會進 Suricata，我們查到的放行之後還能撤銷的機制，例如 Shunting 這篇論文和 Zeek 的 BPF shunt，也都留下這三種 packet。對我們的用處是：`ids` 模式下，資料量小的 connection 可能在 Suricata 比對完之前就被 trust，我們在 Docker 和 Pi 上都看到，這種 connection 要等 FIN 進 Suricata 才出現 alert。代價是長 connection 每個 packet 約多 1 µs；scan 的成本比較高，但 scan 本來就不會被 trust。其他 packet 如果屬於 trusted 的 connection 就直接放行，不是的才進 `ids` chain。`ids` chain 先看 Suricata 就緒了沒，還沒就緒就照 `when_unavailable` 放行或丟掉；就緒之後，`ids` 模式用 NFLOG 送一份 copy、packet 立刻轉送，`ips` 模式用 NFQUEUE，packet 要等 Suricata 的 verdict。

---

## 第 5 頁　trust 以 connection 為單位

trust 的單位是 conntrack 的一條 connection：wnc-gw 在 connection 上設 ct mark 的最高位元，forward chain 看到就直接放行。為什麼不用 nft set 存 5-tuple：5-tuple 會被 port 重用或偽造的 packet 繞過；ct mark 跟著 conntrack 的 entry，新建的 entry 沒有 mark，port 重用時接回舊 entry 的情況，forward chain 會在純 SYN 時先把 trust 清掉。
下面的數字是每轉送一個 packet，整台機器用掉多少 CPU 時間，單位 µs，不是延遲。實驗在 Pi 上做：用 tcpreplay 把 IoT-23 三個 scenario 開頭的 20 萬個 packet（Somfy 整個檔只有 12 萬個），以每秒 1 萬個重播經過 gateway；Suricata 載入 ET Open 的 full rules，用 NFQUEUE，也就是 `ips` 的路徑。表上三欄是三種情況：全部進 Suricata、每條 connection 從第一個 packet 就 trusted、不經過 Suricata 只轉送。trusted 這欄是 trust 最理想的情況，不是 auto trust；SYN／FIN／RST 照樣進 Suricata。
三個 scenario：
- Somfy 門鎖是良性的 IoT 設備，幾乎所有 packet 都在一條連到外部 server 的 HTTPS 長 connection 上；
- 1-1 (Hide and Seek) 是 botnet，一半是對 telnet 等 port 的 SYN scan，其他是 telnet 的 connection 和單向的 UDP；
- 39-1 (IRCBot) 九成是對 SSH port 的 SYN scan。
結果：Somfy 全部進 Suricata 時每個 packet 106 µs，trusted 之後 40 µs，和只轉送差不多；1-1 只降到 60；39-1 幾乎降不下來，因為 SYN 一定進 Suricata。所以 trust 對長 connection 有用，對 scan 沒有用。

---

## 第 6 頁　auto trust

auto trust 是讓 wnc-gw 自己決定要 trust 哪些 connection。上面的圖：connection 一開始是 watching，條件滿足就變 trusted，`ttl` 到期回到 watching、重新觀察；有 alert 的話，還在觀察的這條 connection 之後不再 trust，已經 trusted 的立刻 revoke。
左邊的表是 `[trust]` 的設定和預設值：
`auto` 預設是 `false`：trust 是 gateway 最危險的動作，trusted 之後才送的攻擊，到 TTL 結束前都看不到，所以要使用者明確打開，doctor 也一律給 warning。
`min_packets` 10：兩個方向都至少要有 10 個 packet，所以單向的 scan、只有 SYN 的 connection 永遠不會被 trust。
`min_age` 5 秒：至少觀察 5 秒，這段時間 Suricata 要在 inspection，而且沒有任何 alert。
`ttl` 900 秒：trusted 維持 900 秒，到期後回到 Suricata。
`check_interval` 5 秒：wnc-gw 每 5 秒讀一次 conntrack 的 packet 計數，所以實際被 trust 的時間是 connection 開始後 5 到 10 秒。
右邊的表是 Pi 上 `ids` 的成本，單位是每秒用掉幾 ms 的 CPU 時間，1,000 ms 就是一顆 core 跑滿。流量是 8 條 TCP connection、合計每秒 4,000 個 packet，Suricata 只載入 1 條測試用的 rule。
Suricata 這一列：`auto` 關的時候每個 packet 都進 Suricata，每秒 100.5 ms；打開之後 8 條 connection 都被 trust，降到 13.6 ms，剩下的是 Suricata 沒有流量時本來就有的成本。
wnc-gw 這一列：從 0.5 多到 1.9 ms。多出來的 1.4 ms 幾乎都是讀 conntrack：每 5 秒讀一次，connection 很少的時候，kernel 每次也要掃完整個 conntrack 的 hash table，約 7 ms。
合計每秒省 85 ms，約一顆 core 的 8.5%；換算成每個 packet 省 21 µs。

---

## 第 7 頁　Suricata 沒在 inspection 時

wnc-gw 自己啟動 Suricata，等它送出 `READY=1` 才把 packet 交給它，因為 Suricata 7.0.10 和 8.0.7 初始化時收到 packet 會 segfault。Suricata 還沒就緒、重啟中，或 `ips` 跟不上的時候，照 `when_unavailable` 處理：預設 `accept` 放行，不讓 Suricata 的問題把整個公司網路斷掉；設成 `drop` 就丟掉。`ids` 比較特別，packet 本來就不等 Suricata，所以跟不上時 packet 照樣轉送，只是 copy 被丟掉。不管哪一種，一定記 log：什麼時候開始沒有 inspection、沒有了多久、漏掉多少 copy。Suricata 掛掉時 wnc-gw 會自動重啟它。

---

## 第 8 頁　`setting.toml`

設定檔是 TOML。唯一一定要填的是 `[ports]`：gateway 不猜哪張網卡是 LAN、哪張是 WAN，用網卡名稱或 MAC 指定，demo 用的是 MAC。會改變 packet 怎麼走的是 `mode`、`protection`、`when_unavailable` 和 `[trust]`；`when_unavailable` 和 `[trust]` 前面講過，下一頁講 `mode` 和 `protection`。`xdp` 是第 2 頁那個 eBPF 程式掛在哪：預設 `auto`，網卡支援 native XDP 才掛 XDP，否則掛 TC；`generic` 比 TC 慢，只給測試用。eBPF 程式還沒寫，現在只有 doctor 會判斷。`queue`、`group` 設成範圍就會開多個 Suricata worker 分攤流量。其他是路徑和逾時。

---

## 第 9 頁　`mode` 與 `protection`

上面的表是 `mode`：L2 還是 L3。
部署這一列：預設 `bridge`，插進既有的公司網路中間，內網的設定不用改。`routed` 的 LAN 和 WAN 是不同網段，我們不做 NAT，所以上游 router 要加一條到內網的 route；另外 `routed` 不轉送 ARP 這類非 IP 的 packet。兩種模式的 nft table 完全一樣，差別只在 doctor 檢查的環境；例如 `bridge` 要確認 `br_netfilter` 有載入，沒載入的話 packet 會完全繞過我們的 rule。
CPU 這一列：Pi 的實體網卡、每秒 10 萬個 packet、只轉送時，整台機器每個 packet 的 CPU 時間 `bridge` 是 9.97 µs，`routed` 是 8.02 µs，少約 20%；有 Suricata 時兩者只差 2 到 9%。等一下的 demo 在 Docker 上用的是 `routed`。
下面的表是 `protection`：packet 要不要等 Suricata。預設 `ids`：kernel 立刻轉送，另外用 NFLOG 送一份 copy 給 Suricata，所以 Suricata 再慢都不會拖慢或擋住流量，但也就不能擋，只有 alert；`ids` 還要關掉 checksum validation，doctor 會警告。`ips` 用 NFQUEUE，packet 要等 Suricata 的 verdict，rule 的 action 是 `drop` 就擋。
第一列是 Suricata 每處理一個 packet 用掉的 CPU 時間，只算 Suricata 的執行緒，不是整台機器；在 Pi 上用 full rules 量，範圍是三個 scenario 的最小到最大：`ids` 是 21 到 24 µs，`ips` 是 38 到 48 µs。
第二列是容量，也就是丟掉的 packet 不超過 0.1% 的最高速率，在實體網卡上量：`ids` 是每秒 5 萬到 8 萬個 packet，看流量從哪張網卡進來，而且要開 RPS；`ips` 是 6 萬。
這兩列是不同的實驗，第一列在 veth 上、每秒 1 萬個 packet，第二列在實體網卡上，不能互相推；所以 `ids` 每個 packet 便宜將近一半，容量卻沒有變兩倍。

## 第 10 頁　`doctor`

doctor 是部署時第一個要跑的，只檢查、不改東西。上面的表是它檢查的五類，右邊是沒過會怎樣：
網路：port 對到哪張網卡，`mode` 需要的 bridge、sysctl、位址和 route；沒過的話找不到網卡，或 packet 繞過我們的 nft table。
kernel 和 `nft`：需要的模組，`nft` 有沒有 JSON 支援；沒過的話 table 裝不上，或寫不了 ct mark。
Suricata：有沒有 NFQUEUE／NFLOG、會不會送 `READY=1`，設定載入得了、有 rule，queue／group 沒被別的 Suricata 佔住；沒過的話 Suricata 收不到 packet、起不來，或沒有偵測。
auto trust：Suricata 有輸出 alert、`nf_conntrack_acct` 有開；沒過的話有 alert 的 connection 也會被 trust，或算不了 packet 數。
權限：設定檔、執行檔和它們的上層目錄，非 root 能不能改；能改的話，非 root 就能讓 gateway 用 root 權限跑任意程式。
下面的表是結果的三級：error 是 gateway 沒辦法正確運作，例如設定錯、port 找不到、缺模組，`run` 就不啟動；warning 是暫時的狀態或已知的風險，例如 link down、`ids` 不擋流量，`run` 照常啟動；note 只是資訊。能修的訊息都附上修法的指令。

## 第 11 頁　`doctor` 的輸出：Pi 4 與 Docker

這是 doctor 實際的輸出，只截了兩張表。上面是 Pi 4，`bridge`；下面是 Docker，`routed`；兩邊的 `xdp` 都是 `auto`。
第一張表是 `mode` 需要的環境，兩種模式檢查的東西不一樣：`bridge` 要 LAN、WAN 在同一個 bridge，而且 `bridge-nf-call-iptables` 是 1，不然 bridge 轉送的 packet 不會經過我們的 nft table；`routed` 要 `ip_forward` 打開、兩個 port 有 IPv4 位址、網段不重疊、default route 走 WAN。Docker 這邊 IPv6 forwarding 沒開，是 not met，只給 warning，因為 demo 只用 IPv4。
第二張表是 XDP。doctor 向 kernel 問每張網卡支援哪些 XDP 功能，只讀、不掛任何程式。Pi 4 的兩個 port 都沒有 native XDP，所以之後的 eBPF 程式會掛在 TC；Docker 的 veth 有，所以選 XDP。同樣是 `auto`，doctor 依網卡實際的能力選，換到有 native XDP 的正式設備不用改設定。
doctor 每一項都是這個做法：看實際的能力，不看版本號；看正在跑的狀態；判斷不了就給 warning，不會說沒問題。

## Demo（切到終端機）

投影片停在「Demo」這一頁，切到終端機。demo 在筆電的 Docker 上做：`wnc-gw` 容器跑 wnc-gw 和 Suricata，`mode` 是 `routed`；`wnc-cli`、`wnc-srv` 是 iperf3 的兩端；`wnc-rep` 把 IoT-23 的 pcap 重播進 gateway，設備送出的 packet 從 LAN 進，外面送回來的從 WAN 進。和 Pi 比，nft table、Suricata 的版本和 rule 都一樣，所以 trust、alert 的行為一樣；不一樣的是 kernel 版本、速度和 Suricata 的啟動時間，等一下看到的速度不代表 Pi。同樣的功能我們在 Pi 上用 `demo.sh` 跑過。重播的是三個 scenario 的開頭 500 個 packet，每秒 50 個，大約 10 秒：Somfy 門鎖是良性的，Muhstik 和 Mirai 是被感染的設備。

**1. 設定**（`cat docker/wnc-gw/demo.toml`）
這是 demo 的設定檔。`mode` 是 `routed`、`protection` 是 `ids`；`[ports]` 用 MAC 指定 LAN 和 WAN。`ttl` 只設 60 秒，是為了看得到到期，預設是 900 秒。

**2. doctor**（`docker exec wnc-gw /opt/sg/wnc-gw -c /etc/wnc-gw/demo.toml doctor`）
沒有 error。warning 都是預期的：`ids` 不擋、不做 checksum validation、流量太快會漏 copy、Suricata 啟動和重啟時放行、auto trust 的風險、Suricata 由 wnc-gw 啟動；另外幾個是 Docker 環境造成的。

**3. run**（T1：`docker exec -it wnc-gw /opt/sg/wnc-gw --log-level debug -c /etc/wnc-gw/demo.toml run`）
先看 log：`table installed`、`automatic trust is on`、`suricata started`；載入 52,798 條 rule 要約 15 秒，之後 `suricata is ready`，接著 `forwarded traffic is inspected`，後面帶 `uninspected_ms`。table 先裝好，Suricata 就緒前的流量照樣轉送但沒有 inspection，這段時間記在 log。

**4. Somfy**（T2：`docker exec wnc-rep tcpreplay -i wan -I lan -c /pcaps/somfy.cache --pps=50 /pcaps/somfy.pcap`；T3：`trust list`、`nft list table inet wnc_gw`）
重播大約 10 秒，約 5 到 6 秒後 T1 出現 `connection trusted`。log 說這條 connection 被 trust 了。`trust list` 的 MARK 是 `0xc0000000`：`0x80000000` 是 trusted，`0x40000000` 是經過 gateway。nft 的 counter：`ids` chain 的是送進 Suricata 的 packet，`accept` 那條是 trusted、跳過 Suricata 的。

**5. Muhstik**（T2：`docker exec wnc-rep tcpreplay -i wan -I lan -c /pcaps/muhstik.cache --pps=50 /pcaps/muhstik.pcap`）
重播開始後約 3 秒內，T1 出現 3 筆 `DEBUG suricata alert`，兩條 C&C 各一行 `it will not be trusted`；重播第 7 到 10 秒，NTP 4 條裡 3 條 `connection trusted`。同一台被感染的設備，有 alert 的 C&C connection 永遠不 trust，正常的 NTP 照樣 trust；判斷以 connection 為單位，不是以設備為單位。

**6. Mirai**（T2：`docker exec wnc-rep tcpreplay -i wan -I lan -c /pcaps/mirai.cache --pps=50 /pcaps/mirai.pcap`；T3：`trust list`）
每條下載有兩筆 alert，再加一行 `it will not be trusted`，兩條下載相隔約 5 秒；SSH 那條 `connection trusted`。再看一次 `trust list`，一共 5 條：Somfy、3 條 NTP、SSH。

**7. iperf3**（T2：`docker exec wnc-cli iperf3 -c 10.0.2.2 -t 15 -i 1`）
每秒印一次速度：trusted 之前比較慢，trusted 之後回到沒有 gateway 的水準。T1 每 10 秒會有 `WARN suricata missed packet copies`，後面帶 `missed=…`。原因是 `ids` 下 packet 本來就不等 Suricata，但 kernel 還是要把每個 packet 複製一份給 Suricata，複製本身就有成本；trusted 之後不複製。流量比 Suricata 收 copy 還快時會漏，wnc-gw 會記下漏了多少。這是筆電的速度，不代表 Pi。

**8. kill Suricata**（T3：`docker exec wnc-gw pkill -9 -x Suricata-Main`）
T1 會看到 `WARN suricata exited`，`exit="SIGKILL"`，接著 `WARN forwarded traffic passes without inspection`、`restarting suricata delay_s=1`；約 7.5 秒後 `forwarded traffic is inspected`，後面帶 `uninspected_ms`。`trust list` 裡 trusted 的 connection 還在。沒有 inspection 的時段一定記在 log；`when_unavailable = "drop"` 時，這段期間改成丟掉。
demo 到這裡結束，T1 按 Ctrl-C，會看到 `table removed`。回到投影片的 Q&A。

## 第 2 頁　整體架構

- 規劃的順序（`.claude/skills/gateway-architecture/SKILL.md` §7）：階段 1 nftables + Suricata + ct mark（**已完成**，包含 auto trust）→ 最小的 cloud 迴路（10/25 決定排在階段 2 前面，O13）→ 階段 2 eBPF 算特徵（掛 XDP 或 TC）→ 階段 3 TC 上的 eBPF 轉送 trusted connection（fast path）。「分三階段」是**建議**的切法，不是定案，順序可能調整。
- cloud 不看 payload，只能回三種動作：trust、block、observe（O12，10/25 決定）；edge AI 一樣只能回這三種，這是**建議**（O19），edge AI 的輸入、任務、模型都還沒定。
- 框是 gateway 這台機器，不是 wnc-gw：netfilter、eBPF 在 kernel 裡，packet 由 kernel 轉送，不經過 wnc-gw 這個 process；Suricata 是 wnc-gw spawn 的獨立程式（GPL，不連結進 wnc-gw，DECISIONS.md §8）；edge AI 是合作方的程式。wnc-gw 負責裝 nft table、啟動 Suricata、讀 alert、設 ct mark。
- eBPF 掛在哪（`xdp` 設定，DECISIONS.md §17）：`auto`〔預設〕網卡有 native XDP 才掛 XDP，否則掛 TC；不會自動選 generic XDP（比 TC 慢，而且整張網卡跳過 GRO）。Pi 4 的 bcmgenet 和 USB 網卡的 driver（r8152、lan78xx、smsc95xx）都沒有 native XDP（看 driver 原始碼確認），所以 Pi 上一律 TC。eBPF 程式還沒寫；doctor 已經會判斷每個 port 會掛在哪（向 kernel 的 netdev netlink 讀 `xdp-features`，不掛任何程式，第 11 頁）。XDP 對 TC 的差距**沒有量**，要等 eBPF 程式寫出來。
- fast path 固定用 TC、不用 XDP（10/20 決定）：XDP 只有 ingress、有些硬體不支援；TC 比 netfilter 早執行，trusted 的 connection 繞過 netfilter 時，TC 上算特徵的程式仍看得到這些 packet。
- 保護範圍是公司 LAN 到 Internet 的邊界，不只 IoT。不做 NAT。
- 平台：Raspberry Pi 4（之後換正式設備）、Raspberry Pi OS（Debian trixie）、Suricata 8.0.7（trixie-backports）。
- 被問「為什麼省 CPU 那麼重要」：見第 5、6 頁。

## 第 3 頁　wnc-gw 的 subcommand

- `show interfaces` 列出網卡，方便在設定檔裡指定 port。
- wnc-gw 用 nft JSON（spawn `/usr/sbin/nft`）裝 table，不連結 GPL 的 libnftnl（專案可能閉源）；每次約 7.7 ms（Pi），所以要批次（O4）。用 ctnetlink 讀 conntrack 的計數和寫 ct mark，從 eve.json 讀 alert。
- ct mark 用手寫的 ctnetlink：Pi 上設一筆 13 µs，用 crate 是 20–51 µs（O17）。
- 停止時的順序：換回「沒有 inspection」的 rule → 停 Suricata → 移除 table。SIGHUP（例如 SSH 斷線）也一樣正常停止。同一台機器只能跑一個 `run`（flock）。
- log 只印到 stderr（tracing），`--log-format json` 給程式讀；每一筆 alert 是 DEBUG，有 alert 時每 60 秒一行 INFO 摘要。
- `run` 還會每 10 秒讀 conntrack 表的筆數（到 90% 記 WARN），`ids` 時讀 Suricata 漏掉多少 copy。
- 被問「用什麼權限跑、Suricata 被攻陷會怎樣」：現在是單一 process，實際上用 root 跑：裝 nft table、寫 ct mark 都要 `CAP_NET_ADMIN`，手動 `trust add` 也一樣。Suricata 由 wnc-gw 啟動、共用帳號，doctor 會給 warning（第 10 頁補充）。規劃是拆成只有 `CAP_NET_ADMIN`、`CAP_BPF` 的 privd 和沒有特權的 agent，Suricata 用非 root 加 landlock；這是**建議**，什麼時候拆還沒決定（O1，做 cloud 迴路之前要再決定一次）。
- 被問「授權」：Suricata 和 nft 一樣是 spawn 的獨立程式，wnc-gw 不連結 GPL 的函式庫（DECISIONS.md §8）。Suricata 隨設備散布要盡的義務、ET Open rule 的商用條款**沒有查**。

## 第 4 頁　packet 怎麼走

- 實際裝進 kernel 的 table（`nft list table inet wnc_gw`，README §1、`src/firewall.rs`，counter 的數字省略）：

  ```
  chain forward {
      type filter hook forward priority filter; policy accept;
      counter
      tcp flags & (syn | ack) == syn ct mark & 0x80000000 == 0x80000000 counter ct mark set ct mark & 0x7fffffff   # ①
      ct mark & 0x40000000 == 0x00000000 ct mark set ct mark | 0x40000000                                           # ②
      tcp flags fin,syn,rst jump ids                                                                                # ③
      ct mark & 0x80000000 == 0x80000000 counter accept                                                             # ④
      jump ids
  }
  ```
- 圖上只畫了兩個判斷，實際 forward chain 還有兩條 rule：一、純 SYN 碰到已 trusted 的 connection 先清掉 trust（port 重用時 conntrack 會把新 SYN 接回舊 entry、沿用 mark）；二、connection 第一次經過時設 forwarded 位元 `0x40000000`（auto trust 只看有這個位元的，gateway 自己的 SSH 不會被算進來）。上面的 ①② 就是這兩條，③ 是 SYN／FIN／RST，④ 是 trusted 的放行。
- table 的骨架寫死在程式裡，使用者只能改參數（O11）；Suricata 就緒或停止時只換 `ids` chain 的 rule，不重裝整張 table。
- 被問「為什麼 SYN／FIN／RST 一定進 Suricata」：
  - 目的是 trust 之後 Suricata 還看得到 connection 的開始和結束。結束時 Suricata 會把還沒比對的資料檢查完：Docker 和 Pi 都量到，第一段資料就帶攻擊標記的 connection 先被 trust，FIN 進 Suricata 之後才有 alert（DECISIONS.md §19；原因是**推測**，見「待決與下一步」的 ids alert 晚到）。FIN 不進 Suricata 的話，這個 alert 可能完全不會出現，這是**推論**，**沒有測**。
  - 價值是 alert，不是 revoke：FIN 時才 revoke，這條 connection 的資料已經送完，`ids` 本來也不擋；下一條 connection 是新的 entry，本來就重新觀察。revoke 有用的是 connection 還在時 alert 才到（例如 Suricata 處理落後），那種 alert 來自 trust 之前的資料，和這條 rule 無關；這個情況**沒有測**。
  - trust 之後在 connection 中段送的攻擊，這條 rule 幫不上：Suricata 只看得到開始和結束。
  - 成本：長 connection 每個 packet 約 +1 µs（控制 packet 只佔 0.01–0.04%）；scan 為主的 39-1 +59 µs、1-1 +22 µs（控制 packet 佔 91%、53%），但這類 connection 本來就不會被 trust，不影響 trust 省下的部分（DECISIONS.md §6）。
  - 和抽樣的關係：trust 之後的可見性規劃成三層（`research/literature/trust-bypass/SYNTHESIS.md` §4.3）。L1 是 kernel 算的計數和特徵送 cloud，還沒做；L2 就是這條 rule，已實作；L3 是隨機時間點的抽樣檢查，回到 Suricata 一段時間，還沒做（部分檢查的實驗見第 6 頁補充）。L2 不是為了抽樣做的，是三層裡最便宜、先做的一層。
  - 階段 3 的 TC fast path 也不轉送這三種 packet，交回 netfilter，讓 Suricata 和 conntrack 照樣看得到（SYNTHESIS.md §4.4）。TC 自己看得到每個 packet 的 flag，交回去不是為了讓 TC 知道 connection 的開始和結束。
- 被問「有沒有前例、其他工具也這樣做嗎」：有前例，但不是全部。
  - 有留下控制 packet 的：Shunting（CCS'07，論文），connection 放行後 FIN／RST 仍送給 IPS；Zeek 的 BPF shunt（Zeek 附的 script `shunt.zeek`），filter 不擋 SYN／FIN／RST，文件寫的理由是讓 Zeek 繼續記錄 connection、connection 結束時能停止 shunt；nftables flowtable（Linux kernel 的功能，不是論文），只收 established 的 connection，FIN／RST 回到一般路徑（kernel 文件這樣寫，我們讀 master 程式碼的兩份筆記不一致，**待查證**）。
  - 放行了就不再送的：Suricata 自己的 bypass、Snort 3 的 trust、Zeek 的 XDP shunter（Corelight，2026，預計進 Zeek 8.2）。這些放行之後也不能主動撤銷，只能等逾時（Snort 3 是沒看到撤銷的方式）。
  - 規律：留下控制 packet 的，都是放行之後還要能結束或撤銷的機制（`research/literature/trust-bypass/mechanisms.md` 的比較表）。
- 被問「為什麼不照 Suricata 的用法全部 bypass」：
  - Suricata 的 bypass 是 Suricata 自己判斷後面沒東西可看才放：TLS／SSH 加密之後、重組到 `stream.reassembly.depth`（預設 1 MB）、rule 用了 `bypass` keyword。wnc-gw 是觀察 5–8 秒、沒有 alert 就 trust，那時 Suricata 不一定比對完了，所以要在結束時補一次。
  - NFQ 模式下 Suricata 的 bypass 只在觸發的 packet 上打 mark，後面的 packet 怎麼放行要自己寫 nft rule，Suricata 的文件沒有範例；所以這裡沒有現成的用法可以照，rule 本來就是我們寫的。
  - 全部 bypass 只省長 connection 每個 packet 約 1 µs。
  - Zeek 的 XDP shunter 考慮過把控制 packet 交給 Zeek，沒有採用；簡報寫的缺點是「帶資料的 ACK，SSH 之類幾乎 shunt 不到」，細節**沒有查**。我們的 rule 只比對 SYN／FIN／RST，不含 ACK。
  - 這條 rule 寫死在 table 的骨架裡，不能關；要不要開放成設定**還沒決定**。
- 純 SYN 清 trust：conntrack 在舊 connection 沒有 FIN／RST 就消失時（例如設備重開機），會把同一組 5-tuple 的新 SYN 接回舊 entry，id 不變、mark 沿用；Docker 和 Pi 都重現過。偽造純 SYN 只能讓 trusted connection 回到 Suricata，不能讓沒 trusted 的被放行。
- 多個 queue／group 時用 symhash 分到不同的 Suricata worker（含 port、兩個方向同一個值）。
- demo 第 4 步會看兩個 counter：`ids` chain 的是送進 Suricata 的 packet，第 ④ 條 `accept` 的是 trusted、跳過 Suricata 的 packet。

## 第 5 頁　trust 以 connection 為單位

- 量法：`tests/ids_inline/trust_cost.sh`，Pi 4 鎖 1000 MHz、Pi 內的 veth netns、tcpreplay 綁 CPU 1；Suricata **直接跑 NFQ**（full、和 wnc-gw 一樣的強制設定，不是經過 wnc-gw）；整台機器 CPU 用 `/proc/schedstat`（不是 `/proc/stat`），÷ 經過 forward 的 packet；含 tcpreplay，所以只能看差距；2 輪平均（`tests/ids_inline/results/trust2.kvl`，DECISIONS.md §5）。流量是 IoT-23 各 scenario 的開頭 200,000 個 packet（Honeypot-7-1 整檔只有 119,638 個），每秒 10,000 個，一次約 20 秒。
- 表上的「trusted」是 C3：全部 trust、SYN／FIN／RST 進 Suricata，和 wnc-gw 的實際做法相同。不含 SYN／FIN／RST rule的 C2 是 33–40 µs，五個 scenario 每個 packet 省 38–68 µs（DECISIONS.md §5 的表）；C3 下 39-1 (IRCBot)、1-1 (Hide and Seek) 的控制 packet 佔 91%、53%，所以省得少（DECISIONS.md §6）。另外兩個 scenario 的 C3：44-1 (Mirai) 94.5 → 32.8、Honeypot-5-1 (Amazon Echo) 71.1 → 40.3。
- 三個 scenario 的組成（tshark 數重播的那段，只算 IPv4 packet）：
  - Honeypot-7-1 (Somfy door lock)：良性。99.8% 的 packet 在 2 條連到 port 443 的 TCP connection，其中 `192.168.1.158:10366 → 18.195.134.106:443` 一條就有 10.6 萬個（和 demo 的 `somfy.pcap` 是同一組 5-tuple）；其他是 DNS、DHCP。
  - 1-1 (Hide and Seek)：49% 是單向的 SYN scan（19,741 條，port 23、8080、2323、9527）；19% 是單向、每條 1 個 packet 的 UDP（37,454 條，port 各不相同）；26% 在 932 條 port 23（telnet）的 connection，兩個方向都有 10 個以上 packet；另外 4 條 NTP。
  - 39-1 (IRCBot)：91% 是對 port 22（SSH）的單向 SYN scan（181,996 條）；剩下 9% 在 19 條 TCP connection（HTTP、SSH、HTTPS、IRC 的 6667）。
- 被問「1-1、39-1 有 connection 被 trust 嗎」：
  - 這個實驗的 trusted 欄，是用 prerouting 的 rule 把每條 connection 從第一個 packet 就設成 trusted（`trust_cost.sh` 的 C2／C3），scan 也包括在內，所以全部都是 trusted。降不下來是因為控制 packet 佔 53%、91%，這些照樣進 Suricata。
  - 換成 auto trust：單向的 scan 和單向的 UDP 永遠不會被 trust。有機會的只有兩個方向都有 10 個以上 packet 的 connection，1-1 約 27%、39-1 約 9% 的 packet；還要活過 `min_age`、沒有 alert 才會被 trust（39-1 的 IRC C&C 在 11/02 的離線測試有 alert，那是整個 dataset，不一定在這 20 萬個 packet 裡）。
  - 所以這兩個 scenario 開 auto trust 省得比表上更少：例如 1-1 的單向 UDP 在表上算 trusted，auto trust 下會進 Suricata。auto trust 跑這些 scenario 的數字**沒有量**；重播用固定速率，1-1 的 10 個多小時、Somfy 的 24 小時都壓成 20 秒以內，用重播估 `min_age` 也不準。
- `ids`（NFLOG）路徑時全部進 Suricata 的整台成本約 56–64 µs（`nflog2.kvl`），trust 省的會比這頁少；`ids` 下 auto trust 的實測是第 6 頁。
- 不含 SYN／FIN／RST rule的 C2 下，「全部 trusted − 只轉送」在 8.0.7 是 −4.8 到 +0.9 µs（7.0.10 時到 +3.5）；44-1 (Mirai)、Honeypot-5-1 (Amazon Echo) 比只轉送低約 4–5 µs，兩輪、兩個版本都一樣，原因**沒有查**。
- ct mark 的兩個位元（demo 第 4 步會看到 `0xc0000000`）：`0x80000000` trusted、`0x40000000` forwarded。
- 實體網卡（方案 B，2026-11-02）：trusted 的 packet 整台約 14 µs、進 Suricata 的約 55 µs。
- 只用最高位元、寫入帶 mask：其他程式（例如 mwan3）用的是低位元。
- 限制：scan 幾乎都是純 SYN，一定進 Suricata，trust 對它沒有幫助。
- conntrack 表被塞滿時，early drop 只清沒有 assured 的 entry，trusted 的 TCP connection 不受影響。
- 被問「偽造同一組 5-tuple 的非 SYN packet，不是一樣享有 trust」：TCP 的 packet 不在 window 內時，conntrack 判成 INVALID，packet 沒有對到 connection、比對不到 ct mark，就會進 Suricata；Honeypot-5-1 重播時看過 packet 被判成 INVALID 而進 queue（DECISIONS.md §6）。要注入 window 內的 packet，攻擊者得知道序號，也就是在路徑上；這個情況**沒有測**。UDP 沒有 window，見第 6 頁補充。

## 第 6 頁　auto trust

- 只有 TCP（已建立）和 UDP 會被 trust。
- 被問「UDP 被 trust 之後怎麼辦」：UDP 沒有 SYN／FIN／RST，trusted 之後只能等 TTL 到期才回到 Suricata（DECISIONS.md §6）；目前沒有「不 trust UDP」的設定（`[trust]` 只有 `auto`、`min_packets`、`min_age`、`ttl`、`check_interval`）。UDP 沒有 window，偽造同一組 5-tuple 的 UDP packet 會共用 trust，這是**推論**，沒有測。要不要限制 UDP 的 trust 還沒討論。
- 量法（DECISIONS.md §19，`tests/ids_inline/autotrust_cost_pi.sh saving`）：Pi 4 鎖 1000 MHz、veth，`ids`、預設的 trust 數值；CPU 是 Suricata、wnc-gw 所有執行緒的 schedstat。Suricata 只載入 1 條測試用的 rule（UDP 的 content rule，這個 TCP 流量比對不到）；流量是 Python 產生的 8 條 TCP connection，每條每秒 250 個 1,000 bytes 的 packet；量第 15–75 秒，不 trust、auto trust 各 1 次。ET Open full rules 下**沒有量**。13.6 ms／s 是 Suricata 閒置時本來就有的成本。
- 被問「為什麼要每 `check_interval` 才讀一次 conntrack」：
  - 每個 packet 查 ct mark 本來就是即時的，是 nft 在 kernel 裡做的，和 `check_interval` 無關。`check_interval` 只是 wnc-gw 多久判斷一次：哪些 connection 可以 trust、哪些 trust 到期。
  - alert 不等 `check_interval`：wnc-gw 每 `eve_interval`（預設 0.5 秒）讀一次 EVE，讀到 alert 就立刻 revoke（`src/agent/trust.rs` 的 `on_alert`）。
  - 為什麼要定期讀：trust 的條件是兩個方向各幾個 packet，這個計數在 conntrack 裡。conntrack 只在 connection 建立、狀態改變、結束時發事件，不會每個 packet 通知，所以只能定期去讀。
  - 讀一次有固定成本（下一點），間隔越短越貴：1 秒讀一次時，1,000 條 connection 是 17 ms／s，1 萬條是 101 ms／s；預設 5 秒一次大約是它的 1/5。
  - 讀得快也早不了多少：本來就要觀察滿 `min_age` 5 秒才會 trust，讀得快只是早幾秒。
  - 5 秒是**建議值**，沒有實驗依據（待決與下一步）。之後可能改用 conntrack 的 NEW／DESTROY 事件維護觀察中的 connection，只查這些 connection 的計數，不用每次掃整張表；**還沒決定**。
- 每次讀 conntrack 的成本：固定約 7 ms（kernel 要掃整個 hash table 的 65,536 個 bucket），加上每條經過 gateway 的 connection 約 9.4 µs。預設每 5 秒一次：connection 很少時 1.4 ms／s，1 萬條約 20 ms／s（一顆核心的 2%）。讀表是同步的，讀的期間 wnc-gw 的事件迴圈停住：1 萬條約 0.1 秒；做法待決：放到另一個執行緒，或改用 conntrack 的 NEW／DESTROY 事件。
- 讀 alert：每 `eve_interval`（預設 0.5 秒）讀一次 eve.json 新增的部分（poll）。Pi：沒有 alert 時 0.37 ms／s，每筆 alert 16 µs；延遲 0 到一個間隔。inotify 量過，alert 多時貴 3 倍，已經刪掉。
- 觀察用 conntrack 計數、不用 EVE 的 flow 事件：flow 事件要等 connection 結束或逾時才有，長 connection 等不到。`nf_conntrack_acct` 要開（每個 packet 多 0.1–1.3 µs），沒開時 doctor 報 error。
- `ttl` 900 秒比 Suricata 的 `flow-timeouts.tcp.established`（600 秒）長：trust 結束時 Suricata 已經忘了這條 connection，會從中間接手，不會因為序號過時丟 packet（`ips` 下 `ttl` 不夠長時 doctor 會警告）。
- 被問「TTL 到期後 Suricata 從中間接手，偵測會不會變差」：Docker 上用真的 TCP connection 經過 wnc-gw 測過（`tests/partial_inspect/README.md` 實驗 3b）。Suricata 已經忘了這條 connection 時，`ids` 的 rule 全部抓到；`ips` 第一個 request 的 `flow:established` rule 會漏，後面的抓得到。Suricata 還記得時就取消 trust（例如手動 `trust del`），HTTP 的 rule 會漏、只剩 raw stream 的 rule，`ips` 還會丟 4 個 packet。真實流量**沒有量**。
- `min_packets` 10、`min_age` 5 秒是**建議值**，沒有實驗依據，待確認（待決與下一步）。
- Suricata 停止時，觀察到一半的 connection 全部重來；已經 trusted 的照常到期。alert 比第一次觀察早到也算（記 10 分鐘）。
- 驗證：Docker 和 Pi 都跑過 `protection_docker.sh autotrust`／`protection_pi.sh autotrust`（`ids`、`ips`、`routed` 都測過）。
- 被問「本地 rule 抓不到的攻擊，會不會直接被 trust」：
  - 條件要兩個方向都至少 `min_packets` 個 packet，所以單向的 scan、flood，和只有 SYN 的 connection（例如 Muhstik 那 62 條）永遠不會被 trust，一直進 Suricata。
  - 會被 trust 的是雙向、本地 rule 沒看到問題的 connection。auto trust 只代表本地 rule 沒看到，不代表良性，所以預設關。
  - trusted 之後怎麼再看，兩個方向都**還沒決定**：一是部分檢查（O20）：合成 connection 的實驗裡，只檢查每段開頭、約送 5–8% 的 packet 就抓到後段的攻擊；但長度固定會被「先塞資料再攻擊」繞過，長度隨機時抓到 83–90%（`tests/partial_inspect/README.md` 實驗 5）。二是讓 edge AI 吃抽樣的資料（O19）。
  - 11/02 問的「是 rule 還是 dataset 的問題」，這次沒有新實驗。
- 被問「先裝正常、被 trust 之後再攻擊」：會漏。合成 connection 的實驗裡，只看前 20 個 packet、之後完全不看時，後段的攻擊 0% 抓到（`tests/partial_inspect/README.md` 實驗 5）。現在有的：SYN／FIN／RST 照樣進 Suricata，上面有 alert 就 revoke；TTL 到期回到 Suricata。門檻是固定的，攻擊者可以預測，沒有隨機化。緩解是上一題的部分檢查，**還沒決定**。
- 被問「有 alert 的設備，下一條 connection 會不會又被 trust」：會。alert 是用 5-tuple 記的（10 分鐘），只擋同一組 5-tuple 的下一條 connection；同一台設備換一個 source port 開的新 connection 照樣會被 trust。架構的安全底線寫「被 revoke 過的 connection 或設備，下次門檻要提高」，**還沒做**。要做之前還缺兩件事：一是哪一端是內網的設備，目前沒有判斷，alert 裡只有兩端的 IP 和 port；`routed` 可以看 IP 落在 LAN 的網段（**推論**，程式沒做），`bridge` 兩邊同一個網段，要靠 packet 從哪個 port 進來（netdev ingress 的 mark，已決定、還沒實作）。二是用什麼代表一台設備：IP 會因為 DHCP 改變，內網再有一層 NAT 時好幾台共用一個 IP；MAC 在 `routed` 中間隔著 router 時看到的是 router 的，而且 Suricata 從 NFLOG／NFQ 收 packet，EVE 裡可能沒有 MAC（**沒有查**）。用哪一種、門檻提高多少，**還沒決定**。
- 被問「HTTPS 幾乎都會被 trust，還有意義嗎」：Suricata 對加密流量本來就只看得到 handshake（SNI、憑證、JA3）。handshake 在 connection 開頭，trust 之前就進過 Suricata；handshake 在前 10 個 packet 以內是**推論**，沒有量。trust 之後少看的是加密後的內容，那部分本來就看不到。
- 被問「開 auto trust 之後偵測有沒有變差」：只驗證了 demo 的三個 pcap，alert 和離線跑的一樣；11/02 四個 dataset 開和關的比較**沒有做**。
- 被問「每秒省 85 ms 夠不夠、什麼時候划不來」：每個 trusted packet 省約 21 µs；1 萬條 connection 時讀 conntrack 約 20 ms／s（上面），**推算**每秒要約 950 個 trusted packet 才打平。真實公司流量裡長 connection 的比例**沒有量**。省下的 CPU 給 edge AI：文獻裡 Kitsune 在 Pi 3B 每個 packet 175–1,100 µs（模型不同，只能當量級），不可能逐 packet 看，比較適合吃抽樣的資料或每條 connection 的彙總特徵（O19）。

## 第 7 頁　Suricata 沒在 inspection 時

- 重現：Docker 上 8.0.7、啟動前就有 packet 進 queue 時 50 次有 42 次 segfault；改成收到 `READY=1` 才加 queue 的 rule 後跑 30 次全部正常（DECISIONS.md §10）。
- segfault 的原因用 gdb 確認過：NFQ 執行緒等 kernel 回覆時，就把 queue 裡的 packet 交給還沒初始化完的統計計數器。Pi 上經過 wnc-gw（等 `READY=1`）在 `ping -f` 下啟動 20／20 正常（DECISIONS.md §10）。
- 重啟的退避：1 秒，連續失敗就加倍，最長 60 秒。漏掉的 copy 每 10 秒記一次。
- `ips` 跟不上時放行靠 queue 的 `bypass` 加 `nfq.fail-open=yes`。Suricata 當掉那一刻還在 queue 裡等 verdict 的 packet 會被 kernel 丟掉，`bypass` 只管之後的 packet。
- `ips` 時 exception policy（Suricata 處理不了某條 connection，例如記憶體用完）跟著 `when_unavailable`：`accept` → ignore，`drop` → drop-flow（flow、defrag 用 drop-packet）；`ids` 一律 ignore（拿到的是 copy，丟了也擋不到）。Debian 預設的 `auto` 在 `ips` 等於 drop-flow，會丟正常流量。
- wnc-gw 強制 `stream.midstream=true`：Suricata 重啟後、trust 到期回到 Suricata 的 connection 都是「從中間開始」，Debian 預設會整條丟掉（Pi 上 39-1 (IRCBot) 丟 26%）。
- 漏掉的 copy：Suricata 自己的統計不算 NFLOG socket 丟掉的 copy，wnc-gw 讀 kernel 的 Drops；驗證時兩者完全相同（Docker 53,425、Pi 28,016）。
- wnc-gw 停止、table 移除後流量直接通過（開發者：「沒 run 當然就是通過」）。
- 被問「wnc-gw 自己當掉、被 OOM kill 呢」：
  - Suricata 會跟著結束（`PR_SET_PDEATHSIG`），不會留下佔著 queue 的 Suricata。
  - 被強制結束時 table 會留著，流量照 table 裡最後的 rule 走（**推論**，從程式和 kernel 的行為推，沒有測）：`ids` 和 `ips` 加 `accept` 照常轉送、沒有 inspection；`ips` 加 `drop` 時 packet 被丟掉。
  - 重新 `run` 時換掉留下的 table，並清掉上次留下的 trust。
  - 誰把 wnc-gw 拉起來：systemd unit 還沒做（已決定之後支援 systemd 管理），現在要手動。wnc-gw 死掉的這段時間沒有 log。
- 被問「攻擊者能不能故意弄倒 Suricata，打開放行的空窗」：空窗期可以用 `when_unavailable = "drop"` 改成丟掉，不管哪一種都記 log；Pi 上每次空窗約 40 秒（載入完整 rule，「Demo：環境」）。用特定 packet 讓 Suricata 當掉屬於 Suricata 本身的漏洞，**沒有分析**。空窗期只記 log、沒有對外告警，還沒做。
- 被問「`ids` 下攻擊者大量送 packet，讓 Suricata 跟不上」：會漏。packet 照樣轉送、copy 被丟，wnc-gw 記下漏了多少；`ips` 時照 `when_unavailable`。這種攻擊情境的實驗**沒有做**。小 packet 時的容量換成 Mbps 見第 9 頁補充。
- 被問「rule 怎麼更新、會不會又空窗 40 秒」：現在換 rule 要重啟 Suricata，空窗會記 log。Suricata 本身可以不中斷地重新載入 rule（unix socket 的 `reload-rules`），wnc-gw 啟動 Suricata 時已經開了 unix socket；更新 rule 的流程還沒做。

## 第 9 頁　`mode` 與 `protection`

**`mode`（上面的表）**

- 兩種模式 doctor 的 check：`bridge` 看 LAN、WAN 在同一個 bridge、`br_netfilter`、`bridge-nf-call-iptables`／`ip6tables`；`routed` 看不在 bridge、`ip_forward`、IPv4 位址、網段重疊、default route 走 WAN。
- 量法（DECISIONS.md §1、`tests/cpu_alloc/README.md` 實驗 4，2026-11-04）：方案 B（筆電的 tcpreplay 從兩張實體網卡送進 Pi），2 輪。只轉送、中斷都在 CPU0 時（A0）@100 kpps：`bridge` 9.97 µs、容量 100 kpps；`routed` 8.02 µs（−20%）、容量 150 kpps。開 RPS 時兩者容量都是 300 kpps。有 inspection 時（`ips` 2 queue、`ids` 3 group）只差 2–9%，容量一樣。容量的定義：處理不過來而丟的 packet ≤ 0.1% 的最高速率。流量是 17-1 (Kenjiro) 的開頭 200,000 個 packet，用 `--loop` 重複，讓每個速率至少 5 秒；只轉送是沒有 wnc-gw、沒有 nft rule 的 bridge／routing。
- 這頁的 9.97／8.02 是 Pi 整台機器、packet 從筆電送進來（Pi 上沒有 tcpreplay），和第 5 頁（veth、Pi 上跑 tcpreplay）的「只轉送」基準不同，不能互相比。
- 被問「為什麼 `routed` 比較快」：不是路由比較快，是 `bridge` 要讓 nft 看得到被橋接的 packet，多了 `br_netfilter` 這一步；`routed` 本來就走 IP 層，沒有這一步。
  - veth 上每個 packet 的轉送成本（DECISIONS.md §1，2026-10-24，Pi、單一 UDP flow、60-byte frame、3 輪差異 < 2%）：

    | 設定 | µs／packet |
    |---|---|
    | bridge（沒有 `br_netfilter`） | 3.1 |
    | routed | 4.0 |
    | bridge + `br_netfilter`（沒有 rule） | 6.9 |
    | routed + nft + conntrack | 7.9 |
    | bridge + `br_netfilter` + nft + conntrack | 10.7 |

  - 純 bridge 其實比 routing 便宜。我們的 rule 在 `inet wnc_gw` 的 forward hook；被橋接的 packet 本來只在 bridge 層處理，不經過 IP 層的 hook，沒載入 `br_netfilter` 時 forward chain 一個 packet 都看不到。Pi 的 kernel 沒有 `nf_conntrack_bridge`，不能在 bridge 層用 conntrack，只能靠 `br_netfilter` 把被橋接的 IP packet 再送進 IP 層的 netfilter hook，沒有任何 rule 時每個 packet 就多 3.8 µs。這 3.8 µs 花在哪一段**沒有 profile 過**。
  - 實體網卡上差距比較小：只轉送時少 20%（開 RPS 時 11.79 對 9.99 µs，少 15%），省的主要是收 packet 那顆 CPU；有 inspection 時只差 2–9%，因為大部分 CPU 花在 Suricata。
  - 限制（`tests/cpu_alloc/README.md` 實驗 4）：實體網卡上只轉送和 inspection 只用了 17-1 (Kenjiro)，全部 trust 的那組用 60-1 (Gafgyt)；`routed` 的下一跳是假的 MAC，轉送出去的 packet 沒有人收。
- `bridge` 時 forward chain 看到的 `iifname` 都是 `br0`，之後要靠 netdev ingress 打 mark 判斷方向（已決定、還沒實作）。
- `routed` 的位址和路由由 OS 設定，wnc-gw 只檢查：沒有位址是 warning（DHCP 可能還沒拿到）、網段重疊是 error、default route 不走 WAN 是 warning；note 會寫出內網 gateway 和上游要加的 route。
- `routed`、沒開 RPS 時，同一條新 TCP connection 兩個一模一樣的 packet 同一批收進來，第二個會在 conntrack confirm 時被丟（`insert_failed`），丟的是重複的 packet。
- 預設要不要改成 `routed` 還沒決定（待決與下一步）。
- 被問「和設備上現有的 firewall、NAT、QoS、mwan3 會不會打架，PPPoE、VLAN 呢」：wnc-gw 只動自己的 table `inet wnc_gw`，不執行 `flush ruleset`；ct mark 只用最高位元、寫入帶 mask（第 5 頁補充）；不做 NAT。VLAN：11/05 實機 demo 的 WAN 就是 eth1 上的 VLAN 20（「Demo：環境」）。PPPoE、和 QoS 的互動**沒有測**；OpenWrt（fw4、procd）的後端還沒做。

**`protection`（下面的表）**

- 被問「下面的表兩列是什麼意思」：
  - 第一列是 Suricata 的執行緒每處理一個 packet 用掉的 CPU 時間，越低越好；只算 Suricata，不是整台機器（`ips` 時 verdict 之後 kernel 的轉送算在 Suricata 頭上，見下面的量法）。範圍是三個 scenario 的最小到最大。
  - 第二列是整台 gateway 的容量，越高越好：丟掉的 packet ≤ 0.1% 的最高速率。`ids` 的範圍是兩個 pcap 的結果，卡在不同的地方（下面「投影片上 `ids` 的 50,000–80,000」那一點）。
  - 兩列是不同的實驗：第一列是 veth、每秒 10,000 個 packet、1 個 queue／group；第二列是實體網卡，而且要先調過（`ids` 開 RPS＋3 個 group，`ips` 把網卡中斷搬到 CPU1＋3 個 queue）。所以不能從第一列推第二列：`ids` 每個 packet 便宜將近一半，容量卻沒有變兩倍。
- Suricata 每個 packet 的量法（DECISIONS.md §2，`tests/ids_inline/results/nflog2.kvl`）：Pi、veth、10,000 pps、1 個 queue／group、2 輪、Suricata 8.0.7、workers；三個 scenario 60-1 (Gafgyt)、1-1 (Hide and Seek)、17-1 (Kenjiro)（各取開頭 200,000 個 packet），empty 和 full rules。投影片只放 full rules：`ids` 21.1–24.4、`ips` 37.6–47.8 µs；empty rules（不載入 rule）時 `ids` 19.2–22.2、`ips` 35.3–43.9。整台機器 `ids` 省 4–25 µs／packet。`ips` 貴在 verdict 之後 kernel 的轉送是在 Suricata 的 syscall 裡做。
- 容量（`tests/cpu_alloc/README.md`，方案 B、PAUSE 關、full rules，2026-11-03）：`ids` 要開 RPS（CPU1–3）＋3 個 group，17-1 (Kenjiro) 轉送 120、inspection 80 kpps；**`ids` 不開 RPS 時轉送只有 30–40 kpps**（轉送和 copy 都在收 packet 那顆 CPU 的 softirq 裡做）。`ips` 用「網卡中斷搬到 CPU1＋3 個 queue」兩個 pcap 都到 60；`ips` 只開 1 個 queue 只有 20–30 kpps。容量的定義同上面 `mode` 的量法。`ids` 有兩個容量：轉送容量（丟 ≤ 0.1%）和 inspection 容量（Suricata 漏掉的 copy ≤ 0.1%）。
- 投影片上 `ids` 的 50,000–80,000 packet／s 是兩個 pcap：17-1 (Kenjiro) `ids` 80（inspection 容量）、1-1 (Hide and Seek) `ids` 50（轉送容量）；`ips` 兩個都是 60。1-1 (Hide and Seek) 有 18.4% 的 packet 從 Pi 的 USB 網卡（eth1）進來，**推測**原因是 eth1 的中斷在 CPU0、沒設 RPS，所以 `ids` 的轉送只到 50 kpps（inspection ≥ 70），比 `ips` 的 60 低；eth1 也設 RPS 會不會改善**沒有量**。被問到「`ids` 是不是一定比 `ips` 快」時要講這個例外。
- 被問「容量換成 Mbps 是多少」：
  - 小 packet：這兩個 pcap 的平均 packet 是 60.06 bytes（17-1 (Kenjiro)）和 71.38 bytes（1-1 (Hide and Seek)）。**推算**：`ids` 50–80 kpps 約 29–38 Mbps，`ips` 60 kpps 約 29–34 Mbps。
  - 大 packet、一條 TCP connection（iperf3，1,454 bytes，`tests/cpu_alloc/README.md` 實驗 5）：Pi 開 RPS 時轉送 ≥ 88 kpps（約 1 Gbps），但 Suricata 只檢查得了不到 10 kpps（約 116 Mbps），10 kpps 時那個 worker 已經 100% 忙、漏掉 15%。一條 connection 只會進一個 worker，開多個 group 也沒用；這就是 trust 的用途，大流量的 connection 被 trust 之後不用 Suricata 看。
  - 正式設備的推算沒有做（硬體還沒定）。
- checksum validation：`ids` 下一定要關。方案 B 用 iperf3 的大量 TCP 送進 Pi，GRO 平均把 6.7 個 packet 合併成一份 copy，開著 checksum validation 時 74% 被判成 checksum 錯誤、payload rule 比對不到。關掉的風險是 insertion：攻擊者送接收端會丟掉的 packet 來混淆 Suricata。`ips` 沒有這個問題，kernel 會標出 checksum 還沒算的 packet。
- `ids` 跟不上時 packet 照樣轉送、copy 被丟掉，`when_unavailable` 管不到（第 7 頁）。
- Suricata 一律用 workers runmode（wnc-gw 強制）：autofp 在 Pi 上整台每個 packet 多 15–35 µs（O18）。
- 被問「和直接跑 Suricata 比，wnc-gw 多花多少」：8.0.7 下每個 packet 的成本比值 0.81–1.21（60-1 (Gafgyt) wnc-gw 便宜 18%、Honeypot-7-1 (Somfy door lock) full 貴 21%），**原因沒有查**，每格只量 1 次（`tests/ids_inline/results/compare2.kvl`，DECISIONS.md §20「還沒解釋的量測」）。不要說成結論。
- 預設 `ids` 是開發者的要求：前期只標記、不擋。
- 被問「哪些 rule 改成 `drop`、擋錯怎麼辦」：挑選標準還沒決定。誤報的參考是 11/02 的結果：各 dataset 的 Benign 上有 alert 的比例 0.009%–1.49%（Benign 的 label 本身有疑點）。擋錯時現在能用 `wnc-gw trust add` 讓那條 connection 不進 Suricata；以 IP 為單位的白名單還沒做。
- `ips` 的 `drop` 實測（`tests/demo/DOCKER.md`「ips」一節，Docker、Suricata 8.0.7，把 3 條 rule 改成 `drop`，2026-11-05）：server 回 `uid=0(root)` 的真的 TCP connection，`ips` 下 client 6 秒收到 0 bytes（log 是 `action="blocked"`），`ids` 下同一條 rule 只有 alert、client 照樣收到；真的 TCP connection 收不到東西，是因為重送的內容一樣又被丟。重播 3-1 (Muhstik)：觸發 rule 的那個 `NICK` packet 沒有轉送出去，同一條 connection 的其他 packet 照常轉送；`drop` 丟的是比對到的 packet，不是整條 connection。
- iperf3 `ips` 1.02–1.15 → 50.6–52.2 Gbit/s（第 7 秒 trusted），是 `DOCKER.md` 演練紀錄 Suricata 8.0.8 那一次、筆電的數字；同一次 `ids` 是 27.8–31.2 → 49.1–52.5。`ips` 下每個 packet 都要等 Suricata，所以 trust 在 `ips` 下省得更多。
- wnc-gw 自己的擋（nft 黑名單 set）還沒做；之後 cloud 回 block 時是用 nft set 擋，不是 Suricata（O11）：trusted 的 connection 和之後的 fast path 都不經過 Suricata，黑名單放在 Suricata 就擋不到。

## 第 10 頁　`doctor`

- 完整的 check 項目：設定檔；port 對到哪張網卡、link 狀態；`mode` 的環境（`bridge`／`routed`）；eBPF 掛點（XDP 或 TC）；kernel 模組；`nft`；Suricata：NFQUEUE／NFLOG、`READY=1`；Suricata 的設定、rule 檔、eve-log；auto trust：`nf_conntrack_acct`；其他在跑的 Suricata；哪些檔案非 root 可以改。
- 為什麼 link down 只是 warning：gateway 串在網路中間，開機時線沒插好就拒絕啟動的話，線插上之後網路會不通，或流量完全沒有 inspection（doctor-checks.md §1）。同理，`routed` 沒有位址是 warning。
- doctor 看的是「能力」不是版本號：例如 Suricata 看 `--build-info` 有沒有 NFQueue／NFLOG 支援、`Systemd support`。Suricata 的設定是用 `suricata --dump-config` 加上 wnc-gw 強制的 `--set`，看到的就是實際執行時的設定（約 12 ms、不載入 rule）。rule 檔只檢查有沒有 rule，不檢查語法（要 `-T` 載入全部 rule，太慢）。
- Suricata 最低版本 8.0 的 check 已決定、還沒寫。
- 輸出全部在 stdout（`wnc-gw doctor > report.txt` 可以存下完整報告），finding 集中印在最後。
- demo 的 doctor 輸出（2026-11-06 實際跑的，`assets/doctor_docker_20261106.txt`）：沒有 error，10 個 warning、1 個 note。warning：`net.ipv6.conf.all.forwarding` 是 0（Docker 的拓樸只用 IPv4）、`when_unavailable = "accept"` 放行、`ids` 不擋、`ids` 不做 checksum validation、`ids` 流量太快會漏 copy、Suricata 和 wnc-gw 共用帳號、auto trust 的風險、Docker 裡沒有 `systemctl` 查不到 `suricata.service`、兩個設定檔非 root 可以改（從筆電掛進容器，擁有者是筆電的帳號；Pi 上放在 root 的 `/etc/wnc-gw` 就不會出現，所以這一項佔兩個 warning）。note：`routed` 要內網用 10.0.1.1 當 gateway、上游加 route。
- 不是每則訊息都有修法：漏 copy、Suricata 共用帳號、auto trust、`systemctl` 找不到這四則 warning 沒有修法指令，所以講「能修的訊息都附上修法的指令」。

## 第 11 頁　`doctor` 的輸出：Pi 4 與 Docker

- 截圖是 2026-11-06 跑的，只留 MODE CHECK 和 XDP 兩張表（原圖 `assets/pi_xdp.png`、`assets/docker_xdp.png`，上面還有設定摘要、port 對到哪張網卡）。完整輸出下面還有 kernel 模組、nft、Suricata、權限和 finding（第 10 頁補充）。

- XDP 表的欄位：NATIVE XDP 是 kernel 回報的 `xdp-features`（basic、redirect、rx-sg 等；`no` 是一項都沒有）；ATTACHED XDP 是網卡上現在掛著的 XDP 程式，掛的是 generic XDP 時給 warning（會讓整張網卡跳過 GRO）；CORE HOOK 是照 `xdp` 設定決定的掛點：`auto` 時有 basic 才選 native XDP，否則 TC；`off` 一律 TC；`generic` 選 generic XDP，並給 warning。
- 怎麼讀：kernel 的 netdev generic netlink（dev-get），只讀，不載入任何程式；讀不到時 `auto` 給 warning，並用 TC。DRIVER 欄讀 `/sys/class/net/<網卡>/device/driver`；VLAN（eth1.20）和 veth 是虛擬裝置，沒有這個連結，所以是 `-`。eth1.20 看的是 VLAN 裝置本身的 XDP 能力。
- Pi 沒有 native XDP，原本是從 driver 原始碼推的（DECISIONS.md §17），這是第一次用 doctor 在 Pi 上實際看到。
- veth 有 native XDP 不代表 XDP 比 TC 快：XDP 對 TC 的差距**沒有量**，要等 eBPF 程式寫出來（第 2 頁補充）。
- `bridge` 的表只有 4 項；`br_netfilter` 有沒有載入在 kernel 模組那張表另外檢查。`routed` 的位址、網段、default route 三項是 11/05 加的：沒有位址是 warning（DHCP 可能還沒拿到）、網段重疊是 error、default route 不走 WAN 是 warning（第 9 頁補充）。
- Docker 的 `net.ipv6.conf.all.forwarding` not met 是 warning：Docker 的拓樸只用 IPv4（「Demo（切到終端機）」的 doctor 那一步）。

## 待決與下一步（沒有投影片，被問到再講）

- 還沒決定的三件：第一，auto trust 的數值現在是建議值：預設關、10 個 packet、5 秒、TTL 900 秒；TTL 有理由，要比 Suricata 忘記一條 connection 的 600 秒長，但 packet 數和秒數沒有實驗依據。第二，`ids` 模式下，低流量 connection 的 payload alert 可能比 `min_age` 晚到，connection 會先被 trust、結束時才因為 alert 被 revoke；`ips` 下同樣的 connection 一開始就不會被 trust。第三，`mode` 的預設：`bridge` 部署不用改網段，`routed` 轉送比較省。
- 下一步：先接最小的 cloud 迴路：我們自己做一個模擬的 cloud，wnc-gw 把資料送上去，cloud 回 trust、block 或 observe。這是 10/25 決定的，排在 eBPF 之前。之後是用 eBPF 算特徵（掛 XDP 或 TC），給 cloud 和 edge AI 用，再來是 fast path，trusted 的 connection 在 TC 就直接轉送、不經過 netfilter；這兩步的切法是規劃，順序可能調整。

- 老師 11/04 擔心 `ids` 要複製 2–3 份（Suricata、edge AI、cloud 特徵）的成本：Pi 上 kernel 每多一份 copy，小 packet +3–5 µs、大 packet +7–8 µs，多 2 份轉送容量少約 2 成；只複製前 128 bytes 時大 packet 幾乎不加成本（`tests/cpu_alloc/README.md` 實驗 5）。每個用途要整個 packet 還是只要 header 還沒定。

- 被問「cloud 回 trust 的通道誰保證、上傳什麼、斷線怎麼辦」：cloud 只能回 trust、block、observe（第 2 頁補充）；送 cloud 的欄位只能是數值、bool、事先宣告的 enum，不送 SNI、URL 這類字串的原文。通道的**建議**是 mTLS，請求和回應都簽章、防重放，簽章錯、動作速率異常、連不上時停止接受新的 trust。斷線時 fail-open 還是 fail-closed 還沒決定（O9）。傳輸成本還沒討論；合規**沒有查**。

- 被問「我們的 SoC 有硬體加速，packet 不經過 netfilter，怎麼共存」：nft flowtable（軟體或硬體 offload）命中的 packet 不經過後面的 netfilter，也不會進 Suricata，所以不能對所有 connection 開 offload（OpenWrt 上就是不能開 fw4 的全域 `flow_offloading`）。規劃是只讓 trusted connection 走 fast path；flowtable 能不能當 L3 的 fast path 後端還沒決定（O5）。flowtable 只對 L3 路由的流量有用，`bridge` 時沒有作用；Pi 沒有硬體 offload。
