## 第 2 頁　資料量與對齊結果

這一頁是 IoT-23 全部 scenario 的對齊結果。

這個 dataset，一共 23 個 scenario(是 20 個 malware 加上 3 個 Honeypot)。總共 7.7 億個 packets，3.25 億條 labeled flows。
整體的 flow alignment 是 98.87%。
>這個 98.87% 是把所有 scenario 的 flow 加起來再除，不是各個 scenario 的平均。

右邊的圖，每一列是一個有 label 的 scenario，一共 23 列，後面括號是 malware 或設備的名稱。橫軸是百分比，從 0 到 100%。實心的藍點是 flow alignment，空心的灰圈是 packet coverage。圈畫得比點大，兩個值一樣的時候，圈會套在點的外面。

圖中有兩個指標，
第一個是 flow alignment，意思是有 label 的 flow 裡，有多少條能在 pcap 裡找到剛好對得上的 packet。

> 對得上的意思是：同一個 5-tuple、時間落在這條 flow 的開始和結束之間，找到的 packet 數，剛好等於 Zeek 在 conn.log 裡記的 packet 數。這就是上次講過的對齊方法。

第二個是 packet coverage，意思是 pcap 裡全部的 packet，有多少落在某一條 labeled flow 的範圍裡。
> 它只看範圍，不管 Zeek 記了幾個 packet。像 ARP 這種非 IP packet 沒有 flow，所以永遠算不進去。

> 這兩個指標的方向剛好相反。flow alignment 問的是「label 找不找得到自己的 packet」；packet coverage 問的是「packet 有沒有被某條 label 管到」。所以會出現 flow alignment 幾乎是 0、packet coverage 卻是 100% 的情況，下一頁會講。另外，packet 數是 Zeek 從 pcap 算出來的，所以這個檢查看的是 Zeek 的統計和 pcap 對不對得上，不是 label 標得對不對。

>
> 大部分的 scenario，兩個符號都貼在 100% 附近。掉得最明顯的是：60-1 (Gafgyt) 的 flow alignment 幾乎是 0，34-1 (Mirai) 大約 38%；packet coverage 掉下來的，有 52-1 (Mirai) 大約 61%，8-1 (Hakai) 大約 71%。
>
> 這一頁是補完上次的驗證。上次的 100%，是抽兩個 scenario 的結果；整個 dataset 跑下來是 98.87%，而且每個 scenario 不一樣，所以不能說 IoT-23 對齊 100%。上次抽的 Hakai，就是這裡的 8-1，這次跑出來和上次一致。

**實驗怎麼做**

> - **資料**：Zenodo 那包 IoT-23，tar.gz 的 md5 與 Zenodo 一致；解壓後約 106 GiB、84 個檔案。上次的 2 個樣本是從 Stratosphere 的個別目錄下載，這次用的是 Zenodo 那包。
> - **對齊**：只處理 TCP、UDP、ICMP；5-tuple 雙向相符、時間窗 ±1 µs、找到的 packet 數要等於 `orig_pkts` 加 `resp_pkts`。Honeypot-7-1 只有 Somfy-01 那個 pcap 有 label，其他五個（Somfy-02 到 06）不做對齊，但 packets 有算進 7.7 億。
> - **一個 scenario 有好幾個 pcap 時用哪個**：用最大的那個（完整的錄製）。17-1、3-1、34-1、35-1、9-1 另外還有從主 pcap 篩出來的子集（例如 `only15000000`、`.irc`、`telnet`、依 port 過濾的檔），抽樣比對 100% 都在主 pcap 裡，所以不另外算；Honeypot-4-1 另有一個 2018-09-14 錄的 pcap，label 只涵蓋 10/25 到 26，沒有 label 可以對。6 個有多個 pcap 的 scenario，label 的時間範圍都和被選中的主 pcap 完全一致（2026-10-18 核對）。
> - **串流處理**：最大的單一 pcap 是 60-1，22 GB（22,028,429,274 bytes，等於 20.5 GiB），所以程式用串流處理：一次讀 16 MB、把 flow 當索引，flow 太多放不進 memory 時依 hash 分批。
> - **正確性**：串流版和原版在 Hakai-8-1、Honeypot-7-1（Somfy-01 那個 pcap）兩個小 scenario 的輸出逐字相同；強制分批和不分批的結果也相同（2026-10-17 重跑 `tests/iot23/compare_small.sh` 確認）。

**被問到時**

> - **98.87% 怎麼算？** 321,632,849 條對齊的 flow ÷ 325,309,946 條 labeled flows。對不上的 368 萬條裡，358 萬條（97.4%）來自 60-1；扣掉 60-1 是 99.97%。整體數字是被大 scenario 撐高的：39-1 (IRCBot)、43-1 (Mirai)、17-1 (Kenjiro)、33-1 (Kenjiro) 四個就占全部 flow 的 76.9%。
> - **整體 packet coverage 多少？** 96.42%；分母含沒有 label 的那 5 個，只算 23 個是 96.48%。
> - **7.7 億怎麼來？** 770,313,789 是 23 個 scenario 主 pcap 的總和，其中 Honeypot-7-1 六天的 pcap 都算；沒有 label 的那五天（Somfy-02 到 06）共 544,766 packets，有 label 的部分是 769,769,023。子集 pcap 不重複算。
> - **23 個 scenario 都只有一個 pcap 嗎？Honeypot-7-1 怎麼對齊？** 23 個是 20 個 malware 加 3 個 Honeypot。Honeypot-7-1（Somfy door lock）底下有六天的 pcap（資料夾 Somfy-01 到 06），只有第一天（Somfy-01）有 label，所以對齊用的是 Somfy-01 那一個 pcap；其他五天的 packets 有算進 7.7 億，但沒有 label 可以對。
> - **為什麼資料夾裡有些 scenario 不只一個 pcap？** 見上面「實驗怎麼做」：多出來的是子集，或（Honeypot-4-1）沒有 label 的另一天錄製。

## 第 3 頁　哪些 scenario 不能直接用

> 這一頁看 23 個 scenario 裡，哪些不能直接拿來用。
>
我們從 23 個 scenario 選出了 11 個 usable。篩選條件寫在頁尾：暫定挑 flow alignment 至少 99%，packet coverage 至少 90%。

有四個原因

第一種，conn.log 把 DDoS 記成 0 packet，是 34-1 (Mirai) 和 60-1 (Gafgyt)。這些 DDoS packet 的 TCP checksum 是錯的，而 Zeek 預設會丟掉 checksum 錯的 packet，所以 conn.log 把這些 flow 的 packet 數記成 0，flow alignment 就掉下去了。但 packet 其實都還在 pcap 裡，60-1 的 packet coverage 是 100%。這個原因有文件和抽樣的佐證，但我沒有用 Zeek 重跑確認。
>
第二種，conn.log 比 pcap 早結束，是 52-1 和 49-1，都是 Mirai。conn.log 在 pcap 錄完之前就停了，後面那一段真實流量沒有 label。
>
第三種，非 IP packet 多，是 8-1 (Hakai)、20-1 和 21-1 (Torii)，還有 Honeypot-7-1 (door lock)。這四個的 packet coverage 偏低，已經確認是非 IP packet 太多，主要是 ARP。label 本身沒有問題。
>
第四種，flow alignment 偏低，是 Honeypot-4-1 (Philips HUE)、Honeypot-5-1 (Amazon Echo)、3-1 (Muhstik) 和 44-1 (Mirai)。


**實驗怎麼做**

> - 每個 scenario 的 flow alignment、packet coverage 來自第 2 頁的對齊程式輸出（`tests/iot23/results/*.json`）。
> - 第一列：Zeek 文件查 `ignore_checksums` 的預設值；34-1 抽檢 packet 的 TCP checksum；60-1 用 tshark 檢查 pcap 前 2,000 個 tcp/62336 的 packet。
> - 第二列：比對 conn.log 最後一筆的時間和 pcap 結束的時間。
> - 第三列：用 `results/*.json` 的 `pcap_packets` 減 `pcap_ip_packets` 算非 IP packet 數，和不在任何 labeled flow 範圍內的 packet 數比對；再用 tcpdump 看是哪一種 packet。
> - 第四列：抽樣看少掉的是哪一個 packet。

**被問到時**

> - **第一列的佐證是什麼？** Zeek 的 `ignore_checksums` 預設是 F，官方文件寫「Zeek discards any packets with checksum errors」，而且這些 flow 的 history 是 `C`，Zeek 定義為 bad checksum。34-1 抽檢的 packet 全部是 TCP checksum 錯誤；60-1 抽的 **2,000 個 TCP checksum 全錯**，TCP flags 全部設起來（FIN、SYN、RST、PSH、ACK、URG、ECE、CWR）、payload 只有 1 byte、都打向 162.248.88.215（整個 60-1 的 DDoS 對外打 16 個 IP）。有文件和抽樣支持，**但沒有用 Zeek 重跑確認**。
> - **為什麼 60-1 是 flow alignment 0.02%、packet coverage 100%？** Zeek 不計 checksum 錯的 packet，但仍會為每個 packet 寫下一筆 flow 記錄（5-tuple、`ts`，`duration` 空白，`orig_pkts` 和 `resp_pkts` 都是 0）。pcap 的 packet 落在這筆記錄的範圍內，所以算 covered；但 pcap 找到 1 個、Zeek 記 0 個，所以不對齊。實例：packet 時間 1569018198.313696、192.168.1.195:34509 → 162.248.88.215:62336，conn.log 有同一時間、同一個 5-tuple、0 packet、history 是 `C` 的 DDoS 記錄。60-1 另外 66 條 DDoS 記錄中，26 條是 UDP flood（14 條 udp/80，其餘在 udp/9307、20480、28416、33011），Zeek 正常計數（單條最多 66,027,354 packets），合計約 2.5 億，占 60-1 全部 2.71 億 packets 的 92%；剩下 40 條是 tcp/62336 反方向的記錄（history `^c`），同樣是 0 packet。
> - **第二列早結束多久？** 52-1 早 9.26 小時（packet coverage 61.4%）、49-1 早 0.83 小時（89.8%）；不在範圍內的 packet 幾乎全是 IP packet，也就是後段的真實流量沒有 label。這兩個的 flow alignment 都至少 99.9%。
> - **第三列的數字？** packet coverage 是 8-1 70.6%、20-1 82.2%、21-1 81.8%、Honeypot-7-1 85.3%；非 IP packet 占全部 packet 的 29.4%、17.8%、18.2%、14.7%。只看 IP packet 時，不在範圍內的只有 0 到 1 個。tcpdump 看：8-1 的 6,946 個全是 ARP（10/05 也驗過）、20-1 的 8,949 個全是 ARP、21-1 的 9,146 個全是 ARP、Somfy-01 是 ARP 623 個加 Loopback 509 個等。原因是分母效應：每個 scenario 的 ARP 都是幾千個，小 scenario 的 packet 總數少（8-1 全部只有 23,623 個）就顯得比例高；17-1 也有 19,326 個非 IP packet，但它總共 1.09 億個，比例就很低。
> - **第四列的數字與原因？** Honeypot-4-1 70.1%、Honeypot-5-1 79.6%、3-1 96.2%、44-1 94.9%。大多是 flow 最後一個 ACK 或 RST 落在 Zeek 記的 duration 之外（少 1 個 packet）；這個說法抽樣驗證過，其餘是**推測**。
> - **11 個 usable 是哪些？** Malware-1-1 (Hide and Seek)、7-1 (Linux.Mirai)、9-1 (Linux.Hajime)、17-1 (Kenjiro)、33-1 (Kenjiro)、35-1 (Mirai)、36-1 (Okiru)、39-1 (IRCBot)、42-1 (Trojan)、43-1 (Mirai)、48-1 (Mirai)。
> - **7-1 有一部分 Benign 對不到，為什麼還算 usable？** 7-1 的 Benign 有 75,955 條，只有 10,229 條（13.5%）對得回。對不到的 65,726 條全部是 196.118.25.105 的 DNS（UDP 53、S0），pcap 裡根本沒有這個 IP 的 packet。所以問題不在 label 的內容，而是 conn.log 有 pcap 裡沒有的 flow；拿 pcap 重播時這些 flow 不會出現，算的時候直接略過就好。Benign 只占 7-1 全部 1,145 萬條 flow 的 0.66%，整體 flow alignment 99.43%、packet coverage 99.36%，兩個門檻都過，所以算 usable。
> - **門檻定了嗎？** 還沒，要請老師看。另一個選項是 packet coverage 只算 IP packet：這樣 8-1、20-1、21-1、Honeypot-7-1 會過門檻，usable 變 15 個，多出 Hakai、Torii 兩個家族。目前用的是頁尾的門檻。
> - **usable 的 scenario 可以直接拿來算 detection rate 嗎？** 要小心，「usable」是 scenario 層級的。帶 payload 的攻擊 label 在這些 scenario 裡對齊很差：39-1 的 Attack 只對回 81／677（12.0%），C&C 683／1,530（44.6%）；42-1 的 FileDownload 0／6；48-1 的 C&C-HeartBeat-FileDownload 0／11。

## 第 4 頁　usable scenario 的流量組成

> 這一頁看 11 個 usable scenario 裡面是什麼流量，也回答 10 月 5 號留下的第一個問題：其他 scenario 有沒有 payload。
>
左邊的圖，每一列是一個 usable scenario。橫條是這個 scenario 裡，各種 label 的 flow 各占多少，加起來是 100%。顏色有五種：PortScan、Okiru、DDoS、Other malicious，還有 Benign。
> Other malicious 是把 C&C、Attack、FileDownload 合在一起。每個 malware scenario，是在 Raspberry Pi 上跑一個 malware sample 錄下來的；pcap 裡是那台設備錄製期間的全部流量，所以也會有 DNS、NTP 這些 Benign flow。
>
> 圖上要注意兩件事。第一，Other malicious 在 11 個 scenario 裡都不到 0.14%，圖上幾乎看不到，這本身就是重點。第二，17-1 (Kenjiro) 大約四分之一標成 DDoS，但內容其實是對一千多萬個不同的 IP 送 SYN，是 scan 的樣子，不符合 DDoS 的定義。
>
右邊兩點。第一，Malicious flow 幾乎都是內網的 IoT 設備對外送 SYN，沒有回應，也沒有 payload。沒有回應，在 Zeek 裡記成 S0。第二，scan 的 port 有：23 和 2323，也就是 Telnet；22，也就是 SSH；80、81、8080、8081；還有 37215 和 52869。
>
> 接回上次。上次看 Hakai，也就是 8-1，它的 C&C 只有 SYN，那時候不知道是不是單一樣本的特例。現在看來不是：這 11 個 usable scenario 的 malicious flow，幾乎都是沒有 payload 的 SYN。

**實驗怎麼做**

> - 圖的比例：統計 11 個 usable scenario 的 conn.log.labeled 裡每種 label 的 flow 數。
> - 「沒有回應、沒有 payload」：看 Zeek 的 conn_state 和 payload bytes。**S0** 是 Zeek 的 conn_state，意思是只看到 SYN、沒有回應。11 個 scenario 的 malicious flow 合計 99.16% 是 S0、0.03% 帶 payload。
> - port、目的 IP 數與 label 的實際內容：重新統計 20 個 malware scenario 的 conn.log。

**被問到時**

> - **所以可以在 flow 層級判斷嗎？** 帶 payload 的攻擊很少，所以多數**可以在 flow 層級判斷**，但這是**推論**，不是量出來的。旁證：ET Open 只對少數 port（例如 SSH）有門檻型的 scan rule，Suricata 版有 85 條帶 threshold 或 detection_filter 的 ET SCAN rule，39-1 的 SSH scan 就觸發十幾萬次；但 23、8080、8081、37215、52869 的對外 SYN scan **沒有對應 rule**。所以我的說法是「**ET Open 的 scan rule 有覆蓋缺口**」，不是「簽章 rule 抓不到 scan」。
> - **還有哪些帶 payload、本地要處理的？** 39-1 的 SSH 加密流量、48-1 對 tcp/23 的登入嘗試（從 port 推測）、35-1 的 DDoS、少量 C&C 下載。
> - **這些 port 是什麼？** 23 是 Telnet；2323 是 Mirai 拿來當 Telnet 替代 port 的**慣例**，IANA 登記的服務不是 Telnet；37215 是 Huawei HG532，CVE-2017-17215，Okiru、Satori 會用；52869 是 Realtek SDK 的 miniigd UPnP，CVE-2014-8361，列在 CISA KEV；8080、8081 是常見的替代 HTTP 管理 port。**資料裡只有 SYN，看不到 exploit 內容。**
> - **「幾乎」有多精確？** scan flow 的 S0 比例：1-1 是 97.6%，而且其中 1.6% 帶 payload；其餘 6 個查過的 scenario 是 100%。目的是外部公網 IP，是抽查各 scenario 第一筆 scan flow 看的；「只有 1 個來源 IP」在 1-1、7-1、9-1、17-1、33-1、48-1 是直接數 conn.log 確認的，39-1、43-1 只確認了「至少 1000 條 flow 的來源只有 1 個」。
> - **每條 flow 有幾個 packet？** 11 個 usable scenario、2.96 億條 flow，用 `orig_pkts` 加 `resp_pkts` 算：1 個 packet 的占 78.3%、2 個占 19.2%、3 個占 1.6%、4 個以上約 1%。多數 flow 就是 1 個 SYN（17-1 是 SYN 加重送共 2 個；48-1 是 2 或 6 個）。packet 數超過 100 的 flow 只占 0.02%，卻裝了 8.3% 的 packet，主要是 43-1、35-1 的 DDoS。
> - **IoT-23 的 label 怎麼定義？**（官方定義取自 IoT-23 官網，2026-10-17 讀取；「資料裡」是我對 20 個 malware scenario 的 conn.log 重新統計）
>   - **PartOfAHorizontalPortScan**：同一個 port、送出的 bytes 相近、打很多不同的目的 IP；資料裡幾乎 100% 是 S0，port 有 22、23、2323、80、81、8080、8081、52869（81 主要在 9-1 (Linux.Hajime)，約 257 萬條）。
>   - **Okiru**：「具 Okiru botnet 特徵」，判準同 Mirai（Okiru 是 Mirai 變種）。資料裡全是 tcp/37215 的 SYN、S0，幾乎一條 flow 一個目的 IP（7-1：11,333,397 條打 11,314,381 個 IP），行為上是 scan，不能說「Okiru 就是利用嘗試」。
>   - **DDoS**：大量 flow 打向**同一個**目的 IP。35-1 打 5 個 IP（tcp/80、992、22），43-1 打 1 個 IP（udp/27015），7-1 打 1 個 IP（udp/80），60-1 對外打 16 個 IP。例外是 17-1，見上面。
>   - **Attack**：嘗試利用有漏洞的服務（例如 telnet 暴力登入）。39-1、3-1 是 tcp/22 SF 打 200 到 350 個 IP；48-1 是 tcp/23、91% REJ、2,716 個 IP，從 port 推測是 SSH 或 Telnet 登入嘗試，**我沒看 payload**。
>   - **C&C、HeartBeat、FileDownload**（C&C 是 IoT-23 的 label 名稱，其他地方寫 C2）：C&C 只連 1 到 8 個 IP（IRC tcp/6667 或非標準 port，多數是 S0）；HeartBeat 是 response 小於 1 B 的週期性連線；FileDownload 是 response 大於 3 KB 或 5 KB 的下載（幾乎都是 tcp/80 SF）。
>   - **Mirai、Torii 是家族名稱，不是攻擊手法**：`Mirai` 這個 label 全部只有 2 條（52-1 的 C&C-Mirai），雖然很多 scenario 的家族是 Mirai。
> - **Benign label 可靠嗎？** 有疑點，做 detection rate 之前要先處理。35-1 (Mirai) 的 Benign 有 826 萬條（占 79%），其中 99.9% 是 tcp/23、S0；43-1 (Mirai) 的 2,057 萬條 Benign（30.6%）100% 是 tcp/23、S0；33-1 (Kenjiro) 的 138 萬條（2.5%）98.5% 是 tcp/8080、S0。這些行為**看起來和 Mirai 的 Telnet scan 很像**，這是**推測**，沒有驗證；但它們被標成 Benign，直接當 benign 的話 scan 會被算成誤報。1-1 (Hide and Seek) 的 46.9 萬條 Benign（46.5%）和 9-1 (Linux.Hajime) 的 2.3 萬條（0.35%）分別分散在 79,026 種和 4,233 種 (protocol, port)；Trend Micro 說這兩個家族都用自製的 P2P 通訊，所以**可能**是 P2P 流量，**這也是推測**。對照：17-1 (Kenjiro) 和 36-1 (Okiru) 的 Benign 只用到 34 種和 10 種 (protocol, port)，以 DNS、NTP、ICMP 為主，比較像正常流量。原因我**不確定**；IoT-23 官網只寫 Benign 是「連線中沒有發現可疑或惡意活動」，沒有說怎麼判斷。7-1 (Linux.Mirai) 的 Benign 見第 3 頁：86% 是 pcap 裡沒有的 DNS，對得回的 10,229 條我沒有另外分析。
> - **42-1 可以當正常 Benign 的對照嗎？** 不行。42-1 (Trojan) 有 99.86% 的 flow 被標成 Benign，但其中 44%（1,947 條）是連到外部 185.244.25.183 的 tcp/4975；我用 tshark 看過，是 IRC，packet 裡有 `NICK` 和 `NOTICE AUTH`。正常 Benign 的對照只能用 17-1、36-1。這條 IRC 是不是 C2，我**沒有查證**。

## 第 5 頁　實驗設定

這次主要測試完整的 ET Open rules，能不能直接掛在 Pi 上。
>
只量 IDS engine 的處理上限，engine 直接讀 pcap，沒有走 cli 到 DUT 再到 srv 這條。
> cli 和 srv 是測試用的 client 和 server，DUT 是被測的設備，也就是 gateway。10 月 5 號規劃的整體測試，是讓 packet 從 cli 經過 gateway 到 srv，inline 跑四種設定。這次先不走那條路，只把第三段 NFQUEUE 後面的 IDS engine 單獨拿出來，用 offline 的方式量。我預期這是整條管線最重的一段，inline 還要再加上 NFQUEUE 複製和排隊的成本。但前兩段，還有 inline，這次都沒有量。
>
下面的表格是實驗條件。
- Hardware 是 Raspberry Pi 4，4 GB。改用 Pi 4 是因為 Pi 3 Model B+ 找不到能穩定供電的線材；CPU 鎖在 1000 MHz，是為了避免過熱降頻，讓每次量測的時脈都一樣。
- Engine 是 Suricata 7.0.10 和 Snort 3.12.2.0。
- Rules 是 2026 年 10 月 11 號的 ET Open，大約 5.2 萬條。
- Traffic 是 IoT-23 的 14 個 scenario，下一頁會列出來。
>
> 後面的圖會用到幾個定義，先講一下。速度的單位是 kpps，就是每秒處理幾千個 packet，算法是 packet 數除以 engine 自己回報的處理時間。這個處理時間，是 engine 讀完整個 pcap 之後自己報的秒數，不包含 load time，也就是啟動和載入 rule 的時間。只有一個例外：Suricata 不掛 rule 的時候，改用另一種算法，叫差分法，細節被問到再講。
>
rule set 有三種：`empty` 是不掛任何 rule 的 baseline，`full` 是載入 ET Open 全部的 rule，`gw_corp` 是我們依 gateway 的需求挑出來的。
並且數據上我是將每個設定先暖機一次，再正式跑三次取中位數得到

**實驗怎麼做**

> 第 7、11、13 頁的 14 個 scenario 數據都是這樣量的：
> - **硬體**：Raspberry Pi 4 Model B Rev 1.4、4 GB、Debian 13（trixie）；CPU 鎖 1000 MHz。
> - **讀法**：offline，engine 直接讀 tmpfs 上的 pcap；single packet thread。
> - **matcher**：Suricata 用 `ac-ks`、Snort 3 用 `ac_bnfa`。
> - **rule**：各 engine 用各自版本的 ET rule。Suricata 版載入 52,606 條；Snort 版是 ET 的 Snort 2.9 rule 包，經 snort2lua 轉換後 52,445 條可載入（rule 包啟用的是 52,491 條）。
> - **流量**：14 個 scenario，各取主 pcap 的前 20 萬個 packets，不足的 4 個（20-1、42-1、Honeypot-7-1、Honeypot-4-1）用整檔；兩個 engine 讀同一個檔。
> - **kpps**：engine 回報的 packets ÷ engine 自報的處理秒數。**例外是 Suricata 的 `empty`**：它的自報時間不含 EOF 後約 0.7 秒的 flow 清理，所以改用**差分法**，「大 pcap 的牆鐘時間，減掉同切片前 500 packets 的牆鐘時間」。
> - **load time** = 牆鐘時間 − engine 自報處理時間。
> - **順序與次數**：`empty`／`full`／`gw_corp`、兩個 engine，全部在 2026-10-17 同一次開機跑完（`run_pi_scen2.sh`，12:50 到 18:56 UTC）。5 批依序是：錨點 → `empty` → Suricata 的 `full`／`gw_corp` 交錯 → Snort 3 的 `full`／`gw_corp` 交錯 → 錨點。每格 1 次暖機加 3 次正式，每一輪打亂順序，取 3 次的中位數。正式量測 348 次（含錨點 12 次），作廢 0。
> - **變異**：自報時間的 CV 中位數 0.51%、最大 6.9%（一次離群值）；Suricata `empty` 差分法的 CV 中位數 1.26%、最大 2.65%。
> - **Pi 狀態**：正式量測最高 65.2°C，`get_throttled` 全部是 0x0（沒有降頻），時脈約 1000 MHz；錨點（Honeypot-7-1、`full`）頭到尾，Suricata 差 −1.8%、Snort 3 差 −0.1%。
> - **守恆檢查**：packet 數全部守恆；bytes 有 9 次不守恆，都是 Snort 3 在 34-1，IP 分片使回報值偏大。

**被問到時**

> - **為什麼是 Pi 4，不是 3B+？為什麼鎖 1000 MHz？** 3B+ 曾經發生欠壓降頻，所以換板（這是之前實驗的紀錄，我沒有原始 log）。Pi 4 R1.4 在 Raspberry Pi OS 預設 `arm_boost=1` 下最高 1.8 GHz；官方寫 80°C 起逐步降頻、85°C 時 CPU 和 GPU 都降頻。沒有散熱的話，1.8 GHz 滿載約 30 秒就到 80°C，時脈亂跳，量測不可重現。所以鎖在 1000 MHz：600 秒 4 核滿載最高 77.4°C，沒有降頻。
> - **這是兩個 engine 的最快設定嗎？** 不是。兩邊用同一種 matcher：Debian arm64 的 Suricata 套件沒有 Hyperscan（Hyperscan 只支援 x86），`ac-ks` 是 Suricata 官方建議「沒有 Hyperscan 時」的選項；`ac_bnfa` 是 Snort 3 的預設，但 Snort 自己描述它是 low memory、不是最快，`ac_full` 才是。
> - **ET 有 Snort 3 的 rule 嗎？** ET 沒有另外產 Snort 3 原生 rule，Snort 版是 Snort 2.9 rule 包經 snort2lua 轉換。
> - **差分法是什麼？** 只用在 Suricata 的 `empty`。它的自報時間不含讀到 EOF 之後約 0.7 秒的 flow 清理，所以改用「大 pcap 的牆鐘時間，減掉同切片前 500 packets 的牆鐘時間」來算處理時間。其他組合都是 packets ÷ engine 自報的處理時間。
> - **差分法和自報時間差多少？** 在 flow 很多的 scan 流量上差很多：17-1 前 60 萬 packets，自報是 93.5 kpps，差分是 48.3 kpps。所以 `empty` 和其他 rule set 的比較，**在 scan 流量上要保守看**。
> - **那次離群值是什麼？** Suricata `gw_corp` 在 Honeypot-7-1，第 1 次 2.587 秒，另外兩次是 2.29、2.31 秒；次大的 CV 6.3% 是 Suricata `gw_corp` 的 3-1。
> - **數字穩不穩？** 錨點和 10/11 的主矩陣差都在 2.6% 以內。

## 第 6 頁　效能測試的 14 個 scenario

這是效能測試用的 14 個 scenario。
我們根據不同的流量型態挑選的 scenario，主要是測試 IDS 在遇到不同情況處理的速度如何。量速度不需要 label，所以不限定 usable；右邊打勾的，是同時也在第 3 頁 usable 裡的。
然後前 10 個都是 20 萬個 packet測試，最後 4 個整個檔案不到 20 萬，所以用整個檔。
>
> 每一列是一個 scenario，依 packet 數排：前 10 個都是 20 萬個 packet；最後 4 個不到 20 萬，用整個檔。這個順序和後面兩張速度圖一樣。「流量型態」是依 packet 特徵取的簡稱，後面的速度圖只寫 scenario 名稱，要看流量型態就回來看這張表。「packets」是實際送進 engine 的 packet 數，「平均 packet」是這些 packet 的平均大小，包含 header。最後一欄打勾的，表示它也是第 3 頁那 11 個 usable 之一。
>
> 由上往下看。前 4 個都是對外送 SYN 的 scan 或 probe，只是 port 不同。接著 3-1 是 SSH scan 加 IRC，1-1 是多個 port 加 UDP，34-1 是 TCP 和 UDP 混合。60-1 和 44-1 都是 UDP flood，一個是小 packet，一個是平均 1,360 byte 的大 packet。Honeypot-5-1 是 TLS 下載。最後 4 個不到 20 萬的，是 Honeypot-7-1 的 benign 流量、20-1 連 443 的 C2、42-1 的 file download，還有 Honeypot-4-1 的 benign 流量。
>
> 這頁要回答一個問題：前面說只有 11 個 usable，為什麼這裡用 14 個？因為兩種篩選回答的是不同的問題。detection rate 要拿 alert 跟 label 比，label 必須正確，所以要用那 11 個 usable。處理速度只需要真實的 packet，不讀 label，所以依流量特徵來挑，像是平均大小、payload 比例、TCP 還是 UDP、SYN 比例、目的 port 和目的 IP 的數量。特徵相近的只留一個，讓各種流量情況都有。
>
> 14 個裡面有 6 個也是 usable，就是打勾的 17-1、36-1、48-1、39-1、1-1 和 42-1。另外 8 個不在 usable，原因都跟 label 有關：有的沒有 label，有的 label 跟 pcap 對不上，20-1 是被 packet coverage 的門檻擋掉。packet 本身都是真實流量，拿來量速度沒有問題。

**實驗怎麼做**

> - **挑選**：`10_scenario_features.py` 算每個 scenario 主 pcap 前 20 萬 packets 的特徵，特徵相近的只取一個；特徵與數字在 `tests/ids_throughput/results/scenario_features.tsv`。
> - **特徵定義**：SYN 比例 = 只有 SYN 沒有 ACK 的 TCP packet 占全部 packet 的比例；payload 比例 = 帶 payload 的 packet 占比；目的 port、目的 IP 是不同值的個數。
> - **切片**：取主 pcap 的前 200,000 個 packets，不足的用整檔。用 packet 數而不是 MB 統一大小，因為 IDS 的成本主要在每個 packet、每條 flow；如果統一 MB，小 packet 的 scenario 會多出 20 倍以上的 packet。

**被問到時**

> - **為什麼不只用 11 個 usable？** 11 個 usable 的平均 packet（前 20 萬 packets）都在 60 到 124 B，其中 9 個 SYN 比例至少 91%，幾乎都是 SYN scan。只用它們，會失去 UDP flood、大 packet（44-1 平均 1,360 B）、TLS 下載、benign IoT 這些流量型態，也會失去「Snort 3 `full` 在 TLS 下載（Honeypot-5-1）仍有 80.8 kpps」這個反例。
> - **另外 5 個 usable 為什麼沒選？** 33-1、35-1、43-1、9-1、7-1 的特徵和已選的 scan 幾乎一樣（平均 60 到 78 B、SYN 97.8% 到 99.5%）。例如 7-1 是 60.2 B、SYN 99.3%、99.4% 打 tcp/37215，和已選的 36-1（60.1 B、SYN 99.85%、tcp/37215）幾乎相同。
> - **8 個不在 usable 的各自為什麼？** 3-1 (Muhstik)：flow alignment 96.2%。34-1 (Mirai)、60-1 (Gafgyt)：conn.log 把 DDoS 記成 0 packet；60-1 那些 checksum 錯的 packet 也是 malware 自己送出的，不是 capture 的問題。44-1 (Mirai)：flow alignment 94.9%。20-1 (Torii)：非 IP packet 多，packet coverage 82.2%。Honeypot-5-1 (Amazon Echo)：flow alignment 79.6%。Honeypot-4-1 (Philips HUE)：flow alignment 70.1%。Honeypot-7-1 (door lock)：沒有 label 檔。

## 第 7 頁　`full` 的處理速度

這一頁是掛 `full`，也就是 ET Open 全部 rule 的處理速度。

左邊是 Suricata，右邊是 Snort 3。每一列是一個 scenario，順序和上一頁的表一樣，分成三群：第一群是 scan 和混合流量，第二群是 flood 和下載，這兩群都是 20 萬個 packet；最後一群是不到 20 萬的那 4 個。
橫軸是 kpps，就是每秒處理幾千個 packet，用的是 log 刻度，每隔兩格就差 10 倍。
> 所以圖上看起來只差一小段，實際上可能差了十倍以上。

圖上有兩種點：空心的灰圈是 `empty`，也就是不掛 rule 的 baseline；深色的方塊是 `full`。
兩個點離得越遠，代表掛上 rule 之後慢得越多，也就是 rule 的成本越高。
> 每個 panel 最右邊那一欄 `full time`，是處理完這個 scenario 全部 packet 花了幾秒。時間只能在 packet 數一樣的列之間比；要跨 scenario 比快慢，要看橫軸的 kpps。
>
> Suricata 的 `empty` 用的是差分法，在 scan 流量上要保守看。

下面三個重點。
第一，Suricata 掛 `full`，14 個 scenario 都跑得動，最慢的是 39-1 (IRCBot) 的 15.5 kpps。
> 最快的是 60-1 (Gafgyt)，176 kpps。和 `empty` 比，掛上 `full` 之後大約剩 2 到 8 成的速度。

第二，Snort 3 掛 `full`，有 9 個 scan 和 flood 的 scenario 不到 1 kpps，20 萬個 packet 要跑 217 到 539 秒。
但是看空心的灰圈，Snort 3 不掛 rule 的時候，14 個 scenario 都有 38.6 到 97.9 kpps；掛上 `full` 之後，那 9 個只剩原本的 2% 不到。所以慢的不是 engine 本身，而是 rule。

第三，是哪些 rule 讓 Snort 3 變慢？是帶 IP 清單的 rule，大約占全部 rule 的 3%。把這些 rule 拿掉，17-1 (Kenjiro) 的速度從 0.37 變成 64.3 kpps。
> 這是在 17-1 前 60 萬個 packet 上量的；另外三份流量也量過，被問到再講。圖上其他 scan 和 flood 的 scenario 是不是同一個原因，是我的推論，沒有一個一個量。

所以 Snort 3 掛 `full` 沒辦法直接用。接下來看 memory。

**實驗怎麼做**

> - `empty`、`full` 兩個 engine、14 個 scenario：第 5 頁的流程（2026-10-17 同一次開機，每格 1 次暖機 + 3 次，取中位數）。
> - **時間欄**：engine 自報處理時間的 3 次中位數；不到 100 秒寫一位小數，100 秒以上寫整數。`empty` 不放時間，因為 Suricata 的 `empty` 用差分法，沒有直接的處理時間。
> - **第三點的實驗叫 `sel`**：`full` 扣掉 header 逗號至少 8 個（也就是帶長 IP 清單）的 1,559 條 rule，Snort 3 載入數從 52,445 變 50,886（兩個 engine 移除同一批 sid）。`sel` 是 10/11 的主矩陣（`run_pi_main.sh`）量的，不是 10/17 那次開機；主矩陣有 4 份流量：17-1 (Kenjiro) 前 60 萬 packets、3-1 (Muhstik) 整檔、Honeypot-5-1 (Amazon Echo) 前 14 萬 packets、Honeypot-7-1 (door lock) 整檔，4 份都量了 `full` 和 `sel`（結果見被問到時）。**`sel` 是依成本挑的，不是依偵測價值挑的。**

**被問到時**

> - **帶 IP 清單的 rule 是哪些？** 1,559 條：TOR 803 條（出口節點 121 加中繼節點 682，每條 10 個 IP）、CINS 596 條（每條 50 個）、DROP 69 條（20 到 21 個）、Threatview 42 條（50 個）、COMPROMISED 38 條（30 個）、其他 11 條；合計 42,592 個 **IP／網段項目**。不要說「TOR 出口節點 803 條」。
> - **`sel` 只測了 17-1 嗎？** 不是。主矩陣在 4 份流量上都量了 Snort 3 的 `full` → `sel`：
>   - 17-1 (Kenjiro) scan，前 60 萬 packets：0.37 → 64.3 kpps（176 倍；`full` 實際是 366 pps，`empty` 是 104 kpps）
>   - 3-1 (Muhstik) SSH scan＋IRC，整檔：0.56 → 21.2 kpps（38 倍）
>   - Honeypot-5-1 (Amazon Echo) TLS 下載，前 14 萬 packets：74.5 → 90.1 kpps（1.2 倍）
>   - Honeypot-7-1 (door lock) benign，整檔：21.4 → 22.5 kpps（1.1 倍）
>
>   Suricata 在 4 份上都幾乎不變（`sel` 與 `full` 差不到 3%）。結論：IP 清單 rule 是 Snort 3 在 scan 流量下變慢的主因；TLS 下載和 benign 流量上，Snort 3 本來就不慢。這 4 份是主矩陣的切片，長度和第 6 頁的 20 萬 packets 不完全一樣，所以數字和圖上不一定相同（例如 Honeypot-5-1 圖上 Snort 3 `full` 是 80.8）；Honeypot-7-1 兩邊是同一個檔，都是 21.4。數據在 `tests/ids_throughput/results/pi/pi_R2a1`、`pi_R2a2`、`pi_R2b`、`pi_R1`。
> - **為什麼 IP 清單會拖慢 Snort 3？** 可能的機制，**是不是本實驗的成本來源沒有驗證**：Snort 3 開發文件寫「Rules w/o fast patterns … evaluated for each packet for which the group is selected. These are definitely bad for performance.」，header 的 IP 清單是逐項比對；Talos 2012 建議 IP-only rule 改用 reputation。Suricata 有 radix tree 的 IP-only engine（原始碼看得到），每條 flow 每個方向查一次。兩邊 rule 文字也不同：Snort 版的 TOR rule 有 `flags:S`，Suricata 版用 `threshold`。Snort 3 `full` 的速度大致隨 SYN 加 UDP packet 的比例下降，和這個解釋一致，但這是**推論**。要確認得用 Snort 3 的 rule profiler 與 `suricata --engine-analysis`。
> - **Suricata 會被這批 rule 拖慢嗎？** 幾乎不會：`sel` 與 `full` 差不到 3%。所以「帶 IP 清單的 rule 是問題」只限於 Snort 3。
> - **Snort 3 `full` 另外 5 個 scenario 呢？** 20-1 是 6.3、42-1 是 1.5、Honeypot-5-1 是 80.8、Honeypot-7-1 是 21.4、Honeypot-4-1 是 1.8 kpps。所以 14 個 scenario 中有 12 個約 6.3 kpps 以下，不能說「Snort 3 只有在 scan／flood 下不能用」。
> - **`full` 剩 `empty` 的幾成？** Suricata 是 16%（Honeypot-7-1）到 81%（Honeypot-5-1）；scan 流量上 Suricata 的 `empty` 是差分法，數字要保守看。Snort 3 有 12 個只剩 0.4% 到 7.9%（17-1、36-1 最低，20-1 最高），另外兩個本來就不慢：Honeypot-7-1 是 26%、Honeypot-5-1 是 85%。不到 1 kpps 的那 9 個，最高也只有 1.6%（1-1、34-1）。
> - **時間欄怎麼比？** 例如 Suricata `full` 的 42-1 是 1.2 秒、48-1 是 3.0 秒，但 42-1 只有 24,484 個 packets，48-1 有 200,000 個；換成 kpps，42-1 是 20.6、48-1 是 67.1，42-1 反而比較慢。
> - **只用兩個 engine 都有的 rule 比呢？** 做過 `common`（兩個 engine 都載得進的 sid 交集），結果和 `full` 幾乎相同。同一個 sid 在兩個 rule 包裡的文字不同，結構一致的只有 38.7%，所以 `common` 只是近似。

## 第 8 頁　Memory：`full` 在 1／2／4 GB

> 這一頁看 memory。10 月 5 號說過，完整的 ET Open 在小型 ARM 上很吃 memory，這是社群的經驗；Pi 3B+ 只有 1 GB，要量過才知道。這一頁就是量的結果。
>
這一頁是測試在memory比較低的時候會不會對處理效能有影響
表格用的是 39-1 (IRCBot) 的 20 萬個 packet，掛 `full`。選它是因為 兩個 engine 在這個 scenario 的處理速度較慢、memory 也用得最多，而且它是 usable 的。
>
> 第一欄 Memory，是 Pi 可以用的 memory。我們用韌體的 `total_mem` 設定，把 4 GB 的 Pi 限制成 2 GB 和 1 GB；4 GB 就是沒有限制，這一列就是上一頁 39-1 的數字。後面每個 engine 各兩欄：kpps 是處理速度，RSS 是 engine 實際占用的實體 memory，都是三次的中位數。
>
> 重點是：1 GB 的時候，Suricata 慢了大約 13%，從 15.5 掉到 13.4 kpps。Snort 3 不受影響，三個等級都是 0.38 到 0.39 kpps，RSS 都是 376 MB。
>
> 要注意 1 GB 那一列，Suricata 的 RSS 變成 719 MB，這不是它用得比較少。4 GB 的時候它要用 1,240 MB，1 GB 放不下，放不下的部分就被壓進 zram。zram 是把一部分 memory 壓縮起來當 swap 用，Raspberry Pi OS 預設就開著。被換出去的部分不算在 RSS 裡；另外量到被換出去的量，也就是 VmSwap，最高大約 794 MB。所以不能說 memory 不是問題。
>
> 1 GB 多花的時間大約 2 秒。我推測這個代價比較接近一段固定的換頁時間，所以百分比會隨 pcap 的長短改變；長時間運作的影響，要等 inline 測試才知道。
>
> 另外提醒一下，1 GB 對應的是 Pi 3B+ 的 memory 大小，但 CPU 和 memory 頻寬還是 Pi 4，所以不能直接當成 3B+ 的結果。

**實驗怎麼做**

> - **限制 memory**：改 `/boot/firmware/config.txt` 的 `total_mem`，重開機後生效；4 GB 是不設限制。
> - **4 GB 那一列**：直接用第 7 頁（`full`）和第 11 頁（`gw_corp`）的 39-1 數據，也就是 2026-10-17 同一次開機的量測。
> - **2 GB、1 GB**：2026-10-18 用同一個 39-1 pcap 另外量（`run_pi_mem_scen.sh`，結果在 `tests/ids_throughput/results/pi/pi_mem39_{2gb,1gb}.*`）。每個等級重開機後跑一次，`full`、`gw_corp` × 兩個 engine；每格 1 次暖機 + 3 次正式，取中位數。
> - **數字怎麼算**：kpps = 200,000 ÷ 自報處理時間的中位數；RSS = 每次量到的峰值 RSS（maxrss），取 3 次的中位數。
> - **swap**：只量系統預設的 zram 開。
> - **時脈**：開跑前先等 `vcgencmd` 回報的 ARM 時脈真的降到 1000 MHz 才開始。原因是剛開機的一兩分鐘內，kernel 已經把上限設成 1000 MHz，但 CPU 實際還跑在 1800 MHz（Snort 3 會快 1.76 倍）。這組正式量測的時脈全部是 1000 MHz。
> - **VmSwap**：矩陣跑完後，Suricata 每個 rule set 再單獨跑一次，記錄行程的 VmSwap 峰值；所以它和 RSS 中位數不是同一次量的，不要相加。
> - 這組量測全部正常結束，沒有 OOM。Snort 3 `full` 在 39-1 一次約 8.5 分鐘。

**被問到時**

> - **Snort 3 的 2 GB 為什麼寫 0.38？** 實際是 0.376 kpps，比 4 GB 慢約 4%，超出 3 次之間的差距，所以照實寫；但 1 GB 又回到 0.387，RSS 只有 376 MB，不是 memory 造成的。
> - **為什麼選 39-1？** Suricata 掛 `full` 和 `gw_corp` 時，39-1 都是 14 個 scenario 裡最慢、RSS 最大的（1,240／977 MB，其他 13 個是 1,184／918 MB）；Snort 3 也排在最慢的前幾個；而且它在 11 個 usable 裡。
> - **RSS 會隨 scenario 變嗎？** 主要由 rule 決定：14 個 scenario 中有 13 個的 Suricata RSS 完全相同（`full` 1,184 MB、`gw_corp` 918 MB），只有 39-1 比較大（1,240／977 MB）。所以投影片上的 RSS 都用 39-1。
> - **2 GB 會比較慢嗎？** 39-1 幾乎沒有差（15.3 對 15.5）。
> - **沒有 swap 會怎樣？** **沒有量**。這組只量了系統預設的 zram 開；有 zram 時全部正常結束，只是 Suricata 變慢。

## 第 10 頁　`gw_corp`：本地 IDS 掛哪些 rule

這是是我們挑出來的 rule set，叫做 `gw_corp`，
> 意思是依公司 gateway 的需求，從 ET Open 挑出來、掛在本地 IDS 的 rule。

> 表格是把上一頁圖上的 category 逐一判斷。第一欄是判斷：打勾是全部保留，三角形是只留一部分，叉叉是不保留。第二欄是屬於這一列的 category，上一頁點名的 15 個都在表裡，其他的用數量帶過。第三欄是理由。最後一欄是 rule 數，箭頭左邊是挑之前的條數，右邊是放進 `gw_corp` 的條數。五列左邊加起來是 52,606，就是 `full`。
>
> 由上往下五列。
>
我們保留了全部跟入侵相關的規則
> 第一列，全部保留，38,399 條全部留下，理由是和入侵直接相關。這裡有 MALWARE、PHISHING、EXPLOIT 這些大的 category，還有其他 40 個。
> 像 SCAN、DOS、TELNET。公司內網什麼平台都有，所以我們不依平台排除。gateway 又看得到內網和外網兩個方向，被感染的主機對外 scan、連 C2，還有外面對內網的攻擊，它都看得到，所以 SCAN、DOS、TELNET 也全部保留。
>
第二列，INFO 和 CHAT 只留 IRC，4,585 條只留 12 條。因為 botnet 常拿 IRC 當 C2，這次的 3-1、34-1、42-1 都有 IRC；其他的 INFO 只是資訊。
>
第三列，DYN_DNS、HUNTING 和 TA_ABUSED_SERVICES 不保留。原因是 ET 官方自己說明，這些 rule 觸發了不代表是攻擊。例如 HUNTING，ET 說只建議在主動調查威脅的時候用。
>
第四列，RETIRED、P2P、REMOTE_ACCESS 這些，一共 12 個 category 不保留，839 條。它們是在辨識有人在用某種服務，或是針對過時的技術，比較像公司政策的問題，不是攻擊。
>
第五列，TOR、CINS、DROP 這些，一共 6 個 category 不保留，1,216 條。它們是 IP blocklist，每條 rule 就是一串已知的惡意 IP，
> 不看 packet 內容。這種只比對 IP 的工作，不需要 IDS 去檢查內容，放在前面專門查 IP 的地方比對就好。第 7 頁也看到，把它們寫成 rule 會讓 Snort 3 很慢，這算是一個佐證。
>
> 要強調的是，這張判斷表是我們的分析，不是驗證過的偵測價值，所以想請老師看看這樣挑合不合理。

**實驗怎麼做**

> - `gw_corp` 由 `tests/ids_throughput/12_gateway_rule_corp.py` 產生；每個 category 的判斷在 `results/rule_category_decisions_corp.tsv`，說明在 `RULE_CATEGORIES_corp.md`。
> - 只依 category 判斷，**沒有用 metadata**；INFO、CHAT 用 `msg` 含 IRC 篩出 12 條。
> - 排除 IP blocklist 時，除了整個 category，還用「rule header 裡的逗號至少 8 個」把其他 category 裡帶長清單的 rule 一起排除；`gw_corp` 裡這種 rule 是 0 條。這個條件也篩到了第一列裡 21 條有比對內容的 rule（20 條的長清單其實是 port，1 條是 IP 清單加上內容比對），所以第一列實際放進 rule 檔的是 38,378 條（被問到時）。
> - 保留的 rule 如果要靠別的 rule 先設定 flowbit 才會觸發，就把那些 rule 也補進來（121 條）。
> - Snort 3 版依 sid 對應，少的是 Snort rule 包裡沒有的 sid。
> - category 的說明依 ET 官方的 category 說明（community.emergingthreats.net 的 rule categories 文章）。

**被問到時**

> - **`gw_corp` 總共幾條？** **38,511 條**（Snort 3 版 38,086 條），約是 `full` 的 73%。算法是 38,378 + 12 + 121：38,378 是第一列在量測用 rule 檔裡的條數（見下一題），12 是第二列，121 條是 **flowbits 依賴**：有些保留下來的 rule，要靠別的 rule 先設定 flowbit 才會觸發，所以把那 121 條也補進來。這 121 條來自 INFO 78 條、HUNTING 40 條、GPL_CHAT 3 條（其中 77 條本身也會產生 alert），所以 `gw_corp` 的 rule 檔裡其實有 81 條 INFO、40 條 HUNTING；表格的箭頭右邊不含這 121 條。
> - **第一列寫 38,399 → 38,399，量測用的 rule 檔也是 38,399 條嗎？** 不是。38,399 是 `gw_corp` 應該有的樣子；量測用的 rule 檔裡，這 50 個 category 只有 38,378 條。差的 21 條，是被篩長 IP 清單的條件誤篩：排除 IP blocklist 時，除了整個 category，還用「rule header 逗號至少 8 個」把其他 category 裡帶長清單的 rule 一起排除，這個條件也篩到第一列的 21 條。其中 20 條的長清單其實是 port（header 列了 10 到 13 個 port），1 條是 29 個 IP 的清單加上 content 比對。分別是 MALWARE 14 條（Emotet、zgRAT 的 C2 流量）、EXPLOIT 5 條（HeartBleed、FREAK）、SCADA 1 條、ADWARE_PUP 1 條。它們都有比對內容，不是 IP blocklist，照這頁的原則應該保留，之後要加回。這 21 條在 14 個 scenario 沒有觸發，只占約 3.85 萬條的 0.05%，**推測**對結果影響很小，但**沒有量**。（依據：兩個 engine 掛 `full` 的 112 次量測，每次的 sid 統計都在 `~/datasets/throughput/runs_pi/pi_scen2_{S,N}/*/sids.txt`，這 21 個 sid 一次都沒有出現。）
> - **第二列的 12 條？** INFO 4,548 條只留 3 條、CHAT 37 條只留 9 條，都是 IRC 相關（`msg` 含 IRC）。
> - **第三、四列各是哪些？** 第三列：DYN_DNS 6,096、HUNTING 1,351、TA_ABUSED_SERVICES 120，共 7,567 條。第四列：RETIRED 408、FILE_SHARING 190、REMOTE_ACCESS 86、P2P 80、GAMES 23、INAPPROPRIATE 1，加上 6 個舊版 GPL category（GPL_CHAT 17、GPL_ICMP 14、GPL_RETIRED 9、GPL_INFO 5、GPL_P2P 5、GPL_REMOTE_ACCESS 1），共 839 條。
> - **第五列是哪些？** TOR 803、CINS 299、DROP 68、THREATVIEW 22、COMPROMISED 19、CNC 5，共 1,216 條（header 裡約 25,924 個 IP／網段項目）。ET 的說明都是依 IP 清單產生、用來擋已知惡意 IP 的 rule。CNC 的 5 條清單不長，但也是只比對 IP。
> - **為什麼 IP blocklist 不放 IDS？** 它們只比對 IP、不看內容，本質上是 blocklist。這種查詢用專門查 IP 的資料結構做就好（例如防火牆的 IP set，或 Snort 3 的 reputation、Suricata 的 IP reputation），不需要 IDS 逐 packet 檢查；Cisco／Talos 也公開建議 IP-only 的 rule 改用 reputation。第 7 頁 Snort 3 被拖慢是實測上的佐證，不是主要理由。
> - **category 數對得起來嗎？** 第 9 頁點名的 15 個全部在表裡：第一列 10 個、INFO、DYN_DNS 和 HUNTING、RETIRED、TOR，共 15；「其他 58 個」是 40 + 1（CHAT）+ 1（TA_ABUSED_SERVICES）+ 11 + 5 = 58；category 數 50 + 2 + 3 + 12 + 6 = 73；rule 數 38,399 + 4,585 + 7,567 + 839 + 1,216 = 52,606。
> - **不保留的 rule 之後放哪？** IP blocklist（第五列）打算改用 ② nftables 的 IP set，在管線前段比對，**還沒實作、沒量**。接回 9/21：當時**提過** blocklist **可以**直接灌進 nftables set，是候選做法，不是定案。第三、四列的 15 個 category 交給雲端分析，或不需要。這也對應研究目標：不放本地的 category，就是**雲端卸載的候選**。
> - **nftables set 不會隨清單變慢嗎？** set 用 hash 或紅黑樹實作：單一 IP 查詢約常數時間，CIDR 區間約對數成長，不是「完全不隨清單長度增加」。**這部分沒有實作、沒有量測。** ET 本身也提供防火牆用的 IP 清單（`rules.emergingthreats.net/fwrules/`）。
> - **有用 ET 的 confidence 或 severity 嗎？** 沒有，`gw_corp` 沒有用 metadata，只依 category。
> - **POLICY 呢？** 這份 rule 包的 73 個 category 裡沒有 POLICY，ET 已經併入 INFO。

## 第 11 頁　`gw_corp` 的處理速度

> 這一頁是掛 `gw_corp` 的處理速度。
>
圖的表示跟前面 full 的數據相同
> 圖的看法和第 7 頁一樣：左邊 Suricata、右邊 Snort 3，每一列一個 scenario，橫軸是 kpps、log 刻度。這次多了一種點：空心灰圈是 `empty`，深色方塊是 `full`，engine 顏色的實心點是 `gw_corp`。實心點在方塊的右邊，代表 `gw_corp` 比 `full` 快，離得越遠，快得越多；實心點越靠近空心圈，代表挑完之後剩下的 rule 成本越小。最右邊那一欄換成 `gw_corp time`，看法和第 7 頁一樣。
>
> 兩個重點。
>
> 第一，Suricata 和 `full` 差不多，只快了 1% 到 26%。最慢還是 39-1，15.8 kpps；最快是 60-1，178 kpps。
>
> 第二，Snort 3 在 14 個 scenario 都至少有 11 kpps。最慢是 44-1 (Mirai) 的 11.4，最快是 Honeypot-5-1 (Amazon Echo) 的 94.5。`full` 的時候不到 1 kpps 的那 9 個，全部拉回來了，例如 17-1 (Kenjiro)，處理時間從 532 秒變成 2.5 秒。
>
> Suricata 挑過 rule 之後，速度幾乎不變，這是偵測面完整的代價。memory 有沒有改善，看下一頁。

**實驗怎麼做**

> - 和第 7 頁同一批：2026-10-17 同一次開機，Suricata 一批、Snort 3 一批，每一批都是 `full` 和 `gw_corp` 交錯跑，每格 1 次暖機 + 3 次正式，取中位數。`empty` 同第 7 頁（Suricata 用差分法）。
> - rule 數：Suricata 38,511 條、Snort 3 38,086 條；packets 同第 6 頁。
> - 時間欄：`gw_corp` 自報處理時間的 3 次中位數，格式同第 7 頁。
> - load time = 牆鐘時間 − engine 自報處理時間，取 14 個 scenario 全部正式量測的中位數。

**被問到時**

> - **rule 數量和測試的 packet 數量？** rule 數 Suricata 38,511 條、Snort 3 38,086 條；packets 見第 6 頁，每個 scenario 取前 20 萬個，4 個不足用整檔。
> - **為什麼 Snort 3 快這麼多、Suricata 幾乎不變？** 第 7 頁 `sel` 扣掉的，是 header 帶長 IP 清單的那批 rule（Snort 3 版 1,559 條）；`gw_corp` 一條都沒有（第 10 頁第五列的 IP blocklist，加上第一列裡被同一個條件篩掉的 21 條）。`sel` 實驗（主矩陣的 4 份流量，見第 7 頁被問到時）顯示 Snort 3 在 scan 流量下被拖慢的主因就是這批 rule，所以 `gw_corp` 在 Snort 3 快了 9.6 到 213 倍。Suricata 本來就幾乎不受它們影響（`sel` 和 `full` 差不到 3%），而 `gw_corp` 仍保留約 73% 的 rule，所以只快 1% 到 26%。**但這個因果對這 14 個 scenario 是推論**：`gw_corp` 同時也拿掉了 DYN_DNS 等 8,406 條，沒有單獨量，只是和 `sel` 實驗的結果一致。
> - **範圍與倍數？** Suricata `gw_corp` 是 15.8（39-1）到 178 kpps（60-1），只比 `full` 快 1.01 到 1.26 倍，最多的是 Honeypot-7-1。Snort 3 `gw_corp` 是 11.4（44-1，大 packet 的 UDP）到 94.5 kpps（Honeypot-5-1），在 12 個 scenario 比 `full` 快 9.6 到 213 倍，17-1 最多；Honeypot-5-1 和 Honeypot-7-1 本來就不慢，只快 1.17 和 1.14 倍。
> - **最差情況換成 Mbps 是多少？** Suricata 最慢 15.8 kpps，是 39-1，平均 124 B，約 15.7 Mbps；Snort 3 最慢 11.4 kpps，是 44-1，平均 1,360 B，約 124 Mbps。所以這個上限要用 pps 講，而且要說明流量型態。

> - **為什麼目的 IP 分散時 Suricata 變慢？** 目的 IP 很分散時，Suricata 連 `empty` 都變慢。我**推測**是新 flow 的建立成本，**沒有驗證**。幅度要保守講：差分法的 48-1 到 36-1 是 127 掉到 25.8 kpps，包含 EOF 後的 flow 清理；用自報時間是 138 掉到 66.4 kpps，約 2.1 倍。要先排除的混淆因素：Debian 預設的 `suricata.yaml` 開了 eve 的 `flow` 事件，每條 flow 結束寫一筆 JSON；驗證方法是關掉 eve `flow`、調大 `flow.memcap` 與 `hash-size`，各跑一次。
> - **Suricata 對 rule 數不敏感嗎？** 不能籠統這樣說。`gw_corp`（約 3.9 萬條）比 `full`（約 5.3 萬條）只快 1 到 26%；這輪只比了這兩種 rule 數，rule 數少很多時會怎樣**沒有量**。
> - **load time 有變嗎？** load time 是啟動、載入 rule 的時間：Suricata 從 34.9 秒降到 24.7 秒；Snort 3 從 26.3 秒降到 19.3 秒（14 個 scenario 全部正式量測的中位數）。
> - **load time 的基線？** `empty`：Suricata 0.26 秒、Snort 3 0.23 秒（中位數；Suricata `empty` 的牆鐘減自報時間含 EOF 後的 flow 清理，逐 scenario 0.25 到 6.7 秒，39-1 最大）。

> - 同第 8 頁：和 `full` 是同一批量測（`run_pi_mem_scen.sh`，`full`、`gw_corp` × 兩個 engine 一起跑）。
> - 4 GB 那一列是第 11 頁 39-1 的數據（2026-10-17）；2 GB、1 GB 是 2026-10-18 另外量的，zram 開，每格 1 次暖機 + 3 次取中位數，開跑前等 ARM 時脈降到 1000 MHz，正式量測全部是 1000 MHz。
> - VmSwap 峰值是 Suricata `gw_corp` 另外單獨跑一次取樣的。

**被問到時**

> - **Snort 3 三格為什麼都寫 20.0？** 實際是 20.00、19.89、19.90 kpps，差 0.5%，比同一級 3 次之間的差距還小，是量測誤差。
> - **其他 scenario 的 RSS？** Suricata 14 個 scenario 中有 13 個完全相同，都是 918 MB（`full` 是 1,184 MB），只有 39-1 比較大（977 MB）。Snort 3 `gw_corp` 是 290 到 360 MB，最大是 48-1 的 360 MB（`full` 是 433 MB）。`empty` 的基線：Suricata 165 MB、Snort 3 121 MB。

> - **2 GB 會比較慢嗎？** 39-1 幾乎沒有差（15.7 對 15.8）。
> - **`gw_corp` 沒有 swap 會怎樣？** **沒有量**，同第 8 頁，只量了系統預設的 zram 開。

## 第 13 頁　結論與下一步

> 這一頁把兩個 engine、兩種 rule set 的結果整理在一起。
>
> 表格每一列是一個 engine 掛一種 rule set，單位是 kpps。每個 scenario 先取三次的中位數，再對 14 個 scenario 算最慢、中位數、平均和最快，也就是 Min、Median、Mean 和 Max。平均是算術平均，每個 scenario 的權重一樣，跟它有幾個 packet 無關。平均會被少數很快的 scenario 拉高，例如 Snort 3 `full` 的平均是 8.4，主要是 Honeypot-5-1 的 80.8 撐起來的，所以我們以中位數為主。
>
> 從表上看兩件事。第一，Suricata 挑不挑 rule 幾乎一樣，中位數是 36.4 和 39.9 kpps。第二，Snort 3 一定要先挑 rule：`full` 的中位數只有 0.81 kpps，挑成 `gw_corp` 之後是 31.4 kpps。
>
> 所以我們的選擇是：以 Suricata 為 base，實作能接雲端的 gateway。理由有兩個。第一，效能不被 rule 綁住，rule 可以照偵測需求挑。這和第 10 頁「偵測面完整優先、最後的 IDS 可能自己實作」是同一件事；如果用 Snort 3，rule 怎麼寫會直接決定它能不能用。第二，掛 `gw_corp` 的時候，Suricata 在 14 個 scenario 裡有 10 個比 Snort 3 快，中位數也是 39.9 比 31.4。
>
> 要說明的是，這是依取捨做的選擇，不是數據證明 Suricata 全面比較好。Suricata 的代價是 memory，這在第 8 頁和第 12 頁看過；Snort 3 的 memory 小很多。這個結論也只在這輪的範圍內成立：Pi 4 鎖 1000 MHz、offline、single packet thread、2026 年 10 月 11 號的 ET Open，流量只有 IoT-23。「能接雲端」是接下來要做的設計，這輪還沒有實作。
>
> 下一步的規劃，還有想請老師確認的幾件事，等一下討論的時候再講。

**實驗怎麼做**

> - 數字是第 7、11 頁同一批數據（2026-10-17 同一次開機；`results/pi/pi_scen2_{S,N}.summary.csv` 的 `pps_med`，每個 scenario 3 次中位數），對 14 個 scenario 取 Min、Median、算術平均、Max。

# 附錄：不要犯的錯

**範圍與定位**
- ❌ 不要說這個 gateway 只保護 IoT：保護範圍是**公司內網與外網之間**，內網有桌機、伺服器、手機和 IoT 設備；挑 rule、選 dataset 都不能假設後面只有 IoT
- ❌ 不要說最後的 IDS 一定直接用 Suricata 或 Snort：可能是自己實作（基於 Snort／Suricata），所以 rule set 以偵測面完整為優先，不是只看最快
- ❌ 不要介紹 RFC 9411：上次已經介紹過；被問到才說「效能測試流程沿用上次的規劃」
- 對齊方法上次已經講過：第 2 頁只在 flow alignment 的定義帶過，不要重講一遍
- ❌ 不要把 offline 數字說成 inline throughput／gateway 轉送速度：這輪量的是 IDS engine 的 offline 處理上限；「整條管線最重」「inline 更慢」只是**預期**，①② 與 inline 都沒量
- ❌ 不要把 alert 數說成 detection rate：這輪**沒有量 detection rate**；兩個 engine 的 alert 數也不能直接比（Snort 3 沒有載入 snort2lua 產生的 `event_filter`）
- ❌ 不要說「Pi 3B+ 的結果」：這輪用的是 Pi 4（4 GB）鎖 1000 MHz；1 GB 只對應 3B+ 的 memory 容量，CPU 與 memory 頻寬仍是 Pi 4
- ❌ 不要說「IoT-23 對齊 100%」：上次的 100% 只抽了 2 個 scenario；這輪全 dataset 是 98.87%，且逐 scenario 不均。用語是「補完上次的驗證」，不是「更正」（10/05 已附但書）
- ❌ 不要說「老師建議挑 IoT rule」：老師的建議只是「挑合理的 rule，並說明為什麼合理」，沒有指定挑哪些
- 不要說這輪量了 inline、multi-thread；Pi 上的數字也不是兩個 engine 的最快設定（Suricata `ac-ks`、Snort 3 `ac_bnfa`）
- 接前兩次的語氣不要比原文強：9/21 是「提過 blocklist **可以**灌進 nftables set」，不是「規劃了」

**IoT-23**
- ❌ 不要說「攻擊 flow 對不回 packet」：Zeek 把 DDoS 記成 0 packet，packet 都還在 pcap 裡（60-1 的 packet coverage 是 100%）
- ❌ 不要說「8-1、20-1、21-1 是 log 比 pcap 早結束」：只有 52-1、49-1 是；8-1、20-1、21-1、Honeypot-7-1 的 packet coverage 低，已確認是非 IP packet 多（主要是 ARP）
- 不要說 34-1／60-1 的 checksum 原因已用 Zeek 重跑確認：有文件與抽樣佐證，但沒用 Zeek 重跑
- 不要說 17-1 那 25% 的 DDoS 是真的 DDoS：它是 tcp/52869 的 SYN 打 11,959,048 個不同 IP，是 scan 樣式
- ❌ 不要說「Okiru = 利用嘗試」：Okiru label 是「具 Okiru botnet 特徵」，資料只看得到 SYN 探測
- ❌ 不要說「簽章 rule 抓不到 scan」：要說「ET Open 的 scan rule 有覆蓋缺口」
- 「多數可以在 flow 層級判斷」是推論；scan flow 不是 100% S0（1-1 是 97.6%），所以用「幾乎」
- ❌ 不要把 42-1 當成正常 Benign 的對照：正常 Benign 的對照只能用 17-1、36-1；也不要斷言那條 IRC 是 C2
- 不要直接說「這些 Benign 就是 Mirai scan」或「Benign 是 label 錯誤」：「看起來很像」與「可能是 P2P」都是推測，原因不確定
- 不要說 usable 的 11 個 scenario 帶 payload 的攻擊 label 也對得好：39-1 Attack 約 12%、C&C 約 45%
- 不要說「flow alignment 檢查的是 label 標得對不對」：它檢查的是 Zeek 的 packet 統計與 pcap 對不對得上
- 不要說「98.87% 是各 scenario 的平均」：它是 flow 加總之後再除

**ET Open 與 Pi 實驗**
- ❌ 不要說「Pi 4 在 80°C soft throttle」：官方寫 Pi 4 沒有 soft limit；80°C 起逐步降頻、85°C 時 CPU 與 GPU 都降頻
- 不要說「packet 數與 bytes 都守恆」：packet 數全部守恆，bytes 有 9 次不守恆（Snort 3 在 34-1，IP 分片）
- ❌ 不要說「ET 有 snort-3.0.0 rule 包」：Snort 版是 Snort 2.9 rule 包經 snort2lua 轉換；Snort 的 rule 數一律用載入數（`full` 52,445、`gw_corp` 38,086）
- ❌ 不要說「`full` 掛不起來」：Suricata 掛得起來（15.5–176 kpps）；跑不動的是 Snort 3
- ❌ 不要說「Snort 3 只有在 scan／flood 下不能用」：14 個 scenario 中有 12 個約 6.3 kpps 以下
- 「這種 rule 不該放在 IDS engine」要限定 **Snort 3**：Suricata `sel` 與 `full` 差不到 3%；② nftables set 這輪沒有實作、沒有量測
- ❌ 不要說「TOR 出口節點 803 條」：803 = 出口 121 + 中繼 682
- 「42,592 個 IP」要說「42,592 個 IP／網段項目」
- 不要說 Snort 3 被 IP 清單拖垮的機制已經查明：只有可能的解釋和出處，沒有驗證
- 不要說 Suricata 在目的 IP 分散時變慢的原因已確認：新 flow 建立成本是推測；差分法 127 → 25.8 kpps，自報時間是 138 → 66.4 kpps，要保守講
- ❌ 不要籠統說「Suricata 對 rule set 不敏感」：`gw_corp` 對 `full` 只快 1–26%，但這輪只比了這兩種 rule 數，rule 數少很多時沒有量
- 不要說「14 個 scenario 都是 usable」：效能測試不讀 label，14 個是依流量特徵挑的，只有 6 個也在 usable 內；另外 8 個不在 usable 的原因也不全是「label 與 pcap 對不上」

**Memory**
- 投影片上的 RSS 都是 **39-1 (IRCBot)**；講其他 scenario 的 RSS（例如 Honeypot-7-1 的 1,184／918 MB）時要講明是哪個 scenario
- ❌ 不要說「memory 不是問題」：1 GB 時 Suricata 要靠 zram，39-1 慢約 13%（`full`）／10%（`gw_corp`）
- 不要把 1 GB 變慢的百分比當成固定比例：39-1 是 13%（`full`）／10%（`gw_corp`），多花的時間約 2 秒／1.4 秒；「接近固定換頁時間」是推測
- 不要說「Suricata 在 1 GB 只需要 719 MB（或 749 MB）」：RSS 變小是因為一部分被換進 zram（VmSwap 峰值 794／466 MB）
- ❌ 不要說「`gw_corp` 解決了 Suricata 的 memory 問題」：RSS 仍是 977 MB，1 GB 時一樣要靠 zram、會變慢
- 不要說沒有 swap 時會怎樣：這輪只量了系統預設的 zram 開，沒有 swap 的情況沒有量

**`gw_corp` 與結論**
- ❌ 不要說「數據證明 Suricata 比 Snort 3 好」：選 Suricata 是依取捨；Snort 3 的 memory 小很多，大範圍 scan 下也比較快
- ❌ 不要說「已經能接雲端」：雲端串接還沒實作、沒量
- 不要把 Snort 3 在 `gw_corp` 變快講成已證實的因果：`gw_corp` 同時拿掉了 IP 清單 rule 和 DYN_DNS 等 8,406 條，沒有單獨量，是推論
- 「至少 11 kpps」只講 Snort 3：`gw_corp` 下 Snort 3 最慢是 44-1 的 11.4 kpps、Suricata 最慢是 39-1 的 15.8 kpps
- 不要說 `gw_corp` 的判斷表驗證了偵測價值：那是我們的分析，要請老師確認
- 不要說這輪驗證了 `gw_corp` 多保留的部分有沒有用：沒有量 detection rate，流量也只有 IoT-23，PHISHING、WEB_CLIENT 等沒有驗證
- ❌ 不要舉 POLICY：這份 rule 包的 73 個 category 裡沒有 POLICY（ET 已併入 INFO）
- ❌ 不要說「高信心」：`gw_corp` 沒有用 ET 的 confidence、severity 欄位，也沒有用 metadata，只依 category
- ❌ 不要說「`gw_corp` 沒有漏掉任何攻擊」「`gw_corp` 的 detection rate 和 `full` 一樣」：這輪沒有量 detection rate；第 10 頁不保留的 category（例如 DROP 這類 IP blocklist）現在本地不會產生 alert
- ❌ 不要說「34-1 是非標準 port 的 IRC」：34-1 的 IRC 在標準 port 6667；非標準 port 的例子是 42-1（tcp/4975）
- 不要說 nftables set「完全不隨清單長度增加」：單一 IP 約常數時間、CIDR 區間約對數成長
- ❌ 不要說「約 98% packets 沒有 payload」：4 個切片約 82%（17-1 切片 99.9%）；「IoT-23 整體 98%」無法證實
- 結論表以中位數為主：平均會被少數快的 scenario 拉高（Snort 3 `full` 平均 8.4 主要來自 Honeypot-5-1 的 80.8）

**用詞**
- 同一個概念只有一種說法，照 `slide_implement.md` 0.3 對照表；技術名詞一律英文（rule、category、memory、alert、engine、load time、scan、flood、packet、dataset 等）
- scenario 不翻成中文；scenario 一律帶 malware／設備名稱
- rule set 只用 `empty`、`full`、`sel`、`gw_corp` 這四個名字（`common` 只在第 7 頁被問到時出現）
- kpps 是 engine 處理速度，不是線上速率；最差 scenario 的上限要用 pps 講並說明流量型態
