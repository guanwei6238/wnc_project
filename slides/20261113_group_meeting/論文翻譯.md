## Abstract（摘要）
〔PDF p.2〕

將機器學習模型直接部署在網路 data plane 上，可以用資料驅動的模型（而非預先定義的協定）在 line-speed 下進行智慧化的流量分析。這種能力稱為 Intelligent Data Plane (IDP)，可能改變許多網路設計。新興的 programmable switch 為實現 IDP 提供了關鍵的硬體支援。此方面的既有研究分為兩大類：(i) 著重於從 data plane 擷取有用的 flow 資訊，而把以學習為基礎的流量分析放在 control plane；(ii) 更進一步把學習模型嵌入 data plane，但沒有使用對達到高學習 accuracy 至關重要的 flow-level features。本文提出 NetBeacon，在模型 accuracy 與模型部署效率兩方面推進現有技術水準。具體而言，NetBeacon 提出 multi-phase sequential model 架構，在 flow 進行的不同階段（phase）對 packet 做動態分析，並納入可在 line-speed 下計算的 flow-level features 來提升學習 accuracy。此外，NetBeacon 設計了高效率的模型表示機制，以解決在網路 data plane 上部署樹狀模型時的 table entry 爆炸問題。最後，NetBeacon 以多項緊密配合的設計來管理用來儲存 per-flow 狀態的 stateful storage，強化處理大量並行 flow 的可擴充性。我們實作了 NetBeacon 的原型，並在多項流量分析任務上廣泛評估其效能。

## 1 Introduction（緒論）
〔PDF p.2〕

人工智慧（AI）在各類網路設計中日益普及，例如影片位元率調適（video bitrate adaption）[34, 56]、壅塞控制 [1, 57]、流量最佳化 [11]、路由 [29, 65] 與網路規劃 [66]。這些學習得到的模型通常部署在終端主機 [1, 34, 56, 66] 或網路 control plane [11, 29, 57, 65] 上執行推論，這兩類裝置都配有彈性的通用處理器或 GPU。

然而，把學習得到的模型直接部署在網路 data plane 上做流量分析，目前探索得還相對較少。在網路 data plane 上執行模型推論的關鍵優點，是能以資料驅動的模型（而非預先定義的協定）達成 line-speed（亦即對網路轉送速度零衰減）的智慧化流量分析。這種能力稱為 Intelligent Data Plane (IDP)，可能改變許多網路設計。舉例來說，日益精密的網路攻擊常能繞過憑經驗學得的流量過濾器 [31]，促使學界設計以學習為基礎的惡意流量偵測機制，例如 [14, 37]。然而，與這些做法不同，IDP 能達成 line-speed 的流量分析；相較之下，目前把學習模型部署在網路 control plane 上的最先進做法，處理流量的速度只有約 10 Gbps [14]。此外，把 control plane 放在流量分析的關鍵路徑上，還會帶來額外的反應時間 [2]。除了資安領域，其他網路設計（例如差異化路由 [29]、ECN 門檻調整 [57]，以及緩衝區管理 [19]）也可能受益於 IDP。

IDP 的設計過去被認為「幾乎不可能」，因為要在 data plane 上那些專用且協定固定（protocol-defined）的 ASIC 交換晶片上實現動態、資料驅動的 AI 模型相當困難。幸運的是，programmable switch（例如 P4 switch [8]）的進展，讓 packet 處理邏輯可以依據 Protocol-Independent Switch Architecture (PISA) 客製化。在 PISA 下，網路 packet 由可程式化的 pipeline 以 line-speed 處理，這條 pipeline 由一個 parser、多個 match/action stage 與一個 deparser 組成。雖然 PISA 架構（目前）還不是 Turing Complete，無法對 packet 位元組執行任意運算，但學界已圍繞著 programmable switch 提出許多重要的網路安全設計。

第一類既有研究著重於從 data plane 擷取有用的 flow 資訊，以支援上層應用。例如，NetWarden [53] 與 FlowLens [4] 依賴 programmable switch 蒐集 flow 的分布資訊，再分別在 control plane 上據以進行 covert channel 偵測 [53] 與以學習為基礎的流量分類 [4]。類似地，Poseidon [61] 與 Jaqen [32] 把蒐集到的 flow 資訊（例如 flow 速率）與預先定義的流量過濾政策（例如以門檻為基礎的過濾器）比對，以緩解流量型（volumetric）DDoS 攻擊。這一類設計與 IDP 的關鍵差異在於，它們並未把學習模型直接嵌入 programmable data plane。

第二類既有研究更進一步，

以實現 IDP。例如，pForest [10] 與 SwitchTree [26] 提出把 decision tree 模型部署在 programmable switch 上，做法是把一個 match/action stage 對應到 decision tree 的一層。然而，這兩者的設計雖然以軟體交換器 BMv2 驗證過，卻無法部署在實際硬體上（詳見 § A）。Planter [63] 擴充了 IIsy [55]，提出一個同時包含 feature table 與 code table 的架構，用來在 data plane 上表示 ensemble tree。Planter 雖然很有前景，但缺少幾項關鍵設計：例如，目前並不清楚 Planter 要如何同時多次使用同一個特徵（這在現實中相當常見）。最新的研究 Mousika [51] 提出一種專為 programmable switch data plane 設計的 decision tree 模型，稱為 Binary Decision Tree (BDT)。然而，部署 BDT 所需的 table entry 數量會遇到組合爆炸的問題（詳見 § A）。最關鍵的是，所有這些可實際部署的既有研究，模型中都只使用 per-packet features，完全忽略了 flow-level features。如同我們在 § 2.2 會呈現的，flow-level features 對於提升各種流量分析任務的學習 accuracy 是必要的。

本文提出 NetBeacon，這是一種新穎的 IDP 設計，在模型 accuracy 與模型部署效率兩方面都推進了現有技術水準。具體而言，NetBeacon 由下列創新設計所支撐：

(i) 以 multi-phase sequential model 架構為核心的 data plane aware 學習模型設計。由於一條 flow 在不同 phase 的 packet 帶有不同的 flow-level 狀態，我們的模型會隨著 flow 的進行，在 flow 的不同 phase 做動態分析，減少只靠單一推論模型而過早做出分類決策所造成的錯誤。同時，我們的模型使用經過仔細設計、可在 data plane 上以 line-speed 計算的 flow-level features 與 per-packet features，以確保可部署性。

(ii) NetBeacon 提出一種高效率的模型表示機制，以解決把 decision tree 或 forest 模型表達成 data plane 的 matching table 時的 entry 爆炸問題。與目前最先進的 Mousika [51] 相比，NetBeacon 大幅降低了 table entry 的消耗（部分情況下最多可減少 75%）。

(iii) 我們進一步強化 NetBeacon 處理並行 flow 的可擴充性，做法是區分短 flow 與長 flow 的處理邏輯，並在遇到 storage index 碰撞時允許安全的儲存空間多工（storage multiplexing）。這使 NetBeacon 有可能處理比「用來維護 per-flow 狀態的 register 總數」更多的並行 flow。

我們以 Tofino switch 作為 programmable data plane 實作了 NetBeacon 的原型，並以三個使用案例對 NetBeacon 做了廣泛的評估。實驗結果顯示，NetBeacon 在流量分析／分類的 accuracy 與硬體 table 消耗兩方面都優於現有技術水準。我們也以量化方式研究了交換器硬體（例如 hash 的不完美，以及未來的硬體升級）會如何影響 NetBeacon。

## 2 Background and Motivation（背景與動機）
〔PDF p.3〕

### 2.1 Programmable Data Plane（可程式化 data plane）

傳統交換器配備了為 packet 處理客製化的 ASIC 晶片，以達成高速轉送。因此，要在 ASIC 晶片上實作新的網路協定，需要設備製造商進行設計、製造與嚴格測試，成本昂貴。為了讓協定開發更靈活，大約二十年前，學界提出了軟體定義網路（Software-Defined Networking, SDN），讓軟體 controller 可以透過 OpenFlow 協定 [36] 在交換器上安裝客製化的 flow entry。SDN 非常成功，多年來被廣泛部署，尤其是在資料中心 [13, 20]。近年來，以 Protocol-Independent Switch Architecture (PISA) 為核心的 programmable switch 技術，把網路可程式化的程度提升到另一個層次。交換 pipeline 本身就夠靈活，可以透過 P4 這類領域專用程式語言直接撰寫程式，而不再完全仰賴軟體 controller。

在 PISA 的交換 pipeline 中（Figure 1），網路 packet 先進入 parser 解析 packet 標頭，接著進入多個 match/action stage 對 packet 進行操作，最後到達 deparser 進行 packet 序列化。parser、match/action 與 deparser 都可以程式化，用來實作所需的協定。match/action 支援 exact matching、ternary matching 與 longest prefix matching (LPM)。每一次 match 對應一個 action，action 中可以執行特定的運算與儲存修改。彼此相依的 action 必須放在不同的 stage。 packet 標頭與 metadata 實例存放在無狀態（stateless）儲存中，每當新 packet 到達時就會被重新初始化。PISA 也提供有狀態（stateful）且持久的儲存，例如 counter、meter 與 register。最後，PISA 還提供各種機制（例如 resubmit、recirculation、packet generation）來進一步擴充可程式化的能力。

儘管很靈活，PISA 仍有以下運算與儲存上的限制。第一，它支援布林運算、shift、加法與減法，但不支援乘法與除法。浮點運算、迴圈運算與複雜的條件運算同樣不被支援。主要的運算邏輯是以 match/action stage 實作，而 stage 的數量並非無限（例如 Tofino 1 有 12 個 stage）。同樣地，儲存資源也有限，例如在 Tofino 1 上，每條

### 2.2 Motivation（動機）

PISA 的彈性激發了大量研究，探討實現 intelligent data plane (IDP) 的潛力。我們將既有研究分為三個子類，整理於 Table 1。第一，NetWarden [53] 與 FlowLens [4] 代表利用 programmable switch 蒐集有用 flow 資訊（例如 inter-packet delay 的分布），再於 control plane 上進行流量分析的設計。由於 data plane 與 control plane 之間有互動延遲，流量並不是以 line-speed 分析的。

Poseidon [61] 與 Jaqen [32] 的設計和 NetWarden [53]、FlowLens [4] 相似，差別在於它們蒐集到的 flow 資訊可以直接在 data plane 上使用，以 line-speed 分類流量型 DDoS 攻擊（注意，它們的部分 action 仍需要 control plane 的伺服器參與）。然而，它們的分類邏輯是以門檻驅動的流量過濾器為基礎，而不是機器學習模型。因此，在流量分析邏輯無法準確表示成人工設計的過濾器的使用情境中，這些做法無法通用。

Planter [63] 與 Mousika [51] 邁出了第一步，用 match/action table 表示 decision tree 的分支，把 decision tree 模型嵌入網路 data plane。然而，它們的設計有兩個主要限制：一是在 data plane 上表示學習模型的效率偏低（如 § 7.3 所示），二是只考慮無狀態的 per-packet features，而忽略了有狀態的 flow-level features。

我們以實驗證明 flow-level features（flow 由其 5-tuple 識別）對於提升以學習為基礎的流量分析之 accuracy 是必要的。我們先說明 flow-level features 整體而言比 per-packet features 更重要。為此，我們考慮了三個情境：P2P 應用程式指紋辨識（P2P application fingerprinting）、covert channel 偵測，以及 DDoS 攻擊偵測。對每個任務，我們同時使用 per-packet features（例如 ttl、第 n 個 packet 的 packet 大小）與 flow-level features（例如前 n 個 packet 的 packet 大小之平均值與變異數）訓練一個 decision tree 模型。接著，我們依特徵的 information gain 計算 feature importance，繪於 Figure 2 的上半部。flow-level features 明顯有較高的 importance 分數。

> **Figure 2**（PDF p.4）：flow-level features 在流量分析任務中的必要性。以 ∗ 開頭的特徵是 per-packet features，例如 ∗proto 與 ∗size。
> 〔圖上文字〕上半部為三個任務（App Fingerprinting、Covert Channel、DDoS Attack）各自的橫條圖，縱軸標為 Feature Importance，各條對應的特徵名稱如 size_var、∗proto、bin_10、ipd_min 等；下半部為各任務的 Accuracy(%) 長條圖，圖例有兩種：packet（只用 per-packet features）與 packet+flow（同時用 per-packet 與 flow-level features）。

第二，我們說明 flow-aware 的分類器比 flow-agnostic 的分類器輸出更準確的結果。具體來說，我們訓練兩個 decision tree 模型：一個是如 Mousika [51] 那樣、只使用 per-packet features 的 flow-agnostic 模型；另一個是同時使用 flow-level features 與 per-packet features 的 flow-aware 模型，特徵依其 importance 排序選取。兩個模型使用相同數量的特徵。我們把分類 accuracy 的結果呈現在 Figure 2 的下半部。結果顯示，納入 flow-level features 能顯著提升 accuracy：P2P 應用程式指紋辨識提升 +11%，covert channel 偵測提升 +43%，DDoS 攻擊偵測提升 +21%（這些任務的詳細說明見 § 7.1）。

**Design Goals（設計目標）。** 與既有研究（Table 1）相比，我們設計 NetBeacon 的目標，是同時在網路 data plane 上達成 line-speed 與高 accuracy 的（以學習為基礎的）流量分析，藉此推進現有技術水準。另有其他研究 [45, 50] 以 SmartNIC 而不是 programmable switch 作為 data plane。這兩種硬體的特性截然不同：programmable switch 的 throughput 高得多，但運算能力受到的限制也大得多。本文專注於以 PISA 驅動的 IDP 設計。

**Assumptions, Threat Model, and Limitations（假設、威脅模型與限制）。** 我們假設 NetBeacon 可以取得與任務相關的訓練資料集。機器學習本身有安全弱點，例如資料與模型的 poisoning 攻擊，這不在本文的討論範圍內。我們假設承載 NetBeacon 的 programmable switch 是安全的。由於 flow-level features 會消耗 programmable switch 上的 stateful storage，NetBeacon 能同時維護 per-flow 狀態的並行 flow 數量受限於硬體儲存空間，儘管 NetBeacon 已有專門的設計來改善可擴充性。同時，也可以透過平行部署多個 NetBeacon 實例來擴大流量分析的容量。NetBeacon 不支援在 data plane 上難以計算的 flow-level features（例如 packet 大小的百分位數）。我們以 5-tuple

## 3 The Overview of NetBeacon（NetBeacon 概觀）
〔PDF p.5〕

如 Figure 3 所示，NetBeacon 在架構上圍繞兩個主要元件設計：data plane aware 的模型設計，以及高效率的模型部署。Data plane aware 的模型設計是一種 co-design（協同設計）方法，用來產生對硬體友善的學習模型。為此，我們的 feature engineering 只採用在交換 pipeline 上可擷取或可在 line-speed 下計算的特徵。此外，考量到 flow-level features（例如 packet 大小的平均值）會隨著 flow 進行而改變，NetBeacon 提出 multi-phase sequential model 架構，能隨著 flow 進行做出多次推論決策，直到系統有足夠把握做出最終決策為止。

模型部署的關鍵設計是 model representation 模組。它把學習得到的模型轉譯成 data plane 上的多個 feature table 與一個 model table：feature table 把特徵值編碼成稱為 range mark 的資料結構，range mark 再對應到儲存在 model table 中的推論結果。NetBeacon 設計了高效率的編碼機制，在表示模型時大幅降低 table entry 的消耗。

此外，NetBeacon 設計了 stateful storage management 模組，在 data plane 上達成高效率的 per-flow 狀態管理。一方面，這個模組讓 NetBeacon 能只用 per-packet features 處理短 flow（亦即不為短 flow 維護 per-flow 狀態），這些短 flow 以一個學習模型分類。另一方面，NetBeacon 利用硬體 hash 達成 storage multiplexing。具體而言，當新 flow 的 5-tuple 被 hash 到已被佔用的 register（亦即發生 storage 碰撞）時，如果原本儲存的 flow 已經完成分類（class-determined）或已逾時（timeout），新 flow 就可以接手這個 register；否則，NetBeacon 會對這個新 flow 退回使用無狀態的 per-packet features。如果 packet 屬於原本儲存的那條 flow，則更新 register 並計算特徵以進行模型推論，亦即查詢 feature table 與 model table。

### 4.1 Feature Engineering（Feature Engineering：特徵工程）

NetBeacon 中的 decision tree 學習模型可以同時使用 per-packet features 與 flow-level features。Per-packet features 可以從單一 packet 取得，通常是依據 packet 標頭的欄位，例如 packet 大小與 Time To Live (TTL) 值。Flow-level features 則是結合同一條 flow 中其他 packet 的屬性而得。

我們把 flow-level features 分成 aggregate features 與 summary features。Aggregate feature 表示為 F = aggr(a, c, d)，其中 a 表示 F 所考量的屬性，c 是施加在該屬性上的條件，d 則代表當 packet 滿足 c 時、用來更新 F 值的預先決定的規則。例如，特徵 F = aggr(packet size, [96, 112), +1) 記錄的是一條 flow 中 packet 大小落在 [96, 112) 的 packet 數量。與 aggregate features 不同，summary features 的計算無法輕易用預先決定的更新規則來表示。具代表性的 summary features 有最大值／最小值、平均值與變異數，這些甚至會涉及乘法或除法，而硬體並不原生支援這些運算。我們在 § 6.1 說明 summary features 是如何計算的。

### 4.2 Multi-Phase Sequential Models（Multi-Phase Sequential Model）
〔PDF p.6〕

與既有研究 [26, 51, 63] 相似，NetBeacon 堅持採用以 decision tree 為基礎的學習模型，因為相較於涉及大量非線性運算的神經網路，decision tree 的結構更接近 data plane 上的 match/action 操作。我們採用目前最先進的 decision tree forest 模型，即 Random Forest (RF) 與 XGBoost (XGB)。考量到硬體上的 table entry 數量有限，我們可以透過限制 forest 中 tree 的數量、tree 的最大深度、最大葉節點數等方式來控制模型大小。

在 per-packet 分析中，所有 packet 都被一視同仁；但在 flow-level 分析中， packet 位於 flow 的不同 phase，因此帶有不同的 flow-level 狀態。所以，flow-level features 會隨著 flow 的進行而動態變化。在 Figure 4 中，我們使用兩個資料集，以量化的方式視覺化兩個 flow-level features（即 inter-packet delay IPD 的平均值，以及 packet 大小的變異數）在 flow 不同 phase 的動態變化。很明顯，這兩個特徵都隨時間有顯著的變化。因此，如 Figure 5 所示，只用單一模型根據 flow-level features 做推論，accuracy 偏低。

上述觀察促使我們設計 multi-phase 模型架構，在 flow 的不同 phase 套用不同的模型。在每一個 phase，NetBeacon 使用該 phase 計算出的特徵進行訓練與推論，亦即第 n 個 packet 處的 flow-level features 是依據前 n 個 packet 計算的。我們的模型做出推論決策的那些 packet 稱為 inference point。inference point 的具體安排視任務而定。具體而言，每個 inference point 本質上代表：在我們的模型處理完該 inference point 之前的 n 個 packet 後，對這條 flow 得到的一個分析結果。因此，inference point 可以依任務需求均勻地放置，也可以針對性地放置。例如，如果模型使用變異數作為特徵，由於硬體限制，inference point 應該放在 2 的冪次方（power-of-2）的位置（詳見 § 6.1）。沒有被選為 inference point 的 packet，則沿用前一個、且離它最近的 inference point 的推論結果。因此，兩個 inference point 之間的間隔不應過大。

NetBeacon 為每一個推論 phase 設定一個 determination threshold。當某個 inference point 的分類機率高於對應的 determination threshold 時，表示 multi-phase sequential model 有足夠的把握，不必使用後續的 inference point，就能預先判定這條 flow 的類別。這個設計有助於 data plane 上的 stateful storage 管理（如 § 5.2 所述）。除了 flow-aware 的學習模型之外，NetBeacon 還使用一個 flow-agnostic 模型，來分類無法用 flow-level features 分析的 packet，詳見 § 5.2。

我們先從單一 decision tree 在 data plane 上的表示談起。在 decision tree 中，leaf node 代表分類結果，而從 root node 到某個 leaf node 的路徑，就代表該 leaf node 的 matching rule，通常是多個 feature 範圍的串接。例如在 Figure 6 中，通往 leaf node 1 的路徑是 f1 ∈ [0, 25)、f2 ∈ [0, 46) 且 f3 ∈ [0, 10)。路徑上沒有出現的 feature，其範圍就是允許的最大範圍。例如通往 node 5 的路徑是 f1 ∈ [65, 103)、f2 ∈ [0, 256) 且 f3 ∈ [10, 256)。因此，如果 programmable switch 支援 range matching，decision tree 模型就可以很容易地實作成 Figure 6 的 Model Table (1)，其 key 是多個 feature 範圍的串接，value 則是 leaf node。

**Range Marking（範圍標記）.** NetBeacon 以一個名為 range marking 的新機制，解決上述 entry 組合爆炸的問題。如 § 3 所介紹，decision tree 模型表示成多個 feature table（每個 feature 一個）與一個 model table。Range marking 機制確保每個 leaf node 在 model table 中只會佔用一個 ternary entry，不論有多少 feature table entry 與這個 leaf node 相關。

在 decision tree 模型中，每個 feature 通常有多個 threshold。例如在 Figure 6 中，feature f1 有三個 threshold：25、65 和 103，它們把整個可能的值域（即 [0, 256)）切成四個連續且互不重疊的 basis range，即 [0, 25)、[25, 65)、[65, 103) 和 [103, 256)。Range marking 的目標，是用 ternary bit string（即 0、1，以及同時匹配 0 與 1 的 ∗）來表示這些範圍，使得 (i) 每個 basis range 對應到唯一的 bit string，並且 (ii) 由多個連續 basis range 組合而成的任何新範圍（稱為 associative range）也對應到唯一的 bit string。需要第二個條件，是因為 decision tree 中的一個 node 可能橫跨多個 basis range。例如在 Figure 6 中，node 4 的 parent 有一個 associative range（[0, 65)），橫跨兩個連續的 basis range（[0, 25) 與 [25, 65)）。

正式地說，我們這樣定義 range marking。假設有 n 個 threshold {r_i}，i ∈ [1, n]，把範圍 [0, R) 切成 n + 1 個連續且互不重疊的 basis range，組成集合 S = {[0, r_1), [r_1, r_2), ..., [r_n, R)}。我們的 range marking algorithm F 定義了一個從範圍（basis range 或 associative range 皆可）到 ternary bit string 的映射，並滿足下列條件：

- ∀ i ∈ [1, n]，F([r_i, r_{i+1})) = {0, 1}^k；
- ∀ i, i+m ∈ [1, n]，F([r_i, r_{i+m})) = {0, 1, ∗}^k；
- ∀ i, j, l, l+m ∈ [1, n]，F([r_i, r_{i+1})) ≠ F([r_j, r_{j+1})) ≠ F([r_l, r_{l+m}))

**Range Coding in Feature Tables（feature table 中的 range coding）.** Feature table 中的 key 仍然是 feature 值的範圍（例如 [0, 25)）。雖然現有的 range coding 設計（如 Prefix [46]、SRGE [9]、OPT [43]、Bit-Map [30]、DIRPE [24]）可以把值範圍轉換成 ternary entry，但它們不如我們的 consecutive range coding（CRC）algorithm 有效率，說明如下。

在我們的情境中，每個 feature table 中要編碼的範圍是連續的，並且涵蓋該 feature 所有可能的值。基於這項特性，我們提出以下的 CRC algorithm。CRC 從較低的 basis range 開始編碼（即從 [0, r_1) 到 [r_n, R)）。具體來說，給定一個 basis range [r_{i−1}, r_i)，CRC 會嘗試找出一個最佳的 parent range [p_start, p_end)（即 p_start ∈ [0, r_{i−1}] 且 p_end ∈ [r_i, r_{i+1})），使得在 data plane 上表示這個 parent range 所需的 prefix 數量最少。CRC 把表示 [p_start, p_end) 的 prefix 分成三個部分：表示 [p_start, p_end) 的 acceptance prefix（即 Figure 7 中的 a），以及分別表示 [p_start, r_{i−1}) 與 [r_i, p_end) 的 denial prefix（即 Figure 7 中的 b 與 c）。Denial prefix 的 priority 應高於 acceptance prefix，才能確保 [r_{i−1}, r_i]（原文此處右括號印為 ]）與 [p_start, p_end) 接受的是同一個範圍。

為了找出最佳的 [p_start, p_end)，CRC 求解 Equation (1) 的最佳化問題，其中 Prefix(R) 是依 [46] 表示範圍 R 所需的 prefix 數量。注意，方程式中並未考慮 Prefix([p_start, r_{i−1}))。這是因為表示任何較低 rank 的 basis range（即 [r_0, r_1), ..., [r_{i−2}, r_{i−1})）的 prefix，其 priority 永遠高於 [r_{i−1}, r_i) 的 prefix。因此，我們可以放心地捨棄表示 [p_start, r_{i−1}) 的 prefix，因為它們反正會被表示較低 rank basis range 的 prefix 所遮蔽。

```
min          Prefix([p_start, p_end)) + Prefix([r_i, p_end))        (1)
p_start ∈ [0, r_{i−1}]
p_end   ∈ [r_i, r_{i+1})
```

CRC 之所以能減少表示 [r_{i−1}, r_i) 所需的 prefix 總數，儘管它實際考慮的是更大的範圍 [p_start, p_end)，直覺在於：把 [r_{i−1}, r_i) 擴張成 [p_start, p_end) 之後，[r_{i−1}, r_i) 中原本的一些 prefix 其實可以合併成一個更大的 prefix。例如在 Figure 6 中，[65, 103) 的幾個較小的 prefix（即 01000001、0100001* 等）在把 [65, 103) 擴張成 [64, 104) 之後，被合併為兩個較大的 prefix：010***** 與 01100***。

上述最佳化問題可以直接透過窮舉 p_start 與 p_end 所有可能的值來求解，複雜度為 O(R^2)。我們另外提供一個複雜度為 O((lg R)^2) 的更快求解器，放在 § B。

另一項最佳化是，CRC 不需要編碼最後一個 basis range（即 [r_n, R)）。注意，我們的 range marking 機制一律把 0 指派給 [r_n, R)。因此，如果某個 feature 在 feature table 中沒有被任何 entry 匹配到，它的 range mark 就會取預設值 0，這與我們的 range marking 機制所指派的值相同。所以不需要在 feature table 中表示 [r_n, R)。

**Handling Forest Models（處理 forest 模型）.** 部署 forest 模型的一種做法，是分別表示每一棵 tree，再把各 tree 的 inference 結果彙整成最終結果。這種做法適用於最終結果取各 tree 所給 inference class 的 plurality（相對多數）的 forest 模型（例如 random forest 模型）。具體來說，會在各 tree 的 model table 之後附加一個 plurality matching table。Plurality table 中每一列的 key 是各 tree 的 inference class 的串接，對應的 value 則是各 tree 的 inference class 中的多數。這種情況下的「combinatorial explosion」（組合爆炸）問題很輕微，因為 tree 的數量，以及每棵 tree 的 inference class 數量，都小得多。

然而，上述設計不適用於 gradient boosting tree 模型（例如 GBDT、XGBoost、LightGBM）。這是因為最終的 inference probability 是透過非線性函數（例如 Sigmoid）彙整各 tree 的結果而得，這在 data plane 上很難執行。

因此，NetBeacon 不分別表示各棵 tree，而是把它們的模型表示合併起來。具體來說，對於某個 feature f1，每棵 tree 可能各有一個 feature table。合併這些 feature table，等同於用我們的 range marking algorithm，針對這些 table 中出現過的所有 feature 值範圍，建立一個新的 feature table。至於 model table，每個 entry 代表來自各 tree 的 leaf 的一種組合。因此，model table entry 的 key 是綜合考慮該 entry 所對應各 leaf 的路徑上所有 node（代表 feature 範圍）而得到的 range mark，而對應的 value 則是這些 leaf 的聚合結果（例如 Sigmoid），這可以離線算好。例如在 Figure 9 中，leaf 1-2 與 leaf 2-1 的組合，把 f1 ∈ [25, 256) 與 f1 ∈ [0, 35) 合併，得到 f1 ∈ [25, 35)。這個組合的 value 是 Sigmoid(-0.01+0.5)。

> 〔譯註：圖的內容〕Tree 1 的 root 為 f2 < 10，Yes 分支為 f1 < 25（leaf 1-1 = -0.2、leaf 1-2 = -0.01），No 分支為 leaf 1-3（-0.1）；Tree 2 的 root 為 f2 < 80，Yes 分支為 f1 < 35（leaf 2-1 = 0.5、leaf 2-2 = 0.1），No 分支為 leaf 2-3（-0.5）。右側合併後的 model table 以 (f1, f2) 的範圍為 key：([0, 25), [0, 10)) → Sigmoid(-0.2+0.5)（leaf 1-1 與 2-1）；([25, 35), [0, 10)) → Sigmoid(-0.01+0.5)（leaf 1-2 與 2-1）；([35, 256), [0, 10)) → Sigmoid(-0.01+0.1)（leaf 1-2 與 2-2）。

### 5.2 Stateful Storage Management（stateful storage 管理）

為了利用 flow-level features，NetBeacon 依賴 stateful storage 來維護每個 flow 的 state。先前的研究 [4, 53] 讓 control plane 在收到新 flow 時配置一個不衝突的 storage index。為了做到 line-speed 的流量分析，NetBeacon 改為依賴 data plane 上現成的 hardware hash 來配置 storage index。具體來說，假設有 N 個 stateful register 可用來儲存 flow state，NetBeacon 以 H(5-tuple) % N 計算某個 flow 的 storage index，其中 H 為 hash function。

然而，以 hash 配置 storage index 有配置 collision 的問題，也就是說，兩個不同的 flow（5-tuple 不同）可能得到相同的 storage index。因此必須把真正的 flow ID（例如 5-tuple）與 storage index 一起儲存，NetBeacon 才能察覺 collision。

一旦發生 storage collision，如果新 flow 覆寫了該 storage，原有 flow 與新 flow 的 per-flow state 都會變成髒資料。因此，NetBeacon 提出兩個設計來緩解這個問題：一個設計用來降低整體的 collision 機率，第二個設計則讓覆寫 storage 可以安全進行。

**Differentiating Short and Long Flows（區分 short flow 與 long flow）.** 如 § 2.2 所介紹，在 per-packet features 之外再納入 flow-level features，目的是提升分類 accuracy。流量分析的首要目標，是提升所有 flow 整體的 packet 分類 accuracy；既然如此，為 packet 較少的 short flow 維護 per-flow state，其邊際效益就低於為 long flow 維護 per-flow state。我們以 P2P application fingerprinting 任務來量化地驗證這項觀察。具體來說，我們考慮五種情況：只對 packet 數超過 8（16、1024、2048）個的 flow 納入 flow-level features（即 cutoff 8、cutoff 16 等），以及對所有 flow 都考慮 flow-level features。我們在 Figure 10 中畫出所有 flow 整體的 packet 分類 accuracy。很明顯，前三種情況的整體 accuracy 非常接近。

> **Figure 10**（PDF p.9）：五種情況下，所有 flow 的 packet 分類 accuracy：對所有 flow 使用 flow-level features，以及只對 packet 數超過 8（16、1024、2048）個的 flow 使用 flow-level features。
>
> 〔譯註：圖的內容〕長條圖，橫軸依序為 All、Cutoff 8、Cutoff 16、Cutoff 1024、Cutoff 2048，縱軸為 accuracy (%)。

有鑑於此，NetBeacon 提出只為 long flow 維護 per-flow state。這大幅減少了競爭有限 stateful storage 的 flow 數量。實際上，我們很難事先知道 flow 的長度。因此，NetBeacon 引入一個只使用 per-packet features 的 long-short flow binary classification model，用來判斷某個 packet 是否屬於 long flow。具體做法是依訓練集中 flow 長度的第 80 百分位數，來劃分 long flow 與 short flow。取 long（short）flow 的前 N 個 packet 作為 long（short）flow 的樣本，再用 per-packet features 進行訓練與分類。這個 long-short flow binary classification model 是依任務而定的。例如在 P2P application fingerprinting 任務中，N = 7，accuracy 為 82%。

**Handling Storage Index Collisions（處理 storage index collision）.** 當 storage index 發生 collision 時，若現有 flow 的 inference class 已經確定，或該 flow 已經結束（即其最後一個 packet 的到達時間超過預先設定的 timeout），NetBeacon 就允許新 flow 使用被占用的 register。否則，NetBeacon 對這個新 flow 退回使用 per-packet 的 stateless features。

當 flow 已經通過 multi-phase sequential model（§ 4.2）中定義的最後一個 inference point，或模型在某個中間的 inference point 對該 flow 的 inference 結果已經足夠有信心時，這個 flow 的 inference class/result 就是已確定的。此時，NetBeacon 會把該 flow 的 inference 結果存入 flow class table，以該 flow 的 5-tuple 為 key，用來匹配這個 flow 後續的 packet。同時，它會更新該 flow 的 storage，標記其 inference 結果已確定，表示一旦發生 storage index collision，這個被占用的 register 就可以被後來的 flow 覆寫。新的 entry 是由 control plane 在收到 data plane 發出的、表示某個 flow 的 class 已確定的訊息後，動態插入 flow class table 的。同時，flow class table 中有些 entry 需要定期移除（依 FIFO 或 LRU 原則），以避免 table overflow。

- line 1–2：對 5-tuple 做 hash 得到 H1，取其最後 IndexSize 個 bit 作為 storage index S_id。
- line 3–5： packet 不是 resubmit packet 時，先查 flow class table（T_Class）。若這個 flow 的 5-tuple 已在表中（class 已確定），直接取表中的 class 作為這個 packet 的 class C。

- line 31：最後依 packet 的 class C 執行使用者自訂的處理。

如果 P 是一般 packet （即不是 resubmit packet，下文說明），就用 flow class table T_Class 來匹配（Alg. 1 的 line 4）。如果匹配到，該 packet 的 inference 結果／class 就直接指定為所匹配到的 class。

否則，NetBeacon 會檢查 stateful storage 中是否已經為 packet  P 配置了 per-flow state storage。為此，它用 S_id 取出所儲存的真正 flow ID（例如 5-tuple），並與 P 的 flow ID 比對。如果兩者相同，NetBeacon 就判定這是 S_id 所存 flow 的一個新 packet，並據此更新該 flow 的 state。同時，若 P 恰好是 inference point，NetBeacon 會計算 flow-level features F_f，並以此與從 P 抽出的 per-packet features F_p 一起進行模型 inference。如果分類機率大於預先設定的 threshold dt，這個 flow 的 class 就確定了。之後，data plane 會先更新該 flow 的 storage Reg_sure，表示其 class 已確定，再通知 control plane 把這個 flow 插入 flow class table。如果 P 不是 inference point，就使用已儲存的 inference 結果（即最近一次 inference point 得到的結果）作為它自己的分類結果。

相反地，如果 P 屬於一個尚未有 storage 的 flow，NetBeacon 只使用 P 的 per-packet features 取得其分類結果。如果 P 被分類為 long flow 的 packet，NetBeacon 會檢查 S_id 上的 storage 是空的，還是已經可以被覆寫。如果是，就用 S_id 所指的 storage 為 P 所屬的 flow 初始化 per-flow state。因此，storage register 採延遲釋放（lazy release）：當所儲存的 flow 已經 class-determined（或 timeout），且有新 flow 同時 hash 到這個 register 時，才會被釋放。

在整個流量分析過程中，NetBeacon 利用 resubmit 的 packet 來 (i) 更新既有 flow 的新 inference 結果，或 (ii) 為新 flow 初始化 storage。由於 Resubmit 的目的是觸發前面 stage 中 register 的修改（而不是修改 packet 本身），我們可以改為把 packet  mirror 到 loopback port 來觸發這些修改，而不用 Resubmit 或 Recirculation，這樣原始 packet 就不會被延遲。此外，只有觸發 inference 結果更新的 inference-point packet 才會被 mirror，它們只佔極小一部分的 packet，如 § 7.4 的量測所示。

### 5.4 Control Plane Logic（control plane 邏輯）

在 NetBeacon 中，control plane 負責 (i) 一開始就把 feature table 與 model table 安裝到 data plane 上，以及 (ii) 在 flow class 確定時，依 data plane 送來的請求（在 Tofino switch 上為 digest）更新 flow class table。注意，更新 flow class table 的延遲不會影響流量分析，因為沒有被 flow class table 匹配到的 packet，會改走一般的模型 inference pipeline。因此，control plane 不在 packet 分類的 critical path 上，這確保了 line-speed 的流量分析。

### 6.2 Multi-phase Model Inference（multi-phase 模型 inference）

我們的 multi-phase sequential model 架構在不同的 inference point 套用不同的模型。直觀的做法，是把每個 phase 的各個模型分別表示，各自有自己的 feature table 與 model table。另一種做法則是把它們的表示合併起來。如 Figure 12 所示，feature table 與 model table 都多了一個名為 total_packets 的 key，用來區分不同 phase 的模型。考慮到這些模型可能使用不同的 feature，如果某個 feature 沒有被特定模型使用，該 feature 的 range mark 就設為 ∗，表示任何 range mark。整體而言，模型 inference 需要兩個 stage：一個 stage 並行匹配 feature table，另一個 stage 匹配（合併後的）model table。

我們對 NetBeacon 進行了廣泛的評估，以證明以下三點：(i) 端對端（end-to-end）效能的提升：與 baseline 方法相比，NetBeacon 在流量分析的 accuracy 上有顯著提升，且結果與具備無限 stateful storage 的理想情況相當；(ii) data plane 上高效率的 model 表示：與 baseline 相比，NetBeacon 達到更高的分類 accuracy，同時消耗更少的 data plane table entry；(iii) 我們也探討 NetBeacon 中各個關鍵要素（moving pieces）的影響。

### 7.1 Experiment Setup（實驗設定）
〔PDF p.11〕

**Testbed Setup（測試環境）.** 在端對端實驗中，我們把 programmable switch 連接到兩台 Linux 伺服器。其中一台透過 tcpreplay 重播 pcap 檔，另一台則擷取從 programmable switch 收到的 packet。

**Metric and Features（評估指標與特徵）.** 我們以 packet 層級的 macro-accuracy（定義為各 class 的 Recall 之平均）作為指標。當資料集是平衡的（balanced）時，macro-accuracy 等於 accuracy。除非另有說明，我們在報告評估結果時會將 macro-accuracy 與 accuracy 互換使用。完整的 per-packet features 集合與 [51] 相同。完整的 flow-level features 集合則是 IPD 與 packet size 的 aggregate features 和 summary features。針對不同任務，我們從中挑選最重要的特徵。Model 的訓練使用 Python 的 sklearn 函式庫。

**Tasks（任務）.** 我們以下列任務評估 NetBeacon。

- P2P application fingerprinting（P2P 應用程式指紋辨識）。此任務對 P2P 應用程式的流量進行分類。我們使用三種 P2P 應用程式

  〔PDF p.12〕

  （eMule、uTorrent 與 Vuze）在 PeerRush dataset [41] 中的流量，因此這是一個三類（three-class）分類任務。
- Covert channel detection（covert channel 偵測）。此任務要從良性的 Skype 流量中，辨識出由抗審查（censorship resistance）工具 Facet [28] 所編碼的 covert channel 流量。我們使用 FacetTraffic dataset [3]，並選擇其中 12.5% 的類型作為 covert channel 流量。
- DDoS attack detection（DDoS 攻擊偵測）。此任務要從良性流量中辨識出 DDoS 流量。我們蒐集了八種進階的 DDoS 流量，包括 amplification attack（即 RIPv1、CLDAP、NTP、DNS 與 Memcached，這些是一項真實世界量測研究 [22] 所揭露的）以及 pulsing DDoS attack（依照 [33] 中的三種原始設定）。為避免造成真實世界的損害，我們在一個擁有 650 台 VM 的 virtual private cloud 中執行這些攻擊。良性的背景流量則使用 MAWI dataset [49]，該資料集蒐集自一條 backbone network（2020 年 1 月 15 日）。

### 7.3 Model Representation Performance（Model 表示效能）
〔PDF p.13〕

本節要說明，與其他 IDP 研究相比，NetBeacon 在 data plane 上的 model 表示更有效率。我們以 Mousika 與 Mousika(RF Distilled) [51] 作為兩個 baseline。Mousika 代表直接訓練出的 BDT model；Mousika(RF Distilled) 代表由已訓練的 Random Forest 經 distillation（蒸餾）所得到的 BDT model。

**Experiment Setup（實驗設定）.** 除了上述三個任務（即 P2P application fingerprinting、covert channel detection 與 DDoS attack detection）之外，本部分另外加入一個 traffic type classification（流量類型分類）任務。此任務使用 ISCXVPN dataset [12]，包含六種流量類型：chat、P2P、email、VoIP、streaming 與 file transfer。此任務選用 Random Forest。為了公平比較，NetBeacon 與 Mousika 使用相同的訓練資料。我們先從原始 packet 擷取特徵，作為 NetBeacon 的訓練資料；由於 Mousika 的 model 是 binary decision tree (BDT)，我們再把這些特徵轉換成二元（binary）形式，作為 Mousika 的訓練資料。

評估指標為分類 accuracy，以及表示該 model 所需的 data plane table entry 數量。對 NetBeacon 而言，table entry 數量是

### 7.4 NetBeacon Deep Dive（NetBeacon 深入分析）
〔PDF p.14〕

我們探討影響 NetBeacon 效能的各項因素。

**Throughput（吞吐量）.** Programmable switch 上的 PISA pipeline 保證任何編譯成功的程式都會以 line-speed 執行。P2P application fingerprinting、covert channel detection 與 DDoS attack detection 三個任務，在 100Gb forwarding port 上量測到的 throughput 分別為 99.12 Gbps、99.13 Gbps 與 99.18 Gbps。由於一個 pipeline 中的一個 100Gb loopback port 由 16 個 forwarding port 共用，為了確保 loopback port 不會成為瓶頸，每個 forwarding port 上被 mirror 的 packet 比例平均而言應小於 1/16。在我們的三個任務中，packet 的 mirror 比例分別為 3.8%、0.09% 與 1.28%。

**The Number of Inference Points（Inference point 的數量）.** Multi-phase sequential model 中所使用的 inference point／phase 數量，是影響效能的重要因素。如 § 4.2 所述，在較早的 phase，flow-level 資訊可能還不夠成熟（premature），這可能影響分類 accuracy。從 Figure 15a 可以看到，隨著加入更多 inference point，accuracy 也隨之提高。

**Determination Thresholds（determination threshold 的設定）.** 如 § 4.2 所述，我們為每個 inference point 設定一個 determination threshold。在 Figure 15b 中，我們探討了兩種 determination threshold。較低的 determination threshold 允許更早完成分類並釋放 storage register，但可能造成誤判。可以看到，當可用的 register 數量少（即 IndexSize 小）時，較低的 determination threshold 讓 register 能更早釋放，這足以彌補在較早的 phase 就做出推論決定所損失的 accuracy。因此，較低的 determination threshold 比較高的 determination threshold 取得更好的 accuracy。相反地，當 storage register 的數量較多時，使用較高的 determination threshold 比較有利。所以，determination threshold 應該依可用的硬體資源來決定。

**The Size of Stateful Storage (i.e., IndexSize)（Stateful storage 的大小，即 IndexSize）.** Stateful storage 是維護 per-flow state 與計算 flow-level features 所必需的。因此，緩解不同 flow 所造成的 storage index collision 問題至關重要。在 Figure 15c 中，我們顯示 stateful storage 的大小與分類 accuracy 呈正相關。同時，在有限的 stateful storage 之下，我們的 stateful storage 管理能以不小的幅度提升 packet 分類 accuracy。

**Imperfection of Hardware Hashing（硬體 hash 的不完美）.** 我們統計每個 storage register 被 hash 到的 flow 數量，並將其分布畫在 Figure 15d。理想情況下，所有 register 的命中次數應該相同，即 Figure 15d 中的紅色虛線。實際的分布確實偏離了理想分布，這可能造成額外的 storage index collision。

## 8 Discussion（討論）
〔PDF p.14〕

**Addressable Market Analysis（可服務市場分析）.** 先前針對 learning-based 流量分析的研究 [4, 14, 37]，把 feature engineering 與（或）ML model inference 放在 control plane（例如輔助伺服器）上。因此，它們可以使用相當精細複雜的特徵與 model，但分析 throughput 遠低於 line-speed。另一類研究 [2, 32, 61] 主要考慮 DDoS 緩解，把防禦規則編碼

〔PDF p.15〕

到 programmable switch 上，達成 line-speed 的流量過濾。然而，它們的做法無法推廣到其他 learning-based 流量分析。相較之下，NetBeacon 所主張的 IDP，是把通用的 learning model 直接嵌入 network data plane，以 line-speed 賦予流量分析智慧化的能力。與既有的 IDP 相關設計 [10, 26, 51, 55, 63] 相比，NetBeacon 在分析 accuracy 與 model 表示效率上都更勝一籌。然而，受限於 PISA pipeline，NetBeacon 的特徵與 model 架構都受到限制，這可能影響複雜任務的分析 accuracy，如 Table 5 所量化的。除了 programmable switch 之外，先前的研究也考慮把 SmartNIC [45, 50] 與以 DPDK 驅動的 host networking [35] 當作智慧化的 data plane，以取得更有彈性的運算與儲存，代價是 throughput 低得多（例如，NetFPGA-PLUS 為 200 Gbps，而 Tofino 1 programmable switch 整體為 6.4 Tbps）。

**Scalability Analysis（可擴展性分析）.** NetBeacon 的流量分析具有以下階層：flow class table 儲存已經確定分類 class 的 flow（Alg. 1 第 4–5 行）。當 packet 命中 flow class table 時，就不會再被部署在 flow class table 之後的 ML model 重新分析；否則，packet 進入一般的 ML inference。若 NetBeacon 為該 packet 在 register（SRAM）中維護了 per-flow state（Alg. 1 第 11–19 行），ML inference 會使用 flow-level features；否則，inference 僅基於 per-packet features（Alg. 1 第 21 行）。因此，*NetBeacon 可處理的並行 flow 數量沒有硬性上限（no hard-limit）*，因為必要時它可以退回使用 per-packet features。

NetBeacon 理論上能同時維護的 per-flow state 最大數量，取決於 register（SRAM）的大小以及所使用的 flow-level features。在最需要考量 scalability 的 DDoS 任務中，Tofino 1 switch（共有 4 個 pipeline）的一個 pipeline，最多可在 register（SRAM）中支援 140,000 個 flow index。Tofino 3 的 SRAM 大小增加 80%，pipeline 總數則加倍。在架構上，我們可以平行部署多個 NetBeacon instance，並在這些 instance 之間對 flow 做 load balance。每個 NetBeacon instance 各自獨立地以 line-speed 處理流量。

**Security Analysis（安全性分析）.** 我們討論幾種針對 NetBeacon 的 adaptive（或 whitebox）攻擊。第一類是資源耗盡攻擊（resource exhausting attack）：攻擊者產生大量並行的偽造（bogus）flow，使 switch 上可用的 SRAM 溢出。這本質上是一種 Denial-of-Capability (DoC) 攻擊 [38]。所幸 DoC 攻擊不會讓 NetBeacon 完全失效，因為它可以退回使用 per-packet features。針對 DoC 攻擊，很可能安全的（probably-secure）防禦方式是透過專用的 set-up protocol（例如 Portcullis [40]）。〔譯註：原文用字為 "probably-secure"，此處照字面譯出。〕實務上，DoC 攻擊可以透過聚合 flow（aggregating flows）或平行部署多個 NetBeacon instance 來緩解。

第二類攻擊旨在利用 NetBeacon 中的詳細系統參數。兩個代表性的例子是：(i) stealth attack：攻擊者先傳送良性 packet，待 NetBeacon 判定 flow class 之後，才傳送惡意 packet；(ii) low-rate-long-flow attack：攻擊者迫使 flow 逾時（timeout）。一般而言，這類攻擊有進入門檻，因為攻擊者需要先探測參數設定。為了緩解 stealth attack，NetBeacon 可以對 flow class table 中的 entry 強制設定最大 flow 長度限制。為了緩解 low-rate-long-flow attack，NetBeacon 可以為每個 flow 決定該 flow 專屬的 timeout（例如，已觀察到的最大 IPD 的兩倍）。

## 10 Conclusion（結論）
〔PDF p.15〕

Intelligent Data Plane (IDP) 有可能帶來一種新的網路設計典範：以資料驅動（data-driven）的 model、而非預先定義的 protocol，在 line-speed 下達成智慧化的流量分析。本文提出 NetBeacon，這是最先進的 IDP 設計，在 learning model 的 accuracy 與 model 表示效率上都優於先前的研究。NetBeacon 的核心由三項設計賦能：(i) 以 multi-phase sequential model 架構為中心、考量 data plane 特性的 model 設計，(ii) 高效率的 model 表示機制，以及 (iii) stateful storage 管理的設計。我們實作了 NetBeacon 的原型，並在多個流量分析任務上廣泛評估其效能。

**pForest and SwitchTree.** 在 pForest [10] 與 SwitchTree [26] 中，由左至右的各個 stage，對應 decision tree 由上而下的各層。每個 stage 的 table key 是 decision tree 對應層的 node 以及下一個分支（branch）。Action 的參數是該分支上 node 的資訊，包括 feature 與 threshold。匹配（match）之後，當前 feature 值與 feature threshold 的比較在 action 中執行。如此一來，switch 的 stage 數量就限制了 decision tree model 的深度。SwitchTree 的主要 P4 pseudocode 如 Figure 16 所示，其中 table tree1_level_i 代表 decision tree 1 第 i 層的 node。我們為每個 feature 建立一個 check action，這樣就不必像開源程式碼那樣，去判斷目前要比較的是哪一個 feature。然而不幸的是，在 production-grade switch 上，action 中不允許複雜的條件，且比較運算的兩側都不能是變數。我們在 Figure 16 中以紅色標示編譯錯誤（compiler 版本：9.1.0）。這些因素導致上述兩項研究無法在 production-grade switch 上實現。

**IIsy and Planter.** 在 IIsy [55] 與 Planter [63] 中，先對 feature 編碼，再對 decision tree 編碼。具體而言，feature 編碼把 feature 值對應到 decision tree 的分支，decision tree 編碼再把分支對應到 leaf node。如 Figure 16 所示，ig_md.tree1_feat1_code 代表 tree 1 中 feature 1 的分支。Planter 只給了一個簡單的範例，並不清楚它如何支援複雜的 decision tree model，例如當一棵 tree 中多次使用同一個 feature 時，Planter 如何對分支編碼。

**Mousika.** Mousika [51] 提出了一種對 data plane 友善的 decision tree model：binary decision tree (BDT)，它以 feature 的二進位位元作為 tree node。如 Figure 17 所示，feature f1 在 BDT 中被轉換為 4 個 binary feature，記為 f1-n，分別對應 f1 的四個位元。傳統 DT 中的規則 1 ≤ f1 ≤ 7，在 BDT 中需要由三個 leaf node 共同涵蓋，而一個 leaf node 對應 data plane 上的一個 table entry。這三個 node 恰好就是範圍 [1,7] 的三個 prefix。進一步地，若 1 ≤ f1 ≤ 7 與 1 ≤ f2 ≤ 7 兩者都需要滿足，就需要 3*3 個 leaf node，也就是 data plane 上的 9 個 table entry。簡言之，隨著需要組合的 feature 數量增加，BDT 的 leaf 數量與 data plane 上的 table entry 數量會面臨組合爆炸（combination explosion）的問題。Mousika 並非由 DT 直接轉換，而是透過以 binary feature 訓練來取得 BDT，這在一定程度上緩解了 BDT 的組合爆炸問題。

## Appendix B CRC Algorithm Optimization（CRC 演算法最佳化）
〔PDF p.18〕

如 § 5.1 所述，CRC 演算法需要解決 Equation (1) 中的最佳化問題。我們在此介紹一個 solver。這個 solver 的直覺是：逐步把範圍的 prefix 清單中的前兩個 prefix 合併成一個 prefix。例如，如 Figure 6 所示，[68,103) 的前兩個 prefix 是 010001** 與 01001***。要合併這兩個 prefix，P_start 需要向左移動 4。這是因為合併後的 prefix 需要比現有的 prefix 涵蓋更多（covers），即現有 prefix 之 covers 最大值的兩倍。在 [68,103) 的前兩個 prefix 中，01001*** 的 covers 最大，為 8，所以合併後的 prefix 需要有 16 個 covers。移動的步數為 4，即 16（合併後 prefix 的 covers）- 8（01001*** 的 covers）- 4（010001** 的 covers）= 8 - 4。我們在 Alg. 2 的第 14 行展示這個操作。當範圍的 prefix 清單中只剩一個 prefix（第 12 行），或 diff 為負（第 15 行）時，表示 P_start 無法再移動來合併 prefix。這樣一來，P_start 的移動次數不會超過

範圍 [r_{i-1}, r_i) 的 prefix 清單中的 prefix 數量，因此複雜度為 O(lg ℛ)。P_end 的搜尋想法與 P_start 相同。因此，總複雜度為 O((lg ℛ)²)。

> **Algorithm 2**（PDF p.19）：Consecutive Ranges Coding (CRC)（連續區間編碼）
>
> **Input：** r_1, r_2, ..., r_n 是某個 feature 的 n 個 threshold，該 feature 佔 w 個 bit。Prefix([r_i, r_{i+1})) 回傳以 Prefix 方法 [46] 對範圍 [r_i, r_{i+1}) 求得的 prefix 清單。Num(plist) 回傳清單 plist 的大小。Cov(p) 回傳 prefix p 所涵蓋的值的個數，即 p 的 covers。
>
> **Output：** Tern 是這 n 個範圍的 prefix 清單。

```
 1: r_0 ← 0, r_{n+1} ← 2^w, Tern ← []
 2: for each thresholds i = 1, ..., n do
 3:     Minm ← ∞                  ▷ Minm 是 prefix 數量的最小值
 4:     start ← r_{i-1}, end ← r_i
 5:     while end < r_{i+1} do
 6:         plist1 ← Prefix([r_i, end))
 7:         while start ≥ 0 do
 8:             plist2 ← Prefix([start, end))
 9:             if Num(plist1) + Num(plist2) < Minm then
10:                 Minm ← Num(plist1) + Num(plist2)
11:                 Best_s ← start, Best_e ← end
12:             if Num(plist2) == 1 then
13:                 Break
14:             diff ← Cov(plist2[1]) − Cov(plist2[0])
15:             if diff < 0 then
16:                 Break
17:             start ← start − diff
18:         if Num(plist2) == 1 then
19:             Break
20:         diff ← Cov(plist2[−2]) − Cov(plist2[−1])
21:         if diff < 0 then
22:             Break
23:         end ← end + diff
24:     Tern extend Prefix([r_i, best_e)) with higher priority 2i
25:     Tern extend Prefix([best_s, best_e)) with priority 2i+1
```

## Appendix C Supplements for Implementation（實作補充）
〔PDF p.19〕

**Determined Threshold（Determination threshold 的實作）.** 如 Alg. 1 第 14 行所示，data plane 需要判斷分類機率是否超過 determination threshold。NetBeacon 把分類機率與 threshold 的比較放在 control plane 上，如此一來 determination threshold 可以在不停機（without downtime）的情況下更新。具體而言，對於 class n，若分類機率達到（未達到）threshold，NetBeacon 就取 n + x（n）作為 model table 的 action parameter，其中 x 是任意一個大於 class 總數的數字。這樣，data plane 只需要判斷 action parameter 是否大於 x，就能知道機率是否超過 determination threshold。〔譯註：原文 "n + x (n)" 的括號與 "does (not)" 對應，即達到 threshold 時取 n + x，未達到時取 n。〕

**Flow Class Table Entry Replacement（Flow class table entry 的替換）.** 當 flow class table 已滿時，NetBeacon 會移除部分 table entry，以便插入新的 entry。類比於作業系統的 page replacement 演算法，這裡有兩種 table entry 替換演算法。FIFO（First In, First Out）：control plane 維護一份依插入順序排列的 flow 清單。需要替換 entry 時，FIFO 選擇最早插入的 table entry 作為被替換的 entry。FIFO 適用於各 flow 持續時間差異不大的情境。LRU（Least Recently Used）：可以設定一個計數器，記錄 flow class table 中每個 table entry 所匹配到的 packet 數量。計數器數值沒有變化的時間，就視為該 table entry 未被使用的時間。需要替換 entry 時，選擇最久未被使用的 table entry。LRU 適用於各 flow 持續時間差異很大的情境。
