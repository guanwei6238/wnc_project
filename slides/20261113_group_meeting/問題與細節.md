# 一、背景名詞

### Q1. IDP 是什麼？「line-speed」具體指什麼？
**短答**：IDP（Intelligent Data Plane）是把 ML 模型直接放進網路的 data plane（這篇是 programmable switch 的 pipeline），packet 經過時就做模型推論；line-speed 在論文裡的定義是「不降低網路轉送速度」。

**細節**：
- 論文的定義：line-speed (i.e., zero reduction to the network forwarding speed)。
- 對比：把模型放在 control plane（例如旁邊的 server）的 state-of-the-art 大約只能處理 10 Gbps［14］；而且 control plane 在分析的 critical path 上，會多出反應時間［2］。這個 10 Gbps 是論文引用的一個系統的數字，不是 control plane 方案的普遍上限。
- 論文認為 IDP 除了安全，也可以用在 differentiated routing、ECN threshold adjustment、buffer management。
- 容易誤解：line-speed 是指轉送速度不打折，不是指每個 packet 都做到完整的分析。NetBeacon 裡沒有 per-flow state 的 packet 只用 per-packet features（Q27、Q51）。

**出處**：PDF p.2 Abstract、§1（"at line-speed (i.e., zero reduction to the network forwarding speed)"；10 Gbps 與 reaction time 也在 p.2 §1）。

### Q2. PISA 是什麼？P4 和 Tofino 又是什麼？
**短答**：PISA（Protocol Independent Switch Architecture）是 programmable switch 的 pipeline 架構：parser → 多個 match/action stage → deparser；P4 是寫這條 pipeline 的語言；Tofino 是實作 PISA 的 switch 晶片，論文用的是第一代 Tofino 1。

**細節**：
- packet 先進 parser 解析 header，再依序經過多個 match/action stage 處理，最後由 deparser 把 packet 組回去；三者都可以程式化（Fig. 1）。
- 和 SDN／OpenFlow 的差別：OpenFlow 是 controller 對 switch 裝 flow entry；PISA 讓 pipeline 本身可以用 P4 這類語言程式化。
- 論文說 PISA 還不是 Turing complete。
- 原型：Barefoot Tofino 1，12 個 MAU stage，每條 pipeline 120MB SRAM、6.2MB TCAM；約 1300 行 P4_16（data plane）和 300 行 Python（control plane）。Tofino 1 一台有 4 條 pipeline，整台合計 6.4 Tbps。
- **背景知識，非論文內容**：MAU 是 Match-Action Unit，就是一個 stage。switch 的 port 分屬不同 pipeline，每條 pipeline 有自己的 stage 和記憶體（論文說一個 loopback port 由同一條 pipeline 的 16 個 forwarding port 共用，也是這個概念，p.14 §7.4）。

**出處**：PDF p.2 §1（not Turing Complete）；p.3 §2.1、Fig. 1；p.10 §6；p.15 §8（4 pipelines、6.4 Tbps）。

### Q3. match/action 和 stage 是什麼？為什麼 stage 數會限制設計？
**短答**：每個 stage 裡有 table，用 header 或 metadata 當 key 去比對，命中就執行對應的 action（改 metadata、更新 register 等）。有相依關係的 action 必須放在不同 stage，而 stage 數是固定的（Tofino 1 是 12 個），所以「要幾步才算得出來」直接受硬體限制。

**細節**：
- 原文：Each match corresponds to an action, where specific computation and storage modification can be executed. Mutually dependent actions need to be placed on different stages。
- packet 的 header 和 metadata 是每個 packet 各自一份、下一個 packet 進來就重新初始化（stateless）；跨 packet 的狀態要放在 counter、meter、register（stateful）。
- NetBeacon 裡的例子：
  - variance 的計算有前後相依，要用 4 個 stage（Q17）。
  - 模型推論只要 2 個 stage：一個 stage 平行查所有 feature table，下一個查 model table（Q24）。
  - P2P、covert channel 任務都用滿 12 個 stage，DDoS 用 9 個（Q42）。
  - pForest、SwitchTree 把 tree 的一層對到一個 stage，所以 tree 深度被 stage 數限制。
- **背景知識，非論文內容**：match table 的 entry 由 control plane 寫入，data plane 只能查、不能自己新增 entry。這就是為什麼「判定後寫進 flow class table」要繞到 control plane（Q9、Q31）。

**出處**：PDF p.3 §2.1；p.11 §6.1–6.2；p.12–13 §7.2；p.18 Appendix A。

### Q4. exact、ternary、LPM、range matching 差在哪？
**短答**：exact 是 key 完全相等；ternary 是每個 bit 可以是 0、1 或 `*`（不在乎）；LPM 是取前綴最長的那條（像 routing table）；range 是「值落在 [a, b) 之間」。PISA 支援前三種，range 不一定支援，得拆成多條 ternary entry。

**細節**：
- 原文：The match/action supports exact matching, ternary matching, and longest prefix matching (LPM)（p.3）；range matching is not universally supported on programmable switches, and it has to be coded into ternary matching (bits in a ternary entry are 0, 1, or ∗)（p.6）。
- 例子（Fig. 6）：[65, 103) 要 8 條 ternary entry，例如 `01000001` 表示 65、`0100001*` 表示 [66, 68)、…、`01100110` 表示 102（完整列表在 Q20）。
- ternary entry 有優先序，多筆同時命中時取優先序高的；CRC 就是利用這點（Q22，Fig. 6 左下標了 Higher Priority）。
- **背景知識，非論文內容**：LPM 可以看成 ternary 的特例（mask 是從最高位起連續的 1）。
- **背景知識（細節我不確定）**：P4 語言裡有 range 這種 match kind，但各硬體支援程度不同，底層也常是展開成 TCAM entry。論文只說 not universally supported（Fig. 6 標 Not supported by the switch），Tofino 上的確切情況我無法從論文確認，報告時以論文的說法為準。

**出處**：PDF p.3 §2.1；p.6–7 §5.1、Fig. 6。

### Q5. TCAM 和 SRAM 差在哪？為什麼論文要分開報告？
**短答**（**背景知識，非論文內容**）：TCAM 是能「一次和所有 entry 平行比對、支援 `*` 位元」的記憶體，用來做 ternary 和 LPM；SRAM 是一般記憶體，用來做 exact match、register、counter。TCAM 貴、耗電、容量小很多，所以兩種資源要分開看。

**細節**：
- **背景知識，非論文內容**：TCAM（Ternary Content-Addressable Memory）每個 entry 存 value 和 mask，查詢時所有 entry 同時比對，回傳優先序最高的命中者，所以 ternary entry 數直接吃 TCAM；exact match 通常用 hash table 放在 SRAM。
- 論文的數字：Tofino 1 每條 pipeline SRAM 120MB、TCAM 6.2MB。這兩個數字的單位我無法從論文以外確認，報告時照論文唸，不要拿來換算「每條 flow 用幾 byte」。
- **推論**：NetBeacon 的 feature table、model table 是 ternary（Fig. 12 的 key 標 ternary），吃 TCAM；per-flow state 放在 register，論文寫 registers (SRAM)。所以 entry 爆炸主要是 TCAM 的問題，能同時追蹤多少 flow 主要是 SRAM 的問題。
- 實測用量：P2P SRAM 17.29%、TCAM 31.25%；covert channel 13.44%、34.03%；DDoS 11.11%、1.85%。**推論**：DDoS 的 TCAM 很低，和它非常小的模型一致（四個 phase 是 `1*1`、`1*4`、`1*1`、`1*1`，Q11）。

**出處**：PDF p.4 §2.1、p.10 §6（120MB／6.2MB）；p.11 Fig. 12；p.12–13 §7.2（用量）；p.15 §8（"registers (SRAM)"）；p.19 Appendix D。

### Q6. PISA 不能做哪些運算？這些限制在 NetBeacon 的哪裡出現？
**短答**：只支援 boolean、shift、加、減；不支援乘除、浮點數、loop、複雜條件。結果是：模型選 tree；mean、variance 要靠 shift 或離線換算；機率和 threshold 的比較要事先算進 table；percentile 這類 feature 做不到。

**細節**：
- 原文：it supports boolean, shift, add and subtract operations, but not multiplication and division. Float operations, loop operations, and complex conditional operations are not supported as well。
- 對應到 NetBeacon 的設計：
  - tree 的結構比 neural network 更像 match/action（Q10）。
  - mean：把 tree 的 threshold 離線乘上 inference point 的位置，或用 shift（inference point 要是 2 的次方）；variance 的除法只能 shift，平方只支援只看前 4 bit 的近似（Q17）。
  - XGBoost 最後的 Sigmoid 不能在 data plane 算，改成離線算好放進 model table（Q23）。
  - determination threshold 的比較放在 control plane，data plane 只比較整數 action parameter（Q15）。
  - 不支援難算的 flow-level features，例如 packet size 的 percentile。
  - SwitchTree 在 action 裡做 `<` 比較、兩邊都是變數，Tofino 編譯器（9.1.0）不接受；論文說這是 pForest、SwitchTree 無法上硬體的原因。

**出處**：PDF p.3 §2.1；p.4 §2.2（percentile）；p.6 §4.2；p.8 §5.1；p.11 §6.1；p.18 Appendix A、Fig. 16；p.19 Appendix C。

### Q7. register 是什麼？為什麼一個 packet 只能存取一次？
**短答**：register 是 PISA 上能跨 packet 保存資料的 stateful storage（例如每條 flow 的 packet 數、byte 數）。每個 register 在一個 packet 經過 pipeline 時只能存取一次，所以「先讀、等後面算出結果再寫回」做不到；NetBeacon 要讓 packet（的複本）再走一次 pipeline 才能寫回。

**細節**：
- 原文：PISA also provides stateful and persistent storage, such as counters, meters, and registers（p.3）；Probably, the most "surprising" storage limitation is that each register can only be accessed once when a packet traverses the switching pipeline. As a result, operations such as read-and-then-update registers are not supported natively（p.4）。
- **背景知識，非論文內容**：P4 的 register 是一個用 index 存取的陣列，放在某一個 stage；packet 經過那個 stage 時可以對其中一格做一次「讀－改－寫」（例如加 1），但 pipeline 只往前走，後面的 stage 不能再回頭改它。
- NetBeacon 遇到的地方（Alg. 1）：第 8 行讀 class register，但新的 class 要到後面的 stage 模型推論完（第 13 行）才知道；寫回 class 和 flow ID（第 29–30 行）只能在第二趟做，第 17、27 行的 Resubmit 就是為了這個。論文的說法是 the purpose of Resubmit is to trigger the modification of the registers in previous stages。（「第 8 行和第 29 行是同一個 register，所以需要第二趟」是**推論**，論文只說是 previous stages 的 register。）
- 用詞注意：論文說的「N 個 register」實際上是「N 格可存 per-flow state 的位置」；IndexSize 16 ＝ 最多 65,536 個 per-flow state。每條 flow 的 state 包含 flow ID、class、是否已判定、packet 數、byte 數、平方和等多個欄位（Alg. 1、Fig. 11）。

**出處**：PDF p.3–4 §2.1；p.9 §5.2；p.10 Alg. 1、§5.3；p.11 Fig. 11；p.12 §7.2。

### Q8. resubmit、recirculation、mirror、loopback port 各是什麼？NetBeacon 用哪個？
**短答**：三者都是讓 packet 或它的複本再走一次 pipeline 的機制。Alg. 1 寫的是 Resubmit，但實作改成把 packet mirror 一份到 loopback port：原本的 packet 照常轉送、不被延遲，複本回到 pipeline 去更新前面 stage 的 register。

**細節**：
- 論文：PISA provides various mechanisms (such as resubmit, recirculation, packet generation) to further extend programming capabilities（p.3）。
- **背景知識，非論文內容**：
  - resubmit：ingress 處理完，把 packet 送回 ingress 開頭再處理一次。
  - recirculation：packet 走完（含 egress）之後，經由 recirculation port 再回到 ingress。
  - mirror：複製一份 packet 送到指定的 port。
  - loopback port：設定成「送出去的 packet 會直接回到自己 ingress」的 port。
  - 前兩種都讓原 packet 晚一點出去；mirror 轉送的是原 packet，回頭跑的是複本，所以原 packet 不受影響。
- 原文：we could trigger modifications by mirroring the packet to the loopback port, instead of Resubmit or Recirculation, so that the original packet is not delayed. Further, only the inference-point-packets that trigger inference result updates are mirrored, counting for a very small fraction of packets（p.10）。
- 實測 mirror 比例：P2P 3.8%、covert channel 0.09%、DDoS 1.28%；一個 100Gb loopback port 由同一條 pipeline 的 16 個 forwarding port 共用，所以每個 port 平均要小於 1/16 才不會塞住 loopback port（Q43）。
- **推論**：mirror 的代價是更新變成非同步——複本回到 pipeline 之前，同一條 flow 的下一個 packet 可能還讀到舊的 class 或舊的 flow ID。論文沒有討論這段時間差。

**出處**：PDF p.3 §2.1；p.10 Alg. 1 第 17、27–30 行、§5.3；p.14 §7.4。

### Q9. 在 switch 上講的 control plane 指什麼？digest 是什麼？
**短答**：control plane 是負責「設定 data plane」的軟體，跑在 switch 的 CPU 或外接的 server 上，負責裝 table entry；digest 是 Tofino 上 data plane 傳訊息給 control plane 的機制。NetBeacon 的 control plane 只做兩件事：一開始裝 feature table 和 model table；收到 digest 後把已判定的 flow 寫進 flow class table。

**細節**：
- 原文：the control plane is responsible for (i) installing the feature tables and model table on the data plane at the very beginning, (ii) updating the flow class table upon receiving requests (digest in Tofino switch) from the data plane when the flow class is determined（p.10 §5.4）。程式約 300 行 Python（p.10 §6）。
- 論文在 §8 把 prior art 的 control plane 舉例成 an auxiliary server（p.14）。
- **背景知識，非論文內容**：data plane 不能自己新增 match table 的 entry，所以「判定後寫入 flow class table」必須繞到 control plane，這也是寫入會有延遲的原因（Q33）。
- determination threshold 的比較其實也在 control plane 這邊完成：產生 model table entry 時就把「機率有沒有達到 threshold」編進 action parameter（Q15）。

**出處**：PDF p.10 §5.4、§6；p.14 §8；p.19 Appendix C。

# 二、ML 部分

### Q10. 為什麼用 tree，不用 neural network？
**短答**：論文的理由是 tree 的結構比 neural network 更接近 match/action，neural network 有大量非線性運算。這是「選擇」，論文沒有說 switch 上只能放 tree。

**細節**：
- 原文：Similar to prior art [26, 51, 63], NetBeacon sticks to decision tree based learning models because their constructions are more similar to the match/action operations on the data plane, compared with the neural networks that involve significant non-linear computations。
- ［26, 51, 63］是 SwitchTree、Mousika、Planter，都選 tree。
- **推論**：一棵 tree 的模型推論就是「每個 feature 落在哪個區間 → 走到哪個 leaf」，剛好可以變成查表；neural network 需要乘法和非線性函數，PISA 都不支援（Q6）。
- 論文提到的 SmartNIC 做法之一［45］，題目是 Rearchitecting Traffic Analysis with Neural Network Interface Cards；論文把 SmartNIC 當成「計算能力較強、吞吐較低」的另一類硬體，不在本文範圍（Q53）。

**出處**：PDF p.6 §4.2；p.4 §2.2 Design Goals；參考文獻［45］（p.17）。

### Q11. Random Forest 和 XGBoost 差在哪？NetBeacon 實際用了多大的模型？
**短答**：（前半是**背景知識，非論文內容**）RF 是很多棵獨立訓練的 tree 投票；XGBoost 是 gradient boosting，一棵接一棵修正前面的誤差，最後把所有 tree 的分數加總再過 Sigmoid。實際上 NetBeacon 的模型很小：P2P 每個 phase 只有 1 棵深度 9 的 tree，DDoS 有三個 phase 是深度 1 的 tree。

**細節**：
- **背景知識，非論文內容**：
  - Random Forest（bagging）：每棵 tree 用抽樣過的資料和隨機的 feature 子集各自訓練，彼此獨立；分類時多數決（或平均各棵的機率）。
  - XGBoost（boosting）：第 k 棵 tree 去擬合前 k−1 棵加總後剩下的誤差（gradient）；每個 leaf 是一個實數分數，所有 tree 的分數相加後經過 Sigmoid（二元）或 softmax（多類）得到機率。
- 對 data plane 的影響（論文）：RF 可以每棵 tree 各自查表，最後接一張 plurality table 投票；XGBoost 最後要過 Sigmoid，不能分開算，要把多棵 tree 合併成一張 model table（Q23）。
- 各任務的選擇：P2P 用 RandomForest，covert channel、DDoS 用 XGBoost（Table 4）。論文沒說為什麼這樣分。**推論**：論文的 XGBoost 合併例子用 Sigmoid（二元輸出），而 covert channel、DDoS 正好是二元分類，P2P 是三類。
- 模型大小（Appendix D；`a*b` ＝ a 棵 tree、最大深度 b）：
  - P2P：NetBeacon(Pkt) `2*9`；七個 phase 都是 `1*9`；flow size prediction（long-short 模型）`1*8`。
  - Covert channel：NetBeacon(Pkt) `1*10`；九個 phase 依序 `2*5`、`3*6`、`3*6`、`3*6`、`3*7`、`2*7`、`3*6`、`3*5`、`3*4`。
  - DDoS：NetBeacon(Pkt) `1*4`；四個 phase 依序 `1*1`、`1*4`、`1*1`、`1*1`。
- **推論**：所以 P2P 雖然寫 RandomForest，flow-level 的每個 phase 實際上是單棵 tree；DDoS 有三個 phase 是只切一刀的 tree，表示這個資料集用一兩個 flow-level feature 就分得開。論文用 tree 數、深度、leaf 數控制 entry 數（p.6 §4.2），但沒說明為什麼選這些大小。

**出處**：PDF p.6 §4.2；p.8 §5.1；p.12 Table 4；p.19 Appendix D。

### Q12. per-packet、flow-level、aggregate、summary features 各是什麼？各任務用了哪些？
**短答**：per-packet feature 從單一 packet 就拿得到，通常是 header 欄位（packet size、TTL、protocol）；flow-level feature 要結合同一條 flow 其他 packet 的資訊，又分 aggregate（照固定規則累加，例如「size 落在 [96, 112) 的 packet 數」）和 summary（max／min、mean、variance）。

**細節**：
- aggregate feature 寫成 F ＝ aggr(a, c, d)：a 是看哪個屬性，c 是條件，d 是符合條件時怎麼更新。例子：F ＝ aggr(packet size, [96, 112), +1) 記錄 size 落在 [96, 112) 的 packet 數。summary feature 不能用預先定好的更新規則表示，mean、variance 還需要乘除。
- 實作：每個 aggregate feature 一張 table，a 是 key、c 是 entry、d 是命中後的更新（Fig. 11 第 1–5 行）；max／min 是和 register 裡存的值比較後更新。
- feature 的來源：per-packet features 的完整集合和 Mousika［51］相同；flow-level features 是 IPD（inter-packet delay）和 packet size 的 aggregate、summary features；每個任務依 information gain 挑最重要的幾個。
- 各任務實際用的 flow-level features：
  - P2P（七個）：packet size 的 max、min、mean、variance，IPD 的 min，size 落在 [48, 64) 和 [80, 96) 的 packet 數。
  - Covert channel：size 落在 [96, 112)、[112, 128)、[128, 144)、[144, 160)、[160, 176)、[176, 192) 的 packet 數（全是 aggregate）。
  - DDoS：IPD 的 min 和 packet sizes。
- **推論**：Fig. 2 上半的 bin_x 應該就是這類「落在某個 size 區間的 packet 數」，但論文沒有逐一定義。

**出處**：PDF p.5 Table 2；p.5–6 §4.1；p.11 §6.1、Fig. 11、§7.1；p.12–13 §7.2。

### Q13. 為什麼需要 multi-phase？用一個模型不行嗎？
**短答**：flow-level feature 會隨 flow 進行一直變——前 4 個 packet 算的平均和前 32 個算的不一樣——一個模型很難適用所有時間點。所以在不同 phase 各用一個模型，每個模型都用「那個時間點算得到的 feature」訓練和做模型推論。

**細節**：
- Fig. 4：deviation degree ＝ abs(a − b)/max(a, b)，a 是 feature 的最終值、b 是只看前 n 個 packet 時的值；PeerRush 的 mean of IPD、ISCXVPN 的 variance of packet size 都隨 phase 有明顯變化。
- Fig. 5：single model 對 multi-phase sequential model，三個任務後者都較高；正文只說 using a single model to perform inference based on flow-level features yields low accuracies，沒有給數字。各子圖縱軸起點不同（DDoS 從 96 開始），不要跨子圖比柱高。
- 原文：At each phase, NetBeacon uses the features computed at that phase for both training and inference, i.e., flow-level features at the n-th packet are computed based on the first n packets。
- §1 的說法：reducing the errors introduced by making premature classification decisions based on a single inference model。
- 另一個好處：搭配 determination threshold，有把握就提早判定、提早釋放 storage（Q15、Q30）。

**出處**：PDF p.3 §1 (i)；p.6 §4.2、Fig. 4、Fig. 5。

### Q14. inference point 怎麼選？越多越好嗎？
**短答**：位置依任務決定，可以均勻也可以特別安排；用到 variance 就要放在 2 的次方；兩個 inference point 不能隔太遠，因為中間的 packet 沿用前一次的結果。實驗顯示 inference point 越多 accuracy 越高，但論文沒有量多一個 phase 的成本。

**細節**：
- 原文：The exact arrangement of inference points is task-dependent … the inference points could be placed either uniformly or specifically, according to the task. For instance, if a model uses variance as features, the inference points should be placed at power-of-2 positions … the interval between two inference points should not be too large。
- 實際位置：
  - P2P：{2, 4, 8, 32, 256, 512, 2048}，7 個；用了 mean、variance，全是 2 的次方。
  - Covert channel：{512, 1024, 1500, 2048, 3000, 4096, 6000, 8192, 10000}，9 個。
  - DDoS：{2, 5, 8, 16}，4 個。
  - 後兩個任務沒用 variance，所以不受 2 的次方限制。
- **推論**：covert channel 的第一個 inference point 在第 512 個 packet，表示短於 512 個 packet 的 flow 永遠用不到 flow-level 模型；這和論文說「這個 dataset 的 Skype flow 都很長」一致。
- Fig. 15a：P2P 和 covert channel 兩個任務，accuracy 隨 phase 數增加而上升。
- **論文沒有說**：怎麼系統性地挑位置（沒有演算法），以及多一個 phase 要多付多少 table entry 或 mirror。
- **被問到時可以怎麼回答**：「論文只說依任務決定，給了三組實際位置，成本沒有量。可以推想每多一個 phase，feature table 和 model table 就多一組以 total_packets 區分的 entry（Q24），也多一批要 mirror 的 packet（Q8）。」（**推論**）

**出處**：PDF p.6 §4.2；p.12–13 §7.2；p.14 §7.4、Fig. 15a。

### Q15. determination threshold 怎麼用？data plane 沒有浮點數，怎麼比較機率？
**短答**：每個 phase 有一個 threshold；某個 inference point 的分類機率 ≥ threshold，就表示模型有把握，這條 flow 提早判定，不用等後面的 inference point，同時釋放 register、寫進 flow class table。比較本身是 control plane 產生 model table entry 時就算好、編進 action parameter，data plane 只做整數比較。

**細節**：
- 原文：When the classification probability at a specific inference point is above the corresponding determination threshold, it indicates that the multi-phase sequential model is confident to pre-decide the flow's class without using the subsequent inference points. This design facilitates the stateful storage management（p.6）；Alg. 1 第 14 行 if P ≥ dt。
- 實作（Appendix C）：model table 每個 entry 對應的機率是離線就知道的，所以 control plane 可以先比好：class n 的機率達到 threshold 就存成 n + x，沒達到就存成 n，x 是大於 class 總數的任意數；data plane 只要看 action parameter 是否大於 x。論文說這樣 threshold 可以 updated without downtime（只要改 entry）。
- 取捨（Fig. 15b）：較低的 threshold 讓 flow 早判定、早釋放 register，但可能判錯；register 少（IndexSize 小）時低 threshold 較好，register 多時高 threshold 較好；結論是 threshold 要依可用的硬體資源決定。只比了 0.7 和 0.8，只在 covert channel 任務。
- **論文沒有說**：Fig. 13 主實驗各任務用的 threshold 值；RF（P2P）的「機率」怎麼定義。
- **被問到時可以怎麼回答**：「論文只在 Fig. 15b 比較 0.7 和 0.8，主實驗用哪個值沒寫。」

**出處**：PDF p.6 §4.2；p.10 Alg. 1 第 13–16 行；p.14 §7.4、Fig. 15b；p.19 Appendix C。

### Q16. 不是 inference point 的 packet 怎麼分類？
**短答**：看情況。命中 flow class table 的，直接用表裡的 class；有 per-flow state 的，沿用最近一次 inference point 存在 register 裡的結果；沒有 state 的，用只看 per-packet features 的模型（flow-agnostic model）逐 packet 分類。

**細節**：
- 原文：The packets not selected as inference points use the inference result of its previous and closest inference point（p.6）；If P is not an inference point, it uses the stored inference result (i.e., the result obtained at the most recent inference point)（p.10）；In addition to flow-aware learning models, NetBeacon employs a flow-agnostic model to classify packets that cannot be analyzed using flow-level features（p.6）。
- Alg. 1：第 4–5 行（flow class table）；第 18–19 行（C ← C_stored）；第 21 行（沒有 storage：C ← InferClass(F_p)）。
- **推論**：一條剛拿到 storage 的 flow，在第一個 inference point 之前，register 裡的 class 是「初始化 storage 的那個 packet」的 per-packet 結果（第 21 行算出 C → 第 27 行 Resubmit(C) → 第 29 行寫入）。covert channel 的第一個 inference point 在第 512 個 packet，這段期間不短。
- **推論**：沒有 storage 的 flow，每個 packet 各自用 per-packet 模型分類，所以同一條 short flow 的不同 packet 可能被分到不同 class；論文的 packet-level 指標本來就是逐 packet 算。

**出處**：PDF p.6 §4.2；p.10 Alg. 1、§5.3。

### Q17. mean 和 variance 在沒有乘除的硬體上怎麼算？
**短答**：mean 有兩種做法：把 tree 的 threshold 離線乘上 inference point 的位置（直接比「總和」），或在 2 的次方的位置用 shift 當除法。variance ＝ E(X²) − E(X)²，除法只能用 shift（所以 inference point 必須是 2 的次方），平方用只看前 4 個 bit 的近似，整個計算要 4 個 stage。

**細節**：
- mean 的原文：One way to work around this limitation is to multiply the threshold by the position of the corresponding inference point, which can be done offline, after obtaining the multi-phase sequential models. An alternative way is to rely on the shift operation, which, however, requires the positions of inference points to be a power of 2。
  - **推論**的例子：第 8 個 packet 的 tree 節點若是「mean size < 100」，等價於「total size < 800」，800 可以離線算好放進 feature table，data plane 不用做除法。
- variance 的步驟（Fig. 11）：
  - 第 1 個 stage：register total_size 記 byte 總和、size_square_sum 記 size 平方和（正文把前者叫 total_bytes，指的是同一個）。
  - 第 2 個 stage：packet 數是 2 的次方（例如 8）時，size_mean ＝ total_size >> 3、size_square_sum_mean ＝ size_square_sum >> 3。
  - 第 3 個 stage：算 size_mean 的平方。
  - 第 4 個 stage：兩者相減得到 size_var。
- 平方是近似：only considers the first 4 bits of the value，例如論文說 0b101000001（320）和 0b101011111（351）的平方相同。（小筆誤：0b101000001 其實是 321，不影響論點，兩者前 4 bit 都是 1010。）
- max／min 不需要除法：和 register 裡的值比較後更新。
- **背景知識，非論文內容**：右移 k 位等於除以 2^k 再取整，所以除數只能是 2 的次方。

**出處**：PDF p.11 §6.1、Fig. 11。

### Q19. macro-accuracy 怎麼定義？為什麼用它？
**短答**：論文的主要指標是 packet-level macro-accuracy：每個 packet 算一個樣本，先算每個類別的 recall，再取平均；資料平衡時就等於 accuracy。論文之後把 macro-accuracy 和 accuracy 交替使用。

**細節**：
- 原文：We use packet-level macro-accuracy (defined as the average of Recalls for different classes) as the metric. When the dataset is balanced, macro-accuracy equals to accuracy. Unless otherwise stated, we use macro-accuracy and accuracy interchangeably when reporting evaluation results。
- **背景知識，非論文內容**：類別 c 的 recall ＝ 真正屬於 c 的樣本中被判對的比例。二元分類時 macro-accuracy ＝ (TPR + TNR)/2 ＝ 1 − (FPR + FNR)/2，也叫 balanced accuracy。
- **推論**：用 macro 平均的好處是少數類別不會被多數類別淹沒；P2P（3:6:2）和 DDoS（6:1）的類別比例都不平衡（Table 4）。但「packet-level」表示 packet 多的 flow 權重大，macro 只平衡類別、沒有平衡 flow 長度（Q55）。

**出處**：PDF p.11 §7.1；p.12 Table 4。

# 三、Model representation

### Q20. tree 放進 table 時，entry 為什麼會爆炸？
**短答**：一個 leaf 對應「每個 feature 各落在某個範圍」的組合；switch 不一定支援 range matching，每個範圍要拆成好幾條 ternary entry，而且三個條件要同時成立，所以 entry 數是各範圍 entry 數相乘。Fig. 6 的 leaf 5 要 8 × 1 × 6 ＝ 48 條。

**細節**（照 Fig. 6 算一次）：
- tree 有三個 8-bit feature f1、f2、f3。leaf 5 的路徑是 f3 ≥ 10 → f1 ≥ 65 → f1 < 103，所以 leaf 5 ＝ f1 ∈ [65, 103)、f2 ∈ [0, 256)（路徑上沒出現的 feature 取整個範圍）、f3 ∈ [10, 256)。
- 如果支援 range matching：一條 entry 就夠（Fig. 6 的 Model table (1)，圖上標 Not supported by the switch）。
- 用經典的 prefix 方法［46］拆成 ternary（bit string 是 Fig. 6 (2) 印出來的）：
  - f1 ∈ [65, 103) → 8 條：`01000001` [65,66)、`0100001*` [66,68)、`010001**` [68,72)、`01001***` [72,80)、`0101****` [80,96)、`011000**` [96,100)、`0110010*` [100,102)、`01100110` [102,103)。
  - f2 ∈ [0, 256) → 1 條：`********`。
  - f3 ∈ [10, 256) → 6 條：`0000101*` [10,12)、`000011**` [12,16)、`0001****` [16,32)、`001*****` [32,64)、`01******` [64,128)、`1*******` [128,256)。
- model table 的一條 entry 要同時寫 f1、f2、f3 三段 key，每種組合各一條：8 × 1 × 6 ＝ 48 條（Fig. 6 標 Combinatorial explosion of entries）。
- **推論**：feature 越多、範圍邊界越不對齊 2 的次方，乘起來越大；而且每個 leaf 都要各自展開。
- 容易講錯：48 是這個例子中 leaf 5 一個 leaf 的 entry 數，不是整體的減少比例；整體比較是 Fig. 14 的 75%（Q40）。

**出處**：PDF p.6–7 §5.1、Fig. 6（caption："the number of table entries to represent leaf 5 increases from 1 to 48 (8 × 1 × 6)"）。

### Q21. range marking 怎麼讓每個 leaf 在 model table 只用 1 個 entry？
**短答**：拆成兩層表。每個 feature 一張 feature table，把數值轉成一個 bit string（range mark）；model table 的 key 是各 feature 的 range mark，用 `*` 把相鄰的區間合併，所以每個 leaf 只要一條 entry。範圍展開的成本移到 feature table，而且所有 leaf 共用。

**細節**（照 Fig. 6）：
- f1 在 tree 裡有三個門檻 25、65、103，把 [0, 256) 切成四個 basis range：[0,25)、[25,65)、[65,103)、[103,256)。
- 編法（Table 3 的直覺）：第 j 個 bit ＝ 1，若這個 basis range 落在 [0, r_j) 裡（r_1 ＝ 25、r_2 ＝ 65、r_3 ＝ 103）。所以 [0,25) → `111`、[25,65) → `011`、[65,103) → `001`、[103,256) → `000`（Fig. 6 (a1)）。
- f2 只有門檻 46：[0,46) → `1`、[46,256) → `0`；f3 只有門檻 10：[0,10) → `1`、[10,256) → `0`（Fig. 6 (a2)(a3)）。
- tree 的節點常跨好幾個 basis range（論文叫 associative range）：例如 leaf 4 的 f1 ∈ [0, 65) 跨了 [0,25) 和 [25,65)，在 model table 寫成 `*11`，同時配到 `111` 和 `011`。這就是 range mark 的第二個條件：任意連續幾個 basis range 合起來，也要能用一個 ternary 字串表示。
- model table（Fig. 6 (b)），一個 leaf 一條：leaf 1 (`111`, `1`, `1`)；leaf 2 (`111`, `0`, `1`)；leaf 3 (`0**`, `*`, `1`)；leaf 4 (`*11`, `*`, `0`)；leaf 5 (`001`, `*`, `0`)；leaf 6 (`000`, `*`, `0`)。
- **推論**：原本的 entry 數是「每個 leaf 的各範圍 entry 數相乘」再對所有 leaf 加總；現在變成「各 feature table 的 entry 數相加」＋「leaf 數」，乘法變加法。range mark 的長度等於該 feature 的門檻數（Table 3 的例子 3 個門檻 → 3 bit），門檻越多 model table 的 key 越寬。

**出處**：PDF p.7 §5.1、Fig. 6、Table 3（"each leaf node only consumes a single ternary entry in the model table, regardless of how many feature table entries are related with this leaf node"）；p.8 §5.1（leaf 4 的 `*11`）。

### Q22. range coding（CRC）在做什麼？
**短答**：feature table 的 key 還是範圍，還是要轉成 ternary。CRC（consecutive range coding）利用「這些範圍連續、蓋滿全部值、低的範圍優先序較高」的特性，把某個範圍擴大成較好用 prefix 表示的 parent range，多蓋到的部分用更高優先序的 entry 擋掉，總條數比傳統 prefix 方法少。

**細節**：
- 做法（Fig. 7）：從最低的 basis range 開始編。對 [r_{i−1}, r_i)，找一個 parent range [p_start, p_end)，p_start ∈ [0, r_{i−1}]、p_end ∈ [r_i, r_{i+1})：用 accept prefix 表示 parent range（a），用優先序較高的 deny prefix 擋掉 [r_i, p_end)（c）。[p_start, r_{i−1}) 那段（b）不用管，因為更低的 basis range 的 entry 優先序本來就比較高，會先命中。目標函數是 Equation (1)：min Prefix([p_start, p_end)) + Prefix([r_i, p_end))。
- Fig. 6 的例子：
  - 正文：several smaller prefixes for [65, 103) … are merged to two larger prefixes `010*****` and `01100***` after expanding [65, 103) into [64, 104)。
  - 多出來的 103：Fig. 6 左下有一條優先序較高的 `01100111` [103,104) → `000` 擋掉。
  - 多出來的 64：[25,65) 那組有 `01000000` [64,65) → `011`，優先序更高，先吃掉。
  - 所以 [65, 103) 從 prefix 方法的 8 條變成 3 條（2 條 accept ＋ 1 條 deny；這是數 Fig. 6 左下印出的 entry）。
- 另一個省法：最後一個 basis range [r_n, R) 的 range mark 一定是全 0，不編進 feature table，沒命中就用預設值 0。
- 求解：直接列舉 p_start、p_end 是 O(R²)；Appendix B 給了 O((lg R)²) 的 solver（Alg. 2）。
- 效果：Fig. 8 比較 Prefix［46］和 CRC 在三個任務的 entry 數；正文只說 CRC greatly reduces entry usage，沒給數字。論文也列了 SRGE、OPT、Bit-Map、DIRPE 等方法，說它們不如 CRC，但 Fig. 8 只和 Prefix 比。

**出處**：PDF p.7 Fig. 6；p.8 §5.1、Fig. 7、Fig. 8、Equation (1)；p.18–19 Appendix B、Alg. 2。

### Q23. Random Forest、XGBoost 這種多棵 tree 怎麼表示？
**短答**：RF：每棵 tree 各自用 feature table＋model table 表示，最後接一張 plurality table 做多數決。XGBoost：最後要把各棵 tree 的分數加總再過 Sigmoid，data plane 做不到，所以把多棵 tree 合併——feature table 合併所有 tree 的門檻，model table 每條 entry 是「每棵 tree 各取一個 leaf」的組合，值是離線算好的 Sigmoid(分數和)，並刪掉互相矛盾的組合。

**細節**：
- RF：plurality table 的 key 是各 tree 推論出的 class 串接、value 是多數；因為 tree 數和 class 數都小，這裡的組合爆炸不嚴重。
- XGBoost 的例子（Fig. 9）：leaf 1-2（f1 ≥ 25）和 leaf 2-1（f1 < 35）合成 f1 ∈ [25, 35)，值是 Sigmoid(−0.01 + 0.5)。
- 刪除衝突組合：(i) feature value conflict：leaf 1-1 要 f1 < 25、leaf 2-2 要 f1 ≥ 35，不可能同時成立；(ii) feature semantic conflict：一條路徑要 Max(packet_size) < 10、另一條要 Avg(packet_size) > 20，語意上不可能。
- 論文說保留所有相容的組合可以 retain the accuracy of the original forest model。
- **推論**：XGBoost 合併後 model table 的 entry 數大約是各 tree leaf 數的乘積（扣掉衝突的），tree 數一多還是會變大；這可能是 covert channel 每個 phase 只用 2–3 棵、深度 4–7 的原因之一（Q11）。論文沒有這樣解釋。

**出處**：PDF p.8–9 §5.1、Fig. 9；p.19 Appendix D。

### Q24. multi-phase 的多個模型怎麼放進同一組 table？模型推論要幾個 stage？
**短答**：feature table 和 model table 都多一個 exact match 的 key：total_packets（目前是 flow 的第幾個 packet），用來區分是哪個 phase 的模型；某個 phase 沒用到的 feature，range mark 填 `*`。模型推論只要 2 個 stage：一個 stage 平行查所有 feature table，下一個 stage 查 model table。

**細節**：
- 原文：both the feature tables and model table has an extra key named total_packets, which is used to distinguish models in different phases … if one feature is not used by a specific model, the range mark for this feature is set as ∗ … model inference takes two stages。
- Fig. 12 的 P4 虛擬碼：Feature1 的 key ＝ {total_packets: exact, size_var: ternary}；Model 的 key ＝ {total_packets: exact, feat1_range_mark: ternary, feat2_range_mark: ternary}；`Feature1.apply(); Feature2.apply(); //1st stage`、`Model.apply(); //2nd stage`。
- 論文也提到另一個做法：每個 phase 各自一組 table（Intuitively 可以這樣做），但採用合併的做法。
- flow-agnostic（per-packet）模型和 multi-phase 的各個模型用同樣的方式表示（p.6 §5.1）；它們是否也併進同一組 table，論文沒說。

**出處**：PDF p.6 §5.1；p.11 §6.2、Fig. 12。

### Q25. Mousika 的 BDT 為什麼會用很多 entry？
**短答**：BDT（Binary Decision Tree）把每個 feature 拆成一個個 bit，每個 bit 當成 tree 的一個節點，一個 leaf 對應一條 table entry。一個範圍條件要好幾個 leaf（等於它的 prefix 數），多個 feature 的條件組合起來要相乘，又回到組合爆炸。

**細節**：
- Fig. 17 的例子：4-bit 的 f1 拆成 f1-1 到 f1-4 四個 binary feature；一般 decision tree 的 1 ≤ f1 ≤ 7，在 BDT 要三個 leaf（`0001`、`001*`、`01**`，正好是 [1, 7] 的三個 prefix）；若再加 1 ≤ f2 ≤ 7，就要 3 × 3 ＝ 9 個 leaf，也就是 9 條 entry。
- Mousika 不是從一般 DT 轉換，而是直接用 binary features 訓練 BDT，somewhat alleviates 這個問題；Mousika 的論文題目是 … by Knowledge Distillation，本文的 Mousika(RF Distilled) 就是從 RF 蒸餾出的 BDT。
- Mousika 用一張大 table 表示整個模型。
- 論文給的「NetBeacon 贏 Mousika」的兩個可能原因：BDT 用的 binary features 表達力可能不夠；BDT 本身的設計可能不如 RF、XGB 有效率。

**出處**：PDF p.3 §1；p.13–14 §7.3；p.18 Appendix A、Fig. 17；參考文獻［51］（p.17，INFOCOM 2022）。

# 四、Stateful storage 與 flow class table

### Q26. storage index 怎麼算？為什麼不讓 control plane 分配？
**短答**：把 packet 的 5-tuple 做 hash，取低 IndexSize 個 bit 當 index（論文也寫成 H(5-tuple) % N），每個 packet 一進來就算。不讓 control plane 分配，是因為那要等 control plane 回應、達不到 line-speed；用 data plane 現成的 hardware hashing 就不用等。

**細節**：
- 原文：Prior art [4, 53] involves the control plane to allocate a non-conflicting storage index upon receiving new flows. To achieve line-speed traffic analysis, NetBeacon instead relies on hardware hashing readily available on the data plane to allocate storage indices … H(5-tuple) % N, where H is a hash function。
- Alg. 1 第 1–2 行：H1 ← Hash(P.5t)；S_id ← H1[IndexSize : 0]。正文：the last IndexSize bits of the hash value are used as the storage index。這兩行在查 flow class table（第 4 行）之前，所以每個 packet 都會算。
- **推論**：取低 IndexSize 個 bit 等於對 2^IndexSize 取餘數，所以 N 是 2 的次方；IndexSize 16 → 65,536（論文給的對應）。
- 代價：hash 會 collision（Q27）；而且 Tofino 上的 hash 分布不完全均勻（Fig. 15d，Q41）。
- 用詞注意：論文的 N 有兩個意思——這裡的 N 是 register 格數；long-short 模型的「first N packets」是訓練時取幾個 packet（Q29）。
- **論文沒有說**：flow 是單向還是雙向。論文用 5-tuple（src/dst IP、src/dst port、protocol）定義 flow，也說 NetBeacon 不限定 flow 的定義，但同一個連線的兩個方向算一條還是兩條、hash 是否對稱，沒有交代。
- **被問到時可以怎麼回答**：「論文沒說。若直接 hash 5-tuple，兩個方向會落到不同 index、各自累積 feature；要合成雙向 flow 需要對稱的 hash 或先把 IP／port 排序，論文沒提。」（**推論**）

**出處**：PDF p.5 §2.2（5-tuple、not limited by any flow definition）；p.9 §5.2；p.9–10 §5.3、Alg. 1 第 1–2 行；p.12 §7.2。

### Q27. 兩條 flow hash 到同一格（collision）怎麼辦？
**短答**：register 旁邊存真正的 flow ID（5-tuple），比對不同就知道 collision。新 flow 只有在那一格是空的、或原本的 flow 已判定、或已逾時，才能佔用；否則不搶，新 flow 退回只用 per-packet features。

**細節**：
- 為什麼不能直接覆寫：Once a storage collision occurs, the per-flow states of both the original and new flows will become dirty if the new flow overwrites the storage。
- 兩個對策：減少 collision 的機率（只幫 long flow 存，Q28）；讓覆寫安全（只覆寫可覆寫的格子）。
- 原文：NetBeacon allows the new flow to use the occupied register if the inference class of the existing flow is determined or the flow has been finished (i.e., its last packet arrival time exceeds a predefined timeout). Otherwise, NetBeacon falls back to use per-packet stateless features for the new flow。
- Alg. 1：第 7–9 行讀出 ID 比對；第 23–27 行：預測是 long flow，而且 timeout 或 sure（已判定），才 InitAllRegs，並用 Resubmit 寫入新的 class 和 ID（第 29–30 行）。
- 「空的格子」：§5.3 寫 checks whether the storage on S_id is empty or is ready to be overwritten，但 Alg. 1 第 25 行只寫 if timeout or sure；空格子在演算法裡怎麼判斷，論文沒細講。
- 效果：w/o Optimization 版本就是同時拿掉 long／short 分流和這套 collision 管理；只有 P2P 看得出差別（Q38）。

**出處**：PDF p.9 §5.2；p.10 Alg. 1、§5.3；p.12 §7.2。

### Q28. 為什麼只幫 long flow 存 state？
**短答**：論文的目標是提高「所有 packet」的分類正確率，short flow 的 packet 少，花 storage 給它們換到的好處小。P2P 實驗顯示只對超過 8 或 16 個 packet 的 flow 用 flow-level features，整體 accuracy 和所有 flow 都用非常接近。只存 long flow 也大幅減少搶 storage 的 flow 數。

**細節**：
- 原文：Since the primary goal of traffic analysis is to improve the overall packet classification accuracy across all flows, maintaining per-flow states for shorter flows with fewer packets has lower marginal returns than maintaining per-flow states for longer flows。
- Fig. 10（只有 P2P）：五種情況 All、Cutoff 8、Cutoff 16、Cutoff 1024、Cutoff 2048；the overall accuracies in the first three cases are very close；正文沒給百分比。
- This greatly reduces the number of flows that are competing for the limited stateful storage。
- **推論**：這個論證建立在 packet-level 指標上——short flow 的 packet 在總 packet 數裡占比小。如果目標是「抓到每一條惡意 flow」，short flow 一樣重要（例如很多掃描、連線嘗試都是很短的 flow），這個取捨就不一定成立；而且 Fig. 10 只做了 P2P。

**出處**：PDF p.9 §5.2、Fig. 10。

### Q29. long-short 模型怎麼訓練、怎麼用？
**短答**：一個只用 per-packet features 的二元分類模型，逐 packet 判斷「這個 packet 是不是屬於 long flow」。訓練時用訓練集 flow 長度的 80th percentile 當 long／short 的分界，取每條 long（short）flow 的前 N 個 packet 當樣本；P2P 任務 N ＝ 7、accuracy 82%。

**細節**：
- 原文：In reality, it is difficult to know the flow length in advance. Thus, NetBeacon introduces a long-short flow binary classification model using only per-packet features to decide whether a packet belongs to a long flow or not. Specifically, we divide the long and short flows according to the 80th percentile of the flow length in the training set. The first N packets in the long (short) flows are taken as long (short) flow samples … The long-short flow binary classification model is task-specific. For instance, N = 7 and the accuracy is 82% in the P2P application fingerprinting task。
- P2P 的這個模型大小是 `1*8`（1 棵 tree、深度 8，Appendix D 稱為 flow size prediction）。
- 用法（Alg. 1 第 20–23 行）：只有沒有 storage 的 packet 才會跑；S ← InferFlowSize(F_p)，S > Lth（the long flow threshold）才去試著佔 storage。正文寫成二元分類、演算法寫成「預測 flow size 再和 Lth 比」，論文沒解釋兩者怎麼對應。
- 容易講錯：N ＝ 7 是訓練時每條 flow 取幾個 packet 當樣本，不是要等 7 個 packet 才判斷。
- **推論**：82% 表示約 18% 的 packet 判錯。long flow 被判成 short 會失去 flow-level features；short flow 被判成 long 會佔用 storage。論文沒有分開報這兩種錯誤。
- **推論**：因為是逐 packet 判斷，一條 flow 前幾個 packet 被判 short、後面才被判 long 並拿到 storage 的話，拿到之前的 packet 不會被算進 flow-level feature；這時「第 n 個 packet」的計數和訓練時的定義對不上。論文沒有討論。

**出處**：PDF p.9 §5.2；p.10 Alg. 1 第 20–27 行；p.19 Appendix D。

### Q30. flow 什麼時候算「已判定」？timeout 是多少？register 什麼時候釋放？
**短答**：flow 通過最後一個 inference point，或在中途某個 inference point 機率 ≥ determination threshold，就算已判定；register 被標成可覆寫，但不會主動清掉，要等有新 flow hash 到同一格時才被覆寫（lazily released）。timeout 的值論文沒有給。

**細節**：
- 原文：A flow's inference class/result is determined if it has passed the last inference point defined in the multi-phase sequential model (§ 4.2) or the model is confident enough about the flow's inference result at an intermediate inference point（p.9）。
- 判定之後：存進 flow class table，並更新 register 標記 ready to be overwritten；Alg. 1 第 15 行 UpdateReg_sure(S_id, True)。
- 釋放：a storage register is lazily released when the stored flow is class-determined (or timeout), and meanwhile a new flow is hashed to the register（p.10）。
- 正文和 Alg. 1 的落差：正文說「通過最後一個 inference point」也算已判定，但 Alg. 1 只在 P ≥ dt 時標記 sure、寫 flow class table（第 14–16 行）。**推論**：把最後一個 phase 的 threshold 設成 0 就能一致，但論文沒說。
- **論文沒有說**：timeout 設多少；data plane 上怎麼記錄 last packet arrival time。原文只有 its last packet arrival time exceeds a predefined timeout。
- **被問到時可以怎麼回答**：「論文只說是 predefined timeout，沒給值。§8 的緩解建議改成每條 flow 自己的 timeout（例如觀察到的最大 IPD 的兩倍），看起來原本是全域的固定值（推論），但緩解也沒有實驗。」

### Q31. flow class table：誰寫入、怎麼淘汰、寫入前後 packet 怎麼走？
**短答**：key 是 5-tuple、value 是 class。data plane 判定後用 digest 通知 control plane，由 control plane 插入 entry；表滿時用 FIFO 或 LRU 淘汰。寫入之前，packet 照常走 register＋模型推論的流程；寫入之後，命中的 packet 直接拿 class，不再做模型推論。

**細節**：
- 寫入：NetBeacon saves the inference result of the flow in a flow class table, keyed by the flow's 5-tuple … New entries are dynamically inserted into the flow class table by the control plane after receiving messages from the data plane indicating that a flow's class is determined（p.9）；訊息是 digest（p.10 §5.4）。
- 淘汰（兩處說法略有不同）：§5.2 寫 some entries from the flow class table need to be regularly removed (based on either the FIFO or LRU principle) to prevent table overflow（p.9）；Appendix C 寫 When the flow class table is full, NetBeacon removes table entries（p.19）。
  - FIFO：control plane 記插入順序，替換最早插入的；適合 flow 持續時間差不多的情況。
  - LRU：用 counter 記每條 entry 命中的 packet 數，counter 多久沒變就當成多久沒被用，替換最久沒用的；適合 flow 持續時間差很多的情況。
- 寫入前：the packets that are not matched by the flow class table will instead traverse the regular model inference pipeline（p.10）。寫入後：When matched by the flow class table, a packet will not be re-analyzed by the ML model deployed after the flow class table（p.15）。
- **推論**：表裡存的是 class，不只是「放行」——判定為惡意的 flow 也會進表，後續 packet 直接套用惡意的 class（例如持續 drop）。所以它同時扮演 allowlist 和 blocklist。
- **論文沒有說**：flow class table 有多大、實驗用 FIFO 還是 LRU、兩者對 accuracy 的影響；entry 被淘汰後這條 flow 會怎樣。
- **被問到時可以怎麼回答**：「依 Alg. 1 推論：被淘汰之後，packet 不再命中 flow class table，會去比對 register 的 flow ID。如果那格還沒被別的 flow 佔走，ID 相符，就沿用存的 class，或在後面的 inference point 再做模型推論；如果已經被佔走，就變成『新 flow』，用 per-packet features，之後可能重新拿到 storage，但 feature 要從頭累積。這些都是推論，論文沒有實驗。」

**出處**：PDF p.9 §5.2；p.10 Alg. 1、§5.4；p.15 §8；p.19 Appendix C。

### Q33. control plane 為什麼不在 critical path？
**短答**：packet 的分類不需要等 control plane：flow class table 還沒寫入時，packet 照常走 data plane 上的模型推論流程，結果一樣算得出來；control plane 只是之後把已判定的 flow 寫進表，讓後面的 packet 省掉模型推論。

**細節**：
- 原文：Note that the latency for updating the flow class table does not impact traffic analysis, because the packets that are not matched by the flow class table will instead traverse the regular model inference pipeline. Therefore, the control plane is off the critical path of packet classification in NetBeacon, ensuring line-speed traffic analysis。
- 對比 prior art：NetWarden、FlowLens 的分析在 control plane，Due to the interaction latency between the data plane and the control plane, traffic is not analyzed at line-speed；它們的 storage index 也要 control plane 分配（Q26）。
- **推論**：不在 critical path 不代表沒有代價。control plane 處理 digest 的速度決定 flow class table 多快生效；如果每秒判定的 flow 很多、control plane 跟不上，這段期間這些 flow 的 packet 會繼續走 register 和模型推論的路徑。論文沒有量 control plane 的處理速率、digest 的數量，或 flow class table 生效需要多久。

**出處**：PDF p.4 §2.2；p.9 §5.2；p.10 §5.4。

# 六、限制與安全

### Q46. 論文自己承認的限制有哪些？
**短答**：四類：(1) 能同時維護 per-flow state 的 flow 數受 switch storage 限制；(2) 只能用 data plane 算得出來的 feature，不支援 percentile 這類；(3) 受 PISA 限制，feature、模型大小、inference point 位置都受限，複雜任務的 accuracy 會受影響（Table 5）；(4) threat model 假設有任務相關的訓練資料、不處理 ML 本身的 poisoning、假設 switch 本身是安全的。

**細節**：
- §2.2 Assumptions, Threat Model, and Limitations 的原文：We assume that NetBeacon has access to task-related training datasets. Machine learning itself has security vulnerabilities, such as data and model poisoning attacks, which is out of the scope. We assume that the programmable switches hosting NetBeacon are secure. Since flow-level features consume the stateful storage on programmable switches, the number of concurrent flows for which NetBeacon can simultaneously maintain per-flow state is limited by hardware storage … NetBeacon does not support flow-level features that are difficult to compute on the data plane (e.g., percentile of packet sizes)。
- Caveats：due to hardware constraint, the ML models designed in the area of IDP are limited in features, model sizes (e.g., tree depth) and the locations of inference points。
- §8：both features and model architectures are limited in NetBeacon, which might affect the analysis accuracies in case of complex tasks, as quantified in Table 5。
- §8 Security Analysis 討論的兩類攻擊見 Q47、Q48。
- **推論**（論文沒列為限制、但聽眾可能會想到的）：只看 header、size、IPD，不看 payload（Q54）；判定後不再做模型推論（Q48）；模型更新流程沒描述（Q50）。

**出處**：PDF p.4 §2.2；p.13 §7.2 Caveats；p.15 §8。

### Q47. resource exhausting（DoC）attack 是什麼？怎麼緩解？
**短答**：攻擊者製造大量同時存在的假 flow，把 switch 上存 per-flow state 的 SRAM 塞滿，屬於 Denial-of-Capability（DoC）攻擊。論文說這不會讓 NetBeacon 完全失效，因為可以退回 per-packet features；實務上用 aggregate flows 或平行部署多個 NetBeacon instance 來緩解。

**細節**：
- 原文：The first type is resource exhausting attack where the adversary generates numerous concurrent bogus flows to overflow the available SRAM on a switch. This is essentially a form of Denial-of-Capability (DoC) attack [38]. Fortunately, DoC attacks will not fully break down NetBeacon since it can fall back to use per-packet features. The probably-secure defense against DoC attacks is through dedicated set-up protocols (e.g., Portcullis [40]). Practically, DoC attacks are mitigated by either aggregating flows or deploying multiple NetBeacon instances in parallel。
- 小地方：DoC 引用的［38］在參考文獻裡是 Moore and Zuev 的 traffic classification 論文；Portcullis［40］的題目才是 Protecting Connection Setup from Denial-of-Capability Attacks。**推論**：［38］可能是引用錯誤。
- **推論**：「不會完全失效」的意思是 accuracy 退到 per-packet 的水準（Fig. 13 的 NetBeacon(Pkt)）；對 covert channel 這種 per-packet features 幾乎沒用的任務，退化會很明顯。
- **推論**：只有被 long-short 模型判成 long 的 flow 才會去佔 storage，而且不會搶還在分析中的 flow；所以假 flow 要「看起來像 long flow」才佔得到格子，佔的是已判定或逾時後釋放的格子。論文沒有分析這些細節，也沒有實驗。

**出處**：PDF p.15 §8；參考文獻［38］［40］（p.17）。

### Q48. stealth attack 和 low-rate-long-flow attack 是什麼？作者怎麼緩解？
**短答**：兩者都是針對系統參數的 white-box 攻擊。stealth attack：先送 benign packet，等 NetBeacon 判定這條 flow 之後才送 malicious packet——判定後的 packet 不再做模型推論；緩解是對 flow class table 的 entry 加 maximum flow length limit。low-rate-long-flow attack：讓 flow 逾時；緩解是每條 flow 用自己的 timeout，例如觀察到的最大 IPD 的兩倍。論文認為這類攻擊有門檻，因為攻擊者要先探測參數。

**細節**：
- 原文：The second category of attacks aims at exploiting the detailed system parameters in NetBeacon. Two representative examples are: (i) the stealth attack where the attacker sends benign packets first, and then transmits malicious packets after NetBeacon determines the flow class; (ii) the low-rate-long-flow attack where the attacker forces the flow to timeout. In general, these types of attacks have entry barriers since the adversary needs to probe the parameter setting. To mitigate the stealth attack, NetBeacon can enforce a maximum flow length limit on the entries in the flow class table. To mitigate the low-rate-long-flow-attack, NetBeacon can determine a flow-specific timeout (e.g., twice the maximum observed IPD) for each flow。
- stealth attack 為什麼有效：When matched by the flow class table, a packet will not be re-analyzed by the ML model（p.15）；而且 determination threshold 讓 flow 可能在很早的 inference point 就被判定（例如 DDoS 的第 2 個 packet）。
- low-rate-long-flow：論文只寫 forces the flow to timeout，沒說手法和後果。**推論**：拉長 packet 間隔讓 flow 被當成已結束，register 被別的 flow 佔走，攻擊 flow 之後的 packet 變成「新 flow」，flow-level features 要重新累積或只能用 per-packet features，於是走不到後面的 inference point。
- **論文沒有說**：maximum flow length limit 設多少、到上限後是刪掉 entry 讓 flow 重新分析還是別的處理；flow-specific timeout 怎麼在 data plane 記錄最大 IPD。兩種緩解都沒有實驗。
- **被問到時可以怎麼回答**：「論文只有一句話的緩解，沒有參數也沒有實驗。我的理解是 length limit 到了之後應該讓 entry 失效、讓後面的 packet 重新進入模型推論，但論文沒寫。」
- **推論**：論文把這兩種攻擊歸在 adaptive (or white-box) attacks，white-box 本來就假設攻擊者知道系統；「要先探測參數」這個門檻和 white-box 的假設之間有點矛盾，論文沒有評估門檻到底多高。

**出處**：PDF p.15 §8。

### Q50. 模型或 threshold 要更新時怎麼做？
**短答**：論文只描述了 threshold 的更新：比較結果是 control plane 事先算好、編進 model table 的 action parameter，所以換 threshold 只要改 entry、不用停機。整個模型怎麼重新訓練、怎麼換上去、換的過程中會不會新舊 entry 混用，**論文沒有說**。

**細節**：
- 原文（Appendix C）：NetBeacon puts the classification probabilities and threshold comparisons on the control plane so that the determination threshold could be updated without downtime。
- control plane 的職責寫的是 installing the feature tables and model table on the data plane at the very beginning——只講一開始安裝。
- **背景知識，非論文內容**：P4 程式編譯之後，table 的 key 欄位、register、stage 配置就固定了；control plane 在執行中能新增、修改、刪除的是 table entry。
- **被問到時可以怎麼回答**：「論文只講 threshold 可以不停機更新。推論：如果新模型用的 feature 和 table 結構不變，理論上由 control plane 重寫 feature table 和 model table 的 entry 就好；如果要換 feature（例如新的 size 區間、新的 summary feature），要改 register 和 table 的定義，就得重新編譯、重新載入 P4 程式。更新期間的一致性論文沒有討論。」
- **推論**：已經寫在 flow class table 的 flow，換了模型也不會被重新評估，除非 entry 被移除（依 p.15 §8 的 will not be re-analyzed）。

### Q51. 可擴充性：能同時處理多少 flow？超過會怎樣？
**短答**：實驗設定 IndexSize 16，最多同時維護 65,536 個 per-flow state。超出的 flow 不會被丟掉，而是退回 per-packet features，所以論文說 concurrent flow 數沒有硬上限；但只有拿到 state 的 flow 才有 flow-level features。論文估計 DDoS 任務在 Tofino 1 一條 pipeline 最多可放 140,000 個 flow index，並說可以平行部署多個 instance。

**細節**：
- 原文（Scalability Analysis）：NetBeacon has the following traffic analysis hierarchy: the flow class table stores flows whose classification classes have been determined (line 4-5 in Alg. 1) … If NetBeacon maintains the per-flow state in registers (SRAM) for the packet (line 11-19 in Alg. 1), the ML inference will use flow-level features; otherwise, the inference is purely based on per-packet features (line21 in Alg. 1). Thus, there is no hard-limit on the number of concurrent flows that can be processed by NetBeacon, since it can fall back to use per-packet features whenever necessary。
- 140,000：The theoretically maximum number of per-flow states … is determined by the size of registers (SRAM) and the flow-level features being used. In the DDoS task where scalability matters the most, one pipeline on Tofino 1 switch (with 4 pipelines in total) can support up to 140,000 flow indices in registers (SRAM)。
- 硬體升級：The SRAM size in Tofino 3 increases by 80% and the total number of pipelines doubles。
- 平行部署：we can deploy multiple NetBeacon instances in parallel and load balance flows across these instances. Each NetBeacon instance independently processes traffic at line-speed。
- §1 (iii) 的用詞是 potentially allows NetBeacon to handle more concurrent flows than the total number of registers——「處理」的意思是超出的 flow 退回 per-packet，不是每條都有 flow-level features。
- 實驗證據：P2P high load 時 0.85% 的 flow 退回 per-packet（p.12）；Fig. 15c 顯示 register 越少 accuracy 越低（p.14）。
- **推論**：「沒有硬上限」是指功能不會壞；accuracy 會隨 concurrent flow 增加，往 NetBeacon(Pkt) 的水準退化。

**出處**：PDF p.3 §1 (iii)；p.12 §7.2；p.14 §7.4；p.15 §8。

# 七、可能被教授或同學追問的

### Q52. 這跟規則式 IDS 的 flow bypass 有什麼不同？
**短答**：精神很像：判定之後，後續 packet 不再進重量級分析，只查一張以 5-tuple 為 key 的表。不同在於：NetBeacon 的判定是 ML 模型在某個 inference point 的機率超過 threshold，判定前的分析也在 switch 的 data plane 上以 line-speed 做；表裡存的是 class（惡意、良性都會進表），不只是「放行」；寫入由 control plane 非同步完成。

**細節**：
- NetBeacon 這邊（論文）：flow class table 以 5-tuple 為 key（p.9）；命中就不再被 ML 分析（p.15）；判定條件是通過最後一個 inference point 或機率 ≥ threshold（p.9）；寫入走 digest → control plane（p.10）。
- **背景知識，非論文內容**：規則式 IDS 的 flow bypass，一般是在確定某條 flow 不需要再檢查之後（例如超過檢查深度、內容已加密看不到、或被判定為可信），讓後續 packet 不再送進 IDS 引擎，由 kernel 或網卡依 flow 表直接轉送，目的也是省資源。
- **推論**的差異整理：
  - 判定依據：規則或檢查深度 vs. ML 機率＋threshold。
  - 表的語意：bypass 通常只代表「不用再看」；NetBeacon 的表存 class，惡意的判定也會一直沿用。
  - 判定前看什麼：IDS 在 CPU 上看 payload；NetBeacon 判定前也只看 header、size、IPD，而且全程在 switch 上。
  - 共通的風險：判定後才變惡意的 flow 會漏掉（stealth attack，Q48）；兩者都需要 timeout 或長度上限之類的機制讓 entry 失效。
- 可以補一句：論文說 flow-level 的偵測解讀對 intrusion detection/prevention systems 特別有用（p.13），但沒有和任何 IDS 系統比較。

**出處**：PDF p.9 §5.2；p.10 §5.4；p.13 §7.2 Caveats；p.15 §8。

### Q53. 為什麼不用 SmartNIC 或 eBPF／XDP？
**短答**：論文的理由是吞吐量：SmartNIC 和 DPDK 主機網路比較有彈性、計算和 storage 比較多，但吞吐低很多（論文舉 NetFPGA-PLUS 200 Gbps 對 Tofino 1 整台 6.4 Tbps），所以作者專注在 PISA 的 programmable switch。eBPF **論文沒有提**。

**細節**：
- §2.2 Design Goals：Other art [45, 50] use SmartNICs instead of programmable switches as the data plane. These two types of hardware have drastically different characteristics: programmable switches have much higher throughput, with much limited computation capability. We focus on PISA-driven IDP design in this paper。
- §8：prior art also consider SmartNICs [45, 50] and DPDK-driven host networking [35] as the intelligent data plane to enable more flexible computation and storage, at the expense of much lower throughput (for instance, NetFPGA-PLUS has 200 Gbps while the Tofino 1 programmable switch in aggregate has 6.4 Tbps)。
- **被問到時可以怎麼回答**（**背景知識＋推論**）：「論文沒談 eBPF。eBPF／XDP 跑在主機 CPU 上，有整數乘除、可以用 map 存大量 per-flow state，feature 和模型的限制比 PISA 寬鬆很多；代價是吞吐受 CPU 核心數限制，和論文說的 DPDK 主機網路是同一類取捨。NetBeacon 的 range marking 是為了 TCAM entry 設計的，在 CPU 上不一定需要；但 multi-phase 和『判定後不再做模型推論』的想法和平台無關。」
- **推論**：選哪個平台取決於部署位置：switch 適合 Tbps 等級的匯聚點；主機或 SmartNIC 適合流量較小、但需要較複雜 feature 和模型的地方。

**出處**：PDF p.4 §2.2；p.15 §8。

### Q54. 加密流量可以嗎？
**短答**：**論文沒有說**。但 NetBeacon 的 feature 只有 header 欄位（packet size、TTL、protocol 等）和時間（IPD），不看 payload，所以原理上加密不影響取得 feature（**推論**）；它評估用的 ISCXVPN 本身就是加密／VPN 流量的資料集，covert channel 任務也是在 Skype 流量上做。

**細節**：
- 論文的 feature：per-packet 是 header 欄位；flow-level 是 IPD 和 packet size 的 aggregate、summary features（p.5 Table 2；p.11 §7.1）。
- §9 Related Work 提到有研究專門處理加密流量分類［16, 27, 47, 59］，但沒有說 NetBeacon 和加密的關係。
- ISCXVPN 的參考文獻［12］題目是 Characterization of Encrypted and VPN Traffic using Time-Related Features；論文用它做 Fig. 14(d)。
- **背景知識，非論文內容**：Skype 的通話是加密的；Facet 把影音藏在視訊通話裡（參考文獻［28］題目：Streaming over Videoconferencing for Censorship Circumvention），所以 covert channel 任務本身就是在加密流量上用 size 分布偵測。
- **推論**：反面是 NetBeacon 看不到 payload，不能做 signature 或內容比對（特定 exploit 字串、URL、TLS SNI 之類），這類偵測仍要靠其他系統；論文沒有說它要取代內容檢查。
- **被問到時可以怎麼回答**：「論文沒特別討論加密，但它的 feature 全部來自 header 和時間，不需要解密；它評估用的 ISCXVPN 和 Skype 流量本身就是加密的。代價是它也看不到 payload。」

**出處**：PDF p.5 Table 2；p.11 §7.1；p.13 §7.3；p.15 §9；參考文獻［12］［28］（p.16）。

### Q55. accuracy 是 per-packet 還是 per-flow？會不會偏向 long flow？
**短答**：主要指標是 per-packet（packet-level macro-accuracy），每個 packet 算一次；flow-level 只在 covert channel 給了一組 FPR／FNR（5.3%／7.3%）。long flow 的 packet 多，per-packet 指標自然比較受 long flow 影響，這和 NetBeacon「只幫 long flow 存 state」的設計方向一致（**推論**）。

**細節**：
- §7.1：packet-level macro-accuracy；§7.2 Caveats：flow-level 的定義（至少 5 個 inference point 判對）和數字。
- §5.2 的論證本身就以 packet 為單位：the primary goal of traffic analysis is to improve the overall packet classification accuracy across all flows。
- **推論**：IDS 常在意「每條惡意 flow／每次攻擊有沒有被抓到、多快被抓到」。per-packet 指標下，一條很長的正常 flow 判對就貢獻大量正確的 packet；一條只有幾個 packet 的惡意 flow 判錯，影響很小。macro 平均只平衡了類別，沒有平衡 flow 長度。
- **推論**：flow-level 的定義也有選擇空間（「至少 5 個 inference point」是作者選的），不同定義會得到不同的 FPR／FNR；論文只給一種。
- **被問到時可以怎麼回答**：「主要指標是 per-packet；只有 covert channel 有一組 flow-level 數字。如果要用在 IDS，我會想看每個任務的 flow-level 偵測率和偵測時間，論文沒有。」

**出處**：PDF p.9 §5.2；p.11 §7.1；p.13 §7.2 Caveats。

### Q57. 這篇和 FlowLens、NetWarden、Mousika、Planter 的差別？
**短答**：FlowLens 和 NetWarden 用 switch 收集 flow 資訊（例如 IPD 的分布），ML 分析在 control plane，所以不是 line-speed；Mousika 和 Planter 把 tree 放進 data plane、是 line-speed，但只用 per-packet features，模型轉成 table 的效率也較差。NetBeacon 主張三者兼顧（line-speed、learning-based、flow-aware），這是論文 Table 1 的定位。

**細節**：

### Q58. 實驗的弱點在哪？
**短答**（**推論**為主，每點都有可查的事實）：外部 baseline 只有 Mousika，沒和 control plane 方案比 accuracy 或延遲；主指標是 packet-level，flow-level 只有 covert channel 一組；covert channel 只有 400 條 testing flow；DDoS 是自產攻擊、20% 訓練、模型極小，任務可能偏簡單；安全分析、FIFO／LRU、timeout 都沒有實驗，threshold 只比兩個值；throughput 的量測方法和 accuracy 怎麼從 switch 取出都沒交代。

**細節**：
- baseline：end-to-end 只比 Mousika（p.12 §7.2）；control plane 方案只有 Table 1 的定位（p.4）。
- 指標：packet-level macro-accuracy（p.11）；flow-level 只有 covert channel 的 5.3%／7.3%（p.13）。
- 資料規模與切分：covert 1,600／400 條 flow，Univ2 背景只在 test；DDoS 47,752／191,009，80% 當 test（p.12 Table 4；p.19 Appendix D）。
- 模型很小：DDoS 四個 phase 是 `1*1`、`1*4`、`1*1`、`1*1`；P2P 每個 phase `1*9`（p.19 Appendix D）。**推論**：DDoS 用這麼小的模型就有很高的 accuracy，表示這個資料集的 DDoS 和背景流量很好分，不一定能代表更難的攻擊。
- storage 管理的效益只在 P2P 明顯（p.13）。
- 參數敏感度：threshold 只比 0.7／0.8、只在 covert channel（p.14）；主實驗的 threshold、timeout、flow class table 大小、FIFO 或 LRU 都沒給。
- 攻擊與緩解只有文字（p.15 §8；Q49）。
- 量測細節：throughput 的流量組成、和 100 Gbps 差距的原因、accuracy 怎麼從 switch 輸出取得都沒說（p.11 §7.1；p.14 §7.4）。caption 的 14%／38%／20% 沒說是哪個 load（p.12）。
- **被問到時可以怎麼回答**：「我覺得最大的缺口是沒有 flow-level、偵測時間這類 IDS 在意的指標，以及判定後不再做模型推論的風險沒有量。」

### Q59. 偵測到之後會做什麼？能直接 drop 嗎？判定前已經過去的 packet 怎麼辦？
**短答**：論文只說結果交給 user-defined processing，例如二元的 drop 或 allow，或依結果給不同的 service priority；評估只量分類 accuracy，沒有量 drop 的效果。每個 packet 在經過 switch 的當下用「當時拿得到的結果」處理，判定前已經轉送出去的 packet 不會被追回。

**細節**：
- 原文：Once the inference results for a packet are determined, users can design customized post-processing based on the results, such as making a binary decision of drop or allow, or assigning fine-grained different service priorities accordingly（p.5 §3）；Alg. 1 第 31 行。
- **推論**：每個 packet 都有 class（來自 flow class table、register 裡存的結果，或 per-packet 的模型推論），所以理論上每個 packet 都能立即依 class 處理；但判定前的 packet 用的是較早 phase 或 per-packet 的結果，accuracy 較低（Fig. 5、Fig. 13 的 Pkt 版本）。例如 covert channel 第一個 inference point 在第 512 個 packet，之前的 packet 只靠 per-packet 結果。
- **推論**：如果 user-defined processing 是 drop，Table 5 的 FPR 就直接變成誤擋率，threshold 的選擇（Q15）會更重要。
- **論文沒有說**：誤判之後怎麼補救，例如事後撤銷 flow class table 裡錯誤的 entry。
- **被問到時可以怎麼回答**：「論文只說可以接 drop／allow 或 priority，沒有評估動作本身；誤判的補救也沒討論。」

**出處**：PDF p.5 §3；p.10 Alg. 1 第 31 行；p.13 Table 5。
