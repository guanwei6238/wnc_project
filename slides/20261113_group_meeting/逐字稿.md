# 一、當場講

## 封面

各位好。今天分享的論文是 NetBeacon，全名 An Efficient Design of Intelligent Network Data Plane，Tsinghua University 的團隊寫的，發表在 USENIX Security 2023。
這篇做的事情是：把機器學習模型直接放進 programmable switch 的 data plane，packet 經過 switch 的當下就分類，而且不降低轉送速度。
報告分五個部分：Introduction、Motivation、Design、Evaluation、Conclusion。

---

## 章節頁　Introduction

先講背景：什麼是 Intelligent Data Plane，還有 programmable switch 能做什麼、不能做什麼。

---

## 第 1 頁　Intelligent Data Plane（IDP）

目前訓練出來的模型，通常放在 end-host 或 network control plane 上做推論。control plane 是管理 switch 的部分。上面這一排就是這種做法：switch 收集 flow 的資訊，送到 control plane，模型判定完再把結果送回 switch。
這樣有兩個問題。第一，論文引用的 state-of-the-art 大約只能處理 10 Gbps。第二，control plane 在分析的 critical path 上，會多一段 reaction time。
作者的想法是把模型直接放進 data plane，也就是 switch 裡實際轉送 packet 的部分，下面這一排。packet 經過 switch 的當下就分類，速度是 line-speed，也就是不降低轉送速度。這個方向叫 Intelligent Data Plane，論文裡簡稱 IDP，也有人叫 in-network machine learning。NetBeacon 是其中一個設計。

---

## 第 2 頁　Programmable Data Plane（PISA）

這篇論文是靠 PISA 把模型放進 switch 的。PISA 是 programmable switch 的架構。
看上面的圖，packet 在 PISA 裡依序經過三個元件，這三個元件都可以寫程式，用的是 P4 這類語言。
第一個是 parser，解析 packet 的 header，把後面要用的欄位取出來。
第二個是 match/action，有很多個 stage，packet 一個 stage 接一個 stage 往下走，主要的計算都在這裡做。match 是拿 packet 的某些欄位去查一張 table；查到哪一個 entry，就執行那個 entry 對應的 action，action 裡可以做運算、改 storage。圖上每個 stage 下面灰色的是 register，是能把狀態存下來、給後面的 packet 用的地方。
第三個是 deparser，把處理完的 packet 組回去送出。
下面的表是 PISA 能做的事。match 有三種：exact、ternary、LPM；ternary 是每個 bit 可以指定 0、1，或是「都可以」，後面講 range marking 會用到。運算只有 boolean、shift、加、減。match/action stage 的數量有限，Tofino 1 是 12 個。stateful storage 有 register，但一個 packet 走過 pipeline，對每個 register 只能存取一次。
表上沒有列的就是不能做，像乘除、float、loop。
這些會影響後面的設計：模型選 tree，因為 tree 的結構比 neural network 更像 match/action；像 variance 這種 feature，裡面的除法只能靠 shift 算，所以用到 variance 的話，inference point 要放在 2 的次方的位置。後面會看到。

---

## 章節頁　Motivation

接下來講 prior work 缺什麼，還有為什麼需要 flow-level features。

---

## 第 3 頁　Comparison with prior art in IDP

論文把之前的做法分成三類，用三個欄位來比。
- Line-Speed 是分析在 data plane 上完成，不降低轉送速度。
- Learning-Based 是用 ML 模型來判斷，不是人寫的 threshold 規則。
- Flow-Aware 是判斷時有用到 flow 的資訊，不是只看單一個 packet。

表上有六個 prior work，兩個一類，每一類剛好缺一欄。
- NetWarden 和 FlowLens 缺 Line-Speed：switch 只負責收集 flow 的資訊，分析在 control plane 做。
- Poseidon 和 Jaqen 缺 Learning-Based：收集到的資訊直接在 data plane 用來擋 DDoS，但用的是人寫的 threshold filter。論文另外註明，它們有些 policy 要 control plane 參與，那時候就不是 line-speed。
- Planter 和 Mousika 缺 Flow-Aware：它們把 decision tree 放進 data plane，但只用 per-packet features。
- NetBeacon 三類都要。

三類都有限制，就是表上打叉的那一欄。下面兩行只寫 Planter 和 Mousika，是因為它們和 NetBeacon 一樣都是實做IDP，論文要在兩件事上比它們更進一步。
- 第一是 model deployment efficiency：它們在 data plane 上表示模型的效率低，例如 Mousika 的 table entry 數會有 combinatorial explosion；NetBeacon 要用更少的 table entry。
- 第二是 model accuracy：它們只用 stateless 的 per-packet features，忽略 stateful 的 flow-level features，就是表上 Flow-Aware 的叉；NetBeacon 要把 flow-level features 加進來。
這兩點就是這篇論文的動機。第二點的證據在下一頁；第一點論文放在 evaluation，是後面第 13 頁。

---

## 第 4 頁　Flow-level features 的必要性

論文做了一個實驗，說明加入 flow-level features 之後，分類的 accuracy 會變高。
per-packet feature 是單一 packet 的 header 就看得到的，例如 size、TTL、protocol。flow-level feature 是同一條 flow 前 n 個 packet 的統計，例如 packet size 的 mean、variance，還有 IPD 的最小值；IPD 是 inter-packet delay，就是 packet 之間的間隔。flow 用 5-tuple 來分：來源和目的的 IP、來源和目的的 port，加上 protocol。
實驗的做法是：拿三個任務，P2P 的應用分類、covert channel 偵測、DDoS 偵測，每個任務各訓練兩個 decision tree。一個只用 per-packet features，就像 Mousika 的做法；另一個 per-packet 和 flow-level features 都用。兩個模型用的 feature 數量一樣，再比 accuracy。
圖上每個任務有兩根柱子，紫色斜線是只用 per-packet features 的，綠色交叉是加了 flow-level features 的。加入之後，accuracy 在 P2P 多 11%，covert channel 多 43%，DDoS 多 21%。
所以論文的目標是：在 data plane 上同時做到 line-speed，和用 ML 模型、用得到 flow-level features 的準確分析。
但是 flow-level features 有代價：switch 要幫每條 flow 記住狀態，而 register 有限。後面的設計很大一部分就是在處理這件事。

## 第 5 頁　The architecture of NetBeacon

這是 NetBeacon 的整體架構，圖用虛線分成上下兩層。
上層是模型怎麼訓練出來。這一層在 switch 外面離線做訓練：
拿 pcap 做 feature engineering，得到 training data，訓練出右上角那一串模型，一個 phase 一個。叫 data plane aware，是因為訓練的時候就先遷就 switch：只選 switch 算得出來的 feature，模型用 decision tree。

下層叫 Model Deployment，講的是模型怎麼放進 switch、packet 進來之後怎麼走。這一層要分兩排看。
中間那一排是兩個設計。右邊的 Model Representation，把訓練好的 tree 轉成兩種 table：feature table 把 feature 的值轉成 range mark，model table 再用 range mark 查出結果。左邊的 Stateful Storage Management 管 register，裡面有兩件事：分辨 long flow 和 short flow，還有處理 storage index 的 collision。
最下面那一排，藍色箭頭，才是每個 packet 在 switch 裡真正走的步驟。橘色箭頭不是 packet 的路，是標出上面的設計用在哪一步。
最下排一共七步。先用 5-tuple 查 flow class table，命中的話，沿著下面那條 match 的線直接跳到最後。沒命中，就算 storage index，找到這條 flow 的 register，更新 register，算 feature，查 feature table，查 model table，得到分類結果。最後一步是使用者自己定義的處理，例如 drop 或 allow。
這七步是有 state 的 flow 在 inference point 走的完整路徑；不是 inference point 的 packet，直接用 register 裡存的 class；新的 flow 只用 per-packet features。第 9、10 頁會講。
下面三行是論文在 Introduction 列的三個設計，(i)、(ii)、(iii)，接下來三頁各講一個。要注意，這三個設計不是三個模型：(i) 是模型怎麼設計和訓練；(ii) 是訓練好的模型怎麼變成 table；(iii) 是 per-flow state 怎麼存。
另外，control plane 沒有畫在這張圖上。依論文 5.4 節，它負責兩件事：一開始把 feature table 和 model table 裝進 switch；還有 flow 判定之後，把結果寫進 flow class table。determination threshold 的比較，也是 control plane 在產生 table entry 的時候先算好、編進 entry 裡的，所以改 threshold 不用停機。packet 經過時的推論，全部在 data plane 做。

## 第 6 頁　(i) Multi-phase sequential model

第一個設計，是模型的部分。
flow-level feature 會隨著 flow 進行而變：同一條 flow，前 4 個 packet 算出來的平均，和前 32 個 packet 算出來的平均不一樣。所以只用單一模型去看所有階段的 feature，accuracy 很低。圖就是單一模型和 multi-phase 的比較，三個任務 multi-phase 都比較高；P2P 和 covert channel 差很多，DDoS 的縱軸是從 96 開始，差距看起來比實際大。
做法是這樣。先選幾個位置，叫 inference point，例如 P2P 任務是 flow 的第 2、4、8、32、256、512、2048 個 packet。
訓練的時候，每個 inference point 各訓練一個模型：要訓練第 8 個 packet 的模型，用的 flow-level features 就是由前 8 個 packet 算出來的；訓練樣本實際上怎麼挑，論文沒有細講。所以有幾個 inference point 就有幾個模型：P2P 是 7 個，covert channel 是 9 個，DDoS 是 4 個。
推論的時候，packet 剛好是 inference point，就用對應的那個模型推論一次；其他的 packet 不推論，沿用最近一次的結果。
每個 phase 還有一個 determination threshold。模型除了給 class，還會給一個機率；機率超過 threshold，就提前判定這條 flow，後面的 inference point 不用再做。
模型是 Random Forest 或 XGBoost，都是由 decision tree 組成的 forest，因為 tree 的結構和 match/action 很像。如果 feature 用到 variance，inference point 要放在 2 的次方，因為硬體只能用 shift 做除法。
模型雖然多，但都很小。附錄給的大小：P2P 每個 phase 是一棵深度最多 9 的 tree；DDoS 的四個 phase，有三個深度是 1。
在 switch 裡也不用放 7 組 table。論文的實作把各 phase 的 table 合併：feature table 和 model table 多一個 key，就是這條 flow 目前的 packet 數，用它來區分是哪個 phase。論文說這樣一般來說推論只要兩個 stage：一個 stage 查 feature table，一個 stage 查 model table。這兩個 stage 不包含算 feature 的 stage。
除了這些，還有兩個只用 per-packet features 的模型，一個分類、一個判斷 long 或 short，給沒有 state 的 flow 用，第 8 頁會講。

---

## 第 7 頁　(ii) Model representation：range marking

第二個設計：訓練好的 tree 怎麼放進 table。這個轉換是離線做的：一支 Python 程式讀訓練好的模型檔，產生 table 的 entry，control plane 啟動時再把 entry 裝進 switch。所以 switch 上沒有模型，只有查表。
先看問題。左上是一棵 tree，用三個 feature：f1、f2、f3。一個 leaf 對應從 root 走下來的一串條件，也就是三個 feature 各一段範圍。如果 switch 支援 range matching，一個 leaf 一個 entry 就好，就是右上第一張表；但 switch 不一定支援，前面講的 match 只有 exact、ternary、LPM，所以範圍要拆成 ternary entry。
以 leaf 5 為例：f1 在 [65, 103) 要 8 個 ternary entry，f2 是整個範圍，1 個，f3 在 [10, 256) 要 6 個。三個條件要同時成立，entry 數要相乘，8 乘 1 乘 6，等於 48。這就是 entry 爆炸。
NetBeacon 的做法在下半，把一張表拆成兩種。
第一種是 feature table，每個 feature 一張。以 f1 為例：tree 裡 f1 有三個門檻，25、65、103，把 0 到 255 切成四段。range mark 就用三個 bit，一個 bit 對一個門檻：第一個 bit 是「小於 25 嗎」，第二個是「小於 65 嗎」，第三個是「小於 103 嗎」。所以最小的那一段 [0, 25) 是 111，[25, 65) 是 011，[65, 103) 是 001，最大的那一段是 000。
第二種是 model table，key 是三個 feature 的 range mark。重點是 range mark 可以用「都可以」的 bit 來表示跨好幾段的範圍。例如「f1 小於 65」跨了前兩段，只要後兩個 bit 是 1，第一個 bit 不管，就寫成 星 1 1。
回到 leaf 5：f1 在 [65, 103) 是 001；f2 沒有限制，是 星；f3 大於等於 10，是 0。所以 leaf 5 在 model table 只要 1 個 entry。每個 leaf 都是這樣，不管它的條件跨了幾段。
feature table 自己還是要把範圍轉成 ternary entry，左下那一塊就是 f1 的例子；論文另外設計了一個編碼方法來減少這些 entry，這部分我不展開。

## 第 8 頁　(iii) Stateful storage management

第三個設計：per-flow state 怎麼存。
flow-level feature 要用 register 存狀態。每條 flow 要存的東西有：flow ID、目前的 class、是不是已經判定，還有算 feature 要用的累計值，例如 packet 數、總 size。但 register 有限，論文實驗最多能存 65,536 條 flow 的 state。
怎麼知道一條 flow 存在哪一格？把 5-tuple 做 hash，再除以 register 數取餘數，得到 index。每個 packet 一進來都會算 index；沒命中 flow class table 的，才去讀那一格，比對裡面存的 flow ID，才知道這個 packet 屬不屬於已經有 state 的 flow。
用 hash 的問題是 collision：兩條不同的 flow 可能對到同一格。論文用兩個做法處理。
看圖，這是一條新 flow 的處理。第一個做法：先用 long-short 模型判斷這條 flow 是長的還是短的。這個模型只看單一 packet 的 per-packet features；long 和 short 是用訓練集 flow 長度的 80th percentile 來分。
短的，不存 state，只用 per-packet features 分類。這樣搶 register 的 flow 就少很多。
長的，才進到第二個做法：看 index 對到的那個 register 能不能佔用。如果是空的，或是原本住在裡面的 flow 已經判定了、或是逾時了，新 flow 就佔用它，開始算 flow-level features；不然，新 flow 就退回只用 per-packet features。意思是不去搶還在分析中的 flow，因為搶了，兩條 flow 的 state 都會被弄髒。
為什麼只幫 long flow 存？論文用 P2P 任務做了實驗，Fig. 10 顯示，只對超過 8 個或 16 個 packet 的 flow 用 flow-level features，整體 accuracy 和全部 flow 都用，非常接近。short flow 用 flow-level features，換到的好處很少。
long-short 模型是每個任務各自訓練的。以 P2P 為例，訓練時取 long flow 和 short flow 的前 7 個 packet 當樣本，accuracy 是 82%；其他任務的數字，論文沒有給。
所以退回 per-packet features 的 flow 有兩種：被判成 short 的，和 register 被佔住的。它們用的是另一個只用 per-packet features 的分類模型。

## 第 9 頁　Integrated data plane processing logic（Alg. 1）

這一頁是把前面三個設計合起來之後，data plane 處理一個 packet 的完整邏輯。論文寫成 Alg. 1，圖是我照它畫的簡化流程。裡面新出現的是 flow class table，我認為這是整個系統省資源的關鍵。
packet 進來，先查 flow class table，key 是 5-tuple。命中的話，直接拿存的 class，不再推論。
沒命中，就看有沒有 per-flow state。沒有 state，用 per-packet features 推論。有 state，就更新 state，如果這個 packet 剛好是 inference point 才推論。
一條 flow 什麼時候算判定？兩種情況：推論出來的機率超過 determination threshold，或是走完最後一個 inference point。判定之後，data plane 把 register 標記成已判定，並且通知 control plane，由 control plane 把這條 flow 的 5-tuple 和 class 寫進 flow class table。
要注意兩件事。第一，命中只看 5-tuple，不看 packet 的內容：只要 5-tuple 一樣，後面的 packet 不算 feature、不跑模型，直接套用當初的結果。第二，這個結果會一直用到 entry 被移除為止；論文沒有判定之後再檢查一次的機制。
flow class table 的 entry 依 FIFO 或 LRU 移除，避免表滿。register 在 flow 判定之後，就可以讓給新的 flow。
所以一條 flow 一旦判定，之後所有 packet 只查一張表。control plane 只負責寫表，不在 packet 的 critical path 上：還沒寫進去之前，packet 照樣走一般的推論流程。
這一頁的機制，第 15 頁會回來討論它的風險。

---

## 第 10 頁　Alg. 1 的例子：一條 long flow（P2P 任務）

用一個例子把 Alg. 1 走一遍：看一條 long flow 從第一個 packet 到被判定，switch 做了什麼。用 P2P 任務當例子，inference point 是第 2、4、8、32 個 packet，一直到 2048。
第 1 個 packet：flow class table 沒命中，register 裡存的也不是這條 flow，所以是新 flow。switch 用 per-packet 的模型給這個 packet 一個 class，同時用 long-short 模型判斷它是不是 long flow。判成 long，而且 index 對到的 register 可以用，也就是空的、或舊 flow 已經判定或逾時，就佔用這個 register，把 flow ID 和 class 寫進去。
第 2 個 packet：register 裡的 flow ID 對得上，就更新 register。第 2 個是 inference point，所以算 flow-level features，查 feature table 和 model table，得到新的 class 和機率，再把新的 class 寫回 register。
第 3 個 packet：不是 inference point，更新 register 之後，直接用 register 裡存的 class。
第 4、8、32 個 packet：和第 2 個一樣，只是換成那個 phase 的模型。只要有一次機率超過 threshold，或是走完最後一個、第 2048 個，register 就標記成已判定，並且通知 control plane。
control plane 把這條 flow 寫進 flow class table 之後：後面的 packet 在第一步就命中，直接用存的 class。那個 register 之後如果有別的 long flow 對到，就可以被拿走。
補充一個實作細節：register 一個 packet 只能存取一次，所以要改前面 stage 的 register，就要把 packet 複製一份、再走一次 pipeline。Alg. 1 裡有兩個地方要這樣做：新 flow 初始化 register，還有 inference point 寫回新的 class。不過論文量 mirror 比例的時候說，只有會觸發結果更新的 inference point packet 才被 mirror；新 flow 初始化算不算在裡面，論文沒有交代。比例在第 14 頁。
如果第 1 個 packet 被判成 short，或是 register 被佔住，這個 packet 就只用 per-packet 的模型分類。依 Alg. 1 的寫法，下一個 packet 進來會再判斷一次，所以這條 flow 之後還是有機會拿到 register。這是我從演算法推的，論文沒有明講。

## 第 11 頁　Experiment setup

論文的 evaluation 要證明三件事。第一，end-to-end 的 accuracy 比 baseline 高很多，而且和 stateful storage 不受限的理想情況相當。第二，model representation 有效率：accuracy 比較高，用的 table entry 比較少。第三，研究 NetBeacon 裡各個可調的部分。後面三頁各對應一件，這一頁先講設定。
環境：end-to-end 的實驗不是模擬，是在真的 switch 上做的：Barefoot 的 Tofino 1，data plane 用 P4 寫。switch 接兩台 Linux server，一台用 tcpreplay 把 pcap 送進 switch，另一台接收。指標是 per-packet 的 macro-accuracy，也就是每個 packet 判得對不對，再對各個 class 的 recall 取平均。
end-to-end 的評估用三個任務，流量的來源不一樣。
P2P application fingerprinting：這個不是攻擊，是分辨 eMule、uTorrent、Vuze 三種 P2P 應用。用 PeerRush dataset，模型是 Random Forest，testing flows 大約 24 萬條，7 個 inference point。
Covert channel detection：用 FacetTraffic dataset。Facet 是一個抗審查工具，把影片藏在 Skype 的視訊通話裡；任務是把這種 flow 和正常的 Skype flow 分開。另外加了 Univ2 的背景流量。模型是 XGBoost，只有 400 條 testing flows，9 個 inference point。
DDoS attack detection：攻擊流量是作者自己產生的，一共 8 種：5 種 amplification attack，加上 3 種設定的 pulsing DDoS。作者在一個有 650 台 VM 的 virtual private cloud 裡打，錄下來，再和 MAWI 的 backbone 流量合在一起。模型是 XGBoost，testing flows 大約 19 萬條，4 個 inference point。
所以三個任務都是重播 pcap，不是現場攻擊。
比較對象是 Mousika。Mousika 和 NetBeacon 是同一類做法，都是把 tree 模型放進 data plane，而且是當時最新、能實際部署的，所以論文主要和它比。兩者的差別在：Mousika 用 binary decision tree、只看 per-packet features；NetBeacon 用一般的 Random Forest、XGBoost，加上 flow-level features。這裡的 Mousika 是作者自己重做的版本。另外還有三個版本：NetBeacon 只用 per-packet features 的版本、沒有 storage 管理的版本，還有 Ideal。Ideal 是 end-to-end 實驗裡唯一用模擬的：用 Python 模擬 match/action，每一條 flow 都有自己的 storage，用來看 register 不夠損失了多少。其他像 Fig. 5、Fig. 14 這類模型的比較，論文沒有說在哪裡跑。
network load 用每秒新 flow 數的中位數表示，分 normal、medium、high 三種。

## 第 14 頁　NetBeacon deep dive

第三件事，論文叫 deep dive，看幾個因素對 NetBeacon 的影響。

接著看圖。兩張圖的橫軸都是 IndexSize，就是 flow index 用幾個 bit，越右邊 register 越多。

右圖是 P2P 任務：register 越多，accuracy 越高。藍色是有 storage 管理的完整版，紅色是沒有的，register 少的時候兩條線的差距最明顯。

## 第 15 頁　Discussion：security analysis

講限制。作者在 Discussion 討論了兩種針對參數的攻擊。
第一個是 stealth attack：攻擊者先送 benign packet，等 NetBeacon 判定這條 flow、寫進 flow class table 之後，才送 malicious packet。這正好打在第 9 頁的機制上：判定之後只看 5-tuple，不再看 packet。作者提的緩解，是在 flow class table 的 entry 加 maximum flow length limit。
第二個是 low-rate-long-flow attack：把 packet 間隔拉長，逼 flow 逾時。緩解是每條 flow 用自己的 timeout，例如最大 IPD 的兩倍。
作者認為這兩種攻擊有門檻，因為攻擊者要先探測參數。
投影片下面那一行是我的觀察，不是論文的話：這兩種攻擊和緩解，論文都只有文字討論；我讀完全文，沒有看到對應的實驗。第 11 頁那三個任務的流量裡，也沒有先 benign、後 malicious 的 flow。maximum flow length limit 要設多少，論文也沒有給數值。
另外，因為硬體限制，模型和 feature 都受限，論文說這可能影響複雜任務的 accuracy。下面小字是 Table 5 的 FPR 和 FNR：covert channel 是 8.8% 和 10.9%，DDoS 是 0.7% 和 0.05%。論文沒標明這是 per-packet 還是 flow-level，從上下文看應該是 per-packet 的數字。
論文另外說，covert channel 如果改用「至少 5 個 inference point 判對」當作 flow 偵測到，flow-level 的 FPR 是 5.3%、FNR 是 7.3%。

---

## 第 16 頁　Conclusion 與討論

總結。左邊是論文的結論：NetBeacon 在 model accuracy 和 model representation efficiency 兩方面都超過 prior art，靠的是三個設計：multi-phase sequential model、efficient model representation、stateful storage management。其中第三個，論文在 Introduction 說它讓 concurrent flow 的數量可以超過 register 的數量，用的詞是 potentially。我的理解是：超過 register 數的 flow 是退回 per-packet features，不是每條都有 flow-level features。
右邊四個問題，要先說清楚：這是我讀完之後的看法，不是論文的內容。
第一，判定之後就不再檢查，中途才變成惡意的 flow，會漏掉多少？論文沒有量。
第二，maximum flow length limit 要設多少？到期之後是重新分析，還是直接放行？
第三，determination threshold 論文說要依可用的硬體資源決定，那能不能依負載動態調整？
第四，flow class table 的大小，還有 FIFO 和 LRU 對 accuracy 的影響，論文只描述做法，沒有評估。
我的報告到這裡，謝謝，歡迎提問和討論。

## 第 1 頁　Intelligent Data Plane（IDP）

- 圖是報告人畫的簡圖，不是論文的圖。上排「ML 在 control plane」對應 NetWarden、FlowLens 這類做法：switch 收集 flow 資訊，分析在 control plane（PDF p.4 §2.2）；下排是 IDP。
- 敘述的順序照論文 §1（PDF p.2）：模型「typically deployed either on end-hosts or network control plane」，這兩處「equipped with flexible general-purpose processors or GPUs」；直接放到 data plane 是「a relatively less charted area」；IDP 以前「nearly impossible」，原因是 data plane 的 ASIC switching chip 是 specialized and protocol-defined，programmable switch（PISA）出現後才可行。圖的上排只畫 control plane，沒有畫 end-host。
- 論文沒有說「SDN 的 switch 把 ML 放在 control plane」。SDN 只出現在 §2.1（PDF p.3），講的是 programmability 的演進；當場不講，被問到再答，見第 2 頁補充。
- IDP 的定義：在 network data plane 上以 line-speed 做 intelligent traffic analysis；line-speed 的論文定義是「zero reduction to the network forwarding speed」（PDF p.2 Abstract、§1）。
- 10 Gbps：「the state-of-the-art that deploys learning models on the network control plane can only process traffic at roughly 10 Gbps [14]」（PDF p.2 §1）。[14] 是 Fu, Li, Shen, Xu 的 *Realtime Robust Malicious Traffic Detection via Frequency Domain Analysis*（PDF p.16 參考文獻）。這個數字是論文引用的一個 state-of-the-art，不是 control plane 方案的一般上限，被問到時要這樣說。
- 反應時間：「placing the control plane on the critical path of traffic analysis introduces extra reaction time [2]」（PDF p.2 §1）；[2] 是 Alcoz et al., *Aggregate-Based Congestion Control for Pulse-Wave DDoS Defense*（PDF p.16 參考文獻）。
- 為什麼不換成 SmartNIC 或 DPDK：論文的回答在 Discussion（PDF p.15 §8 Addressable Market Analysis）：SmartNIC、DPDK 的彈性大，但吞吐低，例如 NetFPGA-PLUS 是 200 Gbps、Tofino 1 整台合計 6.4 Tbps。另見 PDF p.4 §2.2 Design Goals：作者只做 PISA 的 programmable switch。
- 論文提到 IDP 除了安全以外也可以用在 routing、ECN threshold、buffer management（PDF p.2 §1）；這次沒有放。
- 背景知識（不是論文原文）：data plane 是 switch 裡實際轉送 packet 的部分；control plane 負責管理 switch、決定 table 的內容，跑在 switch 的 CPU 或旁邊的 server 上。論文對 control plane 的用法見 PDF p.2 §1、PDF p.15 §8（例如 auxiliary servers）。
- 被問到「NetBeacon 是不是在 control plane 做 ML」：不是。NetBeacon 的推論在 data plane；control plane 只做兩件事：一開始安裝 feature table 和 model table、收到 data plane 的通知後更新 flow class table（PDF p.10 §5.4）。在 control plane 做 ML 的是上排的 prior work（NetWarden、FlowLens）。會被拿來反問的一句：Appendix C 寫 NetBeacon puts the classification probabilities and threshold comparisons on the control plane（PDF p.19）；意思是 control plane 在產生 model table entry 時，先把「機率有沒有過 threshold」編進 entry，不是每個 packet 都去問 control plane（見第 9 頁補充）。模型的訓練是離線做的，用 Python 的 sklearn（PDF p.11 §7.1）。

---

## 第 2 頁　Programmable Data Plane（PISA）

- 圖：論文 Fig. 1（PDF p.3）。橘色是 Match、綠色是 Action、灰色是 Register；packet 從左邊進 Parser，經過 Stage 1 到 Stage N 的 Match/Action，最後出 Deparser。
- ASIC → SDN → PISA（PDF p.3 §2.1）：傳統 switch 用客製 ASIC，在上面做新 protocol 需要設備廠商 design、manufacturing、rigorous testing，「an expensive process」；「roughly two decades ago」提出 SDN，讓 software controller 透過 OpenFlow 在 switch 上安裝 customized flow entries，在 data center 廣泛部署；PISA 是「Instead of fully relying on a software controller, the switching pipeline itself is flexible enough to allow direct programming」，語言例如 P4。
- PISA ＝ Protocol Independent Switch Architecture。packet 先進 parser 解析 header，再進多個 match/action stage 處理，最後進 deparser 序列化（PDF p.3 §2.1）。parser、match/action、deparser 都可以用 P4 這類語言寫。
- 三個元件都可以寫程式的原文：「The parser, match/action, and deparser can all be programmed to implement desired protocols」（PDF p.3 §2.1）。論文對 parser 只寫 packet header parsing、對 deparser 只寫 packet serialization；「parser 把後面要用的欄位取出來」「deparser 把 packet 組回去送出」是報告人用 P4 的一般知識補的說法。
- 三種 match（PDF p.3 §2.1）：exact（完全一致）、ternary（每個 bit 可以是 0、1 或 \*，\* 代表 0 和 1 都符合，PDF p.6 §5.1）、LPM（longest prefix matching）。每個 match 對應一個 action。
- 互相有相依的 action 要放在不同 stage（PDF p.3 §2.1）。
- 表與限制的出處：論文把這些寫在「computation and storage constraints」那一段；支援 boolean、shift、add、subtract，不支援乘除；float、loop、複雜的條件運算也不支援（PDF p.3 §2.1）。Tofino 1 有 12 個 stage（PDF p.3 §2.1）；每條 pipeline 的 SRAM 是 120 MB、TCAM 是 6.2 MB（PDF p.3–4 §2.1；PDF p.10 §6）；每個 register 在一個 packet 經過 pipeline 時只能存取一次，所以 read-then-update 這種操作不能原生支援（PDF p.4 §2.1）。
- 另外 PISA 提供 resubmit、recirculation、packet generation 這些機制來擴充能力（PDF p.3 §2.1）。resubmit 後面第 9、10 頁會用到。
- 背景知識（不是論文原文）：ternary 的比對通常用 TCAM，exact 和 register 用 SRAM；所以論文才同時報告 SRAM 和 TCAM 的用量。
- 「為什麼選 tree」：論文的說法是 NetBeacon 和 prior art［26, 51, 63］一樣選 decision tree based 的模型，因為 tree 的結構比 neural network 更像 data plane 的 match/action，後者有大量非線性運算（PDF p.6 §4.2）。論文寫的是「選」tree，沒有說 switch 上只能放 tree，講的時候不要說成「只能」。
- 「為什麼 variance 要 2 的次方」：Var(X) ＝ E(X²) − E(X)²，要除法和平方；data plane 的除法只能用 shift，所以要求 inference point 的位置是 2 的次方；平方只支援近似，只看值的前 4 個 bit（PDF p.11 §6.1）。
- 被問到「12 個 stage 夠不夠」：論文說最新一代 Tofino 的 stage、TCAM、SRAM 幾乎加倍，所以 NetBeacon 的用量可以接受（PDF p.12 §7.2 P2P 段）。

## 第 3 頁　Comparison with prior art in IDP

  - NetWarden［53］、FlowLens［4］：Line-Speed ✗、Learning-Based ✓、Flow-Aware ✓。
  - Poseidon［61］、Jaqen［32］：Line-Speed ✓（加註 ¶）、Learning-Based ✗、Flow-Aware ✓。
  - Planter［63］、Mousika［51］：Line-Speed ✓、Learning-Based ✓、Flow-Aware ✗。
  - NetBeacon：三欄都 ✓。
  - ¶ 的原文：Some defense/detection polices or logic of Poseidon and Jaqen require control plane involvement. In such cases, they cannot be processed at line-speed.
  - 原表的欄位標題是 Line-Speed，以及 Accuracy / Generalization 底下的 Learning-Based、Flow-Aware；投影片省略了上層標題，Poseidon、Jaqen 那格也沒有放 ¶ 的星號和註，這個但書在當場講用一句話帶過。
- 各 prior work 做什麼（PDF p.2 §1、PDF p.4 §2.2）：NetWarden 做 covert channel detection，FlowLens 做 learning-based traffic classification，兩者都是 switch 收集 flow 資訊（例如 inter-packet delay 的分布）、分析在 control plane；Poseidon、Jaqen 在 data plane 用 threshold-based filter 擋 volumetric DDoS，不是 ML 模型。
- 沒列進表的 pForest［10］、SwitchTree［26］：論文說它們在 software switch BMv2 上驗證過，但在實際硬體上無法部署（PDF p.3 §1）；附錄 A 給了編譯錯誤的原因：action 裡不能有複雜條件，比較的兩邊也不能都是變數（PDF p.18 Appendix A、Fig. 16）。

- 投影片下方兩件事的出處：標題和兩個標籤用的是 §1 的說法，NetBeacon「advances state-of-the-art in both model accuracy and model deployment efficiency」（PDF p.3）；兩行的內容來自 §2.2，論文的原文是 their designs have two major limitations（PDF p.4），講的是 Planter 和 Mousika。投影片不寫「兩個限制」，是因為一個是效率、一個是準確度，性質不同；被問到時可以說論文原文是 two major limitations。相關原文：「all these prior deployable art employs only per-packet features in their models, fully ignoring flow-level features」（PDF p.3 §1）；Planter 和 Mousika 的兩個限制是 low efficiency in representing learning models，以及 merely considering stateless per-packet features（PDF p.4 §2.2）。
- 三個欄位的意思是報告人從論文的文字整理的，論文沒有逐欄下定義：Line-Speed 見 §1「zero reduction to the network forwarding speed」（PDF p.2）；Learning-Based 見 §2.2 對 Poseidon、Jaqen 的說法「based on threshold-driven traffic filters, instead of machine learning models」，所以「not generalizable」（PDF p.4）；Flow-Aware 見 §2.2「one flow-agnostic model that uses only per-packet features … and one flow-aware model that uses both flow-level and per-packet features」（PDF p.4）。

## 第 6 頁　(i) Multi-phase sequential model

- 圖：論文 Fig. 5（PDF p.6）。橫軸是三個任務，縱軸是 Accuracy (%)，紫色斜線是 Single model、綠色交叉是 Multi-phase sequential model；三個任務後者都明顯較高。縱軸的起點每張子圖不同（P2P 65、covert channel 80、DDoS 96，看刻度），不要跨子圖比柱高；論文正文沒有給這張圖的百分比，我沒有讀柱高。DDoS 子圖的縱軸從 96 開始，單一模型和 multi-phase 的差距在圖上看起來不小，但實際比 P2P 和 covert channel 小得多（看圖的觀察，論文沒有給數字）；論文正文只說 using a single model … yields low accuracies（PDF p.6 §4.2）。
- Fig. 4（PDF p.6，沒放投影片）：兩張 CDF，量的是 deviation degree ＝ abs(a − b) / max(a, b)，a 是 feature 的最終值、b 是前 n 個 packet 時的值；(a) 是 PeerRush 的 mean of IPD，(b) 是 ISCXVPN 的 variance of packet size；(a) 的 n 取 2、4、8、12、16、32 個 packet，(b) 取 4、8、12、16、32 個 packet（圖例）。論文的結論：兩個 feature 隨 flow 進行都有明顯變化，所以單一模型用 flow-level features 推論，accuracy 低（PDF p.6 §4.2）。
- inference point 的定義：在 flow 的第 n 個 packet，用前 n 個 packet 算出來的 flow-level features 做推論；沒被選成 inference point 的 packet，用前一個、最近的 inference point 的結果，所以兩個 inference point 的間隔不能太大（PDF p.6 §4.2）。inference point 的安排依任務而定，可以均勻也可以特別設計（PDF p.6 §4.2）。
- determination threshold：論文說 NetBeacon 對每個 inference phase 設一個 determination threshold；該 inference point 的分類機率超過它，就表示模型有把握提前判定 flow 的 class，不用等後面的 inference point；這個設計有助於 stateful storage 管理（PDF p.6 §4.2）。
- 模型：Random Forest（RF）和 XGBoost（XGB）；用限制 tree 的數量、最大深度、最大 leaf 數來控制模型大小，因為 data plane 的 table entry 有限（PDF p.6 §4.2）。
- 多個 phase 怎麼放進同一組 table（PDF p.11 §6.2、Fig. 12）：feature table 和 model table 多一個 key，叫 total_packets，用來區分不同 phase 的模型；某個 phase 用不到的 feature，range mark 填 \*；推論用兩個 stage，一個 stage 平行查 feature table，一個 stage 查 model table。論文的寫法是先講每個 phase 各自表示，再講 Alternatively, we can merge their representations；兩個 stage 的原文是 In general, model inference takes two stages。這兩個 stage 只算查表，不含算 feature（variance 要 4 個 stage，PDF p.11 §6.1）。Random Forest 有不只一棵 tree 時，§5.1 的做法要再接一張 plurality table（PDF p.8 §5.1），會多一個 stage；P2P 每個 phase 是 1 棵 tree（PDF p.19 Appendix D），沒有這個問題。被問「那 P2P 為什麼用到 12 個 stage」：論文沒有列每個 stage 做什麼，只給總數（PDF p.12 §7.2）。
- 各任務的 inference point：P2P 是 {2, 4, 8, 32, 256, 512, 2048}（PDF p.12 §7.2）；covert channel 是 {512, 1024, 1500, 2048, 3000, 4096, 6000, 8192, 10000}（PDF p.13 §7.2）；DDoS 是 {2, 5, 8, 16}（PDF p.13 §7.2）。注意 covert channel 和 DDoS 的位置不全是 2 的次方（這兩個任務用到哪些 feature，論文寫的是 packet size 區間的 packet 數、IPD 的最小值、packet size，沒有 variance，PDF p.13 §7.2）；2 的次方的限制只在用 variance 時才需要（PDF p.6 §4.2）。
- inference point 越多越好嗎：Fig. 15a（PDF p.14 §7.4，沒放投影片）顯示 accuracy 隨 inference point 增加而上升；論文沒有討論 inference point 增加的成本。
- 訓練資料怎麼做：論文說每個 phase 用該 phase 算出來的 feature 做訓練和推論，第 n 個 packet 的 flow-level features 由前 n 個 packet 算（PDF p.6 §4.2）。訓練樣本怎麼挑（例如不到 n 個 packet 的 flow 怎麼處理），論文沒有寫。推論時是 per-packet features 加 flow-level features 一起用（Alg. 1 第 13 行，PDF p.10）。
- 機率：Alg. 1 第 13 行的推論同時得到 class 和機率，第 14 行和 determination threshold 比（PDF p.10）。
- 模型大小（PDF p.19 Appendix D；寫法是「tree 數 * 最大深度」）：
  - P2P：七個 phase 都是 1*9；flow size prediction（long-short 模型）是 1*8；NetBeacon(Pkt) 是 2*9。
  - Covert channel：九個 phase 是 {2*5, 3*6, 3*6, 3*6, 3*7, 2*7, 3*6, 3*5, 3*4}；NetBeacon(Pkt) 是 1*10。
  - DDoS：四個 phase 是 {1*1, 1*4, 1*1, 1*1}；NetBeacon(Pkt) 是 1*4。

- 容易講錯：48 是 Fig. 6 這個例子裡 leaf 5 的 entry 數，不是整體的減少比例；整體的比較是第 13 頁的 75%（Fig. 14）。
- 被問到「entry 少 75% 怎麼來的」：「to represent two similarly-performing models, NetBeacon uses much fewer table entries on the data plane (e.g., 75% reduction in covert channel detection)」（PDF p.14 §7.3）；Introduction 的說法是 up to 75% in some cases（PDF p.3 §1 (ii)）。
- range mark 的 bit 怎麼來：Table 3 的設計直覺是，一個 basis range 如果落在 [0, r_j) 裡面，它的 range mark 的第 j 個 bit 就設成 1，預設是 0（PDF p.7 §5.1）。當場講的「第 j 個 bit 是『小於第 j 個門檻嗎』」是報告人的白話說法。
- 「f1 小於 65 寫成 \*11」：Table 3 的 model table 部分，[0, r_i) 的 range mark 是 i−1 個 \* 接 n−i+1 個 1；r_2 ＝ 65、n ＝ 3，所以是 \*11。這對應 Fig. 6 裡 leaf 4 的路徑，f1 的範圍 [0, 65) 跨了 [0, 25) 和 [25, 65) 兩個 basis range（PDF p.7–8 §5.1）。
- 「每個 leaf 只要一個 entry」的原文意思：range marking 保證每個 leaf 在 model table 只佔一個 ternary entry，不管有多少個 feature table entry 和這個 leaf 有關（PDF p.7 §5.1）。

## 第 8 頁　(iii) Stateful storage management

- 圖是報告人依論文 §5.2（PDF p.9–10）畫的流程，不是論文的圖。
- 用 hash 配 index 的原因：prior art［4, 53］要 control plane 為新 flow 配一個不衝突的 storage index；NetBeacon 用 data plane 現成的 hardware hashing，才能 line-speed（PDF p.9 §5.2）。index ＝ H(5-tuple) % N，N 是可用的 register 數（PDF p.9 §5.2）。
- 圖把順序簡化了：圖上 long-short 分類在前，「H(5-tuple) % N 對到的 register」在後。依 Alg. 1（PDF p.10），每個 packet 一進來就先算 hash 和 storage index（第 1–2 行），用 index 讀出 register 裡存的 flow ID（第 7 行），和 packet 的 flow ID 比對（第 9 行），ID 不同才是新 flow；新 flow 先用 per-packet features 推論 class、預測 flow size（第 21–22 行），預測是 long（第 23 行）才檢查 register 能不能佔用（第 24–25 行；§5.3 的原文是 the storage on Sid is empty or is ready to be overwritten），可以的話才初始化（第 26 行）。所以「算 index」是每個 packet 都做，不是只有 long flow 才做；圖為了簡潔，把它併進最後一格的條件裡。
- 容易混淆：論文裡的 N 有兩個意思。「N stateful registers」的 N 是 register 數；long-short 模型的「first N packets」的 N 是訓練時取多少個 packet 當樣本（PDF p.9 §5.2）。講的時候講「register 數」「訓練時取前 7 個 packet 當樣本」，不要只說 N，也不要說成「看前 7 個 packet 才判斷」。
- collision：因為不同 5-tuple 可能 hash 到同一個 register，所以 register 旁邊要存真正的 flow ID（5-tuple），才知道有沒有 collision（PDF p.9 §5.2）。兩個設計：減少 collision 的機率（只幫 long flow 存）、讓覆寫安全（不搶還在分析的 flow）。新 flow 直接覆寫的話，舊 flow 和新 flow 的 per-flow state 都會變 dirty（PDF p.9 §5.2）。
- 「已判定」的定義：flow 走完 multi-phase model 的最後一個 inference point，或是在中途的 inference point，模型對結果夠有把握（PDF p.9 §5.2）。「逾時」：flow 最後一個 packet 到達的時間超過預先設定的 timeout（PDF p.9 §5.2）；論文沒有給 timeout 的值。
- 還在分析的 flow 不會被搶：新 flow 只有在 register 是空的、或舊 flow 已判定、或逾時才能佔用，否則新 flow 退回只用 per-packet features（PDF p.9 §5.2；PDF p.10 §5.3）。
- 為什麼只幫 long flow 存：論文的理由是為 short flow 維護 per-flow state 的邊際效益比較低（PDF p.9 §5.2）。Fig. 10（PDF p.9，沒放投影片）：P2P 任務，五種情況，分別是全部 flow 都用 flow-level features、只對超過 8、16、1024、2048 個 packet 的 flow 用；前三種的整體 accuracy 很接近。論文沒有在正文給這張圖的百分比。
- long-short 模型：二元分類、只用 per-packet features，逐 packet 判斷這個 packet 屬不屬於 long flow（不是等收到 7 個 packet 才判斷）；用訓練集 flow 長度的 80th percentile 分 long 和 short；取 long（short）flow 的前 N 個 packet 當訓練樣本；P2P 任務 N ＝ 7、accuracy 82%（PDF p.9 §5.2）；論文說這個模型是 task-specific，其他任務的 N 和 accuracy 沒有給。原因是實際上沒辦法事先知道 flow 的長度（PDF p.9 §5.2）。
- 被問到「hash 不均勻會怎樣」：Fig. 15d（PDF p.14 §7.4）量了 58,000 條 flow、8,192 個 register 的情況，實際的分布比 ideal 的分布更散，可能造成額外的 collision；沒放投影片。
- 規模：實驗 IndexSize ＝ 16，最多同時維護 65,536 個 per-flow state（PDF p.12 §7.2）；論文估計 DDoS 任務下 Tofino 1 的一條 pipeline 最多可以放 140,000 個 flow index（PDF p.15 §8 Scalability Analysis）。
- register 裡存什麼：Alg. 1 用到的有存 flow ID 的 Reg_ID、存 class 的 Reg_Class、標記已判定的 Reg_sure（PDF p.10）；Fig. 11 的例子有 total_packets、total_size、size_square_sum（PDF p.11 §6.1）。論文沒有列出完整的清單；實際要存哪些累計值，看任務用的 feature，這句是報告人的推論。
- 退回 per-packet features 的兩種 flow：被判成 short 的（Alg. 1 第 23 行不成立），和 register 不能佔用的（第 25 行不成立）。Alg. 1 沒有替這兩種情況寫 else；依 §5.2，它們用 per-packet 的 stateless features 分類（PDF p.9 §5.2）。

## 第 9 頁　Integrated data plane processing logic（Alg. 1）

- 圖是報告人依 Alg. 1（PDF p.10）畫的簡化流程，不是論文的圖。Alg. 1 的對應：
  - 第 1–2 行：算 5-tuple 的 hash，取低 IndexSize 個 bit 當 storage index。
  - 第 4–5 行：packet 命中 flow class table（TClass），直接取 class。
  - 第 7–10 行：沒命中，讀 register 裡存的 flow ID 和 class；ID 相同表示這個 packet 屬於這條有 storage 的 flow，更新所有 register。
  - 第 11–17 行：如果是 inference point，算 flow-level features，用 per-packet 加 flow-level features 推論，得到 class 和機率；機率 ≥ dt（determination threshold）的話，把 register 的「已判定」標記設成 True，並記錄到 flow class table（第 14–16 行）；不論有沒有超過 dt，inference point 都用 Resubmit 把新的 class 寫回 register（第 17 行；PDF p.10 §5.3：用 resubmit 的 packet 更新既有 flow 的新推論結果，或為新 flow 初始化 storage）。
  - 第 18–19 行：不是 inference point，用 register 裡存的 class。
  - 第 20–27 行：ID 不同，是新 flow 的 packet：先用 per-packet features 推論 class，再預測 flow size；預測為 long 的話，檢查 register 是不是逾時或已判定，是的話初始化 register。
  - 第 28–30 行：Resubmit 回來的 packet，用來寫入 class 和 ID。
  - 投影片把「ID 相同、更新 state」和「有 per-flow state」合成一格，沒畫 Resubmit 和新 flow 的初始化。
- flow class table 怎麼寫入：data plane 判定後，用 digest 通知 control plane，由 control plane 插入 entry（PDF p.9–10 §5.2、§5.4）。digest 是 Tofino 上 data plane 傳訊息給 control plane 的機制（PDF p.10 §5.4 的括號）。control plane 只做兩件事：一開始安裝 feature table 和 model table、收到 digest 後更新 flow class table（PDF p.10 §5.4）。
- 不在 critical path：「the latency for updating the flow class table does not impact traffic analysis, because the packets that are not matched by the flow class table will instead traverse the regular model inference pipeline」（PDF p.10 §5.4）。
- Resubmit 與 mirror：每個 register 一個 packet 只能存取一次，要修改前面 stage 的 register（寫 class、寫 ID），要讓 packet 再過一次 pipeline，這就是 Resubmit 的用途（PDF p.10 §5.3）。論文的實作改成把 packet mirror 到 loopback port，而不是 Resubmit 或 Recirculation，這樣原本的 packet 不會被延遲；只有會觸發更新的 inference point 的 packet 才被 mirror，比例見第 14 頁（PDF p.10 §5.3；PDF p.14 §7.4）。
- FIFO、LRU（PDF p.19 Appendix C）：table 滿的時候才替換。FIFO：control plane 維護插入順序，替換最早插入的 entry，適合 flow 持續時間差不多的情況。LRU：用 counter 記錄 entry 被命中的 packet 數，counter 沒有變動的時間就當成沒被用的時間，替換最久沒用的 entry，適合 flow 持續時間差很多的情況。論文沒有量這兩種方法的效果，也沒有給 flow class table 的大小。
- 命中 flow class table 的 packet 不會再被 ML 模型分析（PDF p.15 §8 Scalability Analysis）；這是第 15 頁 stealth attack 利用的地方。
- threshold 怎麼實作（PDF p.19 Appendix C）：model table 的 action parameter 編碼 n 或 n + x（n 是 class、x 是比 class 數大的任意數），機率有達到 threshold 的用其中一種、沒達到的用另一種，data plane 只要判斷 parameter 是否大於 x；論文說這樣 determination threshold 可以不停機更新。論文的原文是 puts the classification probabilities and threshold comparisons on the control plane，意思是比較在產生 entry 時就做好。所以 Alg. 1 第 13 行寫的「得到 class 和機率」是抽象的寫法；實作上 data plane 拿不到機率的數值，只拿到有沒有過 threshold。flow class table 的 FIFO 記錄和替換也是 control plane 做的（PDF p.19 Appendix C）。
- threshold 在 source code 裡的樣子（出處是公開的 `controller.py`，不是論文）：Appendix C 的 x 在程式裡是 50，controller 裝 model table 的 entry 時，class 編號加 50 代表已判定。公開版裡「機率超過 threshold 就加 50」那一行是註解掉的（寫的值是 0.45），生效的只有「第 2048 個 packet 那個 phase 一律加 50」。這只是公開版的狀態，不代表論文的實驗是這樣跑的。
- 容易講錯：「不再推論」指命中 flow class table 的 packet 不再做 ML 推論，不是整條 flow 不再轉送或不再計數。entry 被 FIFO 或 LRU 移除之後，沒被 flow class table 命中的 packet 會走一般的推論流程（PDF p.10 §5.4 的原文）；移除之後這條 flow 是不是會被重新分析，論文沒有明說，這是我從原文推得的。
- 「命中只看 5-tuple」：flow class table 以 flow 的 5-tuple 當 key，用來 match 這條 flow 後面的 packet（PDF p.9 §5.2）；命中之後直接取存的 class（Alg. 1 第 4–5 行，PDF p.10）。
- 判定的兩種情況：走完最後一個 inference point，或是中途的 inference point 機率夠高（PDF p.9 §5.2）。Alg. 1 只寫出機率 ≥ dt 那一種（第 14–16 行）。
- 「這是整個系統省資源的關鍵」是報告人的看法，論文沒有這句話；論文只說命中 flow class table 的 packet 不再被 ML 模型分析（PDF p.15 §8 Scalability Analysis）。
- 「沒有判定之後再檢查一次的機制」是報告人讀完全文的觀察；論文在 §8 提的 maximum flow length limit 是緩解的建議，沒有實作或實驗（PDF p.15 §8）。

## 第 14 頁　NetBeacon deep dive

- §7.4 的小標依序是 Throughput、The Number of Inference Points、Determination Thresholds、The Size of Stateful Storage、Imperfection of Hardware Hashing（PDF p.14）；投影片放第一、三、四項。
- throughput（PDF p.14 §7.4）：「The PISA pipeline on programmable switches ensures that any compiled program will run at line-speed」；P2P、covert channel、DDoS 三個任務分別量到 99.12、99.13、99.18 Gbps，是在 100 Gb 的 forwarding port 上。論文沒有解釋這和 100 Gbps 的差距，所以不要說成「零損失」。
- mirror 比例（PDF p.14 §7.4）：一個 100 Gb 的 loopback port 由一條 pipeline 裡的 16 個 forwarding port 共用，所以每個 forwarding port 被 mirror 的 packet 比例平均要小於 1/16，loopback port 才不會變成瓶頸；實測是 3.8%、0.09%、1.28%（P2P、covert channel、DDoS）。Alg. 1 第 27 行新 flow 初始化也用 Resubmit，論文沒說這部分有沒有算進這些比例。
- 圖：論文 Fig. 15 的 (b)(c)（PDF p.14），(a)(d) 沒放。Fig. 15 caption：(b)、(c) 的任務分別是 covert channel detection 和 P2P application fingerprinting。
- 完整的 Fig. 15（PDF p.14 §7.4）：(a) phase 數的影響，accuracy 隨 inference point 增加而上升；(d) switch 上 hash function 的不均勻（58,000 條 flow、8,192 個 register）。
- (b) 怎麼讀：橫軸是 The bits of flow index (IndexSize)，從 11 到 16；縱軸 Macro-Accuracy (%)；兩條線是 threshold(0.7) 和 threshold(0.8)。論文只比較這兩個 threshold，且只在 covert channel 這個任務上。論文的結論：register 少（IndexSize 小）時，較低的 threshold 讓 register 早一點釋放，補回早期判定損失的 accuracy，所以 accuracy 比較高；register 多時，較高的 threshold 比較有利；所以 determination threshold 要考慮可用的硬體資源來決定（PDF p.14 §7.4）。兩條線大約在 12 和 13 之間交叉，這是我看圖的觀察，論文文字沒有給交叉點。
- (c) 怎麼讀：橫軸同樣是 IndexSize 11 到 16；兩條線是 NetBeacon Full Version 和 NetBeacon w/o Optimization；任務是 P2P。論文的結論：stateful storage 的大小和 accuracy 正相關；在有限的 storage 上，storage 管理讓 accuracy 提高「non-trivial margins」（PDF p.14 §7.4）。「register 少的時候差距最明顯」是我看圖的觀察（IndexSize 較小時兩條線距離比 16 時大），論文的原文是 non-trivial margins upon the limited stateful storage。
- IndexSize 是 flow index 的 bit 數；IndexSize 16 對應最多 65,536 個 per-flow state（PDF p.12 §7.2）。其他 IndexSize 對應的 register 數是 2 的 IndexSize 次方，這是我的換算，不是論文給的數字。
- 容易講錯：「低 threshold 比較好」只在 register 少的時候成立，不是一般結論；而且是這個任務、這兩個 threshold 的結果。
- 和第 16 頁問題 3 的關係：threshold 的比較在產生 table entry 時處理，可以不停機更新（PDF p.19 Appendix C）；論文沒有做「依負載動態調整 threshold」的實驗。

## 第 15 頁　Discussion：security analysis

- 出處：PDF p.15 §8 Discussion 的 Security Analysis。論文先討論第一類攻擊 resource exhausting attack：攻擊者產生大量的 concurrent bogus flows 把 switch 的 SRAM 塞滿，屬於 Denial-of-Capability（DoC）攻擊；論文說這不會讓 NetBeacon 完全失效，因為可以退回 per-packet features；實務上用 aggregate flows 或平行部署多個 NetBeacon instance 來緩解。投影片只放第二類，因為它直接關係到第 9 頁的機制。
- 第二類是針對系統參數的攻擊：stealth attack（攻擊者先送 benign packet，等 NetBeacon 判定 flow class 之後才送 malicious packet）、low-rate-long-flow attack（攻擊者讓 flow 逾時）。論文說這類攻擊有 entry barriers，因為攻擊者要先探測參數設定；緩解方法：stealth attack 用 maximum flow length limit（加在 flow class table 的 entry 上）；low-rate-long-flow attack 用每條 flow 自己的 timeout，例如最大 IPD 的兩倍（PDF p.15 §8）。「把 packet 間隔拉長」是報告人從 low-rate 這個名字和緩解方式的理解；論文只寫 the attacker forces the flow to timeout，沒有說手法。
- **沒有實驗**（投影片上標「報告人的觀察」的那一行）：論文 §7 沒有針對這兩種攻擊或緩解的實驗。這是報告人讀完全文的觀察，講的時候說「我讀全文沒有看到」，不要說成作者承認。
- 論文的 threat model（PDF p.4 §2.2 Assumptions, Threat Model, and Limitations）：假設有任務相關的訓練資料；machine learning 本身的漏洞（例如 data poisoning、model poisoning）不在範圍；假設 programmable switch 本身是安全的。
- Table 5（PDF p.13）：FPR／FNR，P2P 是 7.6%／12%／14.7%\*，covert channel 是 8.8%／10.9%，DDoS 是 0.7%／0.05%；註：The multi-class FPRs are defined under 1 v.s. all。投影片和當場講只放 covert channel 和 DDoS，P2P 的三個數字只留在這裡備查。P2P 那格有三個數字，表格沒有逐一說明各自對應哪個類別或哪個指標；被問到時要說「論文只在註裡說 multi-class 的 FPR 是 1 對其他，三個數字各是什麼，我沒有逐一對過」。
- 當場講說的「論文沒標明，從上下文看應該是 per-packet」是我的推論：Table 5 的 caption 只寫 The FPRs/FNRs in the three tasks，沒有標 packet-level 或 flow-level，依據是 §7.1 的主要指標是 packet-level macro-accuracy（PDF p.11），而 Table 5 之後才說「deeper investigation … flow-level macro-accuracy is fairly decent」（PDF p.13 §7.2 Caveats），表示前面的是 per-packet 的。
- flow-level 的數字（PDF p.13 §7.2 Caveats）：如果把「至少 5 個 inference point 正確辨識出 packet」當作 covert channel flow 被偵測到，flow-level FPR 是 5.3%、FNR 是 7.3%。論文說 flow-level 的解讀對 intrusion detection／prevention 特別有用。
- 論文自己的說法：受 PISA 的限制，features 和 model architecture 受限，可能影響複雜任務的 accuracy（PDF p.15 §8 Addressable Market Analysis）；對需要複雜模型和 feature 的任務，改善 accuracy 是 IDP 的研究方向（PDF p.13 §7.2 Caveats）。
- 其他限制（PDF p.4 §2.2）：concurrent flow 的數量受硬體 storage 限制；不支援 data plane 難算的 flow-level features；可以平行部署多個 NetBeacon instance 來擴充分析容量。
- 容易講錯：Table 5 的 FPR／FNR 論文沒標明，我推論是 per-packet 的，不要拿來和 flow-level 的 5.3%、7.3% 直接比；而且 5.3%／7.3% 只有 covert channel 一個任務。

## 第 16 頁　Conclusion 與討論

- 左欄「論文的結論」的出處：§10 Conclusion 說 NetBeacon outperforms prior art in both learning model accuracy and model representation efficiency，並列出 (i)(ii)(iii) 三個設計（PDF p.15 §10）；三個設計的詳細說法在 §1（PDF p.3 §1）。「concurrent flow 數可以超過 register 數」：論文 §1 (iii) 的原文是 This potentially allows NetBeacon to handle more concurrent flows than the total number of registers（PDF p.3 §1）；§8 Scalability Analysis 說 There is no hard limit on the number of concurrent flows … since it can fall back to use per-packet features（PDF p.15 §8）。論文用的詞是 potentially；注意：超出 register 數的 flow 是退回 per-packet features，不是每條 flow 都有 flow-level features，accuracy 會隨 register 變少下降（Fig. 15c）。
- **右邊四個問題是報告人的看法，不是論文的內容**，講的時候要先說清楚。每個問題對應論文有沒有講：
  - 問題 1（判定後不再檢查會漏多少）：論文只在 security analysis 提到 stealth attack 的情境，沒有量漏掉多少，也沒有量判定後行為改變的 flow 比例（PDF p.15 §8）。
  - 問題 2（maximum flow length limit）：論文只說 NetBeacon can enforce a maximum flow length limit on the entries in the flow class table（PDF p.15 §8），沒有給數值，也沒有說到期之後是重新分析還是放行。
  - 問題 3（threshold 動態調整）：論文的結論是 threshold 要依可用的硬體資源決定（PDF p.14 §7.4）；實作上 threshold 可以不停機更新（PDF p.19 Appendix C）；論文只比較 0.7 和 0.8 兩個值（Fig. 15b），沒有依負載動態調整的實驗。所以投影片寫的是論文的結論「要依硬體資源決定」，問題是「能不能依負載動態調整」。
  - 問題 4（flow class table 的大小與 FIFO／LRU）：論文只在 §5.2（PDF p.9）和 Appendix C（PDF p.19）描述做法，沒有量 table 大小和替換策略對 accuracy 的影響。
- 被問到「這篇和其他方案比怎麼樣」：論文的比較只有 Table 1 的定位和 §7 對 Mousika 的比較；SmartNIC、DPDK 的比較只有 PDF p.15 §8 的文字，沒有實驗。
