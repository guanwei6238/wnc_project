## 第 2 頁　對齊結果

這一頁回答「label 可不可信」：label 和 pcap 裡的 packet 對得多完整。兩個欄位的意思：flow alignment 是 label 的 flow 在 pcap 裡找得到對應 packet 的比例；packet coverage 是 pcap 的 packet 落在某一條 label flow 裡的比例。
逐條 flow 標 label 的三個 dataset，flow alignment 都在 98.8% 以上；最低的 IoT-23 是 98.87%，被 60-1 (Gafgyt) 拉低，扣掉 60-1 (Gafgyt) 是 99.97%，細節 10/19 報告過。

## 第 3 頁　實驗設定

這次要回答的問題是：流量送進本地 IDS，偵測得出來嗎。
Engine 是 Suricata 8.0.7，和 Pi 上同一個套件版本；rule 是 2026-10-30 的 ET Open，52,798 條。
rule 全部啟用，後面每一頁的數字都是這個設定的結果。

## 第 4 頁　偵測怎麼算

Suricata 輸出的 alert 在 eve.json，用 5-tuple 加時間對上 flow，flow 再對回 label。
這樣每條 flow 只有「有 alert」或「沒有 alert」。我們再看觸發的 rule 描述的是不是這種攻擊，叫「rule 對得上」。
所以結果只有四種，用攻擊或正常、有 alert 或沒有 alert 來分：
攻擊流量有 alert，而且 rule 對得上，是偵測到（✓），例子是 CIC-IDS2017 的 SQL Injection，觸發的是 SQLi 的 rule；
攻擊流量有 alert，但 rule 對不上，是原因不符（△），例子是 CIC-DDoS2019 的 DrDoS_DNS，162 條有 alert 的 flow 裡 143 條是攻擊主機的 ping；
攻擊流量完全沒有 alert，是漏報（✗），例子是 IoT-23 的 DDoS；
正常流量有 alert，是誤報，例子是 CIC-IDS2017 的 Monday，全部是 Benign，卻有 adware JA3 的 alert。
「對得上」看 rule 描述的內容，不看名稱一不一樣，例如 FTP-Patator 對 FTP brute force；rule 要描述的是攻擊本身，例如只數 SYN 的 SSH scan rule 描述的是 scan，不算對得上暴力破解；認的是協定使用的 rule（IRC 指令、SNMP `public`），也不算 C&C 或 DDoS。判斷單位是一種攻擊，只要有一條 flow 的 alert 對得上就算 ✓。
還有，很多 rule 有 threshold：例如 SSH scan 同一來源每累計 5 次符合條件的 SYN 才報 1 次。如果一條 flow 只有一個 SYN，有 alert 的 flow 約 20%，但這不是上限，3-1 (Muhstik) 是 31.1%，原因**沒有查**。
所以 scan 和 DoS 不能只看有 alert 的 flow 比例，要看 rule 對不對得上。

最後把四個 dataset 放在一起

## 第 10 頁　結論

回到最初的問題：流量送進本地 IDS，偵測得出來嗎？答案看攻擊型態。
payload 有特徵的，大多偵測到（rule 對得上）：Web 攻擊、exploit、ELF 下載、C&C checkin、FTP 暴力破解。
沒有內容特徵的大量流量，大多沒有偵測到：SYN scan、TCP／UDP flood、反射式 DDoS、HTTP DoS，不是沒有 alert（漏報），就是有 alert 但 rule 對不上（原因不符）；例外是 SSH 等少數 port 有只看 header 的 scan rule。「沒有內容特徵所以沒有偵測到」是**推論**：觀察到的是這些流量大多沒有 rule 對得上的 alert，原因除了沒有內容特徵，也可能是 rule set 沒有對應的 rule、threshold 或設定。
而 malicious flow 大多屬於第二種，所以本地的 rule 大多抓不到量最大的那一類。
本地 IDS 的 rule 主要抓得到有內容特徵的攻擊，另有少數 port 只看 header 的 scan rule；其他 scan、flood 要靠 flow 層級的統計，例如速率、連線對象數。這是推論，這次沒有實作或量測 flow 統計的偵測。

## 第 2 頁　對齊結果

**共用：欄位定義與 usable 條件**

- 這一頁的表只放測試範圍、label 和兩個對齊欄位（flow alignment、packet coverage）。每個 dataset 完整的原始數據（檔案、大小、packets、flows、日期、攻擊）在下面各段開頭的表，被問到時查。
- 欄位定義（四段共用；CICIoT2023 的 label 是整個檔，所以只有 packets、flows）：
  - **packets** 是 pcap 裡的 packet 數。
  - **labeled flows** 是 label 檔裡的 flow 數（IoT-23、CIC-IDS2017 算 TCP／UDP／ICMP；CIC-DDoS2019 另含 Protocol 0，見 CIC-DDoS2019 段）。
  - **flow alignment** 是 labeled flows 裡，在 pcap 找得到剛好對得上的 packet（5-tuple 相同、時間在 flow 的開始與結束之間、packet 數剛好相等）的比例。
  - **packet coverage** 是 pcap 全部的 packet 裡，落在某一條 labeled flow 範圍內的比例。
  - **大小** 是 pcap 的檔案大小，GB 是 10^9 bytes。
- **usable**：flow alignment ≥ 99% 且 packet coverage ≥ 90%（10/19 訂的條件）。usable 只代表對齊的品質（label 和 packet 對得多完整）。
- 投影片上的數字從哪來：IoT-23 是下面表中「全部」那一列（23 個有 label 的 scenario 的 flow alignment；packet coverage 的分母含沒有 label 的 5 個 pcap）；CIC-IDS2017 是 5 天合計；CIC-DDoS2019 是兩天加總（見 CIC-DDoS2019 段）；CICIoT2023 的 label 是整個檔，沒有逐條的 label 可以對，所以是「—」。
- 「測試範圍」欄是跑過的 pcap 合計大小（GB 是 10^9 bytes），四個都是官方給的全部：
  - IoT-23 62.9 GB：28 個 pcap。23 個有 label 的 scenario 就是官方的全部（Honeypot-7-1 底下的 6 個 pcap 只有 Somfy-01 有 label，見 IoT-23 段）；flow alignment 算的是有 label 的 flow，packet coverage 的分母是全部 28 個 pcap。
  - CIC-IDS2017 52.4 GB：5 天，一天一個 pcapng。
  - CIC-DDoS2019 192.7 GB：03-11 的 29.1 GB（146 段）加 01-12 的 163.6 GB（819 段）。
  - CICIoT2023 587.3 GB：309 個檔，每個最多 2 GB。
  - 各 dataset 切檔的方式不同，檔數不能互相比，所以用大小表示測試範圍。

**怎麼讀**

- 表的每列一個範圍：「全部」是 IoT-23 的 28 個 pcap（23 個有 label）；「11 個 usable」是其中對齊品質達標的 11 個 scenario：1-1 (Hide and Seek)、7-1 (Linux.Mirai)、9-1 (Linux.Hajime)、17-1 (Kenjiro)、33-1 (Kenjiro)、35-1 (Mirai)、36-1 (Okiru)、39-1 (IRCBot)、42-1 (Trojan)、43-1 (Mirai)、48-1 (Mirai)。
- 全部：28 個 pcap 共 62.9 GB、770,313,789 個 packet；其中 23 個有 label 的 labeled flows 共 325,309,946 條，aligned 321,632,849（98.87%）、covered 742,702,878（96.42%，分母含沒有 label 的 5 個 pcap，約 54 萬個 packet）。
- 11 個 usable：32.1 GB、413,410,334 個 packet、296,338,640 條 labeled flows，aligned 296,263,818（99.97%）、covered 413,233,218（99.96%）。
- 偵測用的是全部 23 個有 label 的 scenario 的完整 pcap（7.7 億個 packet、3.25 億條 flow），是第 5 頁數字的分母。Somfy-02～06 沒有 label，Suricata 也跑過，都是 0 筆 alert。
- usable 只代表對齊的品質（label 和 packet 對得多完整）；偵測的比對只看 5-tuple 和時間、不看 packet 數，所以 34-1 (Mirai)、60-1 (Gafgyt) 這種 packet 數對不上的 scenario，alert 一樣對得到 flow。52-1 (Mirai)、49-1 (Mirai) 的 label 只涵蓋 pcap 的前 61%、90%，之後的 alert 沒有 label 可對（52-1 (Mirai) 3 筆、49-1 (Mirai) 135 筆，見第 4 頁）。11 個 usable 的結果另外算過：malicious flow 有 alert 的 5.54%（全部 23 個是 5.01%）。

**實驗怎麼做**

- 數字來自 10/19 的對齊結果（28 個 pcap 各一份 json），這次沒有重做對齊。10/19 的偵測只跑每個 scenario 前 20 萬個 packet，這次跑完整的 pcap。
- 為什麼是 28 個 pcap：IoT-23 官方的 tar 是 23 個頂層資料夾，Honeypot-7-1 底下又分 Somfy-01～06，所以是 28 個 pcap；Somfy-02～06 沒有 label 檔，所以 labeled flows 只算 23 個。

**被問到時**

- **98.87% 和 99.97% 差在哪？** 「全部」的 98.87% 被 60-1 (Gafgyt) 拉低（扣掉 60-1 (Gafgyt) 是 99.97%）；usable 的條件是 flow alignment ≥ 99% 且 packet coverage ≥ 90%，第二列的 11 個 scenario 符合。
- **為什麼 usable 只有 11 個？** 條件是 flow alignment ≥ 99% 且 packet coverage ≥ 90%，其他 scenario 不符合，例如 60-1 (Gafgyt) 的 flow alignment 只有 0.02%、Somfy-02～06 沒有 label。flow alignment ≥ 99% 但 packet coverage 不到 90% 的有：8-1 (Hakai) 70.60%、20-1 (Torii) 82.16%、21-1 (Torii) 81.81%、49-1 (Mirai) 89.80%、52-1 (Mirai) 61.36%、Honeypot 7-1 (door lock, Somfy-01) 85.28%。逐個 scenario 的數字見 10/19 的報告。
- **偵測為什麼不只用 11 個 usable？** 偵測的比對只看 5-tuple 和時間，不看 packet 數，對齊失敗的 flow，它的 alert 一樣對得到；只用 11 個會漏掉 3-1 (Muhstik)、34-1 (Mirai)、49-1 (Mirai) 的 C&C 和 60-1 (Gafgyt) 的 DDoS（22 GB）這些 scenario 的結果。
- **7-1 (Linux.Mirai) 的 Benign 呢？** 10/19 的報告另外提到 7-1 (Linux.Mirai) 的 Benign 有 86.5% 對不回 packet；影響的只有 Benign 的數字（Benign 只列數字，見第 9 頁）。
- **資料怎麼取得、有沒有核對？** IoT-23 是 Zenodo 的全部，tar.gz 21.5 GB，解開後 pcap 共 62.9 GB；md5 和 Zenodo 一致，原始壓縮檔存在 NAS。

## 第 3 頁　實驗設定

**怎麼讀**

- 每列一個設定項。Engine、Rules 是軟體版本；Rules 全部啟用，結果檔和補充裡叫 `full`；讀法 offline 是 engine 直接讀 pcap 檔，不是 inline 收即時流量。10/19 為公司 gateway 挑的 `gw_corp`，是從 `full` 的 alert 依 SID 篩出來的，只在補充裡比較（第 9 頁的補充「挑過的 rule set 會不會漏？」）。
- Rules：52,798 條是 ET Open 2026-10-30 的 rule 數；CICIoT2023 有 3 條 rule 載入失敗，載入 52,795 條（原因見「被問到時」的「rule 都有載入嗎？」）。
- rule set：`full` 是 ET Open 全部啟用的 rule；`gw_corp` 是 10/19 依公司 gateway 需求挑的本地 rule（38,506 條，是 10/11 的 SID 清單裡 8.0.7 還有的）；IP 清單是 TOR、CINS、Spamhaus DROP 等長 IP 清單的 1,223 條 rule。
- **`gw_corp` + IP 清單**：`gw_corp` 再加上 IP 清單的 1,223 條 rule。這個組合的數字有算（`tests/detection/results/*_by_label.tsv` 的 `gw_corp+iplist_flows`、`gw_corp+iplist_pct` 欄），投影片不放；第 5 頁 IoT-23 的 Okiru（△，只有 IP 清單的 alert）指的就是這類 rule（它們在 `full` 裡、不在 `gw_corp`）。
- **HOME_NET**（投影片不放）是 Suricata 判斷「內部」的網段，依 dataset 的網路架構設定：CIC-IDS2017 和 CIC-DDoS2019 只放受害端網段，IoT-23 用 Suricata 預設，CICIoT2023 設成 any；原因見「實驗怎麼做」的 HOME_NET。被問到時照這個設定講。

**實驗怎麼做**

- offline：Suricata 直接讀完整的 pcap，在工作站的 Docker 跑；結果由 engine 版本、設定、rule 與 pcap 決定（設定和 Pi 相同），所以 Pi 上同版本的 Suricata 應該得到一樣的結果（**推論**，**沒有量**）。設定和 10/19 一樣：Debian 預設的 `suricata.yaml`、single thread、`ac-ks`、`-k none`，只把輸出限定為 alert。CIC-DDoS2019 的 01-12 是從 zip 解壓後用 pipe 送進 Suricata（見第 2 頁的補充）；用 03-11 驗證過 pipe 和讀檔案的 alert 相同（兩份輸出都保存在工作站的 `~/datasets/detection/pipe_test/0311/` 與 `~/datasets/detection/cicddos2019/0311/`）。
- 版本：Pi 上 10/30 已經升級到 Suricata 8.0.7（gateway 實作要求 8.0 以上），所以這次也用 8.0.7、ET Open 給 8.0.7 的版本。
- rule set：IP 清單的 1,223 條，10/19 決定改用 nftables 的 IP 集合比對，不放在 IDS 裡，但 gateway 一樣比對得到，所以另外算一欄 `gw_corp` + IP 清單。實際只跑一次 `full`，`gw_corp` 的結果是從 `full` 的 alert 依 SID 篩出來的；已知誤差：如果 `gw_corp` 裡有 rule 靠被排除的 rule 先設 flowbits，篩出來的數字會偏高（`tests/detection/README.md`）。
- HOME_NET：Suricata 預設的 HOME_NET 是 RFC1918 三段（10/8、172.16/12、192.168/16）。CIC-IDS2017 和 CIC-DDoS2019 的攻擊者經過防火牆 NAT 之後，在 pcap 裡是 `172.16.0.1`、`172.16.0.5`，會被預設當成內部主機，「外部打內部」的 rule 就不會觸發。所以 HOME_NET 只放受害端網段，模擬 gateway 放在攻擊者與受害者之間：CIC-IDS2017 `192.168.10.0/24`、CIC-DDoS2019 `192.168.50.0/24`。IoT-23 的被感染設備在 192.168.x，預設剛好正確。CICIoT2023 的攻擊者（實驗網路裡的 Raspberry Pi）和受害設備在同一個區網，官方受害清單只有設備名稱，所以 HOME_NET 和 EXTERNAL_NET 都設成 any（不分內外，所有方向的 rule 都適用；但有 3 條 rule 的位址取反後變成空集合，載入失敗，所以載入 52,795 條）。

**被問到時**

- **HOME_NET 設成受害端網段差多少？** CIC-IDS2017 Wednesday 兩種都跑過。DoS Hulk、GoldenEye、Slowloris 兩種設定都是 0；設成受害端網段之後，Slowhttptest 從 0 變 4 條（`Unusually Fast HTTP Requests`），Heartbleed 從 2 條變 1 條（預設設定下另一條 Heartbleed rule 也會觸發）。其他天只跑了受害端網段的設定。第一次用預設 HOME_NET 的輸出沒有保留，這些數字是當時的紀錄。
- **為什麼不用 Snort 3？** 10/19 的結論是以 Suricata 為 base 實作 gateway，這次只測 gateway 要用的 engine。
- **offline 和實際送進 Pi 差在哪？** offline 不會掉 packet（處理完一個才讀下一個），時間用 pcap 的 timestamp；實際送進 Pi 時如果 CPU 跟不上，NFLOG 會丟、NFQ 會排隊或丟，可能影響收到的 alert。所以這次的結果是 offline 的基準結果，不是偵測能力的上限：同一台機器在 flow emergency mode 下結果也會有差異（`flow.memcap` 調大後 DrDoS_SNMP 有 alert 的 flow 從 210 條變 207 條）；Pi 和線上的差異還沒有驗證。Pi 跟不跟得上是另一個測試：目前量過的是 engine 處理 pcap 的速度（結論頁那一行）。
- **Pi 上跑，結果會一樣嗎？** 偵測結果由 engine 版本、設定、rule 和 pcap 決定；Pi 只影響處理速度（10/19 和這次的速度測試量過），所以應該一樣。這是**推論**：這次**沒有量**，沒有在 Pi 上跑偵測，也沒有 inline。
- **同一個 pcap 在同一台機器重跑，結果完全一樣嗎？** alert 一樣，alert 附帶的 flow 紀錄不一定。03-11 從 pipe 讀和讀檔案各跑一次，657 筆 alert 的時間、SID、5-tuple、packet 編號完全相同；但有 15 筆 alert 的 flow 欄位（`flow.start`、packet 數）不同，全部在 Syn 時段（14:30 左右），當時 Suricata 處在 flow emergency mode。所以 flood 讓 flow table 滿的時候，結果會受執行時序影響；Pi 的 CPU 比較慢，在 flood 的 pcap 上可能有少量差異，這也是**推論**，**沒有量**。
- **flood 會不會把 Suricata 塞爆、影響結果？** flood 時 Suricata 的 flow table 會滿：Debian 預設的 `flow.memcap` 是 128 MiB，IoT-23 43-1 (Mirai)（IoT-23 全部 28 個 pcap 只有這一個）、CIC-DDoS2019 兩天、CICIoT2023 的 DDoS-PSHACK_Flood、RSTFINFlood、TCP_Flood 跑的時候都進入過 flow emergency mode（提早回收 flow）；CICIoT2023 全部 309 個檔裡，有 56 個進入過（DDoS-TCP_Flood 16、PSHACK_Flood 15、RSTFINFlood 14、SYN_Flood 11 個檔）。把 `flow.memcap` 調到 4 GiB 重跑這幾個 pcap，就不再進入 emergency mode；結果幾乎一樣：03-11、PSHACK、TCP_Flood 每個 label 的數字不變，RSTFINFlood、43-1 (Mirai) 的 alert 是同樣的 5-tuple 和 rule、只差觸發時間，01-12 只有 DrDoS_SNMP 有 alert 的 flow 從 210 條變 207 條。4 GiB 重跑只做了最初那 3 個 CICIoT2023 檔，其他 53 個進入過 emergency mode 的檔**沒有量**。表上用的是預設設定（和 Pi 上一樣）的結果。DrDoS_SNMP 為什麼差 3 條，**沒有查**。（`tests/detection/memcap_check.sh`、`~/datasets/detection/memcap_test/`）
- **rule 都有載入嗎？** CICIoT2023 的 HOME_NET、EXTERNAL_NET 都設成 any 時，有 3 條 rule 的位址取反之後變成空集合，載入失敗（52,795／52,798 條）：`ET DNS DNS Lookup for localhost.DOMAIN.TLD`、`ET INFO Outbound Multiple Non-SMTP Server Emails`、`ET INFO Inbound Frequent Emails - Possible Spambot Inbound`；其他三個 dataset 52,798 條全部載入。

## 第 4 頁　偵測怎麼算

**怎麼讀**

- 上方三格是資料的流向：alert（eve.json 的輸出）→ 用 5-tuple + 時間對上 flow → flow 對回 label。
- 下表四列：
  - **有 alert 的 flow**：該 label 的 flow 裡，有任何 alert 的；分母是該 label 的 flow 數，只是逐條 flow 的比例，不代表認出攻擊。
  - **rule 對得上的 flow**：有 alert，而且觸發的 rule 描述的就是這種攻擊。rule 對得上的 flow 一定是有 alert 的 flow，但有 alert 的 flow 不一定 rule 對得上。
  - **判斷（每種攻擊）**：✓ 有 rule 對得上的 flow（偵測到）；△ 有 alert 但都對不上（原因不符）；✗ 沒有 alert（漏報）。三個符號互斥，一種攻擊只會是其中一個。
  - **誤報**：Benign flow 裡有 alert 的。
- 2×2 的說法：攻擊流量 × 有／沒有 alert 是 ✓／△（有 alert，看 rule 對不對得上）和 ✗（沒有 alert）；正常流量 × 有 alert 是誤報，正常流量沒有 alert 是正常、不另外算。
- 以實際輸出的 alert 為準：被 threshold 壓掉的不算，因為 gateway 實際上也只會收到輸出的 alert。
- 「rule 對得上」是看 rule 描述的內容，不是看名稱相同：例如 CIC-IDS2017 的 FTP-Patator 對的是 FTP 登入失敗回應的 rule（FTP brute force）。原則是 rule 要描述攻擊本身，四種情況不算對得上，一種情況算：
  - 只數 SYN 的 SSH scan rule（SID 2003068、2001219）：只看 SYN 封包（`flags:S`），不比對任何內容、也不需要連線建立，同一來源 120 秒內 5 個 SYN 就報，scan 或正常的頻繁連線也會觸發，描述的是 scan，不是暴力破解或連線嘗試（這兩條 rule 的 reference 雖然指向 brute force，比對條件只有 SYN）。所以 CIC-IDS2017 的 SSH-Patator 和 IoT-23 的 Attack 是 △；CICIoT2023 的 DictionaryBruteForce 只剩 LibSSH 的 rule（SID 2006546）5 條，仍是 ✓：這條 rule 要連線已建立、比對 client 送出的 `SSH-…libssh` banner，同一來源 30 秒內 5 次才報，描述的是用工具反覆登入（只數 SYN 的 SSH scan 有 103 條，不算）。IoT-23 的 PartOfAHorizontalPortScan 靠 SSH scan 仍是 ✓，因為 scan 本來就是它描述的。
  - 認的是協定使用的 rule：IRC 指令（NICK、USER、JOIN、PING／PONG、authorization）認的是有人在用 IRC，不是 C&C，所以 IoT-23 的 C&C 只算 Mirai checkin 與 Muhstik CnC，共 1,238 條，仍是 ✓；SNMP 的 `GPL SNMP public access`（SID 2101411）只比對送往 161 的 SNMP request 裡的 community 字串 `public`（classtype 是 attempted-recon，沒有速率條件），一般網管也會這樣用，在 CIC-DDoS2019 另外 4 項攻擊（03-11 的 Syn、01-12 的 DrDoS_NetBIOS、DrDoS_SSDP、DrDoS_UDP）也觸發，認的是有人在用 SNMP，不是 DDoS，所以 DrDoS_SNMP 是 △。
  - 只認得出工具的 rule：IoT-23 FileDownload 類的 `ET HUNTING curl User-Agent to Dotted Quad`（SID 2034567）只認得出有人用 curl，不是下載的 ELF 檔，和 IRC 同型，不算；FileDownload 類的 77 條 flow 每條都另有下載 ELF 的 rule，所以 FileDownload 類仍是 ✓。
  - 名稱寫 brute force 的 rule 不算 scan：`ET SCAN Rapid IMAP／IMAPS／POP3／POP3S Connections - Possible Brute Force Attack`（SID 2002992–2002995）名稱雖然以 ET SCAN 開頭，寫的卻是暴力破解，描述的不是 scan，所以 CIC-IDS2017 的 Portscan、Infiltration – Portscan 和 CICIoT2023 的 Recon 都不算這四條（CIC-IDS2017 Portscan 有 alert 的 185 條裡，有 10 條只有這四條 rule）。
  - 回應裡出現 `/etc/passwd` 內容的 rule（`ET ATTACK_RESPONSE`，SID 2002034、2025879）算：回應裡有 passwd 檔的內容，代表透過 web 漏洞執行命令成功。CICIoT2023 的 Uploading_Attack 和 Backdoor_Malware 觸發的是同一對 rule，連 server 都相同（192.168.137.236 與 192.168.137.11 的 80 port，回給攻擊主機 192.168.137.147），流量看不出差別；CommandInjection 對得上的是其中的 2002034，看到的也是注入命令的輸出。所以 CommandInjection、Backdoor_Malware、Uploading_Attack 三種一起算，都是 ✓。

**實驗怎麼做**

- alert 對 flow：同一個 5-tuple（雙向都算，ICMP 不看 port），alert 的 packet 時間落在 flow 的開始和結束之間就對上；落不進任何 flow 的，再看 Suricata 那條 flow 的起始時間和 label 的 flow 起始時間是否相差 1 毫秒以內（有些 alert 要等 flow timeout 才送出，時間會在最後一個 packet 之後）。
- 比對不用 packet 數，所以對齊失敗的 flow，它的 alert 一樣對得到。
- rule 對得上的判斷：每種攻擊的 SID 清單在 `tests/detection/results/related_rules.tsv`，每條有理由欄；`ET SCAN*` 的意思是 rule 名稱以 ET SCAN 開頭，但扣掉 IMAP／POP3「Possible Brute Force」的四條（SID 2002992–2002995，清單裡寫成 `ET SCAN* -2002992,2002993,2002994,2002995`）（CIC-IDS2017 的 Portscan、Infiltration – Portscan 和 CICIoT2023 的 Recon 用這個）。一個 label 的 flow 裡，至少有一筆 alert 的 SID 在清單裡，這條 flow 就算 rule 對得上。這份清單是依 rule 名稱與內容做的人工判斷，不是自動算出來的，目前還沒有逐條複查。算出來的結果在 `tests/detection/results/unified_by_label.tsv`（計算是 `tests/detection/related_flows.py`），四個 dataset 用同一個標準。
- rule 對得上的 SID 都在 `gw_corp` 裡（IoT-23 下載類的 HUNTING、INFO 的 SID 不在，但這些 flow 都同時有 `gw_corp` 的 SID 2019240），所以 rule 對得上的 flow，`full` 和 `gw_corp` 一樣。
- 對不上的筆數：CIC-IDS2017 5 天、CIC-DDoS2019 兩天都是 0 筆。IoT-23 的 23 個 scenario 有 138 筆對不上：49-1 (Mirai) 135 筆（`ET MALWARE Mirai Variant Checkin Response`）、52-1 (Mirai) 3 筆，都是 label 沒有涵蓋的 pcap 後段（49-1 (Mirai) 的 label 只涵蓋 pcap 的前 90%、52-1 (Mirai) 前 61%）；其他 21 個 scenario 都是 0 筆。CIC-DDoS2019 01-12 的 39,472 筆 alert 裡有 38,510 筆是攻擊者 172.16.0.5 → 192.168.50.1 的 `GPL ICMP PING`，對到的是 CSV 的 Protocol 0 flow：原版 CICFlowMeter 把 ICMP 記在 Protocol 0、port 0/0（見第 2 頁的補充）。
- CIC-DDoS2019 的比對多一個條件：非 TCP／UDP 的 alert（例如 ICMP）對到同一對 IP 的 Protocol 0 flow。IoT-23 與 CIC-IDS2017 不加這個條件。
- 同一筆 alert 落在兩條以上 flow（同 5-tuple、時間重疊）時，每條都算：IoT-23、CIC-IDS2017、CIC-DDoS2019 兩天都是 0 筆。03-11 的 CSV 有重複列（同一條 flow 出現兩次），每組只留一條再比對，所以同一筆 alert 不會算成兩條 flow 有 alert（見第 2 頁的補充）。
- CICIoT2023 的 label 是整個檔，不經過這一步：攻擊檔裡 Suricata 算出的每條 flow 都算該檔的攻擊，有 alert 的 flow 直接數 alert 的 `flow_id`（第 9 頁的補充）；判斷 ✓△✗ 用同一份 `related_rules.tsv`。

**被問到時**

- **threshold 的例子？** IoT-23 的 `ET SCAN Potential SSH Scan OUTBOUND`（SID 2003068）是 `type threshold, track by_src, count 5, seconds 120`：同一個來源 120 秒內，每累計 5 次符合條件的 SYN 才報 1 次。它數的是符合條件的 SYN 比對次數，不是 flow 數。如果一條 flow 只有一個 SYN，有 alert 的 flow 約 20%，但這不是上限：39-1 (IRCBot) 的 SSH scan 實際是 20.0%，3-1 (Muhstik) 的 SSH scan 是 31.1%，比 20% 高，為什麼，**沒有查**。CIC 兩個 dataset 的 SSH scan（SID 2001219）是 `type both`：累積 5 次報 1 次，之後 120 秒內不再報（第 7 頁的補充）。Heartbleed 的 rule 120 秒內只報 1 次，11 條攻擊 flow 只有 1 條有 alert。
- **「有 alert」就是認出這個攻擊嗎？** 不一定，所以才分 ✓ 和 △。例如 CIC-DDoS2019 的攻擊 flow 有 alert，是因為攻擊主機一直在 ping 受害主機，或有背景的 SSH 連線、零星連資料庫 port，DrDoS_SNMP 則是 SNMP request 裡的 `public`（見第 7 頁），這些是 △（原因不符）。CIC-IDS2017 的 SSH-Patator 也是：31 條有 alert 的 flow 都是只數 SYN 的 SSH scan。表格把觸發的 rule 寫出來，讓人判斷是不是跟攻擊有關。
- **為什麼不按 flow 一條一條送？** 判斷單位是 flow，但送進去的是整個 pcap、順序不變，因為很多 rule 要看好幾條 flow 才觸發（例如 SSH scan 要同一來源 5 個 SYN），真實的 gateway 看到的流量也是交錯的；送完再用 label 對回 flow。
- **這是不是 detection rate？** 不是。有 alert 的 flow 比例只是逐條 flow 的比例，不代表認出攻擊（alert 可能和攻擊無關）；rule 對得上的 flow 比例也是逐條 flow 的比例，受量影響。「這種攻擊有沒有被偵測到」看每種攻擊的判斷，✓ 才是偵測到。
- **rule 對得上是誰判斷的？** 依 rule 名稱與內容判斷，清單和理由都在 `related_rules.tsv`，不是自動算出來的，也還沒有逐條複查；清單改了，✓ 的個數就可能變，所以數字要連同清單一起看。判斷的原則是 rule 要描述攻擊本身，不算的四種情況（只數 SYN 的 SSH scan、協定的使用、只認得出工具、名稱寫 brute force）和算 `/etc/passwd` 的理由見上面「怎麼讀」。
- **為什麼分成四種結果、不只算一個比例？** 只看有 alert 的比例，分不出「認出攻擊」和「只是碰巧有 alert」：例如 CIC-DDoS2019 19 項都有 alert，但只有 2 項 ✓；IoT-23 的 DDoS 沒有 alert，是漏報。四種結果把「沒有 alert」和「有 alert 但 rule 對不上」分開。

## 第 5 頁　IoT-23

**逐列說明**（當場不講，被問到某一列或時間夠時用）

- 這一頁是 IoT-23 全部 23 個有 label 的 scenario，用完整的 pcap、`full` 這個 rule set，只列 malicious 的 label。

- 表上依序是 ✓、△、✗。數量最大的三種是 PartOfAHorizontalPortScan、Okiru、DDoS，占 malicious flow 的 99.98%。
- ✓ 有三列。PartOfAHorizontalPortScan 靠 39-1 (IRCBot)、3-1 (Muhstik) 的 SSH scan，scan 本來就是它描述的；其他 port 的 SYN scan 沒有對得上的 rule，只有 17 條 IP 清單的 alert。C&C 21,995 條裡有 1,238 條 rule 對得上，是 C&C checkin：49-1 (Mirai) 的 Mirai checkin 和 3-1 (Muhstik) 的 Muhstik CnC；IRC 指令的 rule 認的是有人在用 IRC，不是 C&C，所以不算。FileDownload 類 82 條裡有 77 條 rule 對得上，是 ELF 下載。
- △ 有兩列。Okiru 6,099 萬條只有 34 條有 alert，而且都是 IP 清單的 rule（只比對對方 IP 在不在 TOR、Spamhaus DROP 這類清單上，不在 `gw_corp`），不是認出 Okiru。Attack 9,398 條裡有 1,389 條有 alert，其中 1,385 條是 SSH scan，只數送往 22 的 SYN，描述的是 scan，不是這些連線嘗試，所以也是 △。
- ✗ 是 DDoS 等 8 種，合計 1,957 萬條完全沒有 alert，其中 60-1 (Gafgyt) 22 GB 的 DDoS 一筆 alert 都沒有。
- Benign 3,086 萬條裡有 2,837 條有 alert，是誤報，細節在第 9 頁。

**怎麼讀**

- 每列一個 malicious label 或一組 label，flows 是 23 個有 label 的 scenario 加總；欄位定義見第 4 頁。「有 alert 的 flow」是該 label 的 flow 裡有任何 alert 的；「rule 對得上的 flow」是其中觸發的 rule 描述的就是這種攻擊的；「判斷」是 ✓（偵測到）、△（原因不符）、✗（漏報），三個符號互斥，定義在第 4 頁。
- 「觸發的 rule」是 ET Open 的 rule 名稱（縮寫）：✓ 列寫對得上的 rule，△ 列寫實際觸發的 rule，✗ 列寫「—」。
- FileDownload 類是三種 label 合計（flows／有 alert 的 flow／rule 對得上的 flow）：`C&C-FileDownload` 53／50／50、`FileDownload` 18／16／16、`C&C-HeartBeat-FileDownload` 11／11／11，合計 82／77／77；有這三種 label 的 scenario 是 35-1 (Mirai)、42-1 (Trojan)、43-1 (Mirai)、44-1 (Mirai)、48-1 (Mirai)、49-1 (Mirai)、52-1 (Mirai)，7 個都有 alert。
- DDoS 等 8 種是 `DDoS` 19,538,713、`C&C-HeartBeat` 33,673、`C&C-PartOfAHorizontalPortScan` 888、`C&C-HeartBeat-Attack` 834、`C&C-Torii` 30、`PartOfAHorizontalPortScan-Attack` 5、`Okiru-Attack` 3、`C&C-Mirai` 2，合計 19,574,148 條，有 alert 都是 0，所以都是 ✗。其中最後六種（888、834、30、5、3、2）合計 1,762 條，分布在 48-1 (Mirai)、20-1 (Torii)、21-1 (Torii)、17-1 (Kenjiro)、36-1 (Okiru)、52-1 (Mirai) 六個 scenario。
- Benign 列：Benign 30,860,691 條（`Benign` 30,858,735 條、label 寫成小寫 `benign` 的 1,956 條），有 alert 2,837 條（2,834 加 3）；Benign 沒有要對的攻擊，所以「rule 對得上的 flow」和「判斷」寫「—」，「觸發的 rule」寫誤報主要的 rule（flow 數前三名：SSH scan、IRC、BitTorrent）。各 rule 的條數、為什麼不直接叫 false positive rate，見第 9 頁的補充。
- 表下的總結：malicious 合計 294,449,255 條，有 alert 14,762,773 條（5.01%），rule 對得上 14,758,406 條（5.01%）；`gw_corp` 的有 alert 14,762,716 條。15 種是 ✓ 5、△ 2、✗ 8：
  - ✓ 5 種：PartOfAHorizontalPortScan（SSH scan rule）、C&C（Mirai、Muhstik 的 C&C checkin）、C&C-FileDownload、C&C-HeartBeat-FileDownload、FileDownload（ELF 下載）。
  - △ 2 種：Okiru（34 條 flow 只有 IP 清單的 alert，和 Okiru 的內容無關，rule 對不上）、Attack（1,389 條有 alert：只數 SYN 的 SSH scan 1,385 條、IP 清單 3 條、VPNFilter 與 Mirai 的 User-Agent rule 同 1 條 flow，rule 都對不上）。
  - ✗ 8 種：上面「DDoS 等 8 種」。
- 有 alert 的 14,762,773 條裡，14,711,802 條來自 39-1 (IRCBot) 的 SSH scan、45,289 條來自 3-1 (Muhstik) 的 SSH scan。沒有任何 alert 的 malicious flow 占 94.99%。
- 「有 alert 的 flow」和「rule 對得上的 flow」差在哪：
  - PartOfAHorizontalPortScan 14,757,108 對 14,757,091，少的 17 條只有 IP 清單的 alert。
  - C&C 4,165 對 1,238：rule 對得上的 1,238 條是 3-1 (Muhstik) 6（Muhstik CnC）、49-1 (Mirai) 1,232（Mirai checkin）；對不上的 2,927 條是 IRC 指令的 rule（34-1 (Mirai) 1,767、39-1 (IRCBot) 1,156，認的是有人在用 IRC，不是 C&C），加上 43-1 (Mirai) 的 2 條（`ET HUNTING` 的 .arm 下載、curl User-Agent）和 52-1 (Mirai) 的 2 條（ELF 下載、curl User-Agent）是下載類的 rule，對不上 C&C。
  - Attack 1,389 對 0：SSH scan 1,385 條（3-1 (Muhstik) 1,264、39-1 (IRCBot) 121，只數 SYN，不算）、IP 清單 3 條（48-1 (Mirai)）、VPNFilter 與 Mirai 的 User-Agent rule 1 條 flow（17-1 (Kenjiro)），rule 都對不上，所以是 △。
- 各 label 有 alert 的 scenario 數（有 alert 的 scenario ÷ 有這個 label 的 scenario，不論 rule 對不對得上）：PartOfAHorizontalPortScan 4／11、Okiru 2／5、DDoS 0／7、C&C-HeartBeat 0／5、C&C 6／10、Attack 4／5、FileDownload 類 7／7、其他 6 種 0／6。例如 PartOfAHorizontalPortScan 的 4／11，是 11 個 scenario 有這個 label，其中 4 個有 alert：39-1 (IRCBot)、3-1 (Muhstik) 是 SSH scan 的 rule；1-1 (Hide and Seek)（11 條）、52-1 (Mirai)（6 條）只有 Spamhaus DROP 的 IP 清單 rule。
- 分成兩組看：第 2 頁補充裡的 11 個 usable scenario，和其餘 12 個。其餘 12 個 scenario 有 malicious flow 28,946,099 條、有 alert 49,601 條，主要是 3-1 (Muhstik) 的 SSH scan 46,553 條、34-1 (Mirai) 的 IRC 1,767 條、49-1 (Mirai) 的 1,245 條（Mirai checkin 1,232、ELF 下載 13）。兩組的結論一樣：比例幾乎都來自 SSH scan。
- 觸發的 rule 看的東西不一樣：
  - SSH scan 的 rule **只看 header**：送往 22 port 的 SYN，同一個來源 120 秒內每累計 5 次符合的 SYN 報 1 次（數的是 SYN 的比對次數，不是 flow 數）。它是「計數型」的 rule，不看內容，描述的是 scan：PartOfAHorizontalPortScan 算對得上，Attack 不算。ET Open 只有少數 port（SSH、VNC、資料庫等）有只看 header 的 scan rule；資料庫 port 的 rule 不是計數型，是外部送往該 port 的每個 SYN 都報，同一來源每分鐘最多 5 筆。
  - C&C checkin 是 `ET MALWARE` 的 rule，比對的是 C&C 通訊的內容：3-1 (Muhstik) 的 `ET MALWARE ELF/Muhstik`、49-1 (Mirai) 的 `ET MALWARE Mirai Variant Checkin Response`。
  - ELF 看的是下載檔案開頭的 ELF magic，payload 有特徵。IRC 的 rule 看的是 NICK、USER 這些指令字串，認的是有人在用 IRC，不是 C&C，所以不算對得上。`ET HUNTING` 的 curl User-Agent（SID 2034567）只認得出下載工具，不是下載的 ELF 檔，也不算。
  - 只有 IP 清單的 alert：對方 IP 在 Spamhaus DROP 清單上，不是認出 scan 或 Okiru，這些 flow 都對不上；PartOfAHorizontalPortScan 有 17 條、Okiru 有 34 條、Attack 有 3 條是這種。PartOfAHorizontalPortScan 另有 SSH scan 對得上，所以仍是 ✓；Okiru 只有這種 alert，所以是 △；Attack 的 alert 是只數 SYN 的 SSH scan 與這種 IP 清單，都對不上，也是 △。
- 沒有 alert 的流量：PartOfAHorizontalPortScan 的 SYN scan（Telnet 23／2323、52869、80 等）、Okiru 的 37215、DDoS、C&C-HeartBeat 和 C&C-Torii，除了少數 IP 清單之外沒有 alert。SYN scan 沒有完成 handshake、沒有 payload，也沒有對應的 scan rule；Okiru 的 37215 也是只有 SYN；DDoS 大多是 TCP SYN flood；C&C-HeartBeat 的 33,673 條、C&C-Torii 的 30 條也是 0。
- Okiru、Attack 要和 ✗ 一起看：Okiru 有 34 條 flow 只有 IP 清單的 alert，Attack 有 1,389 條 flow 有 alert（只數 SYN 的 SSH scan、IP 清單等），rule 都對不上，所以這兩種攻擊是 △，不算進偵測總表（第 9 頁）的 5／15；Okiru 其餘 6,099 萬條 flow 大多是對 37215 的 SYN probe，沒有 alert。✗ 那一列是整種攻擊都沒有 alert 的 8 種（DDoS 等）。

**實驗怎麼做**

- 全部 23 個有 label 的 scenario、完整的 pcap、rule set 是 `full`；alert 對 flow 的方法見第 4 頁。Somfy-02～06 沒有 label，Suricata 也跑過，都是 0 筆 alert。
- 和 10/19 的關係：10/19 只跑每個 scenario 前 20 萬個 packet、Suricata 7.0.10；這次跑完整的 pcap、Suricata 8.0.7，alert 數不能直接比。
- 49-1 (Mirai)、52-1 (Mirai) 的 label 只涵蓋 pcap 的前 90%、61%，之後的 alert 沒有 label 可對（49-1 (Mirai) 135 筆、52-1 (Mirai) 3 筆，見第 4 頁），不算進表。
- 數字來自 `tests/detection/results/unified_by_label.tsv` 的 iot23 列（rule 對得上的 flow 依 `related_rules.tsv` 的 SID 清單算，見第 4 頁），和 alert 的 SID 統計（`iot23_sids.tsv`、`iot23_by_scenario.tsv`）；目的 port 來自 10/19 的 `tests/iot23/ports_summary.txt`。C&C 的 1,238 條是精確值，不用重跑比對：49-1 (Mirai) 只有 Mirai checkin 一條 SID；3-1 (Muhstik) 的 6 條 flow 每條都有 Muhstik 的兩條 SID（非標準 port 的 IRC JOIN 落在其中 5 條，不算），所以 6 條全部對得上。
- `gw_corp`／`gw_corp` + IP 清單的數字：PortScan 14,757,091／14,757,108；Okiru 0／34；C&C 4,162／4,162；Attack 1,386／1,389；FileDownload 類 77／77。`gw_corp` 和 `full` 幾乎一樣，差別在 IP 清單（Okiru 的 34 條要加上 IP 清單才有）。
- SSH scan：SID 2003068（`ET SCAN Potential SSH Scan OUTBOUND`），PortScan 14,757,091 條（39-1 (IRCBot) 14,711,802、3-1 (Muhstik) 45,289）算 rule 對得上；Attack 也有 1,385 條（3-1 (Muhstik) 1,264、39-1 (IRCBot) 121）觸發同一條 rule，但這條 rule 只數 SYN、描述的是 scan，Attack 不算。rule 內容：`alert tcp $HOME_NET any -> $EXTERNAL_NET 22 (… flags:S,12; threshold: type threshold, track by_src, count 5, seconds 120; …)`；`type threshold` 是同一個來源 120 秒內每累計 5 次符合條件的 SYN 報 1 次，數的是比對次數，不是 flow 數。
- IRC（不算 rule 對得上，認的是有人在用 IRC，不是 C&C）：SID 2002024（NICK）、2002023（USER）、2002025（JOIN）、2002027（PING）、2002028（PONG）、2000355（authorization，34-1 (Mirai) 1,590 條）、2000348（非標準 port 的 IRC JOIN，3-1 (Muhstik) 5 條）。39-1 (IRCBot) 的 C&C 是 914、876、847、847、847 條 flow；34-1 (Mirai) 的 C&C 有 2002023、2002024 各 1,641 條、2002027、2002028 各 978 條。
- C&C checkin：SID 2034743（`ET MALWARE ELF/Muhstik Botnet CnC Activity`）與 2029319（`ET MALWARE ELF/Muhstik - IRC CnC Checkin`）各 6 條（3-1 (Muhstik)）；SID 2027366（`ET MALWARE Mirai Variant Checkin Response`）1,232 條（49-1 (Mirai)）。三條 rule 都在 `gw_corp`。Muhstik 的兩條 rule 落在同樣的 6 條 flow，所以 C&C rule 對得上的是 6 + 1,232 = 1,238 條。
- ELF：SID 2019240（`ET INFO Executable and linking format (ELF) file download Over HTTP`），C&C-FileDownload 50、C&C-HeartBeat-FileDownload 11、FileDownload 16，共 77 條 flow、7 個 scenario。這條 rule 在 `gw_corp` 裡（10/19 挑 rule 時因為 flowbits 相依被補進來）。`ET HUNTING curl User-Agent to Dotted Quad`（SID 2034567）只認得出下載工具，和 IRC 同型，不算 rule 對得上；這 77 條 flow 每條都另有下載 ELF 的 rule，所以 77 條不受影響。
- IP 清單：SID 2400047 等（`ET DROP Spamhaus DROP Listed Traffic Inbound`）。

**被問到時**

- **「FileDownload 類（3 種）」包含哪些、差在哪？** FileDownload 18 條、C&C-FileDownload 53 條、C&C-HeartBeat-FileDownload 11 條。IoT-23 的 FileDownload 是「有檔案下載到被感染的設備」；名稱前面加 C&C 表示下載來自 C&C server，再加 HeartBeat 表示同一條連線也有 C&C server 用來追蹤被感染設備的心跳。三種觸發的都是 ELF 下載的 rule，判斷都是 ✓，所以放在同一列。
- **「DDoS 等 8 種」包含哪些、差在哪？** 共同點只有完全沒有 alert（✗），行為各不相同：DDoS 19,538,713 條（被感染設備對同一個 IP 送大量 flow，60-1 (Gafgyt) 的 22 GB 就是這種）、C&C-HeartBeat 33,673 條（C&C server 追蹤被感染設備的定期小連線）、C&C-PartOfAHorizontalPortScan 888 條、C&C-HeartBeat-Attack 834 條、C&C-Torii 30 條（Torii botnet 的 C&C）、PartOfAHorizontalPortScan-Attack 5 條、Okiru-Attack 3 條、C&C-Mirai 2 條。用「-」連起來的 label 看起來是同一條 flow 同時符合兩種行為；IoT-23 官方頁面沒有寫組合 label 的規則，這是**推論**。
- **IoT-23 的 label 各是什麼意思？**（官方定義，stratosphereips.org 的 IoT-23 頁面）Attack：被感染設備攻擊其他主機（例如暴力破解登入、在 request 裡注入命令）；C&C：被感染設備連到 C&C server，判斷依據是定期連線、從那台 server 下載執行檔，或有 IRC 類、解得開的指令來回；DDoS：被感染設備在做 DDoS；FileDownload：有檔案下載到被感染設備；HeartBeat：C&C server 用來追蹤被感染設備的連線；Mirai、Okiru、Torii：連線特徵符合該 botnet；PartOfAHorizontalPortScan：同一個 port、不同目的 IP 的大量連線，是在掃描，為之後的攻擊收集資訊。
- **數量最大的三種是什麼情況？** 三種（PortScan、Okiru、DDoS）占 malicious flow 的 99.98%（合計 294,382,345 條 ÷ 294,449,255 條）。
  - PortScan 的有 alert 的 flow 6.9%，幾乎全部來自 SSH scan（port 22）：39-1 (IRCBot) 7,356 萬條，有 alert 的實際是 20.0%，threshold 是第 4 頁講的每累計 5 次符合的 SYN 才報 1 次；3-1 (Muhstik) 14.6 萬條，有 alert 的 45,289 條（31.1%）。另外兩個有 alert 的 scenario 是 1-1 (Hide and Seek)（11 條）和 52-1 (Mirai)（6 條），都是 Spamhaus DROP 的 IP 清單 rule（對方 IP 在清單上；1-1 (Hide and Seek) 是回應 23、9527、8080 的 packet），不是認出 scan。
  - 其他 port 的 SYN scan，除了這幾條 IP 清單之外沒有 alert：Telnet（23／2323）、52869（10/19 做過 port 統計的 scenario 裡量最大，約 5,150 萬條）、80、8080、8081、81、9527。
  - Okiru 的 34 條也全部是 IP 清單 rule（7-1 (Linux.Mirai)、36-1 (Okiru)，回應 37215 的 packet）。Okiru label 大多是對 37215 port 的 SYN（Huawei HG532 的漏洞 CVE-2017-17215）：只有 SYN、沒有完成 handshake、沒有 payload，而且 ET Open（2026-10-30 快照，含停用的 rule）裡沒有 CVE-2017-17215 的 rule。
  - DDoS 7 個 scenario 都是 0。IoT-23 的 DDoS 大多是 TCP：17-1 (Kenjiro) 1,366 萬條送往 tcp/52869 的 SYN、35-1 (Mirai) 送往 tcp/80 與 tcp/992；43-1 (Mirai) 的 65,803 條是 UDP（udp/27015）。60-1 (Gafgyt) 有 358 萬條（pcap 22 GB）、34-1 (Mirai) 14,394 條、7-1 (Linux.Mirai) 39,584 條、44-1 (Mirai) 1 條，這四個的目的 port **沒有查**。
- **C&C 的 4,165 條有 alert、1,238 條 rule 對得上，是哪裡來的？** C&C 共 21,995 條（有 alert 的 18.9%）：49-1 (Mirai) 的 `ET MALWARE Mirai Variant Checkin Response` 1,232 條（1,922 條中）、3-1 (Muhstik) 的 `ET MALWARE ELF/Muhstik` 6 條（8 條中），這兩個加起來是 rule 對得上的 1,238 條（5.6%）；對不上的有 alert：34-1 (Mirai) 的 IRC 1,767 條（6,706 條中）、39-1 (IRCBot) 的 IRC 1,156 條（1,530 條中，75.6%），另外 43-1 (Mirai)、52-1 (Mirai) 各 2 條（HUNTING 或 ELF 下載的 rule；HUNTING 不在 `gw_corp`），是下載類的 rule，對不上 C&C。C&C-HeartBeat 的 33,673 條是 0。
- **Attack 的 1,389 條有 alert，為什麼是 △？** 3-1 (Muhstik) 的 SSH scan 1,264 條、39-1 (IRCBot) 的 SSH scan 121 條（共 1,385 條）、48-1 (Mirai) 的 IP 清單 3 條、17-1 (Kenjiro) 1 條（`ET USER_AGENTS VPNFilter Related UA (Hakai/2.0)` 和 `ET MALWARE Mirai Variant User-Agent (Outbound)` 在同一條 flow）。SSH scan 只數同一來源送往 22 的 SYN，描述的是 scan，不是這些連線嘗試本身；IP 清單和 User-Agent 的 rule 也對不上，所以 rule 對得上是 0 條，是 △。
- **C&C 為什麼不算 IRC 的 rule？** IRC 的 NICK、USER、JOIN、PING／PONG、authorization 這些 rule 比對的是 IRC 協定本身，認的是有人在用 IRC，不是 C&C 專屬；同一批 rule 也落在 42-1 (Trojan) 的 Benign 上（IRC 換 nick，比較像 label 標錯）。所以 34-1 (Mirai) 的 1,767 條、39-1 (IRCBot) 的 1,156 條 IRC 的 alert 都對不上 C&C。IoT-23 標 C&C 時，把 IRC 類的指令當成判斷依據之一，所以這些 flow 標成 C&C 沒錯；但 gateway 收到 IRC 的 alert 只知道有人在用 IRC，不知道是不是 C&C，照「rule 要描述攻擊本身」不算。C&C 只算 C&C 專屬的 rule：Mirai checkin（49-1 (Mirai) 1,232 條）與 Muhstik CnC（3-1 (Muhstik) 6 條），共 1,238 條，C&C 仍是 ✓。
- **PartOfAHorizontalPortScan 和 Attack 都靠 SSH scan，為什麼一個 ✓、一個 △？** rule 要描述的是這種攻擊本身。PartOfAHorizontalPortScan 這個 label 描述的就是掃描，SSH scan rule 數的是同一來源送往 22 的 SYN，描述的也是 scan，所以對得上；Attack 要對的是攻擊（連線嘗試）本身，只數 SYN 的 scan rule 不看登入或密碼，描述的不是它，所以不算。
- **Okiru 為什麼是 △、不是 ✗？** 34 條 flow 有 alert（IP 清單的 rule），所以不是沒有 alert；但這些 rule 比對的是對方 IP 在不在清單上，和 Okiru 的內容無關，所以 rule 對不上，是 △。
- **有 payload 的 label 對齊不是很差嗎？** 10/19 提過，帶 payload 的 label，flow alignment 比較低（例如 39-1 (IRCBot) 的 C&C 44.6%、42-1 (Trojan) 的 FileDownload 0／6），因為 Zeek 記的 packet 數和 pcap 對不上。這次 alert 對 flow 只用 5-tuple 加時間，不用 packet 數，所以不受影響。

- **Telnet scan 為什麼沒有 rule？** ET Open 的 SCAN category（2026-10-30 快照共 286 條）有 SSH、VNC、資料庫 port 等的 scan rule，但沒有 Telnet 23／2323、52869、8081、37215 的。整份快照提到 37215 的只有 SID 2025132，而且 37215 只出現在 reference 網址，rule 本身比對的是 52869 port 的 Realtek CVE-2014-8361。

- 這個 dataset 的 label 是整個檔：官方把每次攻擊錄到的流量整段標成那種攻擊，一個檔一種攻擊，檔裡每條 flow 都算那種攻擊，第 9 頁的 flow 比例就是這樣算的。
- 所以攻擊檔裡實驗網路的背景流量也算在攻擊上，背景流量的 alert 也落在攻擊流量上：這一頁每種攻擊都有 alert，沒有漏報。
- malicious flow 9.32 億條，有 alert 的 0.004%，rule 對得上的 0.0002%；33 種攻擊裡，偵測到（✓）11 種、原因不符（△）22 種、漏報（✗）0 種。
- ✓ 的 11 種是 Web 攻擊 6 種、暴力破解 1 種、Recon 4 種，rule 對得上，像 BeEF、SQLi、`/etc/passwd`、LibSSH 的 brute force、Nmap。
- Web 攻擊裡的 Uploading_Attack，16 條有 alert 的 flow 有 2 條觸發 `/etc/passwd` 的 rule，和 Backdoor_Malware 是同一對 rule，連 server 都相同，流量看不出差別；回應裡出現 /etc/passwd 的內容，代表透過 web 漏洞執行命令成功，所以 CommandInjection、Backdoor_Malware、Uploading_Attack 三種一起算。
- △ 的 22 種有 alert，但 rule 都對不上這種攻擊，是 Recon-PingSweep、DDoS、DoS、Mirai 的各種 flood 和 Spoofing：alert 是背景流量的 UPnP、ping，rule 對不上這種攻擊；HTTP flood 只有 User-Agent 異常類的 rule（大多是 HUNTING），Mirai 的 GRE flood 有 1,027 條 HUNTING 的 port 53 大封包 rule 落在 flood 本身，也都對不上。
- 說這些 alert 是背景，是以 4 個 Benign 檔為基準：Benign 檔也出現的 rule 就是背景。這是一種啟發式，同一個 SID 也可能同時落在攻擊流量上，所以 △ 的意思是「有 alert，但沒有找到 rule 對得上的」。
- Benign 4 個檔 34.6 萬條 flow 裡有 5,157 條有 alert，是誤報，細節在第 9 頁。

**怎麼讀**

- 每列是一種攻擊或一類攻擊（括號是這一類的攻擊種類數，309 個檔全部判斷），flows 是 Suricata 算出的 flow 數（官方沒有逐條的 label 檔，見第 2 頁的補充）；欄位定義見第 4 頁。「有 alert 的 flow」是 Suricata 的 flow 裡有 alert 的（數 alert 的不重複 `flow_id`）；「rule 對得上的 flow」是其中 alert 的 SID 在 `related_rules.tsv` 該種攻擊的清單裡的；「判斷」是 ✓（偵測到）、△（原因不符）、✗（漏報），三個符號互斥，定義在第 4 頁。
- ✓ 的列（flows／有 alert 的 flow／rule 對得上的 flow）：
  - Web-based（6 種）合計 20,069／410／115：Backdoor_Malware 2,642／51／4、BrowserHijacking 2,951／65／16、CommandInjection 3,971／81／3、SqlInjection 5,736／133／88、Uploading_Attack 1,339／16／2、XSS 3,430／64／2。
  - Brute Force（DictionaryBruteForce）7,313／248／5：只算 LibSSH 的 rule（SID 2006546）5 條；只數 SYN 的 SSH scan（SID 2003068、2001219）有 103 條 flow，不算。
  - Recon（4 種）合計 1,476,827／6,822／1,847：HostDiscovery 673,022／1,472／399、OSScan 190,789／1,124／614、PortScan 218,276／1,103／638、VulnerabilityScan 394,740／3,123／196。
- △ 的列：Recon-PingSweep 1,829／11／0；DDoS（12 種）746,342,689／17,701／0；DoS（4 種）14,198,947／6,515／0；Mirai（3 種）169,315,173／4,935／0；Spoofing（2 種）160,726／1,958／0。各類觸發最多的都是背景的 `GPL MISC UPnP malformed advertisement` 與 `GPL ICMP PING`（有這兩條 rule 的 flow 數，UPnP／ICMP PING；ICMP PING 是 `*NIX` 那條，`BSDtype` 的 flow 數幾乎一樣）：DDoS 11,314／3,295、DoS 3,725／1,262、Mirai 2,069／1,117、Spoofing 1,124／513、PingSweep 6／5。另外 HTTP flood 有 HUNTING 的 User-Agent rule，Mirai 的 GRE flood 有 `ET HUNTING Large non-DNS Packet on Port 53`（1,027 條），udpplain 有 Edonkey（見下面的 △ 說明）。
- Benign 列：4 個 Benign 檔（`BenignTraffic`、`BenignTraffic1`–`3`）Suricata 算出的 flow 345,984 條，有 alert 5,157 條（誤報 1.49%；`gw_corp` 3,676 條）；Benign 沒有要對的攻擊，所以「rule 對得上的 flow」和「判斷」寫「—」，「觸發的 rule」寫誤報主要的 rule（UPnP、ICMP PING）。細節見第 9 頁的補充。
- 表下的總結：malicious flow 931,523,573 條（305 個攻擊檔的 Suricata flow 合計，照官方 label 含背景流量），有 alert 38,600 條（0.0041%）、rule 對得上 1,967 條（0.000211%）；33 種攻擊是 ✓ 11（6 + 1 + 4）、△ 22（Recon-PingSweep 1 + DDoS 12 + DoS 4 + Mirai 3 + Spoofing 2）、✗ 0。
- label 是整個檔（官方：整段擷取都算該攻擊，含背景流量），所以背景流量的 flow 與 alert 也算在攻擊裡。
- 判斷依據：
  - ✓ = 攻擊流量上有 alert，而且觸發的 rule 描述的就是這種攻擊：SID 在 `related_rules.tsv` 該種攻擊的清單裡（都在 `gw_corp` 裡）。
  - △ = 攻擊流量上有 alert，但觸發的 rule 都對不上這種攻擊：背景流量的 rule（UPnP、ICMP PING 等）、HUNTING 類（不在 `gw_corp`）、或和這種攻擊無關的 rule。
  - ✗ = 攻擊流量上完全沒有 alert：這個 dataset 沒有。照官方 label，整個檔的 flow 都算攻擊，背景的 alert 也落在攻擊流量上，所以每種攻擊都至少有背景的 alert。
- 「以 Benign 檔出現過的 SID 為背景」是一種啟發式：Benign 檔也會觸發的 rule 當成背景，同一個 SID 也可能同時落在攻擊流量上（背景流量和攻擊流量都觸發同一條 rule）。它用來說明 △ 的 alert 是背景、不是這種攻擊造成的，不用來判斷 ✓；✓ 由 `related_rules.tsv` 的 SID 判斷。
- rule 對得上的 flow 都有攻擊主機參與（11 種都查過），`ET SCAN*` 這種比較寬的規則也沒有把背景流量算進去。
- 只看 Benign 檔沒出現過的 rule 時，33 種分成三群：有相關 alert 的 11 種、有 Benign 沒有的 rule 但對不上的 6 種、找不到 Benign 以外相關 alert 的 16 種。第一群的 11 種，rule 描述的就是該攻擊，都是 ✓。第二、三群的 22 種在第 4 頁的定義下都有 alert（背景的，或 rule 對不上的），是 △，所以 △ 共 22 種。第二群的 6 種：
  - DDoS-HTTP_Flood、DoS-HTTP_Flood：User-Agent 異常類的 rule，大多是 HUNTING（`ET HUNTING Chrome/0 in User-Agent`；DoS 兩個檔另有 `ET WEB_SERVER Fake Googlebot UA 2 Inbound` 合計 3 條）。
  - Mirai-udpplain：`ET P2P Edonkey Search Request`，25 個檔裡有 11 個檔、14 條，落在 flood 的 flow 上，和 udpplain 無關。
  - DDoS-SlowLoris：`ET WEB_SPECIFIC_APPS WordPress posts-layout`，和 Slowloris 無關。
  - Mirai-greeth_flood、Mirai-greip_flood：`ET HUNTING Large non-DNS Packet on Port 53`，greeth 541 條、greip 486 條。
- 第三群的 16 種（沒有找到 Benign 以外的相關 alert，不是保證攻擊流量上一定沒有）：DDoS 的 ACK_Fragmentation、ICMP_Flood、ICMP_Fragmentation、PSHACK_Flood、RSTFINFlood、SYN_Flood、SynonymousIP_Flood、TCP_Flood、UDP_Flood、UDP_Fragmentation；DoS 的 SYN_Flood、TCP_Flood、UDP_Flood；Recon-PingSweep；DNS_Spoofing；MITM-ArpSpoofing。它們的 alert 都來自實驗網路的背景流量（Benign 檔也有的 rule，或 DNS 查 .cc／.to、External IP Lookup、STUN、TLS handshake failure、403 Forbidden、路由器的 `ET HUNTING Double User-Agent` 等），或完全沒有 Benign 以外的 rule；在統一定義下這 16 種都是 △。
- ✓ 的例子：BrowserHijacking 觸發 5 條 BeEF rule（`ET WEB_CLIENT The Browser Exploitation Framework (BeEF)`）；SqlInjection 觸發 SQLi 與 Sqlmap 的 rule；Backdoor_Malware、CommandInjection、Uploading_Attack 觸發 `ET ATTACK_RESPONSE Possible /etc/passwd via HTTP`（CommandInjection 看到的是注入命令的輸出，Backdoor_Malware 另有 webshell 的 PHP POST，Uploading_Attack 是上傳的檔案執行命令後的輸出）；DictionaryBruteForce 觸發 `ET SCAN LibSSH Based Frequent SSH Connections Likely BruteForce Attack`（5 條 flow；只數 SYN 的 SSH scan 另有 103 條 flow，不算）；Recon-OSScan 觸發 `ET SCAN NMAP OS Detection Probe`；VulnerabilityScan 觸發 `ET SCAN Nmap Scripting Engine User-Agent`。

**實驗怎麼做**

- 309 個檔全部跑完，檔案與取得方式見第 2 頁的補充（官方 309 個檔、587.3 GB）。Benign 基準是 4 個 Benign 檔裡出現過的 10 個 SID。
- 多檔的 flood（每種 8–29 個檔），其他檔多出來的 rule 都是背景流量（403 Forbidden、Go HTTP client User-Agent、.cc TLD 的 DNS 查詢、External IP Lookup、TLS Handshake Failure、STUN、Jabber），在 ICMP、UDP、TCP 這些不相干的 flood 檔都出現，所以判斷不變。
- Mirai 的 GRE flood（greeth、greip）多了 `GPL SNMP trap Format String`（SID 2100227，在 `gw_corp`）和 `ET TFTP Outbound TFTP ACK`（SID 2008118）：alert 落在 GRE 封裝的內層 packet 上，內層的 IP 是隨機的，是 flood 的亂數內容碰巧對上打到 162、69 port 的 rule，和 Mirai 無關，所以 rule 對不上，是 △。
- HOME_NET 與 EXTERNAL_NET 都設成 any（見第 3 頁的補充）。
- 判斷：✓ 的 SID 清單在 `tests/detection/results/related_rules.tsv`（每種攻擊一列、每條有理由欄）；數字在 `tests/detection/results/unified_by_label.tsv` 的 ciciot2023 列。這個判斷是依 rule 名稱與內容做的，不是自動算出來的。`tests/detection/results/ciciot2023_judgement.tsv` 記的是只看 Benign 檔沒出現過的 rule 時每種攻擊的 alert 與理由，它的判斷欄是上面的三群，不是第 4 頁的 ✓△✗（那一欄第一群的 11 種，和第 4 頁標準下的 ✓ 11 種是同樣的攻擊）；每個檔的數字在 `results/ciciot2023.tsv`。✓ 的攻擊（Web、Recon、Brute Force）都只有 1 個檔。

**被問到時**

- **每一列包含哪些、差在哪？** 列名是 CICIoT2023 論文的分類，同一列的攻擊判斷都相同；判斷和同類不同的單獨一列。
  - Web-based（6 種，✓）：BrowserHijacking 2,951 條（用 BeEF 改瀏覽器的設定、劫持瀏覽器）、CommandInjection 3,971 條（在 DVWA 的輸入欄位注入系統命令）、SqlInjection 5,736 條（SQL injection；alert 裡看得到 Sqlmap）、XSS 3,430 條（在網址裡塞 script，這是從 alert 看出來的）、Backdoor_Malware 2,642 條（用 DVWA 和 Remot3d 裝後門，取得未經授權的存取）、Uploading_Attack 1,339 條（上傳惡意檔案）。工具名稱除了另外註明的，都是論文寫的。
  - Brute Force（✓）：只有 DictionaryBruteForce 一種，用字典檔試 SSH 密碼。
  - Recon（4 種，✓）：HostDiscovery 673,022 條（找網段裡有哪些主機）、OSScan 190,789 條（猜作業系統）、PortScan 218,276 條（掃開了哪些 port）、VulnerabilityScan 394,740 條（用 nmap 和 vulscan 掃漏洞），論文寫的工具都是 nmap。同類的 Recon-PingSweep（用 nmap、fping 找網段裡活著的主機，1,829 條）是 △，單獨一列。
  - DDoS（12 種，△）和 DoS（4 種，△）差在攻擊者幾台：論文寫 DoS 是一台 Raspberry Pi 攻擊，DDoS 是多台一起。DDoS 依封包分 12 種：TCP flag 的 flood（SYN_Flood 2.27 億條、TCP_Flood 1.80 億、PSHACK_Flood 1.75 億、RSTFINFlood 1.46 億）、切碎的封包（ACK_Fragmentation 1,235 萬、ICMP_Fragmentation 30 萬、UDP_Fragmentation 14 萬）、ICMP_Flood 19 萬、UDP_Flood 81 萬、SynonymousIP_Flood 424 萬（來源和目的位址都設成被攻擊的位址的 TCP-SYN）、HTTP 層的 HTTP_Flood 49 萬與 SlowLoris 12 萬。DoS 的 4 種是 HTTP_Flood 133 萬、SYN_Flood 613 萬、TCP_Flood 470 萬、UDP_Flood 204 萬。
  - Mirai（3 種，△）：Mirai botnet 的 flood，greeth_flood 9,684 萬條（GRE 封裝 Ethernet frame）、greip_flood 7,234 萬條（GRE 封裝 IP 封包）、udpplain 14 萬條（大量 UDP）。
  - Spoofing（2 種，△）：DNS_Spoofing 86,708 條（偽造 DNS 回應）、MITM-ArpSpoofing 74,018 條（偽造 ARP，讓流量經過攻擊者，做中間人）。
- **為什麼這個 dataset 沒有 ✗？** 照官方 label，整個檔的 flow 都算那種攻擊，而攻擊進行時實驗網路其他設備的背景流量也一起錄進去，背景流量的 alert（UPnP、ICMP PING 等）也落在攻擊流量上，所以每種攻擊都有 alert。這不代表偵測到攻擊，只代表有 alert，而 rule 對不上，是 △。
- **為什麼要以 Benign 檔為基準？** 每個檔都有實驗網路的背景流量，Benign 檔也會觸發 `GPL ICMP PING`、`GPL MISC UPnP malformed advertisement` 等 rule，所以單看「有沒有 alert」每個檔都有。我們把 Benign 檔也出現的 rule 當成背景，用來說明 △ 的 alert 是背景，不是這種攻擊造成的；這是啟發式，同一個 SID 也可能同時落在攻擊流量上。
- **Spoofing 為什麼是 △、不是 ✓？** ARP spoofing 是 ARP，Suricata 的 rule 看不到；DNS spoofing 只有背景 alert。有 alert，但 rule 對不上這種攻擊。
- **Recon-PingSweep 為什麼是 △？** 做 sweep 的主機（.178）送了 138 個 ICMP echo 到 79 台主機，完全沒有觸發 alert；檔裡有 11 條有 alert 的 flow（UPnP 6、ICMP PING 5），都是背景流量，其中 ICMP PING 的 alert 來自另一台主機（.59），rule 對不上 sweep。
- **Uploading_Attack 為什麼是 ✓？** 16 條有 alert 的 flow 裡，2 條觸發 `/etc/passwd` 的 rule（SID 2002034、2025879），其他 14 條是背景的 UPnP、ICMP PING 和 403 Forbidden。這對 rule 是 ATTACK_RESPONSE 類，看的是回應裡出現 passwd 檔的內容，代表透過 web 漏洞執行命令成功。Backdoor_Malware 觸發的是同一對 rule，連 server 都相同（192.168.137.236 與 192.168.137.11 的 80 port，回給攻擊主機 192.168.137.147），CommandInjection 也是同一類，三種的流量看不出差別，所以一起算 ✓。如果被問「rule 抓到的不是上傳這個動作」：上傳的檔案就是拿來在 server 上執行命令的，回應裡出現 passwd 代表這次攻擊成功了；上傳那一步本身沒有 rule 抓到。這是依 rule 內容與流量做的人工判斷。
- **DictionaryBruteForce 的 rule 對得上為什麼只有 5 條？** 248 條有 alert 的 flow 裡，103 條是只數 SYN 的 SSH scan（SID 2003068、2001219），只看 SYN、不比對內容，描述的是 scan，不算；LibSSH 的 rule（SID 2006546，`ET SCAN LibSSH Based Frequent SSH Connections Likely BruteForce Attack`）5 條，要連線已建立、比對 client 送出的 `SSH-…libssh` banner，同一來源 30 秒內 5 次才報，描述的是用 libssh 這類工具反覆登入，也就是暴力破解，所以算，這種攻擊仍是 ✓。
- **Mirai-udpplain 為什麼是 △？** 唯一 Benign 沒有、也不是背景的 rule 是 `ET P2P Edonkey Search Request`（25 個檔裡有 11 個檔、14 條）。alert 落在 flood 的 flow 上（例如第一個檔那條是單向 34,648 個 packet），和 udpplain 這種攻擊無關，所以是 △。
- **CICIoT2023 的攻擊者在哪？** 攻擊者是實驗網路裡的 Raspberry Pi，和受害設備在同一個區網；如果 gateway 放在公司內網與外網之間，這類內網對內網的攻擊根本不會經過 gateway。這次 HOME_NET 設成 any，不分內外，所有方向的 rule 都適用（3 條 rule 因此載入失敗）。
- **限制是什麼？** 判斷是依 rule 名稱與內容的人工判斷，不是自動算出來的；✓ 的攻擊（Web、Recon、Brute Force）每種都只有 1 個檔，同一種攻擊沒有其他錄製可以對照；背景與攻擊流量混在同一個檔裡，alert 落在哪條 flow 上是依官方 label 整個算進攻擊。
- **這是不是偵測率？** 不是。這一頁每種攻擊只有一個判斷（✓△✗），不是比例；表上的有 alert 的 flow 和 rule 對得上的 flow 是照官方 label、整個檔的 flow 都算攻擊（含背景流量）算出來的，彙總在第 9 頁。

## 第 9 頁　偵測總表

**逐列說明**（當場不講，被問到某一列或時間夠時用）

- 這是老師要的狀態表，我們放 security gateway 角度的重要數字：每個 dataset 一列，之後每次報告都更新這一張。
- 欄位是 malicious flow 的條數（IoT-23 2.94 億、CIC-IDS2017 50.5 萬、CIC-DDoS2019 6,984 萬、CICIoT2023 9.32 億）、有 alert 的 flow 比例、rule 對得上的 flow 比例、rule 對得上的攻擊種類（也就是偵測到 ✓ 的種類數除以攻擊種類數），和誤報（Benign 有 alert 的比例），都是全部 rule（`full`）的結果。
- 有 alert 的 flow 比例四個都很低：IoT-23 是 5.01%，而且幾乎都是 39-1 (IRCBot) 的 SSH scan，扣掉整個 39-1 (IRCBot) scenario 只有 0.02%；CIC-IDS2017 是 0.39%；CIC-DDoS2019 約 0.002%；CICIoT2023 約 0.004%。rule 對得上的 flow 比例一樣低，甚至更低：IoT-23 5.01%、CIC-IDS2017 0.38%、CIC-DDoS2019 0.00001%、CICIoT2023 0.0002%。CICIoT2023 照官方的 label，攻擊檔裡每條 flow 都算攻擊，所以背景流量的 flow 和 alert 也算在裡面，有 alert 的 flow 將近九成是背景的 rule。
- 以攻擊種類來看，IoT-23 15 種裡有 5 種、CIC-IDS2017 15 種裡有 9 種、CICIoT2023 33 種裡有 11 種 rule 對得上，也就是偵測到；CIC-DDoS2019 全部是 flood，19 項裡只有 2 項。這個 19 是「日期 × label」的項目數（03-11 有 7 項、01-12 有 12 項，Syn 等兩天都有），不是 19 種不同攻擊；各 dataset 的分類粒度不同，不能直接比。rule 對得上的大多是有 payload 特徵的攻擊（Web 攻擊、exploit、惡意程式下載、C&C），另外幾種靠只看 header 的 scan rule（SSH、資料庫 port），例如 IoT-23 的 PartOfAHorizontalPortScan 和 CIC-IDS2017 的 Portscan，scan 本來就是這些 rule 描述的；只數 SYN 的 SSH scan rule 不算對得上暴力破解或連線嘗試，所以 IoT-23 的 Attack 和 CIC-IDS2017 的 SSH-Patator 是 △；認的是協定使用的 rule（IRC 指令、SNMP `public`）也不算對得上 C&C 或 DDoS，所以 CIC-DDoS2019 的 DrDoS_SNMP 也是 △。rule 對得上，是指有 alert 對得上攻擊內容，不代表認出了 flood 的行為。反過來，沒有內容特徵的流量大多沒有偵測到（不是原因不符，就是漏報），這是**推論**：原因除了沒有內容特徵，也可能是 rule set 沒有對應的 rule、threshold 或設定。
- 誤報最高是 CICIoT2023 的 1.49%，其他是 IoT-23 0.009%、CIC-IDS2017 0.65%、CIC-DDoS2019 0.30%。這只列數字，不當成 false positive rate，因為 Benign label 本身有疑點；CICIoT2023 攻擊檔裡背景流量的 alert 照官方 label 算在攻擊上，不在誤報裡。

**怎麼讀**

- 每列一個 dataset；後面各 dataset 的細節在第 5–8 頁，Benign 的細節在下面「Benign 上的 alert」。
- **malicious flows**：label 是 malicious 的 flow 條數，投影片寫成億、萬：IoT-23 2.94 億是 294,449,255 條、CIC-IDS2017 50.5 萬是 505,429 條、CIC-DDoS2019 6,984 萬是 69,835,414 條（03-11 的 19,829,165 加 01-12 的 50,006,249）。IoT-23 是全部 23 個有 label 的 scenario；CIC-IDS2017 不含 Attempted；CIC-DDoS2019 是兩天的攻擊 flow（03-11 已去掉重複列）；CICIoT2023 9.32 億是 931,523,573 條，是 305 個攻擊檔裡 Suricata 算出的 flow（`flow.total`）合計，照官方 label 每條都算該檔的攻擊（含背景流量），4 個 Benign 檔不算在內。CICIoT2023 的 flow 是 Suricata 切的，其他三個是 label 檔（Zeek、CICFlowMeter）切的。
- **有 alert 的 flow 比例**：有 alert 的 malicious flow ÷ malicious flow（定義在第 4 頁）。`full` 是 ET Open 全部，`gw_corp` 是 10/19 挑的本地 rule。IoT-23、CIC-IDS2017 兩者幾乎一樣；CIC-DDoS2019 差一半（1,578 條對 746 條），主要因為 `GPL ICMP PING` 不在 `gw_corp`（第 7 頁）；CICIoT2023 少了約三分之一（38,600 條對 24,995 條），少掉的 13,605 條裡 8,603 條有 `GPL ICMP PING`，其他主要是 INFO（3,318）、HUNTING（1,569）類。
  - IoT-23 `full` 14,762,773 條（5.0137%）、`gw_corp` 14,762,716 條；CIC-IDS2017 `full` 1,947 條（0.3852%）、`gw_corp` 1,941 條（0.3840%）；CIC-DDoS2019 `full` 1,578 條（0.0023%）、`gw_corp` 746 條（0.0011%）。
  - CICIoT2023 的有 alert 的 flow：每個攻擊檔 alert 的 distinct `flow_id` 加總，`full` 38,600 條（0.0041%）、`gw_corp` 24,995 條（0.0027%）。其中 33,412 條（87%）上面的 alert 全是 4 個 Benign 檔也出現過的 rule，也就是背景流量（`GPL MISC UPnP malformed advertisement` 21,702 條、`GPL ICMP PING *NIX` 7,774 條等）；至少有一條 Benign 沒出現過的 rule 的只有 5,188 條（0.0006%）。`gw_corp` 的數字是從 `full` 的 alert 依 SID 篩出來的，沒有另外跑；如果有 rule 靠被排除的 rule 先設 flowbits，篩出來的數字會偏高（`tests/detection/README.md`）。
- **rule 對得上的 flow 比例**：rule 對得上的 flow ÷ malicious flow（定義在第 4 頁，SID 清單在 `tests/detection/results/related_rules.tsv`）：IoT-23 14,758,406／294,449,255（5.0122%）、CIC-IDS2017 1,900／505,429（0.3759%）、CIC-DDoS2019 10／69,835,414（0.000014%）、CICIoT2023 1,967／931,523,573（0.000211%）。rule 對得上的 SID 都在 `gw_corp` 裡（IoT-23 下載類的 HUNTING、INFO 的 SID 不在，但這些 flow 都同時有 `gw_corp` 的 SID 2019240），所以 rule 對得上的 flow，`full` 和 `gw_corp` 一樣。
- **rule 對得上的攻擊種類**：分子是 rule 對得上的 flow > 0 的攻擊種類數，也就是 ✓ 的個數；分母是 label 的種類數（IoT-23 15 種 malicious label、CIC-IDS2017 15 種攻擊、CIC-DDoS2019 兩天 19 項、CICIoT2023 33 種攻擊）；CIC-DDoS2019 的 19 是「日期 × label」的項目數：03-11 的 7 項加 01-12 的 12 項，Syn、LDAP、MSSQL、NetBIOS、UDP、UDPLag／UDP-lag 兩天都有，不是 19 種不同攻擊，各 dataset 的分類粒度不同，不能直接比。只有 IP 清單的 alert、和攻擊無關的 alert，或描述的不是攻擊本身的 rule（只數 SYN 的 SSH scan、IRC 指令與 SNMP `public` 這種協定的使用、只認得出工具的 curl User-Agent、名稱寫 brute force 的 IMAP／POP3 rule）都不算（是 △）。四個 dataset 的判斷用同一個標準（第 4 頁）。
- rule 對得上，是有 alert 對得上攻擊內容，不代表認出了 flood 的行為：例如 CIC-DDoS2019 的 DrDoS_NTP 靠的 MON_LIST rule 只有 3 條 flow（< 0.01%）。反過來，只比對協定使用的 rule 不算：DrDoS_SNMP 靠的那條 rule 只比對送往 161 的 `public` 字串，一般網管也會這樣用，所以是 △；只數 SYN 的 SSH scan rule 描述的是 scan，不是暴力破解，所以 CIC-IDS2017 的 SSH-Patator 是 △。
- ✓△✗ 各幾種：IoT-23 ✓ 5、△ 2、✗ 8；CIC-IDS2017 ✓ 9、△ 1、✗ 5；CIC-DDoS2019 ✓ 2、△ 17、✗ 0；CICIoT2023 ✓ 11、△ 22、✗ 0。分子是哪幾種：
  - IoT-23 的 5 種：PartOfAHorizontalPortScan（SSH scan rule）、C&C（Mirai、Muhstik 的 C&C checkin）、C&C-FileDownload、C&C-HeartBeat-FileDownload、FileDownload（ELF 下載）。Okiru 只有 Spamhaus DROP 的 IP 清單 alert，和 Okiru 的內容無關；Attack 的 alert 是只數 SYN 的 SSH scan 與 IP 清單；兩種都是 △，不算進 5／15。
  - CIC-IDS2017 的 9 種：Web Attack – XSS、Web Attack – SQL Injection、Infiltration、FTP-Patator、Heartbleed、Infiltration – Portscan、Portscan、DoS Slowhttptest、DDoS；SSH-Patator 的 alert 是只數 SYN 的 SSH scan，是 △；沒有 alert（✗）的 5 種是 DoS Hulk、GoldenEye、Slowloris、Web Attack – Brute Force、Botnet。
  - CIC-DDoS2019 的 2 項：03-11 的 MSSQL（MC-SQLR）和 01-12 的 DrDoS_NTP（MON_LIST）；DrDoS_SNMP 的 alert 有 103 條是 SNMP `public`（協定的使用），和其他 16 項一樣有 alert 但 rule 對不上，是 △。
  - CICIoT2023 的 11 種：第 8 頁表上的 ✓（Web-based 6 種含 Uploading_Attack、Brute Force 1 種、Recon 4 種）；其他 22 種有 alert、rule 對不上，是 △。
- 讀法：有 alert 的 flow 比例四個都很低，因為 malicious flow 大多是 scan、flood（IoT-23 99.98%、CIC-IDS2017 98.5%、CIC-DDoS2019 100%；CICIoT2023 的 DDoS、DoS、Mirai 三類占 flow 的 99.8%），沒有內容可以比；以攻擊種類來看，rule 對得上的大多是 Web 攻擊、exploit、惡意程式下載、C&C 這些有 payload 特徵的；有 payload 但沒有特徵的（例如 IoT-23 的 C&C-HeartBeat、C&C-Torii，CIC-IDS2017 的 Botnet、HTTP DoS）就沒有 rule 對得上。這裡的因果（沒有內容特徵 → 沒有偵測到）是**推論**：觀察到的是這些流量沒有 rule 對得上的 alert，原因除了沒有內容特徵，也可能是 rule set 沒有對應的 rule、threshold 或設定。如果只算比對 payload 的 rule、不算只看 header 的 scan rule，是 IoT-23 4／15、CIC-IDS2017 8／15、CICIoT2023 9／33。
- IoT-23 的 5.01% 幾乎都是 39-1 (IRCBot) 的 SSH scan；扣掉整個 39-1 (IRCBot) scenario 只有 0.02%（49,694／220,887,611）。CIC-DDoS2019 的 19 項每一項都有 alert，但 rule 對得上的只有 2 項，其他是攻擊主機的 ping、背景 SSH 連線、資料庫 port scan（第 7 頁），DrDoS_SNMP 另有 SNMP `public`（協定的使用）。
- **誤報（Benign 有 alert）**：有 alert 的 Benign flow ÷ Benign flow（`full`：IoT-23 2,837／30,860,691＝0.0092%、CIC-IDS2017 10,293／1,581,058＝0.6510%、CIC-DDoS2019 333／109,424＝0.3043%、CICIoT2023 5,157／345,984＝1.4905%；`gw_corp`：2,474（0.0080%）、7,420（0.4693%）、315（0.2879%）、3,676（1.0625%））。只列數字，不當成 false positive rate（見下面「Benign 上的 alert」）。
- 「誤報」這個名稱有限制：Benign label 有標錯的（IoT-23 的 Mirai User-Agent、IRC 換 nick），INFO 類的 rule 只是記錄事件、不是攻擊的判定；CICIoT2023 攻擊檔裡背景流量的 alert 照官方 label 算在攻擊上，不在誤報裡。所以這一欄是「Benign label 的 flow 有 alert 的比例」，不是真正的 false positive rate。

**Benign 上的 alert（誤報這一欄的細節）**

- 這一欄回答「正常流量會不會一直有 alert」：IoT-23 的 Benign 有 3,086 萬條，有 alert 的 2,837 條（0.009%）；CIC-IDS2017 158 萬條裡有 10,293 條（0.65%）；CIC-DDoS2019 10.9 萬條裡有 333 條（0.30%）；CICIoT2023 34.6 萬條裡有 5,157 條（1.49%）。
- 這裡只列數字，不算 false positive rate，因為這幾個 dataset 的 Benign label 本身有疑點。CICIoT2023 的 flow 是 Suricata 在 4 個 Benign 檔裡算出來的，照官方 label 每條都算 Benign。
- Benign flows 是 label 為 Benign 的 flow 數；「有 alert」是其中有 alert 的 flow 數；各 dataset 的 Benign 列也在第 5–8 頁的表裡，「觸發的 rule」寫的是誤報主要的 rule 類型。
- IoT-23 是全部 23 個 scenario 的 Benign：30,860,691 條（含 label 寫成小寫 `benign` 的 1,956 條），有 alert 2,837 條（`gw_corp` 2,474 條）。
- CIC-DDoS2019 是 03-11（52,561 條，其中 175 條有 alert；重複列每組只留一條，見第 2 頁的補充）加 01-12（56,863 條，其中 158 條有 alert），合計 109,424 條、333 條有 alert（`gw_corp` 315 條）；Benign flow 也含 Protocol 0 的 flow，它們都沒有 alert。
- CICIoT2023 是 4 個 Benign 檔（`BenignTraffic`、`BenignTraffic1`–`3`）的數字：flows 是 Suricata 的 `flow.total` 合計 345,984，有 alert 的 flow 5,157（`gw_corp` 3,676）；官方沒有逐條的 label 檔，所以這是 Suricata 算出的 flow，照官方 label 每條都算 Benign。
- `gw_corp` 的數字會少一些：IoT-23 2,474、CIC-IDS2017 7,420、CIC-DDoS2019 315。`gw_corp` 去掉 INFO、HUNTING、P2P 等：例如 CIC-IDS2017 從 10,293 降到 7,420；IoT-23 從 2,837 降到 2,474，主要是 9-1 (Linux.Hajime) 的 255 條都不在 `gw_corp`（BitTorrent 最多 242 條，其餘是 IP 清單）。
- IoT-23 Benign 的 rule（flow 數）：SSH scan OUTBOUND 1,150、IRC Nick change 1,019、IRC authorization 873、Mirai UA 211（33-1 (Kenjiro) 208、17-1 (Kenjiro) 3）、BitTorrent DHT 214。表上「觸發的 rule」寫 flow 數前三名：SSH scan、IRC、BitTorrent；Mirai UA（211 條）在這裡說明，見下面「為什麼不算 false positive rate」。
- 數字是第 5–8 頁各 dataset 結果裡 Benign 那一列，rule set 是 `full`，alert 對 flow 的方法和攻擊的 label 一樣；CICIoT2023 的 label 是整個檔，用的是 Suricata 自己算的 flow。

**實驗怎麼做**

- 這一頁沒有新的實驗，是第 5–8 頁各 dataset 結果的彙總；rule set 是 `full`，`gw_corp` 的結果是從 `full` 的 alert 依 SID 篩出來的（第 3 頁）。
- rule 對得上是依 rule 名稱與內容做的人工判斷，不是自動算出來的；每種攻擊的 SID 清單和理由在 `tests/detection/results/related_rules.tsv`，算出來的結果在 `tests/detection/results/unified_by_label.tsv`（計算是 `tests/detection/related_flows.py`），CICIoT2023 只看 Benign 檔沒出現過的 rule 時的理由另見 `tests/detection/results/ciciot2023_judgement.tsv`（判斷欄是那個判法的三群，不是 ✓△✗）。

**被問到時**

- **CICIoT2023 的 flow 比例怎麼算？** 照官方 label：論文 Sec. 4 寫每次攻擊錄到的流量整段標成那種攻擊（第 2 頁的 CICIoT2023 段），所以 305 個攻擊檔裡 Suricata 算出的每條 flow 都算 malicious。分母和分子都含背景流量：有 alert 的 38,600 條裡 33,412 條（87%）只有 Benign 檔也出現的 rule；扣掉這些是 5,188 條（0.0006%）。這種攻擊有沒有被偵測到，看第 8 頁的 ✓、△、✗。
- **flow 比例這麼低，為什麼還說 rule 對得上的攻擊種類？** 這是兩個問題：flow 比例受量影響，量最大的是 scan、flood（沒有 payload 特徵），把比例壓得很低；攻擊種類是每種攻擊一個判斷，不受量影響。例如 IoT-23 15 種裡有 5 種 rule 對得上，但量最大的 PortScan、Okiru、DDoS 占 99.98%。
- **CIC-DDoS2019 每一項都有 alert，為什麼只算 2 項？** 其他的 alert 是攻擊主機的 `GPL ICMP PING`、背景的 SSH 連線、資料庫 port 的 scan rule，DrDoS_SNMP 則是 SNMP `public`（協定的使用），rule 對不上 DDoS，是原因不符（△），不是認出 DDoS（第 7 頁）。這 2 項裡，rule 對得上的 flow 都 < 0.01%（NTP 3、MSSQL 7 條）。
- **挑過的 rule set（`gw_corp`）會不會漏？** 這四個 dataset 不會。`gw_corp` 是 10/19 為公司 gateway 挑的 38,506 條（去掉 INFO、HUNTING、P2P 等），rule 對得上的 SID 全部在 `gw_corp` 裡，所以 rule 對得上的 flow 和攻擊種類兩者完全相同；差在無關的 alert 和誤報變少：有 alert 的 flow IoT-23 14,762,773 → 14,762,716、CIC-IDS2017 1,947 → 1,941、CIC-DDoS2019 1,578 → 746（ICMP PING 不在 `gw_corp`）、CICIoT2023 38,600 → 24,995（主要也是 ICMP PING，另外是 INFO、HUNTING）；誤報 0.009% → 0.008%、0.65% → 0.47%、0.30% → 0.29%、1.49% → 1.06%。`gw_corp` 的數字是從 `full` 的 alert 依 SID 篩出來的，沒有另外跑；會和真的只載入 `gw_corp` 不同的，只有要靠被排除的 rule 先設定狀態旗標的 rule：flowbits 有 753 條 `gw_corp` rule 要檢查旗標，其中 3 條的旗標只由被排除的 rule 設定，xbits 46 條裡有 1 條，hostbits 沒有，這 4 條在四個 dataset 都沒有觸發，所以篩出來的數字等於只用 `gw_corp`（沒有實際只載入 `gw_corp` 重跑對照）。這只代表這四個 dataset；公司網路的其他攻擊可能用到被去掉的類別，所以主要的數字用全部 rule。
- **這是不是 detection rate？** 不是。有 alert 的 flow 比例和 rule 對得上的 flow 比例都只是逐條 flow 的比例，不代表認出攻擊，也受量影響；「這個攻擊有沒有被偵測到」看 ✓，也就是「rule 對得上的攻擊種類」那一欄。
- **Benign 有 alert 是 false positive rate 嗎？** 不是，所以這一欄叫「誤報」、只列數字，不叫 false positive rate。這幾個 dataset 的 Benign label 本身有疑點（見下一題）。
- **為什麼不算 false positive rate？**
  - IoT-23 有 211 條 Benign 觸發 `ET MALWARE Mirai Variant User-Agent (Outbound)` 和 `VPNFilter Related UA (Hakai/2.0)`（33-1 (Kenjiro) 208 條、17-1 (Kenjiro) 3 條），比較像 label 標錯。42-1 (Trojan) 的 1,019 條是連到 185.244.25.183:4975 的 IRC 換 nick（非標準 port），IoT-23 把這些 flow 標成 Benign。39-1 (IRCBot) 的 Benign 有 587 條、3-1 (Muhstik) 有 560 條、其他 scenario 有 3 條觸發 SSH scan OUTBOUND。
  - CIC-IDS2017 Monday（全部 Benign）有 4,201 條觸發 SID 2028795、1,726 條觸發 SID 2028780，兩條都是 `ET JA3 Hash – [Abuse.ch] Possible Adware`（TLS client 指紋和 adware 相同）；其他有 INFO 類（TLS handshake 失敗）和 ET DNS 類（查 .to／.cc 網域，在 `gw_corp` 裡）。
  - CIC-DDoS2019 Benign 的 alert 幾乎都是 SSH scan OUTBOUND（333 條中 311 條）。
  - CICIoT2023 的 4 個 Benign 檔：flow 是 Suricata 算的（官方沒有逐條的 label 檔），alert 主要是 `GPL MISC UPnP malformed advertisement` 和 `GPL ICMP PING`，是實驗網路的背景流量。
  - INFO 類的 rule 只是記錄事件（例如 TLS handshake 失敗、查 .to／.cc 網域），不是攻擊的判定，所以 Benign 上有這類 alert 不一定是真的誤報。

## 第 10 頁　結論

**怎麼讀**

- 兩列是兩種攻擊型態；「偵測」欄的 ✓ 大多、△／✗ 大多，指的是這一型態的攻擊大多偵測到（✓：攻擊流量上有 alert，且 rule 描述的就是這種攻擊）、大多沒有偵測到，所以寫「大多」。第二種沒有偵測到的有兩種：漏報（✗，沒有 alert，例如 IoT-23 的 DDoS、CIC-IDS2017 的 DoS Hulk）和原因不符（△，有 alert 但 rule 對不上，例如 CIC-DDoS2019、CICIoT2023 的 flood）。
- 第一種的例子：IoT-23 的 C&C checkin、ELF；CIC-IDS2017 的 XSS、SQLi、Infiltration、FTP、Heartbleed；CICIoT2023 的 Web 攻擊、Recon 的 OS 偵測與 Nmap NSE；其中 HostDiscovery、PortScan 靠的是只看 header 的 scan rule，不是 payload。
- 第一種的反例也要講：CIC-IDS2017 的 Web Attack – Brute Force（0／73）、Botnet（Ares，0／736），IoT-23 的 C&C-HeartBeat（0／33,673）也有 payload，但沒有 alert；所以寫「大多」。
- 第二種「沒有內容特徵」包含兩類：SYN scan 這種沒有 payload 的，和 UDP flood、HTTP DoS 這種有 payload、但 payload 沒有特徵的。HTTP DoS（Hulk、GoldenEye、Slowloris）送的是正常格式的 HTTP request，沒有偵測到是因為 payload 沒有特徵，不是只有 header。
- CIC-DDoS2019 兩天合計 6,984 萬條攻擊 flow 只有 1,578 條有 alert（`gw_corp` 746 條），而且幾乎都不是認出 DDoS：大多是攻擊主機的 ping、背景 SSH 連線、資料庫 port 的 scan rule（SYN flood 亂打 port 時打到，或攻擊主機零星連資料庫 port）；只有 10 條（MC-SQLR 7、NTP 3）rule 對得上，而且只占該 label 極少的 flow，rule 對得上的 flow 比例 < 0.01%（第 7 頁）。
- 第二種占 malicious flow 的比例：IoT-23 99.98%（23 個 scenario 的 PortScan + Okiru + DDoS）、CIC-IDS2017 98.5%（DoS／DDoS／Portscan，含 Infiltration – Portscan）、CIC-DDoS2019 100%、CICIoT2023 99.8%（DDoS、DoS、Mirai 三類的 flow，照官方 label 含背景流量）。
- 例外是有只看 header 的 scan rule 的 port：IoT-23 39-1 (IRCBot) 的 SSH scan（占 IoT-23 malicious flow 的 25.0%）實際有 20.0% 的 flow 有 alert。即使算進這個例外，IoT-23 的 malicious flow 仍有 94.99% 沒有任何 alert。
- 所以如果問「流量送進去偵測得出來嗎」：有內容特徵的大多偵測到；scan、flood 這種量最大的，本地的 rule 大多沒有偵測到（漏報或原因不符）。其中「沒有內容特徵 → 沒有偵測到」的因果是**推論**：原因除了沒有內容特徵，也可能是 rule set 沒有對應的 rule、threshold 或設定。
- 最後一行「要靠 flow 層級的統計」是**推論**，這次**沒有實作或量測** flow 統計的偵測。
- 表下的速度一行：在 Pi 上用 10/19 的量法（engine 直接讀 tmpfs 上的 pcap、單一 thread、1000 MHz），Suricata 8.0.7、和偵測同一份 rule，量了 41 個切片（IoT-23 10/19 的 14 個 scenario 重測，和 10/19 只差 −4% 到 +10%；CIC 27 個，依流量型態歸類、同一類只量一個）。`full` 最慢的是 HTTP flood（CIC-IDS2017 DoS Hulk 6.2、CICIoT2023 DDoS-HTTP_Flood 8.5 kpps）；CIC 三個 dataset 的 Benign 是 15.5（CIC-IDS2017）、16.0（CIC-DDoS2019）、22.0（CICIoT2023）kpps。這是 Pi 讀代表性切片（每個最多 20 萬 packets）量的 engine 處理速度，engine 直接讀 pcap，不是 gateway 的線上吞吐量；線上的留到下一步（第 11 頁）。

**實驗怎麼做**

- 這一頁沒有新的實驗，是整合第 5–9 頁的結果；占比用的是各 label 的 flow 數。速度一行來自 `tests/ids_throughput/README.md` 實驗 5（`results/pi/pi_scen3_*.summary.csv`）。

**被問到時**

- **flow 統計是老師建議的嗎？** 不是。老師只問了「偵測得出來嗎」，並要狀態表；flow 統計是我們從結果推出來的方向。
- **已經證明 flow 統計抓得到嗎？** 沒有。這是**推論**，這次**沒有實作或量測**。
- **和研究目標的關係？** 研究目標裡有「Flow 資料收集與雲端卸載」：scan／flood 需要的是 flow 的統計資訊，不是 payload，所以這和 flow 資料收集接得上。
