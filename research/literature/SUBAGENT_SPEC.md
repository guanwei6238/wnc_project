# 論文精讀 Subagent 規格

每個 subagent 只負責**一篇**論文，輸出**一份**報告到 `research/literature/papers/<slug>.md`。
跨論文的比較與 Research Gap 判斷**不是你的工作**，由主 agent 在收齊後做。

---

## 1. 研究主題（判斷「相關」與「可改進」的唯一標準）

> 如何在資源受限的 IoT Security Gateway 上，透過高效率的封包處理、Flow 資料收集與雲端卸載機制，
> 降低地端運算及傳輸成本，同時維持網路轉送效能與雲端 IDS 所需資料的完整性和即時性。

拆成四個**組件**與三個**約束**，下面的欄位會反覆用到：

| 組件 | 約束 |
|---|---|
| C1 高效率封包處理 | K1 維持網路轉送效能（throughput / latency 不被拖垮） |
| C2 Flow 資料收集 | K2 雲端 IDS 所需資料的完整性（壓縮/卸載後偵測力損失多少） |
| C3 雲端卸載機制 | K3 即時性（從封包出現到偵測結果的時間） |
| C4 降低地端運算與傳輸成本 | |

參考平台：Raspberry Pi 3B+（Cortex-A53 x4、1 GB RAM、USB2 網卡）、Linux、nftables + NFQUEUE。
專案目前用規則式 IDS（Suricata / Snort）為本地檢測的基準。

## 2. 你的邊界

- 唯讀研究。只可寫入你自己的輸出檔，不要修改 repo 其他任何檔案，不要 commit / push，不要安裝東西。
- 用 WebSearch / WebFetch 找論文。**不得**使用盜版來源（Sci-Hub 等）或繞過付費牆。
- 全程繁體中文，技術名詞與論文專有名詞保留英文。

## 3. 第 0 步：確認論文存在（必做，先於一切）

主 agent 給你的標題、年份、期刊**可能不準確**（它來自推薦清單，未經查證）。請：

1. 找到論文的真實書目：標題、作者、年份、出處、DOI、可取得的 URL。
2. 與給定資訊不同時，明確列出差異，不要默默修正。
3. **找不到這篇論文**，或只找到名稱相近但內容不同的論文：報告只寫「找不到」、你搜尋了什麼、找到了什麼相近的，然後**停止**。不要憑印象補內容。
4. 記錄取得程度：`全文` / `僅摘要` / `僅二手描述`。僅摘要時，下面無法從摘要確認的欄位一律寫「未能確認」。

## 4. 證據標記（每個事實都要標）

| 標記 | 意思 |
|---|---|
| `[原文 p.N]` / `[原文 Fig.N / Table N]` | 在論文全文看到，附頁碼或圖表編號 |
| `[摘要]` | 只在摘要看到 |
| `[二手]` | 別人對這篇論文的描述（附 URL） |
| `[推測]` | 你的推論，不是論文寫的 |
| `未能確認` | 找不到證據 |

規則：
- **數字必須標出處**。沒有出處的數字不要寫。
- 論文沒寫的事，寫「論文未說明」，不要用常識補。
- 區分「作者承認的限制」與「你觀察到、作者沒承認的限制」，後者一律標 `[推測]` 或附證據。

## 5. 輸出模板

```
# <論文簡稱>
## A. 書目與取得狀況
標題 / 作者 / 年份 / 出處 / DOI / URL
與給定資訊的差異：
取得程度：全文 | 僅摘要 | 僅二手

## B. 核心貢獻（≤3 條，附出處標記）

## C. 指定的 9 項
1. Research Problem
2. Architecture（Packet、Flow、Edge、Cloud 如何分工；可附簡單文字圖）
3. Processing Location（Kernel / User space / Cloud / 交換器資料平面）
4. Hardware（x86、ARM、Raspberry Pi、P4 Switch…，列出型號與規格）
5. Dataset（名稱、版本、是否公開、是否為 IoT-23 / CICIoT2023 / 真實流量）
6. Baseline（與哪些系統比；是否在同硬體、同資料上重跑）
7. Metrics（Throughput、Latency、CPU、RAM、準確率…）
8. Limitations（作者承認的）
9. Research Gap（這篇留下的未解問題；分「作者自述」與「[推測]」）

## D. 補充欄位（為了找出可改進處）
D1. 與研究主題對照
    C1 封包處理 / C2 Flow 收集 / C3 雲端卸載 / C4 降成本：各標 ○（核心）△（部分）×（無），附一句證據
    K1 轉送效能 / K2 資料完整性 / K3 即時性：論文有沒有量測？量了什麼、沒量什麼
D2. 卸載與資料
    什麼被送到雲端（原始封包 / Flow record / 特徵 / 判決結果）？
    誰決定要送、依據什麼（門檻、信心值、規則…）？
    資料量縮減比（附條件）？縮減造成多少偵測力損失？
D3. 成本記帳
    地端 CPU / RAM / 能耗、傳輸 bytes / 頻寬、雲端運算：各自有沒有量？
    time-to-detection 或端到端延遲有沒有量？
D4. 偵測方法與威脅模型
    規則式 / 異常 / ML / DL；偵測哪些攻擊；是否需要解密或 payload。
    這個方法的成本模型能不能直接套到規則式 IDS（Suricata/Snort）？[推測] 要說理由。
D5. 實驗可信度
    流量來源（重播 / 即時 / 合成）、速率範圍、每組重複次數、有沒有變異量或信賴區間、
    有沒有 ablation、ML 論文要看訓練/測試切分有無洩漏、
    程式碼與資料是否公開（artifact available?）。
D6. 移植到我們平台的障礙
    依賴的硬體/軟體（P4 交換器、GPU、特定網卡驅動、kernel 版本、TLS 解密…）。
    能否在 Pi 3B+ 上跑？阻礙是什麼？標明是已驗證還是 [推測]。
    （XDP/eBPF 類論文：額外查 Pi 3B+ 的 USB 網卡驅動是否支援 native XDP，只有 generic 的話影響為何。）
D7. 對六個假說方向的證據
    Edge–Cloud IDS 分工 / Flow Feature Compression / Dynamic Flow Monitoring /
    XDP-eBPF 真正省多少 / Cloud Data Offloading 的成本-時效平衡 / 不同硬體限制下是否仍有效。
    每個方向：本論文提供「支持 / 反駁 / 無關」的證據是什麼。
    **只回報本論文的證據，不要替整個領域下結論。**
D8. 可借用與可改進
    可借用的元件（演算法、資料結構、參數、評估方法），標出處。
    可能的改進方向（最多 5 條，全部標 [推測]，每條要指出它基於上面哪個限制或缺口）。
D9. 引用網路（為了找到更值得讀的論文）
    查 references 與 cited-by（Semantic Scholar / OpenAlex / Google Scholar）。
    列出 ≤5 篇「建議追加閱讀」，每篇寫：書目、為什麼（後續改進者 / 替代方案 / 被其比較的基準 / 同題更貼近我們）、
    存在確認程度（已確認 DOI / 未驗證）。不要列只是領域通論的論文。

## E. 關鍵數字表
| 指標 | 數值 | 條件（硬體、資料、規則/模型） | 出處 |
（論文中和效能、成本、偵測力有關的主要數字，全部列出）

## F. 自評
哪些欄位「未能確認」、原因；你對這份報告最不確定的三件事。
```

## 6. 品質檢查（交出前自己過一遍）

- [ ] 第 0 步完成；找不到論文時沒有編造任何內容
- [ ] 每個數字都有出處標記
- [ ] 沒有把「[推測]」寫成事實
- [ ] 作者承認的限制與你推測的限制已分開
- [ ] D9 的每篇建議論文都標了存在確認程度
- [ ] 報告 1500–2500 字（不含表格），沒有貼大段原文（引用 ≤2 句且附頁碼）

## 7. 最後回覆給主 agent 的內容

只回覆：輸出檔路徑、取得程度、一句話結論、三個最不確定的地方。報告本體在檔案裡。
