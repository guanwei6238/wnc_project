# Pi 3B+ 硬體現實與吞吐量預算

**先講結論：Pi 3B+ 可以當功能原型，但它跑出來的吞吐量數字量到的是 USB 匯流排，不是你的演算法。**
這不是說不能用，而是說**實驗設計要先承認這件事**，否則後面的數據會沒有意義。

## 1. Pi 3B+ 的結構性瓶頸

| 項目 | 規格 | 影響 |
|---|---|---|
| SoC | BCM2837B0，Cortex-A53 ×4 @ 1.4 GHz | DPI / 加解密都靠純軟體 |
| RAM | 1 GB LPDDR2（**不可擴充**） | Suricata 大規則集 + conntrack table 會吃緊 |
| 內建網路 | LAN7515：**Gigabit PHY 掛在 USB 2.0 上** | 實測單向約 **220–230 Mbps**，不是 1 Gbps |
| USB | 4 個 USB 2.0，**與內建網路共用同一條 USB 2.0 bus** | 加第二張 USB 網卡 → 兩張卡搶同一條 480 Mbps 的 bus |
| 加解密指令 | A53 的 Crypto Extensions **在 BCM2837 上沒有啟用** | 沒有硬體 AES → TLS / VPN 吞吐量會很慘。**上機第一件事就是驗證這點** |
| 儲存 | microSD | 大量寫 log（Suricata eve.json）會變成瓶頸，也會磨損卡 |

## 2. 吞吐量預算推估

路由 / 防火牆的每個封包要**過 bus 兩次**（一張卡收進來、另一張卡送出去）。兩張卡都在同一條 USB 2.0 上：

```
USB 2.0 理論              480 Mbps
實際 payload（扣協定開銷）  ~320–400 Mbps
轉發需雙向過 bus  ÷2      ~150–200 Mbps  ← 理論上限
兩張卡競爭 + 中斷開銷       ~90–150 Mbps   ← 實務可期待值
再開 nftables + conntrack   略降
再開 Suricata DPI (4×A53)   ~20–60 Mbps    ← 你真正會看到的數字
```

> 有人在 OpenWrt 論壇上報告：Pi 3B 接兩張 USB 網卡做 router，
> 原本 ~200 Mbps 的網路掉到 **50 Mbps 以下**。這個數量級要有心理準備。

小封包（64 byte）的情況更糟：那時候你撞到的是 **pps 上限**而不是 bps 上限。
USB 網卡的中斷與 URB 批次處理會讓 pps 天花板遠低於原生 PCIe 網卡。
**這其實是一個值得量的數字**（RFC 2544 的 frame size sweep 就會把它畫出來）。

## 3. 因應策略：先量天花板，之後所有數字都正規化

這是讓 Pi 的數據仍然有意義的關鍵手法：

1. **Step 0 — 量 baseline ceiling**：純轉發，`nftables` 完全空規則、無 conntrack、無 DPI。
   得到 `T_max`。這是這台硬體的物理天花板。
2. 之後每個配置量到的 `T_x`，都報告 **`T_x / T_max`（相對留存率）**，而不是只報絕對 Mbps。
3. 相對留存率**可以跨硬體比較**。等你換到正式設備，再重跑同一組實驗、拿到新的 `T_max`，
   就能驗證「留存率是否維持」，並區分出哪些下降來自演算法、哪些來自硬體。

這樣你在 Pi 上做的工就不會白費，而且報告會有一條清楚的方法論。

> 平台方向現在已經定案為 **OpenWrt + ARM**（見第 5 節），這套「留存率」方法論不只沒有過時，
> 反而更重要：Pi 3B+ 的天花板是 USB 2.0 bus 卡出來的怪異數字，正式的 ARM router SoC
> 多半是原生網路介面，兩者的 `T_max` 會差一個量級以上。用相對留存率而不是絕對 Mbps 來比較，
> 才能把「演算法本身的行為」跟「硬體規格不同」這兩件事分開看，不會因為換了硬體就以為
> 演算法退步了。

## 4. 雙網路 port 的三個選項

| 方案 | 成本 | 吞吐量 | 建議 |
|---|---|---|---|
| **內建 eth0 + USB 網卡** | ~NT$200–500 | 共用 USB bus，會互搶 | ✅ **主線做法**，最接近正式設備的形態 |
| **內建 eth0 + WiFi (wlan0)** | 免費，現在就能做 | WiFi 不過 USB bus，但變異大 | ✅ **今天就可以先開工**，功能驗證夠用，但**不要拿來報吞吐量數字** |
| **內建 eth0 + VLAN (802.1Q)** | 免費，需要支援 VLAN 的 switch | 一條線跑兩個網段，bus 壓力加倍 | 內外網邏輯隔離的正規做法，但實體只有一條線 |

**USB 網卡採購建議**：買晶片是 **AX88179A** 或 **RTL8153** 的 USB 3.0 千兆網卡。
雖然 Pi 3B+ 只有 USB 2.0，但這兩顆晶片的 Linux 驅動（`ax88179_178a` / `r8152`）成熟。
（是否能沿用到正式設備要看第 5 節選出來的板子是不是原生雙 port——如果是，這張卡就純粹是
前期原型的成本；如果最後還是得靠 USB 網卡湊 port，這張卡才用得上。）
**避開** 晶片是 `smsc95xx` 或雜牌 100M 的便宜卡。

## 5. 正式設備的選型（之後要換的時候看這裡）

> **目標平台已經定案：OpenWrt + ARM。** 這份文件早期調查階段把 x86 mini PC
> （N100/N150 + i226）列為「最推薦」，理由是它能跑滿血 DPDK / native XDP。
> 這個結論已經過時，**不是因為 x86 效能不夠**，而是因為方向已經確定要做成 OpenWrt
> 韌體形態的設備——OpenWrt 對 ARM router SoC 的支援本來就比 x86 mini PC 更成熟、
> 套件庫更貼近這個形態。另外，DPDK 本身也不是這個架構要走的路（不管 x86 或 ARM
> 都一樣），理由是 kernel bypass 會讓 conntrack / nftables / 路由表都不能用，跟
> 「這台設備要維持是一台真正的 Linux host」衝突——完整推理見 `00-reading-list.md`
> B-1 段落。**不要用「ARM 不能跑 DPDK」當理由**，那是錯的：DPDK 官方支援 aarch64，
> 只是消費級 router SoC 沒有對應 PMD。

已知的 ARM 候選（沿用前期調查已經出現過的板子，還沒有做最終選型）：

| 平台 | 網路 | 備註 |
|---|---|---|
| Rockchip RK3588 板（如 NanoPi R6S） | 原生 2×2.5GbE | ARM，網路是原生的，有 crypto extensions；需查證 OpenWrt 支援完整度 |
| FriendlyElec R5S / R4S | 原生多 port | 專門做 router 的板子，OpenWrt 社群支援風評好，需查證目前版本狀況 |
| Raspberry Pi 5 + PCIe 網卡 HAT | PCIe 2.0 ×1 | 留在 Pi 生態，但 PCIe 只有一條，頻寬要共享；OpenWrt 對 Pi 5 的支援仍在發展中 |

> **待決定：具體選哪一塊板子。** 這是開發者還沒做的決定，這裡先列出判準，不預先定案：
> 1. **OpenWrt 官方／社群支援程度**——有沒有在 OpenWrt 的硬體支援清單上、有沒有人已經跑穩
> 2. **網路介面是否原生**（PCIe / 內建多個 MAC），還是要靠 USB 網卡湊出雙 port
> 3. **RAM 夠不夠跑裁切過的 Suricata 規則集**——Suricata 跑完整規則集常見建議是
>    RAM ≥ 4 GB，一般 ARM router 的 RAM 遠低於此，代表規則集勢必要裁，這是硬限制
> 4. **有沒有硬體 AES / crypto extension**——這是 Pi 3B+ 已經踩過的坑（見第 1 節），
>    換平台後要重新驗證一次，不要假設有

## 6. 上機第一件事

跑 `pi/preflight.sh`，它會把上面所有假設在你的實機上驗證一遍
（USB bus 拓撲、link speed、有無 AES 指令、有無 BTF、XDP 掛載模式），
並印出這台機器實際的能力清單。**不要憑推測寫報告。**
